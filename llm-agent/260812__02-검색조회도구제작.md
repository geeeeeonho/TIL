# LangChain 검색·조회 도구 제작 — RAG · Text-to-SQL

> 핵심 흐름: **문서 데이터는 검색 가능한 RAG 구조로 만들고, 표 형태 데이터는 안전한 Text-to-SQL 조회 구조로 만든다.**

## 0. 전체 제작 흐름

```text
[문서·FAQ 같은 비정형 데이터]
원본 데이터
   ↓
Document
   ↓
Text Splitter
   ↓
Embeddings
   ↓
VectorStore(Chroma)
   ↓
Retriever
   ↓
RAG Chain
   ↓
검색 근거 + 생성 답변

[DB 표 같은 정형 데이터]
자연어 질문
   ↓
DB 스키마 설명
   ↓
LLM이 SELECT 작성
   ↓
1차 가드: SELECT 한 문장 검사
   ↓
2차 가드: 읽기 전용 DB 연결
   ↓
SQL 실행
   ↓
조회 결과 기반 답변
```

핵심 구분:

| 데이터 | 주로 사용하는 방식 | 이유 |
|---|---|---|
| FAQ·문서·텍스트 | RAG | 의미가 비슷한 문서를 찾아 근거로 사용 |
| 주문·재고·매출 같은 표 | Text-to-SQL | 조건·집계·JOIN을 SQL로 정확하게 조회 |

# 2. RAG를 LangChain 부품으로 만들기

## 2.1 전체 부품

이전처럼 직접 모든 단계를 호출하지 않고 LangChain의 공통 부품 규약으로 연결.

| 단계 | LangChain 부품 | 역할 |
|---|---|---|
| 문서 표현 | `Document` | 본문 + metadata 보관 |
| 문서 분할 | `RecursiveCharacterTextSplitter` | 긴 글을 작은 청크로 분할 |
| 임베딩 | `HuggingFaceEmbeddings` | 텍스트 → 벡터 |
| 벡터 저장 | `Chroma` | 문서 벡터 저장·검색 |
| 검색기 | `Retriever` | 질문 → 관련 `Document` 목록 |
| 생성 | Prompt + Model | 검색 자료를 근거로 답변 |

전체 흐름:

```text
원본 데이터
  ↓
Document
  ↓
Splitter
  ↓
Chunks
  ↓
Embeddings
  ↓
Chroma VectorStore
  ↓
as_retriever()
  ↓
질문 → 관련 Document 목록
```

# 3. `Document` — 본문과 metadata를 한 몸으로

## 3.1 기본 구조

```python
from langchain_core.documents import Document

sample = Document(
    page_content="유사도 검색할 본문 내용",
    metadata={
        "id": "id01",
        "title": "문서 제목",
    },
)

print(sample)
```

`Document`의 핵심:

```text
page_content = 실제 검색 대상 본문
metadata     = 문서와 함께 유지할 정보
```

metadata 예:

- 문서 ID
- 제목
- 파일명
- 페이지 번호
- 카테고리
- 작성일

검색 결과가 나왔을 때 **본문뿐 아니라 출처 정보도 같이 추적** 가능.

---

## 3.2 CSV 한 행 → `Document` 하나

```python
import pandas as pd
from langchain_core.documents import Document

hd_df = pd.read_csv("data/helpdesk_faq.csv")

hd_docs = [
    Document(
        page_content=row.text,
        metadata={
            "id": row.id,
            "title": row.title,
        },
    )
    for row in hd_df.itertuples()
]

print("문서 수:", len(hd_docs))
print("본문:", hd_docs[0].page_content)
print("metadata:", hd_docs[0].metadata)
```

핵심:

```text
표 1행
→ Document 1개
→ 본문은 page_content
→ 식별 정보는 metadata
```

# 4. `RecursiveCharacterTextSplitter` — 긴 문서 분할

## 4.1 왜 자르는가

너무 긴 문서를 통째로 임베딩·검색하면:

- 필요한 부분보다 불필요한 내용이 많아짐
- 검색 단위가 너무 커짐
- 프롬프트에 들어가는 자료가 길어짐

따라서 문서를 **검색하기 좋은 크기의 청크**로 분할.

---

## 4.2 기본 코드

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=100,
    chunk_overlap=40,
)

hd_chunks = splitter.split_documents(hd_docs)

print("원본 문서 수:", len(hd_docs))
print("청크 수:", len(hd_chunks))
print("청크 길이:", [len(chunk.page_content) for chunk in hd_chunks])
print("metadata:", hd_chunks[0].metadata)
```

`split_documents()`를 사용하면 분리된 청크도 `Document` 형태이며 원본 metadata가 유지됨.

---

## 4.3 주요 인자

| 인자 | 의미 |
|---|---|
| `chunk_size` | 한 청크의 목표 최대 크기 |
| `chunk_overlap` | 앞뒤 청크가 겹치도록 남길 길이 |

`chunk_overlap`의 목적:

```text
청크 A: ......중요 문장의 앞부분
                    ↓ 겹침
청크 B: 중요 문장의 앞부분......뒷부분
```

문장이 청크 경계에서 잘려 의미가 끊어지는 문제를 완화.

> `chunk_overlap = chunk_size의 20%` 같은 값은 고정 규칙이 아님. 문서 성격과 검색 품질을 보고 조정하는 값.

---

## 4.4 `Recursive`의 의미

큰 구분 기준부터 시도하고, 충분히 작아지지 않으면 더 작은 기준으로 내려가며 분할.

개념적으로:

```text
문단
 ↓ 너무 큼
줄바꿈
 ↓ 너무 큼
공백·문자 단위
```

목적은 **가능한 자연스러운 경계를 유지하면서 크기를 제한**하는 것.

# 5. Embeddings — 텍스트를 벡터로

## 5.1 LangChain 임베딩 규약

```python
from langchain_huggingface import HuggingFaceEmbeddings

embeddings = HuggingFaceEmbeddings(
    model_name="jhgan/ko-sroberta-multitask"
)
```

수업에서 사용한 SentenceTransformer 모델을 LangChain의 임베딩 부품으로 감싼 형태.

---

## 5.2 주요 메서드

| 메서드 | 사용 시점 | 입력 |
|---|---|---|
| `embed_documents(...)` | 문서를 색인할 때 | 문자열 여러 개 |
| `embed_query(...)` | 검색 질문을 벡터화할 때 | 문자열 1개 |

```python
query_vector = embeddings.embed_query("VPN 접속")

print("벡터 길이:", len(query_vector))
print("앞 5개:", [round(v, 4) for v in query_vector[:5]])
```

핵심:

```text
문서 ─┐
      ├─ 같은 임베딩 공간 → 벡터 유사도 비교
질문 ─┘
```

# 6. Chroma VectorStore와 Retriever

## 6.1 VectorStore 만들기

```python
from langchain_chroma import Chroma

hd_store = Chroma.from_documents(
    documents=hd_chunks,
    embedding=embeddings,
    collection_name="helpdesk_demo",
    ids=[f"hd-{i}" for i in range(len(hd_chunks))],
)
```

`Chroma.from_documents(...)`가 내부에서 수행하는 핵심:

```text
Document
  ↓
embedding 계산
  ↓
벡터 + 본문 + metadata 저장
```

현재 `langchain-chroma` 구현은 문서 추가 시 ID를 이용해 Chroma의 upsert를 수행하므로, **같은 ID는 같은 항목을 갱신하는 식으로 관리 가능**.

실무에서는 랜덤 ID보다 원본 문서 ID·청크 번호 등을 이용해 **재현 가능한 고유 ID**를 만드는 편이 안전.

예:

```python
chunk_ids = [
    f"{chunk.metadata['id']}-chunk-{i}"
    for i, chunk in enumerate(hd_chunks)
]
```

---

## 6.2 VectorStore → Retriever

```python
hd_retriever = hd_store.as_retriever(
    search_kwargs={"k": 2}
)
```

`k=2`:

- 질문과 가까운 문서 2개 반환
- 너무 작으면 근거 부족 가능
- 너무 크면 관련 없는 문서까지 포함될 수 있음

---

## 6.3 Retriever의 규약

```python
found = hd_retriever.invoke(
    "재택에서 사내 시스템에 못 들어가요"
)

print(type(found).__name__)
print(type(found[0]).__name__)

for doc in found:
    print(doc.metadata["title"])
    print(doc.page_content)
```

형태:

```text
입력  : 질문 문자열
출력  : list[Document]
```

이 공통 규약 덕분에 검색기 내부 구현이 바뀌어도 뒤쪽 RAG 코드는 비슷하게 유지 가능.

# 7. RAG 색인 제작 전체 코드

## 7.1 헬프데스크 FAQ

```python
import pandas as pd

from langchain_chroma import Chroma
from langchain_core.documents import Document
from langchain_huggingface import HuggingFaceEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter

# 1. 원본 데이터
faq_df = pd.read_csv("data/helpdesk_faq.csv")

# 2. Document 변환
faq_docs = [
    Document(
        page_content=row.text,
        metadata={"id": row.id, "title": row.title},
    )
    for row in faq_df.itertuples()
]

# 3. 분할
splitter = RecursiveCharacterTextSplitter(
    chunk_size=200,
    chunk_overlap=40,
)
faq_chunks = splitter.split_documents(faq_docs)

# 4. 임베딩
embeddings = HuggingFaceEmbeddings(
    model_name="jhgan/ko-sroberta-multitask"
)

# 5. 청크별 고유 ID
faq_chunk_ids = [
    f"{chunk.metadata['id']}-chunk-{i}"
    for i, chunk in enumerate(faq_chunks)
]

# 6. VectorStore
faq_store = Chroma.from_documents(
    documents=faq_chunks,
    embedding=embeddings,
    collection_name="helpdesk_kyoan",
    ids=faq_chunk_ids,
)

# 7. Retriever
faq_retriever = faq_store.as_retriever(
    search_kwargs={"k": 2}
)

print("색인 완료 - 청크 수:", len(faq_chunks))
```

전체를 기억하면:

```text
CSV
→ Document
→ Splitter
→ Embeddings
→ Chroma
→ Retriever
```

# 9. RAG 체인 — 검색과 생성을 한 번에

검색기만 있으면 아직:

```text
질문
→ 검색
→ Document 목록
```

RAG는 여기에 생성 단계를 연결.

```text
질문
  ├───────────────→ question 그대로
  │
  └→ Retriever → Document → context 문자열
                           ↓
                  Prompt + Model
                           ↓
                          답변
```

문서의 RAG 그림도 이 구조를 표현함.

# 10. 검색 결과를 프롬프트용 문자열로 변환

Retriever 결과는 `list[Document]`.

프롬프트 `{context}`에는 일반 문자열이 필요하므로 합쳐야 함.

```python
def format_docs(docs):
    """검색된 Document를 제목과 함께 하나의 문자열로 합친다."""
    return "\n\n".join(
        f"[{doc.metadata['title']}] {doc.page_content}"
        for doc in docs
    )
```

테스트:

```python
sample_docs = faq_retriever.invoke("VPN 접속 방법")
print(format_docs(sample_docs))
```

부품을 체인에 넣기 전 개별 테스트하는 습관이 중요.

```text
Retriever 테스트
→ format_docs 테스트
→ Prompt 테스트
→ 전체 Chain 연결
```

# 12. LCEL로 RAG 체인 조립

## 12.1 `RunnablePassthrough`

입력을 그대로 다음 단계로 통과.

```text
질문 → RunnablePassthrough() → 같은 질문
```

---

## 12.2 두 갈래로 분기

```python
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

rag_chain = (
    {
        "context": faq_retriever | format_docs,
        "question": RunnablePassthrough(),
    }
    | rag_prompt
    | model
    | StrOutputParser()
)
```

딕셔너리 부분의 흐름:

```text
같은 질문
   ├─ context  → Retriever → format_docs
   └─ question → 그대로 통과

결과
{
    "context": "검색된 자료 문자열",
    "question": "원래 질문"
}
        ↓
rag_prompt
```

LCEL에서 이 병렬 매핑은 `RunnableParallel`과 같은 방식으로 동작.

---

## 12.3 실행

```python
answer = rag_chain.invoke(

print(answer)
```

# 13. 답변과 검색 근거를 함께 받기

## 13.1 단순 병렬 방식

```python
from langchain_core.runnables import RunnableParallel

rag_with_sources = RunnableParallel(
    answer=rag_chain,
    sources=faq_retriever,
)

out = rag_with_sources.invoke(
    "VPN이 연결되지 않을 때 어떻게 해야 해?"
)

print("답:", out["answer"])
print(
    "출처:",
    [doc.metadata["title"] for doc in out["sources"]],
)
```

출력 구조:

```python
{
    "answer": "생성된 답",
    "sources": [Document(...), Document(...)],
}
```

장점:

- 답변 확인
- 근거 문서 확인
- UI에서 출처 표시 가능
- 디버깅 가능

주의:

`answer=rag_chain` 내부 검색과 `sources=faq_retriever` 검색이 각각 실행되어 **검색이 두 번 수행될 수 있음**.

---

## 13.2 검색을 한 번만 하고 근거 재사용

```python
from langchain_core.runnables import RunnableLambda


def search_docs(question):
    docs = faq_retriever.invoke(question)
    return {
        "context": format_docs(docs),
        "question": question,
        "sources": docs,
    }


def make_answer(data):
    prompt_input = {
        "context": data["context"],
        "question": data["question"],
    }

    answer = (
        rag_prompt
        | model
        | StrOutputParser()
    ).invoke(prompt_input)

    return {
        "answer": answer,
        "sources": data["sources"],
    }


rag_with_source = (
    RunnableLambda(search_docs)
    | RunnableLambda(make_answer)
)
```

실행:

```python
result = rag_with_source.invoke(
    "VPN 접속 방법을 알려줘"
)

print(result["answer"])
print(
    [doc.metadata["title"] for doc in result["sources"]]
)
```

흐름:

```text
질문
 ↓
검색 1회
 ↓
context + question + sources
 ↓
답변 생성
 ↓
answer + sources
```

```python
    ("human", "{question}"),
])

book_chain = (
    {
        "context": book_retriever | format_docs,
        "question": RunnablePassthrough(),
    }
    | book_prompt
    | model
    | StrOutputParser()
)

print(
    book_chain.invoke("전자책은 몇 대까지 볼 수 있어요?")
)
```

중요:

헬프데스크 체인에는 `faq_retriever`, 서점 체인에는 `book_retriever` 사용.

검색 대상과 검색기 변수를 섞으면 엉뚱한 문서가 근거로 들어감.

# 16. Text-to-SQL — 자연어 질문을 DB 조회로

문서가 아니라 데이터베이스 표에 답이 있는 경우.

예:

- 개발팀 주문 건수
- 가장 비싼 비품
- 부서별 주문 수
- 주문 금액이 가장 큰 부서

처리 흐름:

```text
자연어 질문
   ↓
DB 스키마 설명 제공
   ↓
모델이 SQL 생성
   ↓
SQL 안전성 검사
   ↓
DB 실행
   ↓
결과 확인
   ↓
자연어 답변
```

Text-to-SQL에서 중요한 것은 **모델에게 데이터베이스 설계도를 정확히 제공하는 것**.

---

# 17. SQLite DB 준비

```python
import sqlite3
from pathlib import Path

import pandas as pd

DB_PATH = Path("output") / "helpdesk.db"
DB_PATH.parent.mkdir(exist_ok=True)
DB_PATH.unlink(missing_ok=True)

# 초기 데이터 생성용 일반 연결
_conn = sqlite3.connect(
    DB_PATH,
    isolation_level=None,
)
_conn.execute("pragma foreign_keys = on")

_conn.executescript(
    Path("data/setup_day19.sql").read_text(
        encoding="utf-8"
    )
)

_conn.execute("pragma foreign_keys = on")

# 에이전트 조회용 읽기 전용 연결
_ro_conn = sqlite3.connect(
    f"file:{DB_PATH}?mode=ro",
    uri=True,
    isolation_level=None,
    check_same_thread=False,
)


def run_query(sql):
    """사람이 직접 확인할 SELECT 실행용."""
    cur = _conn.execute(sql)
    return pd.DataFrame(
        cur.fetchall(),
        columns=[desc[0] for desc in cur.description],
    )
```

연결을 두 개로 나누는 이유:

```text
_conn    = 준비·검증용 일반 연결
_ro_conn = 에이전트가 사용하는 읽기 전용 연결
```

에이전트에게 불필요한 쓰기 권한을 주지 않는 것이 핵심.

# 18. 모델이 만든 SQL은 그대로 실행하지 않기

모델은 잘못된 SQL이나 의도하지 않은 SQL을 만들 수 있음.

따라서 문서의 그림처럼 **두 겹 가드** 사용.

```text
자연어 질문
   ↓
스키마 제공
   ↓
모델이 SQL 생성
   ↓
┌─────────────────────┐
│ 가드 1              │
│ SELECT 한 문장 검사 │
└─────────────────────┘
   ↓
┌─────────────────────┐
│ 가드 2              │
│ 읽기 전용 DB 연결   │
└─────────────────────┘
   ↓
DB 조회
   ↓
결과
```

| 가드 | 역할 | 의미 |
|---|---|---|
| 1. 문자열 검사 | 명백한 쓰기·다중 문장 거부 | 빠른 사전 차단 |
| 2. 읽기 전용 연결 | DB 연결 자체가 쓰기 거부 | 실제 권한 경계 |

---

# 19. 가드 1 — `SELECT` 한 문장만 허용

```python
from langchain.tools import tool


@tool
def run_select(sql: str) -> str:
    """읽기 전용 SQL(SELECT) 한 문장을 실행한다."""

    stmt = sql.strip().rstrip(";")

    # SELECT로 시작하고 내부에 추가 세미콜론이 없는 한 문장만 허용
    if not stmt.lower().startswith("select") or ";" in stmt:
        return (
            "거부: 이 도구는 SELECT 조회 "
            "한 문장만 실행할 수 있습니다."
        )

    try:
        return str(_ro_conn.execute(stmt).fetchall())
    except sqlite3.Error as exc:
        return f"에러: {exc}"
```

테스트 예:

```python
attempts = [
    "select count(*) from hd_order",
    "select 1; delete from hd_order",
    "delete from hd_order",
    "select 1 from hd_order where 1=0 union select 1",
]

for sql in attempts:
    print(sql)
    print(run_select.invoke({"sql": sql}))
```

판단:

```text
SELECT 단일 문장             → 허용
SELECT; DELETE               → 거부
DELETE                       → 거부
복잡하지만 SELECT인 조회     → 허용 가능
```

이 검사는 SQL 의미 전체를 완벽하게 판별하는 보안 장치가 아님.

---

# 20. 가드 2 — 읽기 전용 연결

```python
try:
    _ro_conn.execute("delete from hd_order")
    print("삭제됨 - 이러면 안 됨")
except sqlite3.Error as exc:
    print("막힘:", exc)
```

핵심:

```text
문자열 검사
= 무엇을 막을지 코드로 판단

읽기 전용 연결
= 애초에 쓰기 권한 자체를 주지 않음
```

따라서 실제 안전 경계는 **DB 권한 제한** 쪽이 더 강함.

1차 검사는:

- 명백한 잘못을 빨리 거부
- 로그를 깔끔하게 유지
- 모델에게 수정 메시지 반환

2차 검사는:

- 1차 검사를 통과한 쓰기 시도까지 DB 차원에서 차단

# 23. 에이전트가 만든 SQL 확인

```python
def called_tools(result):
    """메시지 궤적에서 호출한 도구와 인자를 추출한다."""
    calls = []

    for message in result["messages"]:
        for call in getattr(message, "tool_calls", []) or []:
            calls.append((call["name"], call["args"]))

    return calls


def show_sql(result):
    """생성된 SQL과 최종 답을 확인한다."""
    for _, args in called_tools(result):
        if "sql" in args:
            print("만든 SQL:", args["sql"])

    print("답:", result["messages"][-1].content)
```

이 코드는 SQL 동작 자체보다 **에이전트가 무엇을 했는지 추적하는 용도**.

# 25. SQL을 실행 전에 구조화해서 받기

에이전트에게 바로 실행까지 맡기지 않고:

```text
질문
→ SQL 계획 생성
→ 사람이/코드가 검사
→ 승인
→ 실행
```

중간 개입이 필요한 경우 `with_structured_output()` 사용 가능.

---

## 25.1 SQL 계획 스키마

```python
from pydantic import BaseModel, Field


class SqlPlan(BaseModel):
    """자연어 질문을 SQL 조회 계획으로 변환한 결과."""

    sql: str = Field(
        description="실행할 SELECT 한 문장"
    )
    reason: str = Field(
        description="이 SQL로 질문에 답할 수 있는 이유"
    )
    tables: list[str] = Field(
        description="SQL에서 사용하는 표 이름 목록"
    )
```

---

## 25.2 구조화 계획 생성

```python
planner = model.with_structured_output(SqlPlan)

plan = planner.invoke(
    schema_prompt
    + "\n\n질문: 주변기기 분류 비품의 평균 단가는?"
)

print(type(plan).__name__)
print("SQL:", plan.sql)
print("이유:", plan.reason)
print("표:", plan.tables)
```

장점:

- 감사 로그 기록
- SQL 실행 전 확인
- 어떤 표를 사용하려는지 확인
- 사람 승인 단계 추가 가능

# 26. 구조화된 SQL의 사전 점검

```python
allowed_tables = {
    "hd_item",
    "hd_order",
}

if set(plan.tables) <= allowed_tables:
    print(
        run_select.invoke({"sql": plan.sql})
    )
else:
    blocked = set(plan.tables) - allowed_tables
    print("실행하지 않음:", blocked)
```

주의:

`plan.tables`도 모델이 생성한 값이므로 이것만 믿으면 안 됨.

즉:

```text
모델이 말한 tables 검사
= 편리한 사전 점검·로그

실제 읽기 전용 연결
= 최종 권한 방어선
```

구조화 출력은 안전성을 높이는 보조 장치이지 DB 권한을 대신하지 않음.

# 27. 도구 실행 + 구조화 최종 응답

구조화 결과까지 포함한 에이전트도 가능.

```python
from langchain.agents.structured_output import ProviderStrategy


class SqlAnswer(BaseModel):
    sql: str = Field(
        description="실행한 SELECT 한 문장"
    )
    reason: str = Field(
        description="이 SQL을 사용한 이유"
    )
    tables: list[str] = Field(
        description="사용한 표 이름 목록"
    )
    answer: str = Field(
        description="사용자에게 전달할 최종 답변"
    )
```

```python
book_sql_agent = create_agent(

        SqlAnswer,
        strict=True,
```

```python

            "role": "user",

```

`strict=True`는 provider/model의 strict structured output 지원 여부에 영향을 받음.

# 29. RAG와 Text-to-SQL 비교

| 항목 | RAG | Text-to-SQL |
|---|---|---|
| 대상 | 문서·FAQ·텍스트 | DB 테이블 |
| 핵심 입력 | 자연어 질문 | 자연어 질문 |
| 모델에게 필요한 정보 | 검색된 문서 내용 | DB 스키마 |
| 실제 조회 | Retriever | SQL |
| 결과 | 관련 `Document` | 행·집계 결과 |
| 생성 근거 | 검색 문서 | DB 실행 결과 |
| 안전 핵심 | 근거 없는 생성 방지 | 읽기 전용 권한·SQL 제한 |

공통 구조:

```text
질문
 ↓
외부 데이터에서 근거 조회
 ↓
조회 결과를 모델에게 전달
 ↓
최종 답변
```

차이:

```text
RAG         → 의미 유사도 검색
Text-to-SQL → 구조화된 표를 SQL로 정확히 계산·조회
```

# 30. 전체 시스템 관점

```text
                    사용자 질문
                         ↓
                 어떤 데이터가 필요한가?
                  ↙               ↘
          문서·FAQ                 DB 표
             ↓                      ↓
         Retriever               Text-to-SQL
             ↓                      ↓
      관련 Document             SELECT 실행 결과
             ↘                      ↙
                  근거 데이터
                      ↓
                     LLM
                      ↓
                   최종 답변
```

핵심 역할 분리:

```text
LLM       = 무엇을 찾고 어떻게 답할지 판단
Retriever = 문서에서 관련 근거 검색
SQL       = 표에서 조건·집계·JOIN 수행
DB 권한   = 허용 가능한 실제 작업 범위 제한
```

# 31. 핵심 코드 패턴

## Document

```python
doc = Document(
    page_content="본문",
    metadata={"id": "1", "title": "제목"},
)
```

## Splitter

```python
splitter = RecursiveCharacterTextSplitter(
    chunk_size=200,
    chunk_overlap=40,
)
chunks = splitter.split_documents(docs)
```

## Embeddings

```python
embeddings = HuggingFaceEmbeddings(
    model_name="jhgan/ko-sroberta-multitask"
)
```

## Chroma

```python
store = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    collection_name="my_collection",
    ids=ids,
)
```

## Retriever

```python
retriever = store.as_retriever(
    search_kwargs={"k": 2}
)

docs = retriever.invoke("질문")
```

## RAG 체인

```python
rag_chain = (
    {
        "context": retriever | format_docs,
        "question": RunnablePassthrough(),
    }
    | rag_prompt
    | model
    | StrOutputParser()
)
```

## 답 + 근거

```python
rag_with_sources = RunnableParallel(
    answer=rag_chain,
    sources=retriever,
)
```

```python
@tool
```

```python
sql_agent = create_agent(
```

# 32. 총정리

| 개념 | 핵심 | 대표 코드 |
|---|---|---|
| `Document` | 본문 + metadata | `Document(page_content=..., metadata=...)` |
| Splitter | 긴 문서를 청크로 분리 | `RecursiveCharacterTextSplitter(...)` |
| `chunk_overlap` | 경계 문맥 일부 유지 | `chunk_overlap=...` |
| Embeddings | 텍스트 → 벡터 | `HuggingFaceEmbeddings(...)` |
| VectorStore | 벡터 저장·유사도 검색 | `Chroma.from_documents(...)` |
| Retriever | 질문 → `Document` 목록 | `.as_retriever()` |
| `format_docs` | 문서 목록 → context 문자열 | `"\n\n".join(...)` |
| RAG 체인 | 검색 + 프롬프트 + 생성 | LCEL `|` 연결 |
| `RunnablePassthrough` | 질문 그대로 전달 | `RunnablePassthrough()` |
| `RunnableParallel` | 같은 입력을 병렬 처리 | `RunnableParallel(...)` |
| 근거 반환 | 답변과 출처 동시 반환 | `answer + sources` |
| 고정 체인 한계 | 필요 없어도 검색 실행 | 체인은 경로가 고정됨 |
| Text-to-SQL | 자연어 → SQL → DB 조회 | `create_agent(..., [run_select])` |
| 스키마 프롬프트 | DB 구조를 모델에게 설명 | 표·열·관계·규칙 |
| SQL 1차 가드 | SELECT 단일 문장 제한 | 문자열 검사 |
| SQL 2차 가드 | 쓰기 자체 차단 | SQLite `mode=ro` |
| 구조화 SQL | SQL·이유·사용 표를 객체로 받음 | `with_structured_output(SqlPlan)` |
| 구조화 에이전트 | 실행 후 결과도 스키마화 | `response_format=ProviderStrategy(...)` |

# 33. 최종 기억할 흐름

```text
[RAG]
원본 문서
→ Document
→ Splitter
→ Embeddings
→ VectorStore
→ Retriever
→ Prompt
→ Model
→ 답변

[Text-to-SQL]
자연어 질문
→ DB 스키마
→ SQL 생성
→ SELECT 검사
→ 읽기 전용 DB 실행
→ 결과
→ 답변
```

**한 문장 정리**

> **문서에서는 Retriever가 근거를 찾고, 데이터베이스에서는 SQL이 값을 조회하며, LLM은 그 조회 과정을 선택하고 결과를 설명한다.**

# 34. 문서 검사 및 교정 사항

- 원본의 표와 이미지 흐름을 확인해 Markdown 표와 텍스트 프로세스로 재구성.
- 페이지의 **RAG 체인 그림**을 `질문 → 검색 갈래 / 질문 갈래 → Prompt → Model → 답변` 구조로 반영.
- 페이지의 **Text-to-SQL 두 겹 가드 그림**을 `SELECT 사전 검사 + 읽기 전용 DB 연결` 구조로 반영.
- `jhgan/ko-sroberta-[깨진 문자]-multitask`처럼 깨진 모델명을 `jhgan/ko-sroberta-multitask`로 교정.
- 헬프데스크·서점 예시에서 `faq_retriever`를 덮어쓰던 부분을 `faq_retriever` / `book_retriever`로 분리.
- 서점 색인 예시의 `faq_store`, `faq_retriever`, `book_helpdesk`처럼 이름이 섞인 부분을 서점 기준 변수명으로 통일.
- `book_chain`이 서점 검색기 대신 `faq_retriever`를 사용하던 부분을 `book_retriever`로 교정.
- 검색기 변수 혼용 때문에 보안 USB 질문에 전자책·결제 문서가 검색되던 예시는 **검색 실패 사례가 아니라 잘못된 Retriever 연결 사례**로 판단해 정리에서 수정.
- `chunk_overlap`을 `chunk_size의 약 20%`로 고정하는 표현을 제거하고 **튜닝값**으로 교정.
- Chroma ID는 청크 단위로 안정적인 고유 ID를 생성하도록 수정.
- `RunnableParallel(answer=rag_chain, sources=retriever)`는 검색이 두 번 실행될 수 있음을 명시하고, 검색 1회 재사용 패턴을 별도로 정리.
- 에이전트 입력 형식을 현재 공식 예시의 `messages=[{"role": "user", "content": ...}]` 형태로 통일.
- 도구 import를 현재 상위 API 예시인 `from langchain.tools import tool` 형태로 정리.
- `run_select()`의 예외 범위를 일반 `Exception` 대신 `sqlite3.Error` 중심으로 좁힘.
- `plan.tables` 검사는 모델이 생성한 값에 대한 **사전 점검**일 뿐 실제 보안 경계가 아니라는 점을 보완.
- 실제 DB 안전성은 SQL 문자열 검사보다 **읽기 전용 연결·권한 제한**이 더 중요한 구조라는 점을 명확화.
- `ProviderStrategy(..., strict=True)`는 provider/model의 strict structured output 지원 여부를 확인해야 함.
