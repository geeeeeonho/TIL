# 멀티툴 에이전트 개발 파이프라인

> 목표: 질문의 성격에 따라 **문서 검색(RAG) · SQL 조회 · 외부 API · 현재 상태 도구**를 모델이 선택하고, 필요하면 여러 도구를 연속 호출해 최종 답을 만드는 구조.

---

## 0. 전체 구조

```text
사용자 질문
   ↓
Agent
   ↓  질문 + Tool 이름/설명/인자 스키마를 보고 판단
┌──────────────────────────────────────────────┐
│ search_policy       → 문서/RAG               │
│ run_select          → SQL/정형 데이터        │
│ business_day_after  → 외부 API + 계산        │
│ get_today           → 현재 실행 시점         │
└──────────────────────────────────────────────┘
   ↓
Tool 결과(Observation)
   ↓
추가 도구가 필요하면 다시 판단
   ↓
최종 답변
```

핵심 원칙:

- **답이 있는 곳이 다르면 도구도 달라짐**
- 정해진 경로는 **Chain**, 질문마다 경로가 달라지면 **Agent**
- Agent 라우팅의 핵심은 `if` 문보다 **Tool 이름 + docstring + 인자 정의**
- Tool 결과를 본 뒤 다음 Tool을 다시 선택하는 반복 구조가 **ReAct**

# 1. 개발 준비

## 1.1 모델 준비

load_dotenv('.env')

if not os.getenv('OPENAI_API_KEY'):

`temperature=0`:

- 출력 표현의 변동을 줄이는 설정
- **도구 선택이 완전히 결정적이라는 뜻은 아님**
- Tool 설명이 모호하면 `temperature=0`이어도 선택이 흔들릴 수 있음

## 1.2 RAG 저장소 준비

```python
from langchain_chroma import Chroma
from langchain_huggingface import HuggingFaceEmbeddings

embeddings = HuggingFaceEmbeddings(
    model_name='jhgan/ko-sroberta-multitask'
)

policy_store = Chroma(
    persist_directory='data/chroma_day20',
    collection_name='policy_day20',
    embedding_function=embeddings,
)

policy_retriever = policy_store.as_retriever(
    search_kwargs={'k': 3}
)
```

중요:

- **적재할 때와 검색할 때 같은 임베딩 모델 사용**

- 클라우드 DB와의 핵심 차이는 영속성 자체보다 **공유·중앙관리·SQL JOIN/필터 결합**에 있음

# 2. Tool 설계부터 시작

Agent가 Tool을 고를 때 주로 보는 정보:

```text
Tool 이름
Tool 설명(docstring)
인자 이름
인자 타입
```

함수 내부 구현 코드는 라우팅 판단의 직접 근거가 아님.

## 좋은 Tool 설명

```python
@tool
def business_day_after(start_date: str, days: int) -> str:
    """접수일부터 지정한 영업일 뒤 날짜를 계산한다.

    주말과 한국 공휴일을 제외한다.
    처리 기한, 검토 완료일, 업무 완료 예정일을 물을 때 사용한다.
    start_date는 YYYY-MM-DD 형식이다.
    """
```

좋은 docstring 점검:

1. **무엇을 하는가**
2. **언제 사용하는가**
3. **어떤 값을 받는가**
4. **어떤 결과를 반환하는가**

> `docstring`과 `system_prompt`는 역할이 다름.
>
> - `docstring`: **개별 Tool 사용 설명서**. 라우팅과 인자 생성에 직접 영향
> - `system_prompt`: **Agent 전체 행동 규칙**. 근거 사용, SQL 규칙, 답변 방식 등 전역 정책

## 3.2 영업일 계산 Tool

```python
from datetime import date, timedelta
from langchain_core.tools import tool

WEEKDAY_NAMES = '월화수목금토일'


@tool
def business_day_after(start_date: str, days: int) -> str:
    """접수일부터 영업일(days)만큼 뒤 날짜를 계산한다.

    주말과 한국 공휴일은 제외한다.
    처리 기한이나 완료 예정일을 물을 때 사용한다.
    start_date는 YYYY-MM-DD 형식이다.
    """

    # 1. 입력 검증
    try:
        day = date.fromisoformat(start_date.strip())
    except ValueError:
        return f"'{start_date}'는 올바른 날짜가 아님. YYYY-MM-DD 형식 필요"

    # 2. 공휴일 확보
    holidays = {}

    for year in (day.year, day.year + 1):
        try:
            res = requests.get(
                f'https://date.nager.at/api/v3/PublicHolidays/{year}/KR',
                timeout=10,
            )
            res.raise_for_status()
        except requests.RequestException as error:
            return f'공휴일 조회 실패: {error}'

        holidays.update({
            h['date']: h['localName']
            for h in res.json()
        })

    # 3. 주말/공휴일 제외하며 계산
    left = days
    skipped = []

    while left > 0:
        day += timedelta(days=1)

        weekday = WEEKDAY_NAMES[day.weekday()]
        holiday_name = holidays.get(day.isoformat())

        if day.weekday() >= 5:
            reason = f'{weekday}요일'
            if holiday_name:
                reason += f'·{holiday_name}'

            skipped.append(f'{day.isoformat()}({reason})')
            continue

        if holiday_name:
            skipped.append(f'{day.isoformat()}({holiday_name})')
            continue

        left -= 1

    # 4. 결과 반환
    end = f'{day.isoformat()}({WEEKDAY_NAMES[day.weekday()]}요일)'

    return (
        f'{start_date}부터 {days}영업일 뒤: {end}\n'
        f"건너뛴 날: {', '.join(skipped)}"
    )
```

핵심:

- 외부 서비스는 항상 실패 가능
- `requests.RequestException` 처리
- Agent 내부 Tool은 실패 시 **에러 문자열을 Observation으로 반환**하면 모델이 상황을 읽고 안내 가능
- 결과값만 주기보다 **건너뛴 날짜와 이유**까지 반환하면 검산 가능

> 위 예시는 시작 연도와 다음 연도까지만 공휴일을 가져오는 학습용 구현. 매우 긴 기간을 계산한다면 계산 범위에 맞게 연도를 동적으로 추가해야 함.

# 4. ReAct: 판단 → 행동 → 관찰

ReAct 기본 반복:

| 단계 | 역할 | 예 |
|---|---|---|
| Reasoning | 다음 행동 결정 | 영업일 계산 필요 판단 |
| Acting | Tool 호출 | `business_day_after(...)` |
| Observation | Tool 결과 확인 | `2026-05-15` |

```text
질문
→ Tool 선택
→ Tool 실행
→ 결과 확인
→ 추가 Tool 필요 여부 판단
→ 최종 답변
```

중요:

- 내부 추론 전체가 사용자에게 그대로 노출되는 구조로 이해하면 안 됨
- 실무에서 관찰 가능한 핵심은 **어떤 Tool을 어떤 인자로 호출했는가**와 **Tool 결과가 무엇이었는가**

---

## 4.1 메시지 기록

```python
from langchain.agents import create_agent
from langchain_core.messages import AIMessage, HumanMessage, ToolMessage

agent = create_agent(
    model,
    [business_day_after],
    system_prompt='필요할 때 도구를 사용한다.',
)

result = agent.invoke({
    'messages': '2026-05-08 접수 건이 5영업일이면 언제 끝나?'
})
```

기록 구조:

| 메시지 | 의미 |
|---|---|
| `HumanMessage` | 사용자 질문 |
| `AIMessage(tool_calls 있음)` | Tool 선택 + 인자 생성 |
| `ToolMessage` | Tool 실행 결과 |
| `AIMessage(tool_calls 없음)` | 최종 답변 |

```text
HumanMessage
→ AIMessage(tool_calls)
→ ToolMessage
→ AIMessage(final)
```

## 4.2 Tool 호출 기록 확인

```python
def tool_names(result):
    names = []

    for message in result['messages']:
        if isinstance(message, AIMessage):
            for call in message.tool_calls:
                names.append(call['name'])

    return names


def step_count(result):
    return sum(
        1
        for message in result['messages']
        if isinstance(message, AIMessage)
    )
```

사용 목적:

- 어떤 Tool이 선택됐는지 확인
- Tool을 몇 번 호출했는지 확인
- 다단계 실행 여부 확인
- 라우팅 오류 디버깅

# 5. 실행 흐름 관찰: `stream`

`invoke()`:

```text
전체 실행 완료
→ 최종 상태 반환
```

`stream()`:

```text
단계가 진행될 때마다 중간 상태 반환
```

| `stream_mode` | 반환 단위 | 사용 목적 |
|---|---|---|
| `messages` | 모델 메시지/토큰 조각 | 화면에 생성 과정 표시 |
| `updates` | 이번 단계에서 새로 생긴 상태 | 방금 일어난 변화 확인 |
| `values` | 현재까지 누적된 전체 상태 | Agent 실행 궤적 확인 |

Agent 동작 분석에는 `values`가 직관적.

```python
for snapshot in agent.stream(
    {'messages': '2026-05-08부터 5영업일 뒤는?'},
    stream_mode='values',
):
    latest = snapshot['messages'][-1]
    print(type(latest).__name__)
```

# 6. 문서 검색 Tool 만들기

## 6.1 검색은 작은 Chunk, 전달은 넓은 문맥

문서를 너무 크게 자르면:

- 질문과 관계없는 내용이 함께 섞임
- 임베딩 표현이 넓어짐
- 검색 정밀도 저하 가능

Chunk를 너무 작게 자르면:

- 문장이 중간에서 끊김
- 이유·조건·결론이 서로 다른 Chunk로 분리됨

따라서:

```text
검색 단계    → 작은 Chunk
모델 전달 단계 → 검색 Chunk + 앞뒤 Chunk
```

---

## 6.2 Chunk metadata

예시:

```python
metadata = {
    'doc_id': 'ai20',
    'chunk_no': 2,
    'chunk_total': 5,
    '쪽': 20,
    '소제목': '이용자 개인정보의 AI 학습 사례',
}
```

| metadata | 용도 |
|---|---|
| `doc_id` | 같은 원문 묶음 식별 |
| `chunk_no` | 현재 Chunk 위치 |
| `chunk_total` | 문서 범위 초과 방지 |
| `쪽` | 출처 표시 |
| `소제목` | 근거 위치 설명 |

---

## 6.3 검색 Chunk 앞뒤 확장

```python
def with_neighbors(store, hit, window=1):
    """검색된 Chunk의 앞뒤 문맥을 같은 문서에서 가져옴."""

    tag = hit.metadata

    want = [
        n
        for n in range(
            tag['chunk_no'] - window,
            tag['chunk_no'] + window + 1,
        )
        if 0 <= n < tag['chunk_total']
    ]

    got = store.get(
        where={
            '$and': [
                {'doc_id': {'$eq': tag['doc_id']}},
                {'chunk_no': {'$in': want}},
            ]
        }
    )

    pairs = sorted(
        zip(got['metadatas'], got['documents']),
        key=lambda p: p[0]['chunk_no'],
    )

    return '\n'.join(text for _, text in pairs)
```

왜 `sorted()` 필요?

- 저장소 `get()` 결과 순서가 항상 Chunk 순서라는 보장 없음
- `chunk_no` 기준 재정렬 필요

`window=1`:

```text
이전 Chunk + 검색 Chunk + 다음 Chunk
```

너무 크게 설정하면:

- 토큰 증가
- 비용 증가
- 무관한 문맥 증가

---

## 6.4 출처까지 함께 묶기

```python
def policy_context(store, hits, window=1):
    blocks = []

    for hit in hits:
        tag = hit.metadata

        blocks.append(
            f"[{tag['쪽']}쪽 · {tag['소제목']}]\n"
            + with_neighbors(store, hit, window)
        )

    return '\n\n'.join(blocks)
```

검색 결과에 출처를 먼저 포함시키면 모델이 답변에서 근거를 표시하기 쉬움.

실무 개선:

- 여러 검색 결과의 neighbor 영역이 겹치면 같은 Chunk가 중복될 수 있음
- `doc_id + chunk_no` 기준 중복 제거 가능

# 7. RAG Chain vs 검색 Tool

## Chain

```text
질문
→ 검색
→ 프롬프트
→ LLM
→ 답변
```

장점:

- 흐름 고정
- 예측 가능
- 모델 호출 수 적음
- 빠르고 저렴

단점:

- 검색이 필요 없는 입력도 검색됨

예:

```text
"고마워"
→ 벡터 검색 실행
→ 관련 없는 top-k 문서가 억지로 붙음
```

벡터 검색은 보통 **"관련 없음"을 반환하지 않고 top-k 중 상대적으로 가까운 것**을 반환하기 때문.

---

## Agent + 검색 Tool

```python
@tool
def search_policy(query: str) -> str:
    """생성형 AI 개인정보 처리 안내서에서 관련 규정 대목을 검색한다.

    학습데이터, 개인정보 고지, 동의, 국외이전, 위탁 등
    AI 서비스 개인정보 규정을 물을 때 사용한다.
    """

    hits = policy_retriever.invoke(query)
    return policy_context(policy_store, hits)
```

```python
policy_agent = create_agent(
    model,
    [search_policy],
)
```

Agent는 검색 자체를 하나의 선택지로 봄.

```text
규정 질문 → search_policy 호출
인사말    → Tool 호출 없음
```

> 검색 질의를 무조건 "명사 하나"로 줄일 필요는 없음. 벡터 검색에는 **의미가 충분히 남는 짧고 명확한 질의**가 유리함. 지나친 축약은 검색 맥락을 잃을 수 있음.

# 8. RAG 답변은 근거 기반으로 제한

```python
cited_agent = create_agent(
    model,
    [search_policy],
    system_prompt=(
        '개인정보 관련 질문은 search_policy로 찾은 내용에만 근거한다. '
        '자료에서 확인되지 않으면 확인할 수 없다고 답한다. '
        '답 끝에 사용한 쪽 번호를 표시한다.'
    ),
)
```

핵심:

```text
검색
→ 문맥 + 출처 전달
→ 자료에 근거해 답변
→ 출처 표기
```

주의:

- 벡터 검색은 관련 없는 질문에도 top-k를 반환할 수 있음
- `"찾은 내용에만 근거"`는 프롬프트 규칙이지 절대적 보안장치는 아님
- 신뢰성이 중요하면 추가 검증 필요
  - similarity threshold
  - reranker
  - 근거 존재 검사
  - 출처 ID 검증

# 9. SQL 조회 Tool 만들기

정형 데이터 질문:

```text
"국외 이전 서비스가 몇 개?"
"부서별 신청 좌석 합계는?"
"국외 이전 서비스를 신청한 부서는?"
```

이런 질문은 RAG보다 **SQL 조회**가 적합.

---

## 9.1 기본 흐름

```text
자연어 질문
→ Agent가 SQL 생성
→ run_select Tool 호출
→ DB 실행
→ 결과 관찰
→ 자연어 답변
```

모델은 DB 내부 구조를 자동으로 아는 것이 아님.

따라서 **Schema 설명이 모델의 눈**.

---

## 9.2 읽기 전용 연결

```python
import sqlite3

_ro_conn = sqlite3.connect(
    f'file:{DB_PATH}?mode=ro',
    uri=True,
    isolation_level=None,
    check_same_thread=False,
)
```

`mode=ro`:

```text
DB 자체를 읽기 전용으로 열기
→ DELETE / UPDATE / INSERT 차단
```

---

## 9.3 SQL Tool 안전장치

```python
@tool
def run_select(sql: str) -> str:
    """SELECT 조회 한 문장만 실행하고 결과를 반환한다."""

    stmt = sql.strip().rstrip(';')

    if not stmt.lower().startswith('select') or ';' in stmt:
        return '거부: SELECT 한 문장만 실행 가능'

    try:
        rows = _ro_conn.execute(stmt).fetchall()
        return str(rows)
    except Exception as error:
        return f'에러: {error}'
```

보호 구조:

```text
1차: 문자열 검사
2차: DB 읽기 전용 연결
```

1차 검사만으로는 충분하지 않음.

```sql
select 1 from ai_service where 1=0 union select 1
```

위 SQL도 `SELECT`로 시작하므로 문자열 검사를 통과함.

따라서 실제 방어선:

```text
읽기 전용 계정/연결
+ 최소 권한
```

실무에서는 추가 고려:

- 쿼리 시간 제한
- 결과 행 수 제한
- 허용 테이블/열 제한
- SQL parser 기반 검사
- DB 계정 권한 분리

# 10. Schema Prompt 설계

좋은 Schema 설명에 필요한 정보:

```text
1. 테이블 이름
2. 컬럼 이름
3. 컬럼 의미
4. 허용 값
5. 테이블 관계(FK/JOIN)
6. 생성 가능한 SQL 규칙
```

예:

```python
SCHEMA_PROMPT = """
너는 사내 AI 서비스 도입 대장을 조회한다.
반드시 run_select로 실제 값을 조회한 뒤 답한다.

표:

ai_service(
    service_id text,
    service_name text,
    vendor text,
    category text,
    personal_data text,
    overseas_transfer text,
    monthly_cost int,
    review_status text
)

personal_data: '예' / '아니오'
overseas_transfer: '예' / '아니오'
review_status: '승인' / '검토중' / '보류'

ai_request(
    request_id int,
    service_id text,
    dept text,
    seats int,
    request_date text,
    status text
)

관계:
ai_request.service_id -> ai_service.service_id

규칙:
- SELECT 한 문장만 사용
- 위 테이블과 컬럼만 사용
- 정해진 값은 원래 문자열 그대로 비교
"""
```

좋은 Schema 설명이면 모델이 스스로:

- `WHERE`
- `COUNT`
- `GROUP BY`
- `ORDER BY`
- `JOIN`

등을 구성할 수 있음.

# 11. 여러 Tool을 하나의 Agent에 결합

## 11.1 현재 상태 Tool

```python
from datetime import date

@tool
def get_today() -> str:
    """현재 실행 환경의 날짜를 YYYY-MM-DD 형식으로 반환한다."""
    return date.today().isoformat()
```

현재 날짜·시간처럼 변하는 값은 모델 기억보다 **실행 환경에서 직접 조회**하는 방식이 안전.

---

## 11.2 Tool 목록 구성

```python
ALL_TOOLS = [
    search_policy,
    run_select,
    business_day_after,
    get_today,
]
```

```python
desk = create_agent(
    model,
    ALL_TOOLS,
    system_prompt=(
        SCHEMA_PROMPT
        + '\n개인정보 규정은 search_policy로 확인한다.'
    ),
)
```

라우팅 예:

| 질문 | Tool |
|---|---|
| 대화를 학습에 쓰려면? | `search_policy` |
| 국외이전 서비스 몇 개? | `run_select` |
| 5영업일 뒤는? | `business_day_after` |
| 오늘 며칠? | `get_today` |

핵심:

```text
코드에서 if/elif로 직접 분기하지 않음
→ 모델이 Tool 설명을 읽고 선택
```

# 12. Multi-Tool 실행 패턴

## 12.1 서로 독립적인 Tool 두 개

질문:

```text
"개인정보를 입력하는 서비스는 몇 개고,
학습데이터에 개인정보가 섞이면 어떻게 해야 해?"
```

필요 Tool:

```text
run_select
search_policy
```

둘이 서로의 결과를 필요로 하지 않으면 한 `AIMessage` 안에 여러 `tool_calls`가 생성될 수 있음.

```text
AIMessage
 ├─ run_select(...)
 └─ search_policy(...)
```

---

## 12.2 앞 Tool 결과가 다음 Tool 인자가 되는 경우

질문:

```text
"개발팀의 가장 빠른 신청은 5영업일이면 언제 끝나?"
```

실행:

```text
1. run_select
   ↓
접수일 = 2026-05-08

2. business_day_after(
       start_date='2026-05-08',
       days=5
   )
   ↓
완료일 계산
```

전체 궤적:

```text
질문
→ AIMessage: run_select 호출
→ ToolMessage: 접수일
→ AIMessage: business_day_after 호출
→ ToolMessage: 완료일
→ AIMessage: 최종 답변
```

이때 Tool 순서를 코드에서 고정하지 않아도 됨.

**앞 Observation이 다음 Action의 입력이 되는 것**이 ReAct 반복의 핵심.

# 13. Tool 선택 오류 디버깅

## 13.1 Tool을 안 부름

증상:

```text
tool_calls = []
```

원인:

- Tool 설명이 사용 시점을 알려주지 못함

개선:

```text
"정보를 조회한다"
        ↓
"AI 서비스의 개인정보 국외이전 여부를 확인할 때 사용한다"
```

---

## 13.2 잘못된 Tool 선택

확인:

```text
tool_calls의 name
```

나쁜 이름:

```text
lookup
check
search1
```

좋은 이름:

```text
search_policy
service_status
business_day_after
```

Tool 이름만 봐도 용도가 드러나게 설계.

---

## 13.3 Tool은 맞지만 결과가 틀림: 조용한 실패

예:

```text
DB key = 's3'
모델 인자 = 'S3'
→ 조회 결과 없음
```

에러는 발생하지 않지만 결과가 틀림.

확인 위치:

```text
tool_calls.args
ToolMessage
```

개선:

- Tool 내부에서 `strip()`, `lower()` 등 입력 정규화
- 허용 값 명확히 설명
- 찾지 못한 경우 단순 `'없음'`보다 원인을 알 수 있는 문자열 반환

```python
service_id = service_id.strip().lower()
```

---

## 13.4 같은 Tool을 반복 호출

원인 예:

```text
"확실히 하려면 여러 번 호출한다"
```

이런 docstring은 반복 호출을 유도.

개선:

```text
한 번 호출하면 현재 상태를 확정적으로 반환한다
```

# 14. Local RAG → Cloud Vector DB 확장

Agent 입장에서 저장소가 바뀌어도 중요한 것은 **검색 함수의 입출력 규약**.

```text
query 문자열
→ 검색
→ Document 목록
→ Tool에서 문자열 Context로 변환
```

---

## 14.1 Supabase + pgvector 검색

```python
from supabase import create_client
from langchain_core.documents import Document

supabase = create_client(
    os.environ['SUPABASE_URL'],
    os.environ['SUPABASE_ANON_KEY'],
)


def cloud_faq_search(query, k=3, category=None):
    rows = supabase.rpc(
        'match_faq',
        {
            'query_embedding': embeddings.embed_query(query),
            'match_count': k,
            'filter_category': category,
        },
    ).execute().data

    return [
        Document(
            page_content=(
                f"질문: {row['question']}\n"
                f"답변: {row['answer']}"
            ),
            metadata={
                'faq_id': row['faq_id'],
                'category': row['category'],
                'team_name': row['team_name'],
                'similarity': row['similarity'],
            },
        )
        for row in rows
    ]
```

Tool로 감싸기:

```python
@tool
def search_research_faq(query: str) -> str:
    """연구비 FAQ에서 집행·정산·카드 등록 관련 안내를 검색한다."""

    docs = cloud_faq_search(query, k=3)
    return '\n\n'.join(d.page_content for d in docs)
```

Agent 바깥 구조는 거의 변하지 않음.

---

## 14.2 Chroma vs Supabase pgvector

| 기준 | Chroma(Local) | Supabase + pgvector |
|---|---|---|
| 시작 난이도 | 낮음 | 프로젝트/키 설정 필요 |
| 같은 PC에서 영속 저장 | `persist_directory` 사용 시 가능 | 가능 |
| 여러 사용자 공유 | 별도 배포 필요 | 중앙 DB로 쉬움 |
| SQL 조건 결합 | metadata filter | `WHERE` 활용 |
| 다른 테이블 결합 | 별도 처리 | `JOIN` 가능 |
| 네트워크 | 불필요 | 필요 |
| 운영 환경 | 로컬/프로토타입에 편함 | 공동 운영·서비스에 유리 |

선택 기준:

```text
혼자 실험/프로토타입
→ Local Chroma

여러 사용자가 공유
+ 데이터 지속 업데이트
+ SQL 필터/JOIN 필요
→ PostgreSQL + pgvector 계열
```

# 16. 최종 핵심 정리

| 개념 | 핵심 |
|---|---|
| ReAct | Tool 결과를 보고 다음 행동을 다시 결정하는 반복 |
| Tool | 모델이 선택할 수 있는 하나의 행동 |
| docstring | Tool 라우팅의 핵심 설명서 |
| system prompt | Agent 전체 정책과 제약 |
| `AIMessage.tool_calls` | 선택한 Tool과 인자 |
| `ToolMessage` | 실제 Tool 실행 결과 |
| RAG Chunk | 작게 검색하고, 앞뒤 문맥을 붙여 전달 |
| metadata | Chunk 연결 + 출처 추적 |
| Chain | 흐름이 고정된 작업에 적합 |
| Agent | 질문에 따라 경로가 달라지는 작업에 적합 |
| SQL Agent | Schema 설명이 모델의 DB 시야 |
| SQL 보안 | 문자열 검사보다 읽기 전용 권한이 핵심 |
| Multi-Tool | 독립 호출 또는 결과 의존 연쇄 호출 |
| 디버깅 | Tool 이름뿐 아니라 **인자와 ToolMessage까지 확인** |
| Vector DB 교체 | 검색 입출력 규약만 맞추면 Agent 구조 재사용 가능 |

한 줄 구조:

```text
질문
→ Agent 판단
→ 적절한 Tool 호출
→ 결과 관찰
→ 필요 시 다음 Tool 호출
→ 근거 기반 최종 답변
```

가장 중요한 기준:

```text
좋은 Agent = Tool이 많은 Agent가 아님

좋은 Agent
= 역할이 겹치지 않는 Tool
+ 명확한 설명
+ 안전한 실행
+ 관찰 가능한 실행 기록
+ 신뢰할 수 있는 근거
```
