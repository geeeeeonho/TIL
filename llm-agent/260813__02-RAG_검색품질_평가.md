# RAG 검색 품질 평가

> 검색기를 만든 뒤 **정량 평가 → 실패 분석 → 개선 → 재평가**하는 흐름 정리  
> 기준 자료: 업로드된 `RAG 검색 품질 평가` 노트북

---

## 0. 전체 개발 파이프라인

```text
[문서]
  ↓
청킹(chunk_size / overlap)
  ↓
각 청크에 고유 ID 부여
  ↓
임베딩
  ↓
Vector DB 색인 고정
  ↓
────────────────────────────────────
[평가셋]
질문 + 정답 청크 ID + 근거 문장
  ↓
질문 검색
  ↓
상위 K개 청크 ID 추출
  ↓
정답 청크와 비교
  ↓
Hit@K / Precision@K / Recall@K / RR·MRR@K
  ↓
문항별 실패 분석
  ↓
원인에 맞는 한 가지 요소 수정
  ↓
같은 평가셋으로 재평가
  ↓
기존 정답 문항의 회귀(regression) 여부 확인
```

핵심:

- **RAG 답변 품질 이전에 검색 품질부터 따로 측정**
- 검색 평가는 LLM 호출 없이 **임베딩 + 검색 결과만으로 가능**
- 평균 점수만 보지 않고 **실패한 질문을 직접 확인**
- 한 번에 하나만 바꾼 뒤 같은 평가셋으로 다시 측정

---

# 1. 왜 검색 평가가 필요한가

RAG에서 최종 답변이 틀리는 원인은 크게 나뉨.

```text
질문
 ↓
검색 실패 ──→ 정답 근거 자체가 모델에 전달되지 않음
 ↓
검색 성공
 ↓
생성 모델의 답변 생성
```

검색 결과가 잘못되면 이후 모델이 아무리 좋아도 근거 기반 답변이 어려움.

따라서 아래 설정을 감으로 정하면 안 됨.

- `k`: 검색 결과를 몇 개 가져올지
- `chunk_size`: 청크 크기
- `chunk_overlap`: 청크 겹침
- 임베딩 모델
- 질의 표현
- 하이브리드 검색 여부
- 리랭킹 여부

기준이 되는 것이 **검색 평가셋과 검색 지표**.

---

# 2. 평가셋 설계

평가셋은 기본적으로 세 요소로 구성.

| 요소 | 의미 |
|---|---|
| 질문 | 실제 사용자가 물을 법한 질의 |
| 정답 라벨 | 답이 실제로 들어 있는 **청크 ID 목록** |
| 근거 문장 | 정답 청크 안에서 실제 답이 되는 원문 발췌 |

예시 구조:

```text
query_id: q01

질문:
"프롬프트에 주민등록번호가 들어오면 어떻게 처리해야 하나?"

정답 청크:
["ai33-0"]

근거 문장:
"... 개인식별 가능성이 높은 정보를 탐지·삭제 ..."
```

## 청크 단위로 라벨링해야 하는 이유

정답 라벨을 문서 단위로 붙이면 문제가 생김.

```text
문서 A
├─ 청크 A-0  ← 답 없음
├─ 청크 A-1  ← 실제 정답
└─ 청크 A-2  ← 답 없음
```

검색 결과가 `A-0`인데 문서 단위로 평가하면:

```text
같은 문서 A
→ 정답 처리
→ 실제로는 근거가 없는데 점수를 얻음
```

이를 **허위 크레딧(false credit)** 으로 볼 수 있음.

따라서:

> **RAG 검색 평가는 실제 답이 들어 있는 청크 단위로 라벨링하는 것이 핵심.**

---

## 근거 문장도 함께 저장하는 이유

청크 ID는 청킹 방식에 종속됨.

```text
chunk_size=400
↓
ai33-0
ai33-1
ai33-2
```

청킹 규칙을 바꾸면 ID와 경계가 달라질 수 있음.

```text
chunk_size=600
↓
기존 gold chunk ID를 그대로 사용할 수 없음
```

반면 **근거 문장 자체는 원문에 남아 있음**.

따라서 청킹을 다시 했을 때:

```text
근거 문장
→ 새 색인에서 해당 문장 검색
→ 새 청크 ID 확인
→ 정답 라벨 재구축
```

가능.

# 3. 평가용 Vector DB 고정

교안의 평가용 색인:

```text
data/chroma_day20/
└─ guide_400
```

설정:

```text
문서: 안내서 2건, 총 74쪽
chunk_size = 400
chunk_overlap = 80
청크 수 = 299
청크 ID = "{문서id}-{순번}"
예: ai33-0
```

평가에서는 **색인을 임의로 다시 만들지 않음**.

이유:

1. 재임베딩 비용 발생
2. 청킹 규칙이 달라지면 기존 정답 청크 ID와 비교 불가
3. 평가 조건이 바뀌어 재현성이 깨짐

---

## 임베딩 모델도 동일해야 함

```python
from langchain_chroma import Chroma
from langchain_huggingface import HuggingFaceEmbeddings

eval_embeddings = HuggingFaceEmbeddings(
    model_name="jhgan/ko-sroberta-multitask"
)

eval_store = Chroma(
    persist_directory="data/chroma_day20",
    collection_name="guide_400",
    embedding_function=eval_embeddings,
)
```

중요:

```text
색인을 만들 때 사용한 임베딩 모델
          =
검색할 때 사용하는 임베딩 모델
```

모델이 달라지면 오류가 바로 발생하지 않더라도 **벡터 공간이 달라져 검색 순위가 잘못될 수 있음**.

# 5. 검색 결과에서 청크 ID만 추출

정답 라벨이 청크 ID이므로 검색 결과도 같은 형태로 비교해야 함.

```python
def search_ids(store, query, k):
    """질문과 가장 가까운 청크 k개의 ID를 검색 순서대로 반환."""

    retriever = store.as_retriever(
        search_kwargs={"k": k}
    )

    docs = retriever.invoke(query)

    return [d.id for d in docs]
```

흐름:

```text
query
 ↓
Retriever
 ↓
Document 1
Document 2
Document 3
 ↓
Document.id 추출
 ↓
["ai33-0", "ai31-2", "ai20-1"]
```

`ids=`로 저장한 Chroma의 청크 ID는 검색 결과의 `Document.id`로 사용 가능.

# 6. 검색 품질 지표 4개

검색 결과:

```python
predicted = ["a-0", "b-1", "c-2"]
```

정답:

```python
relevant = ["b-1", "d-0", "e-1"]
```

상위 3개 기준:

```text
검색 결과: a-0, b-1, c-2
                ↑
              정답
```

## 6-1. Hit@K

질문:

> 상위 K개 안에 **정답이 하나라도 있는가?**

```text
있음 → 1
없음 → 0
```

예:

```text
Hit@3 = 1
```

코드:

```python
def hit_at_k(predicted, relevant, k):
    return 1 if any(
        p in relevant
        for p in predicted[:k]
    ) else 0
```

해석:

- `1`: 최소 하나의 근거를 찾음
- `0`: 상위 K개에서 정답을 전혀 찾지 못함

---

## 6-2. Precision@K

질문:

> 가져온 K개 중 **정답이 몇 개인가?**

교안 구현:

```text
Precision@K
= 상위 K개의 정답 수 / K
```

예:

```text
상위 3개 중 정답 1개

Precision@3
= 1 / 3
= 0.333
```

코드:

```python
def precision_at_k(predicted, relevant, k):
    return sum(
        1 for p in predicted[:k]
        if p in relevant
    ) / k
```

해석:

- 높음 → 검색 결과 대부분이 관련 청크
- 낮음 → 정답 이외의 청크가 많이 섞임

> 이 노트북에서는 검색 결과가 K개보다 적더라도 **분모를 K로 고정**하는 정의를 사용.

---

## 6-3. Recall@K

질문:

> 찾아야 할 전체 정답 중 **몇 개를 찾았는가?**

```text
Recall@K
= 찾은 정답 수 / 전체 정답 수
```

예:

```text
전체 정답 = 3개
검색된 정답 = 1개

Recall@3
= 1 / 3
= 0.333
```

코드:

```python
def recall_at_k(predicted, relevant, k):
    return sum(
        1 for p in predicted[:k]
        if p in relevant
    ) / len(relevant)
```

### Recall은 반드시 `정답수`와 같이 해석

정답 청크가 6개인데 `K=3`이면 검색이 완벽해도:

```text
최대 Recall = 3 / 6 = 0.5
```

즉 낮은 Recall이 항상 검색 실패를 뜻하지 않음.

다음 문제일 수도 있음.

```text
질문 범위가 너무 넓음
        ↓
정답이 여러 청크에 분산
        ↓
K보다 정답수가 많음
```

이 경우:

- 질문을 여러 질문으로 분리
- 해당 유형만 K 증가
- 낮은 Recall을 검색기 결함으로 잘못 해석하지 않기

---

## 6-4. RR / MRR@K

질문:

> **첫 번째 정답이 몇 위에 나타났는가?**

```text
1위 → 1 / 1 = 1.0
2위 → 1 / 2 = 0.5
3위 → 1 / 3 = 0.333
없음 → 0
```

코드:

```python
def mrr_at_k(predicted, relevant, k):
    for rank, p in enumerate(predicted[:k], 1):
        if p in relevant:
            return 1 / rank

    return 0.0
```

예:

```text
첫 정답 = 2위
값 = 1 / 2 = 0.5
```

### 보충

문항 **하나**에 대해 계산한 값은 정확히는 `Reciprocal Rank(RR)`.

여러 문항의 RR을 평균낸 값이:

```text
Mean Reciprocal Rank
= MRR
```

따라서 이 노트북에서는 함수 이름을 `mrr_at_k()`로 사용하지만 전체 평가에서:

```python
scores["MRR"].mean()
```

했을 때 MRR의 의미가 됨.

# 7. 네 지표 한 번에 비교

| 지표 | 핵심 질문 | 높을수록 의미 |
|---|---|---|
| Hit@K | 하나라도 찾았나? | 최소 근거 확보 성공 |
| Precision@K | 가져온 것 중 몇 개가 맞나? | 잡음이 적음 |
| Recall@K | 찾아야 할 것 중 얼마나 찾았나? | 근거 누락이 적음 |
| MRR@K | 첫 정답이 얼마나 앞에 있나? | 정답 순위가 좋음 |

예:

```text
정답 3개
검색 결과 3개
2위에 정답 1개
```

결과:

```text
Hit@3       = 1
Precision@3 = 0.333
Recall@3    = 0.333
RR@3        = 0.5
```

해석:

```text
정답 자체는 찾음
하지만 정답 대부분을 놓침
첫 정답도 1위가 아님
```

# 8. 평가셋 전체 측정

```python
def evaluate(store, k):
    rows = []

    for row in evalset.itertuples():
        # 문항마다 검색은 한 번만 수행
        predicted = search_ids(
            store,
            row.query,
            k,
        )

        relevant = gold_map[row.query_id]

        rows.append({
            "query_id": row.query_id,
            "Hit": hit_at_k(predicted, relevant, k),
            "P": precision_at_k(predicted, relevant, k),
            "R": recall_at_k(predicted, relevant, k),
            "MRR": mrr_at_k(predicted, relevant, k),
        })

    return pd.DataFrame(rows)
```

실행:

```python
scores = evaluate(eval_store, 3)
```

핵심:

```text
질문 1개
 ↓
검색 1회
 ↓
동일한 검색 결과
 ↓
4개 지표 계산
```

지표마다 검색을 다시 실행할 필요 없음.

# 11. 단일 정답 질문과 Recall

정답 청크가 1개인 질문:

```text
정답을 찾음
→ Hit = 1
→ Recall = 1

정답을 못 찾음
→ Hit = 0
→ Recall = 0
```

따라서 **정답수가 1이면 Hit과 Recall이 동일**.

반대로 여러 정답을 요구하는 열거형 질문에서는 크게 달라질 수 있음.

예:

```text
정답 6개 중 1개만 검색

Hit = 1
Recall = 1 / 6
```

즉:

> Hit가 높다고 해서 필요한 근거를 충분히 가져왔다는 뜻은 아님.

# 12. K를 바꾸며 평가

`k`:

> 검색 순위 중 **상위 몇 개까지 사용할지** 결정하는 값.

```python
compare = pd.DataFrame([
    {
        "K": k,
        **evaluate(
            eval_store,
            k,
        )[
            ["Hit", "P", "R", "MRR"]
        ].mean().round(3),
    }
    for k in (3, 10)
])

display(compare)
```

## K 증가의 의미

```text
K=3

1위
2위
3위
──── 여기까지만 사용


K=10

1위
2위
3위
...
10위
──── 더 넓게 사용
```

검색 모델과 순위 계산 자체가 바뀐 것이 아님.

> **K를 키워 Hit이나 Recall이 올라도 검색기가 개선된 것은 아님.**

같은 순위 결과를 더 많이 사용했을 뿐.

### K와 지표의 관계

같은 검색 순위를 기준으로 K를 늘리면:

- Hit@K: 감소하지 않음
- Recall@K: 감소하지 않음
- MRR@K: 기존 첫 정답이 있으면 그대로, 새 범위에서 처음 정답이 발견되면 증가
- Precision@K: 관련 없는 결과가 추가되면 낮아지는 경향. **항상 반드시 감소하는 것은 아님**

실제 서비스에서는:

```text
답변에 청크 3개만 넣음
→ K=3 성능이 중요

후보 20개 검색 후 리랭킹
→ 1차 검색 Recall@20이 중요
```

처럼 쓰임에 맞는 K로 평가.

# 13. 질문 출처별 평가

노트북의 빈 실습 코드 정리.

```python
by_source = scores.merge(
    evalset[
        [
            "query_id",
            "질문출처",
            "정답수",
        ]
    ],
    on="query_id",
)

source_summary = (
    by_source
    .groupby("질문출처")[
        [
            "Hit",
            "R",
            "MRR",
            "정답수",
        ]
    ]
    .mean()
    .round(3)
)

display(source_summary)
```

해석 시:

```text
출처 A의 Recall이 낮음
```

만 보고 검색기가 해당 출처에 약하다고 판단하면 안 됨.

먼저:

```text
출처 A의 평균 정답수가 더 많은가?
```

확인.

정답수가 많으면 구조적으로 Recall이 낮아질 수 있음.

# 14. 지표 조합으로 문제 위치 찾기

| 증상 | 의미 | 우선 확인 |
|---|---|---|
| Hit·Recall 낮음 | 정답이 후보에 잘 들어오지 않음 | 청킹·임베딩·질의 표현 |
| Hit 높음 + MRR 낮음 | 정답은 있지만 뒤쪽 순위 | 리랭킹·질의 재작성 |
| Precision 낮음 | 관련 없는 청크가 많이 포함 | K·필터·검색 조건 |
| 특정 열거형 질문만 Recall 낮음 | 정답이 여러 청크에 분산 | 질문 분리·유형별 K |
| K를 크게 하면 정답 등장 | 후보에는 있으나 순위가 낮음 | 순위 문제 |
| K를 크게 해도 없음 | 질문과 문서 표현이 크게 다름 | 하이브리드·동의어·임베딩 |

# 15. Hit=0 실패 문항 진단 순서

## 1단계. 정답 라벨 검증

```text
정답 청크 ID가 실제 색인에 존재하는가?
그 청크에 정말 답이 있는가?
```

문제 있으면:

```text
평가셋 오류
```

검색기를 수정할 문제가 아님.

## 2단계. K를 임시로 넓혀 보기

```text
K=3 → 정답 없음
K=20 → 정답 있음
```

의미:

```text
검색 후보에는 들어오지만 순위가 너무 낮음
```

개선 후보:

- 질의 재작성
- 리랭킹

## 3단계. K를 넓혀도 정답이 없는가

가능성:

```text
질문의 표현
        ≠
문서의 표현
```

개선 후보:

- 동의어 확장
- 질의 재작성
- 하이브리드 검색
- 임베딩 모델 검토

## 4단계. 정답이 여러 청크에 분산됐는가

```text
질문 하나
 ↓
정답 청크 5~6개
```

대응:

- 질문 분리
- 해당 질문 유형만 K 증가

## 5단계. 정답이 청크 경계에서 잘렸는가

대응:

- `chunk_size`
- `chunk_overlap`
- 청킹 전략

주의:

> 청킹을 바꾸면 청크 ID가 달라지므로 **정답 라벨도 다시 연결해야 함**.

## 6단계. 문서에 애초에 답이 있는가

답이 없다면 검색기가 해결할 수 없음.

대응:

- 문서 추가
- 데이터 보강
- `답할 수 없음` 평가 문항으로 별도 구성

RAG 시스템은:

```text
근거 없음
→ 억지 답변 생성 X
→ 모른다고 답변
```

하는 능력도 평가해야 함.

# 16. 검색기 개선 순서

교안에서 제시한 개선 방향.

## 1. K 조정

가장 간단.

단:

```text
점수를 높이기 위해 K만 증가
```

시키는 것은 검색 품질 개선이 아님.

서비스에서 실제 사용하는 후보 수에 맞춰 설정.

## 2. 청크 크기·Overlap 조정

문제가 청크 경계나 문맥 부족에 있을 때.

```text
chunk_size
chunk_overlap
```

수정.

영향:

```text
새 색인 필요
+ 정답 청크 라벨 재연결 필요
```

## 3. 질의 재작성

```text
사용자 질문
 ↓
검색용 질의
 ↓
Retriever
```

긴 질문을 분해하는 것도 포함.

## 4. 하이브리드 검색

벡터 검색:

```text
의미가 비슷한 표현
```

에 강함.

어휘 검색:

```text
고유명사
조문 번호
제품명
희귀 전문용어
```

처럼 문자열 일치가 중요한 검색에 강함.

```text
Vector Search
      +
Keyword Search
      ↓
Hybrid Search
```

## 5. 리랭킹(Reranking)

```text
1차 검색으로 후보를 넉넉하게 추출
 ↓
질문 + 각 후보 청크를 더 정밀하게 평가
 ↓
순위 재정렬
```

특히:

```text
Hit 높음
MRR 낮음
```

일 때 검토.

## 6. 임베딩 모델 변경

```text
임베딩 모델 변경
→ 모든 문서 다시 임베딩
→ Vector DB 재구축
→ 기존 평가 조건 재검증
```

영향 범위가 크므로 무조건 먼저 바꾸는 요소가 아님.

# 17. 실험 원칙

## 한 번에 하나만 변경

잘못된 실험:

```text
chunk_size 변경
+ embedding 변경
+ K 변경
→ 점수 상승
```

어느 변경이 효과를 냈는지 알 수 없음.

올바른 방식:

```text
기준선
 ↓
K만 변경
 ↓
평가

기준선
 ↓
청킹만 변경
 ↓
평가
```

> **한 번에 한 변수만 바꾸고 같은 평가셋으로 비교.**

## 평균 상승만 확인하지 않기

평균이 상승해도:

```text
기존에 맞던 질문
→ 새 버전에서 실패
```

할 수 있음.

따라서:

```text
전체 평균
+
문항별 변화
```

를 함께 확인.

## 평가셋 과적합 방지

실패 문항을 계속 보면서 검색기를 튜닝하면:

```text
그 평가셋에만 잘 맞는 검색기
```

가 될 수 있음.

따라서 최종 확인용 문항을 별도로 남김.

```text
개발/튜닝 평가셋
        +
최종 검증용 Holdout
```

# 18. 최종 RAG 검색 평가 개발 흐름

```text
1. 문서 준비
   ↓
2. 청킹 기준 확정
   ↓
3. 각 청크에 고유 ID 부여
   ↓
4. 임베딩 + Vector DB 구축
   ↓
5. 색인 버전 고정
   ↓
6. 실제 질문 수집
   ↓
7. 질문별 정답 청크 라벨링
   ↓
8. 근거 문장 저장
   ↓
9. Retriever로 Top-K 검색
   ↓
10. 검색 청크 ID 추출
   ↓
11. Hit / Precision / Recall / RR 계산
   ↓
12. 전체 평균(MRR 포함)
   ↓
13. Hit=0 실패 질문 분석
   ↓
14. 문제 유형 분류
   │
   ├─ 후보 자체 없음 → 청킹·임베딩·질의
   ├─ 순위가 낮음 → 리랭킹
   ├─ 잡음 많음 → K·필터
   └─ 질문이 너무 넓음 → 질문 분리·K
   ↓
15. 한 요소만 수정
   ↓
16. 같은 평가셋으로 재측정
   ↓
17. 기존 정답 문항 회귀 확인
   ↓
18. Holdout 평가
```

# 19. 핵심 코드 압축본

```python
import pandas as pd


# ---------------------------------------------------------
# 1. 검색
# ---------------------------------------------------------

def search_ids(store, query, k):
    """상위 K개 검색 결과의 청크 ID 반환."""

    retriever = store.as_retriever(
        search_kwargs={"k": k}
    )

    return [
        doc.id
        for doc in retriever.invoke(query)
    ]


# ---------------------------------------------------------
# 2. 평가 지표
# ---------------------------------------------------------

def hit_at_k(predicted, relevant, k):
    return int(
        any(
            p in relevant
            for p in predicted[:k]
        )
    )


def precision_at_k(predicted, relevant, k):
    return sum(
        p in relevant
        for p in predicted[:k]
    ) / k


def recall_at_k(predicted, relevant, k):
    return sum(
        p in relevant
        for p in predicted[:k]
    ) / len(relevant)


def rr_at_k(predicted, relevant, k):
    for rank, p in enumerate(
        predicted[:k],
        start=1,
    ):
        if p in relevant:
            return 1 / rank

    return 0.0


# ---------------------------------------------------------
# 3. 정답 라벨
# ---------------------------------------------------------

gold_map = {
    row.query_id: row.gold_chunks.split("|")
    for row in evalset.itertuples()
}


# ---------------------------------------------------------
# 4. 전체 평가
# ---------------------------------------------------------

def evaluate(store, k):
    rows = []

    for row in evalset.itertuples():
        predicted = search_ids(
            store,
            row.query,
            k,
        )

        relevant = gold_map[
            row.query_id
        ]

        rows.append({
            "query_id": row.query_id,
            "Hit": hit_at_k(
                predicted,
                relevant,
                k,
            ),
            "P": precision_at_k(
                predicted,
                relevant,
                k,
            ),
            "R": recall_at_k(
                predicted,
                relevant,
                k,
            ),
            "RR": rr_at_k(
                predicted,
                relevant,
                k,
            ),
        })

    return pd.DataFrame(rows)


scores = evaluate(
    eval_store,
    k=3,
)


# ---------------------------------------------------------
# 5. 전체 평균
# ---------------------------------------------------------

print(
    scores[
        ["Hit", "P", "R", "RR"]
    ].mean()
)
```

문항별 `RR`의 전체 평균이 **MRR**.

# 20. 최종 요약

| 개념 | 핵심 |
|---|---|
| 검색 평가 | 생성 모델과 분리해 Retriever 자체를 측정 |
| 평가셋 | 질문 + 정답 청크 ID + 근거 문장 |
| 청크 라벨 | 문서 단위가 아닌 실제 답이 있는 청크 단위 |
| 근거 문장 | 청킹 변경 후 정답 라벨을 다시 찾기 위한 기준 |
| Hit@K | 최소 하나라도 찾았는가 |
| Precision@K | 가져온 K개 중 정답 비율 |
| Recall@K | 전체 정답 중 찾은 비율 |
| RR | 한 질문에서 첫 정답 순위의 역수 |
| MRR | 여러 질문의 RR 평균 |
| `정답수` | Recall 해석 시 반드시 같이 확인 |
| K | 검색 품질 자체가 아니라 사용할 검색 범위 |
| 실패 분석 | 평균보다 Hit=0 문항부터 직접 확인 |
| 개선 | 원인에 맞는 요소 하나만 수정 |
| 재평가 | 같은 평가셋으로 다시 측정 |
| 회귀 확인 | 평균이 올라가도 기존 성공 문항이 깨졌는지 확인 |
| Holdout | 평가셋에 과적합되는 것을 막기 위한 최종 검증 |

## 한 줄 정리

```text
RAG 검색 개발
= 검색기 제작
→ 평가셋 구축
→ Top-K 검색
→ 지표 측정
→ 실패 질문 분석
→ 한 요소 수정
→ 같은 기준으로 재평가
```

> **재지 못하면 고칠 수도 없다.**  
> RAG 검색 품질은 느낌이 아니라 **같은 평가셋과 같은 지표로 반복 측정**해서 개선.
