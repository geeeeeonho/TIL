# MCP 에이전트 계획·프롬프트·구조화 출력 핵심 정리

> 목표: MCP 도구를 연결한 에이전트가 **계획 → 실행 → 검증 → 결과 적재**까지 처리하는 흐름 정리  
> 중복된 구조화 출력 예제는 하나로 통합

---

# 1. 전체 흐름

```text
MCP 도구 연결
↓
필요한 도구만 선택
↓
시스템 프롬프트로 도구 사용 규칙 지정
↓
TodoListMiddleware로 계획 생성
↓
DB 조회 → 계산 → 시각화 → 리포트 저장
↓
실제 산출물 검증
↓
자유 문장 결과를 구조화
↓
DataFrame / JSON 적재
```

핵심:

> **도구만 연결하는 것에서 끝나지 않고, 계획·프롬프트·검증·구조화를 추가해 안정적인 자동화 파이프라인으로 만든다.**

# 2. MCP 서버와 도구 준비

이번 흐름에서는 세 MCP 서버를 결합.

| 서버 | 역할 | 주요 도구 |
|---|---|---|
| SQLite | DB 조회·집계 | `db_read_query`, `db_list_tables`, `db_describe_table` |
| Code Runner | 계산·그래프 | `code_run-code` |
| Filesystem | 텍스트·리포트 저장 | `files_write_file` |

## 서버 설정

```python
SQLITE = {
    "command": "uvx",
    "args": [
        "--with", "mcp==1.9.4",
        "--from", "mcp-server-sqlite",
        "mcp-server-sqlite",
        "--db-path", str(DB_PATH),
    ],
    "transport": "stdio",
}

CODE_RUNNER = {
    "command": "npx",
    "args": ["-y", "mcp-server-code-runner"],
    "transport": "stdio",
    "env": CHILD_ENV,
    "cwd": str(OUTPUT_DIR),
}

FILESYSTEM = {
    "command": "npx",
    "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        str(OUTPUT_DIR),
    ],
    "transport": "stdio",
}
```

코드 실행 서버의 `cwd`와 파일 서버의 허용 폴더를 같은 `OUTPUT_DIR`로 지정.

```text
code_run-code의 상대경로 기준
=
files_write_file의 상대경로 기준
=
OUTPUT_DIR
```

따라서 모델에는 긴 절대경로 대신 **파일 이름만** 전달 가능.

# 3. 필요한 도구만 에이전트에 전달

```python
client = MultiServerMCPClient(
    {
        "db": SQLITE,
        "code": CODE_RUNNER,
        "files": FILESYSTEM,
    },
    tool_name_prefix=True,
)

mcp_tools = await client.get_tools()
```

`tool_name_prefix=True`:

```text
db_read_query
code_run-code
files_write_file
```

서버별 접두사를 붙여 이름 충돌 방지.

필요한 도구만 선택.

```python
ALLOWED = {
    "db_read_query",
    "db_list_tables",
    "db_describe_table",
    "code_run-code",
    "files_write_file",
}

TOOLS = [
    tool for tool in mcp_tools
    if tool.name in ALLOWED
]
```

> **에이전트에 넘긴 도구 = 에이전트가 가진 실제 권한**

# 4. 계획 없는 에이전트의 한계

복합 요청:

```text
연도별 매출 계산
+ 국가별 매출 계산
+ 전년 대비 증감률 계산
+ 그래프 저장
```

계획 장치 없이 실행하면 도구를 이어서 사용할 수는 있지만:

```text
현재 무엇을 하는지
무엇을 완료했는지
무엇이 남았는지
```

를 명시적으로 관리하지 않음.

```python
plain_agent = create_agent(
    model,
    TOOLS,
    system_prompt=SYSTEM_BASE,
    middleware=[LIMIT],
)
```

결과에도 `todos`가 없음.

```text
복합 요청이 길어질수록
→ 단계 누락 가능성 증가
```

# 5. 미들웨어(Middleware)

## 개념

에이전트의 기본 루프:

```text
모델 호출
→ 도구 실행
→ 모델 호출
→ ...
```

**미들웨어**는 이 루프 자체를 수정하지 않고, 정해진 위치에 기능을 추가하는 장치.

```python
agent = create_agent(
    model,
    tools,
    middleware=[...],
)
```

---

## 5-1. 훅(Hook)

미들웨어가 개입할 수 있도록 라이브러리가 미리 만든 실행 위치.

| 훅 | 시점 |
|---|---|
| `before_agent` | 에이전트 시작 전 1회 |
| `before_model` | 모델 호출 전 |
| `wrap_model_call` | 모델 호출 자체를 감쌈 |
| `after_model` | 모델 응답 후 |
| `wrap_tool_call` | 도구 호출 자체를 감쌈 |
| `after_agent` | 에이전트 종료 후 1회 |

### `before/after`와 `wrap` 차이

```text
before / after
→ 호출 전후 상태 처리

wrap
→ 호출 자체를 제어
```

예:

```python
def wrap_model_call(self, request, handler):
    # 호출 전
    response = handler(request)
    # 호출 후
    return response
```

`wrap`은 `handler()`를 직접 호출하므로:

- 재시도
- 호출 차단
- 대체 모델
- 요청·응답 수정

등이 가능.

---

## 5-2. 미들웨어 예시

| 목적 | 미들웨어 |
|---|---|
| 계획 | `TodoListMiddleware` |
| 모델 호출 제한 | `ModelCallLimitMiddleware` |
| 도구 호출 제한 | `ToolCallLimitMiddleware` |
| 실패 재시도 | `ModelRetryMiddleware`, `ToolRetryMiddleware` |
| 대체 모델 | `ModelFallbackMiddleware` |
| 사람 승인 | `HumanInTheLoopMiddleware` |
| 대화 요약 | `SummarizationMiddleware` |
| 개인정보 처리 | `PIIMiddleware` |

기준:

```text
복잡한 작업 → 계획
폭주·요금 → 호출 제한
실패 반복 → Retry / Fallback
위험한 쓰기 작업 → Human-in-the-Loop
긴 대화 → Summarization
```

# 6. Plan-and-Execute

## 개념

```text
Plan
→ 전체 작업을 먼저 할 일 목록으로 작성

Execute
→ 목록을 따라 단계별 실행
```

### ReAct와 차이

| 방식 | 특징 |
|---|---|
| ReAct | 생각 → 행동 → 관찰을 한 단계씩 반복 |
| Plan-and-Execute | 전체 계획을 먼저 만들고 진행 상태 추적 |

# 7. `TodoListMiddleware`

LangChain에서는 `TodoListMiddleware`를 사용해 계획 기능 추가.

```python
SYSTEM_PLAN = SYSTEM_BASE + (
    " 여러 단계가 필요한 복합 요청은 "
    "먼저 계획을 세우고 단계별로 처리하라."
)

analyst = create_agent(
    model,
    TOOLS,
    middleware=[
        TodoListMiddleware(),
        LIMIT,
    ],
    system_prompt=SYSTEM_PLAN,
)
```

`TodoListMiddleware`를 붙이면:

```text
write_todos 도구 추가
+
state에 todos 추가
```

따라서 결과에서 계획 확인 가능.

```python
result = await analyst.ainvoke({
    "messages": question
})

for item in result.get("todos", []):
    print(item["status"], item["content"])
```

예상 흐름:

```text
write_todos
→ 1단계 실행
→ write_todos 상태 갱신
→ 2단계 실행
→ ...
→ completed
```

완료 개수 확인:

```python
todos = result.get("todos", [])

completed = sum(
    item["status"] == "completed"
    for item in todos
)

print(completed, "/", len(todos))
```

> 계획 항목의 개수·문장은 실행마다 달라질 수 있음.  
> 중요한 것은 **계획이 존재하고 모든 단계가 완료됐는가**.

# 8. 모델 호출 제한

복합 작업에서 같은 도구를 반복 호출하거나 루프에 빠지는 상황 방지.

```python
LIMIT = ModelCallLimitMiddleware(
    run_limit=20,
    exit_behavior="end",
)
```

```text
run_limit
→ 모델 호출 최대 횟수

exit_behavior="end"
→ 예외 대신 지금까지의 결과를 반환
```

자동 에이전트에는 호출 상한을 두는 편이 안전.

# 9. 시스템 프롬프트 = 도구 사용 규칙

에이전트가 도구를 가지고 있어도 **어떤 작업에 어떤 도구를 써야 하는지** 명확하지 않으면 잘못 선택할 수 있음.

## 모호한 프롬프트

```text
파일로 저장할 때는 files_write_file을 사용하라.
```

문제:

```text
그래프.png
→ files_write_file 선택 가능
```

하지만 `files_write_file`은 텍스트 파일 저장 도구.

그래프를 정상 생성하지 못할 수 있음.

---

## 구체적인 프롬프트

```text
DB 조회
→ db_read_query

추가 계산
→ code_run-code

그래프
→ code_run-code 안에서 matplotlib.savefig()

Markdown / 텍스트
→ files_write_file
```

그래프 규칙도 명시.

```python
matplotlib.use("Agg")
plt.rcParams["font.family"] = FONT
```

그리고:

```python
plt.savefig("그래프.png")
```

> **도구가 여러 개일수록 "무엇을 어느 도구로 처리하는가"를 명확히 분리해야 함.**

# 10. 시스템 프롬프트 핵심 규칙

실습에서 사용한 규칙을 압축하면 다음과 같음.

```text
1. DB 조회·집계는 db_read_query
2. 숫자를 암산하거나 지어내지 않음
3. 테이블·열이 불확실하면 스키마 먼저 확인
4. 계산·그래프는 code_run-code
5. 코드 실행 결과는 마지막에 print
6. 그래프는 savefig로 저장
7. 텍스트만 files_write_file로 저장
8. 파일 경로 대신 파일 이름만 사용
9. 여러 단계 요청은 먼저 계획 생성
```

코드 실행 서버 주의:

```python
print(result)
```

표준 출력이 있어야 결과 확인 가능.

경고만 반환되는 경우:

```python
import warnings
warnings.filterwarnings("ignore")
```

그래프는 GUI 없이 저장:

```python
import matplotlib
matplotlib.use("Agg")
```

# 11. 자동 데이터 분석 파이프라인

전체 분석 흐름:

```text
① 수집
   db_read_query
↓
② 분석·통계
   code_run-code
↓
③ 시각화
   code_run-code + savefig
↓
④ 리포트 저장
   files_write_file
```

예:

```text
1. invoices에서 연도별 매출 조회
2. 전년 대비 증감률 계산
3. 연도별 매출 그래프 저장
4. Markdown 리포트 저장
```

사용자 요청에서도 단계를 명확하게 작성.

```python
pipeline_q = (
    "1) invoices 표에서 연도별 매출 합계를 조회하고, "
    "2) 전년 대비 증감률을 계산하고, "
    "3) 연도별 매출 막대그래프를 저장하고, "
    "4) 결과를 마크다운 리포트로 저장해줘."
)
```

> **요청이 구체적일수록 에이전트의 실행 계획도 정확해짐.**

# 12. 실행 결과는 실제 산출물로 검증

에이전트가:

```text
"저장했습니다."
```

라고 답했다고 성공한 것은 아님.

## 파일 존재 여부

```python
path.exists()
```

하지만 0바이트 파일도 `True`.

따라서 크기까지 확인.

```python
size = path.stat().st_size if path.exists() else 0
```

## PNG 검증

PNG 파일의 시작 바이트:

```python
PNG_MAGIC = b"\x89PNG"
```

```python
is_png = (
    path.exists()
    and path.read_bytes()[:4] == PNG_MAGIC
)
```

그래프 코드 내부에서도 확인 가능.

```python
import os

plt.savefig("chart.png")
print(os.path.getsize("chart.png"))
```

핵심:

```text
도구의 "성공" 메시지
≠ 실제 작업 성공

실제 파일·크기·서명
= 검증 기준
```

# 13. 자유 문장 결과의 한계

에이전트의 최종 답변은 사람에게 읽기 좋은 자유 문장.

```text
"매출이 가장 높은 국가는 미국이며 총 매출은 ...입니다."
```

하지만 실행마다 문장 형식이 달라질 수 있어:

```text
DataFrame
JSON
DB
대시보드
```

에 바로 적재하기 어려움.

따라서 **구조화 출력**으로 변환.

---

# 14. `with_structured_output`

## 구조 정의

Pydantic으로 결과 틀 생성.

```python
from pydantic import BaseModel, Field

class AnalysisResult(BaseModel):
    metric: str = Field(
        description="집계 대상과 방법이 드러나는 지표 이름"
    )

    value: float = Field(
        description="핵심 수치 하나"
    )

    interpretation: str = Field(
        description="수치를 설명하는 한 문장"
    )
```

필드 설명은:

```text
짧고 명확하게
"이 칸에 무엇이 들어가는가"
```

를 작성.

긴 명령문을 넣으면 모델이 설명 자체를 값처럼 사용할 수 있음.

---

# 15. 자유 문장 → 구조화 결과

```python
structurer = model.with_structured_output(
    AnalysisResult
)
```

## 1단계: 에이전트가 실제 분석

```python
result = await analyst.ainvoke({
    "messages": question
})

answer_text = result["messages"][-1].text
```

## 2단계: 분석 결과를 틀에 옮김

```python
info = structurer.invoke(
    f"질문: {question}\n답변: {answer_text}"
)
```

질문과 답변을 **함께** 전달.

```text
질문
→ 어떤 지표인지 설명

답변
→ 실제 분석 결과
```

답변만 넣으면 `metric`이 `"매출"`처럼 지나치게 일반화될 수 있음.

중요:

> 구조화 단계는 **새로 분석하는 단계가 아니라 기존 답을 정해진 틀에 옮기는 단계**.

---

# 16. 구조화 결과 사용

```python
print(info.metric)
print(info.value)
print(info.interpretation)
```

`value`는 실제 `float`.

따라서 바로:

- 계산
- 비교
- 정렬
- 저장

가능.

딕셔너리 변환:

```python
row = info.model_dump()
```

# 17. DataFrame과 JSON 적재

```python
rows = []

for question in QUESTIONS:
```


# 18. 전체 구현 흐름

```python
# 1. MCP 서버 연결
client = MultiServerMCPClient(
    {
        "db": SQLITE,
        "code": CODE_RUNNER,
        "files": FILESYSTEM,
    },
    tool_name_prefix=True,
)

tools = await client.get_tools()

# 2. 필요한 도구 선택
tools = [
    tool for tool in tools
    if tool.name in ALLOWED
]

# 3. 모델 준비
model = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0,
    timeout=60,
)

# 4. 미들웨어
limit = ModelCallLimitMiddleware(
    run_limit=20,
    exit_behavior="end",
)

# 5. 계획 에이전트
agent = create_agent(
    model,
    tools,
    system_prompt=SYSTEM_PLAN,
    middleware=[
        TodoListMiddleware(),
        limit,
    ],
)

# 6. 복합 요청 실행
result = await agent.ainvoke({
    "messages": question
})

# 7. 계획 확인
todos = result.get("todos", [])

# 8. 최종 문장 추출
answer = result["messages"][-1].text

# 9. 구조화
structurer = model.with_structured_output(
    AnalysisResult
)

info = structurer.invoke(
    f"질문: {question}\n답변: {answer}"
)

# 10. 적재
row = info.model_dump()
```
