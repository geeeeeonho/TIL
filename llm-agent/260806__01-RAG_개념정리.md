# RAG 기본 정리

## 1. RAG란?

**RAG(Retrieval-Augmented Generation)**  
= **검색(Retrieval) + 증강(Augmented) + 생성(Generation)**

질문과 관련된 문서를 먼저 검색한 뒤, 검색 결과를 프롬프트에 넣어 LLM이 답을 생성하는 방식.

- **Retrieval**: 질문과 관련된 문서 검색
- **Augmented**: 검색한 문서를 프롬프트에 추가
- **Generation**: LLM이 문서를 근거로 답변 생성

모델을 다시 학습하지 않고 필요한 근거를 옆에 제공한다.

장점:

- 문서만 교체하면 새로운 정보 반영 가능
- 구축 속도가 빠르고 비용이 비교적 적음
- 답변에 사용한 문서를 남길 수 있어 출처 확인 가능
- 최신 문서·사내 문서·전문 자료 활용 가능

```text
질문(Query)
→ 관련 문서 검색(Retriever)
→ 근거 추가
→ 답변 생성(Generator)
```

> RAG의 핵심은 LLM보다 **검색기가 적절한 근거를 찾는 것**에 있음.

---

## 2. RAG 핵심 구성 요소

| 구성 요소 | 역할 |
|---|---|
| 문서 저장소 | 사용할 원문과 정보를 저장 |
| 임베딩 모델 | 문서와 질문을 의미 벡터로 변환 |
| 벡터 DB | 임베딩 벡터·원문·메타데이터 저장 |
| 검색기(Retriever) | 질문과 의미가 가까운 문서 검색 |
| 생성기(Generator) | 검색한 문서를 근거로 답변 생성 |

---

## 3. RAG의 두 단계

### 3.1 색인(Indexing)

서비스 사용 전에 문서를 미리 저장하는 단계.

```text
문서
→ 임베딩
→ 벡터 변환
→ 벡터 DB 저장
```

저장 정보:

- 문서 원문
- 임베딩 벡터
- 문서 ID
- 카테고리·작성일·권한 등의 메타데이터

문서가 바뀌지 않으면 반복할 필요가 없는 작업.

### 3.2 질의(Query)

사용자가 질문할 때마다 실행되는 단계.

```text
질문
→ 질문 임베딩
→ 메타데이터 필터
→ 벡터 검색
→ 관련 문서 Top-K
→ LLM 답변 생성
```

---

## 4. 의미 기반 검색

RAG에서는 단어가 정확히 같은 문서보다 **의미가 비슷한 문서**를 찾음.

```text
임베딩 + 유사도 계산 + Top-K
```

### 임베딩

문서와 질문을 의미를 나타내는 숫자 벡터로 변환하는 작업.

- 문서: 색인 단계에서 미리 임베딩
- 질문: 사용자가 질문할 때 임베딩

### 코사인 유사도

두 벡터의 방향이 얼마나 비슷한지 계산.

- `1`에 가까울수록 의미가 비슷함
- 값이 높을수록 관련성이 큼

| 문서 | 코사인 유사도 | 결과 |
|---|---:|---|
| 환불 절차 안내 | 0.998 | 1위 |
| 배송 지연 보상 | 0.416 | 2위 |
| 회원 등급 혜택 | 0.254 | 제외 |

### Top-K

유사도 점수가 높은 문서 중 상위 `K개`만 선택.

```text
Top-3
→ 가장 관련성이 높은 문서 3개 반환
```

- K가 너무 작음: 필요한 근거 누락 가능
- K가 너무 큼: 불필요한 문서 혼입 가능

---

## 5. 벡터 DB

**벡터 DB**는 임베딩 벡터를 저장하고 빠르게 검색하기 위한 전용 데이터베이스.

### 주요 기능

- **저장**: 벡터·원문·메타데이터 저장
- **인덱싱**: 가까운 벡터를 빠르게 찾도록 구조화
- **검색**: 질문 벡터와 가까운 문서 K개 반환

### 관계형 DB와 비교

| 구분 | 관계형 DB | 벡터 DB |
|---|---|---|
| 저장 대상 | 숫자·문자 형태의 행과 열 | 고차원 벡터·원문·메타데이터 |
| 잘 찾는 것 | 값이 정확히 일치하는 데이터 | 의미가 가까운 데이터 |
| 검색 방식 | 키·조건 기반 정확 매칭 | 벡터 거리 기반 근사 검색 |
| 질문 예시 | `id = 7`인 행 검색 | 질문과 비슷한 문서 5개 검색 |

---

## 6. 벡터 인덱스

문서가 적으면 모든 문서와 질문을 비교할 수 있음.  
문서가 많아지면 전체 벡터를 매번 계산하기 어려워 인덱스를 사용.

### Flat

모든 벡터를 하나씩 비교하는 정확 검색.

| 특징 | 내용 |
|---|---|
| 정확도 | 100% |
| 속도 | 느림 |
| 용도 | 소규모 데이터·정답 기준 평가 |

### ANN

**ANN(Approximate Nearest Neighbor)**  
= 근사 최근접 이웃 검색

```text
약간의 정확도 손실
↔
큰 속도 향상
```

정확도를 조금 포기하고 검색 속도를 크게 높이는 방식.

### HNSW

**HNSW(Hierarchical Navigable Small World)**  
= 계층 구조로 연결된 탐색 그래프

```text
위층: 가까운 영역으로 크게 이동
→ 중간층: 범위 축소
→ 아래층: 주변을 자세히 검색
```

모든 벡터를 확인하지 않아 빠름.

| 특징 | 내용 |
|---|---|
| 구조 | 계층형 그래프 |
| 속도 | 빠름 |
| 정확도 | 비교적 높음 |
| 단점 | 메모리 사용량 큼 |
| 용도 | 일반적인 벡터 검색 |

### IVF·IVF-PQ

벡터를 여러 군집으로 나눈 뒤 관련성이 높은 군집만 검색.

- 검색 범위 축소
- 일부 정확도 손실 발생
- PQ 결합 시 메모리 절감
- 초대규모 데이터에 적합

### 인덱스 비교

| 방식 | 검색 방법 | 특징 | 용도 |
|---|---|---|---|
| Flat | 전체 벡터 계산 | 정확하지만 느림 | 소규모·평가 기준 |
| HNSW | 계층 그래프 탐색 | 빠르고 정확하지만 메모리 사용량 큼 | 일반적인 벡터 검색 |
| IVF·IVF-PQ | 군집 일부만 탐색 | 검색 범위와 메모리 절감 | 초대규모 데이터 |

## 7. 메타데이터 필터링

**메타데이터**는 벡터와 함께 저장하는 문서의 꼬리표 정보.

예시:

- 카테고리
- 날짜
- 작성자
- 문서 종류
- 사용자 권한

검색 순서:

```text
메타데이터 조건으로 후보 제한
→ 남은 문서에서 의미 검색
→ Top-K 선택
```

### 예시 조건

```text
카테고리 = notice
날짜 >= 2024
```

| 문서 | 카테고리 | 날짜 | 유사도 | 결과 |
|---|---|---|---:|---|
| 환불 규정 개정 | notice | 2024-05 | 0.93 | 통과 |
| 환불 문의 후기 | review | 2024-06 | 0.95 | 분류 조건 제외 |
| 구 환불 규정 | notice | 2022-01 | 0.91 | 날짜 조건 제외 |
| 환불 절차 안내 | notice | 2024-03 | 0.89 | 통과 |

유사도가 가장 높아도 필터 조건에 맞지 않으면 제외.

### 필터링이 필요한 이유

- **최신성**: 오래된 문서 제외
- **권한 관리**: 접근할 수 없는 문서 제외
- **정확도 향상**: 다른 분류의 문서 제외
- **정보 유출 방지**: 비공개 문서가 근거로 사용되는 문제 방지

## 9. ChromaDB 컬렉션

**컬렉션(Collection)**은 같은 용도의 문서를 한곳에 저장하는 공간.

관계형 DB의 `table`과 비슷함.

```text
company_policy
customer_faq
product_manual
```

용도가 다른 문서는 컬렉션 분리.  
검색은 선택한 컬렉션 내부에서만 실행.

### 컬렉션 적재 요소

| 항목 | 의미 | 예시 |
|---|---|---|
| `ids` | 문서마다 고유한 이름표 | `d1`, `d2`, `d3` |
| `documents` | 사람이 읽는 원문 | `"환불 절차 안내"` |
| `embeddings` | 문서의 의미 벡터 | `[0.9, 0.1, 0.1]` |
| `metadatas` | 검색 필터용 정보 | `{"category": "notice"}` |
| 거리 기준 | 벡터의 가까움을 계산하는 방식 | 코사인·L2·내적 |

---

## 10. 거리와 유사도

벡터 DB는 유사도 대신 **거리(distance)**를 반환할 수 있음.

- 유사도: 클수록 가까움
- 거리: 작을수록 가까움

### 코사인 거리

```text
코사인 거리 = 1 - 코사인 유사도
```

| 순위 | 문서 | 거리 | 의미 |
|---|---|---:|---|
| 1위 | 환불 절차 안내 | 0.002 | 질문과 거의 같은 의미 |
| 2위 | 배송 지연 보상 | 0.584 | 비교적 멂 |
| 제외 | 회원 등급 혜택 | 0.746 | 가장 멂 |

임베딩 모델과 벡터 DB의 거리 계산 방식을 맞춰야 함.  
코사인 기반 임베딩에 다른 거리 방식을 사용하면 검색 성능이 떨어질 수 있음.

## 11. 검색 결과로 답변 생성

검색기가 반환한 Top-K 문서를 LLM 프롬프트의 근거로 추가.

```text
RAG 프롬프트
= 지시 + 근거 + 질문
```

### 지시

답변 규칙 지정.

```text
아래 근거만 사용해 답한다.
근거에 내용이 없으면 모른다고 답한다.
```

### 근거

검색한 Top-K 문서 원문.

```text
[1] 환불 절차 안내
수령 후 30일 이내에 환불을 요청할 수 있다.
```

### 질문

사용자가 입력한 원래 질문.

```text
돈을 돌려받고 싶어.
```

### 전체 예시

```text
[지시]
아래 근거만 사용해 답한다.
근거에 내용이 없으면 모른다고 답한다.

[근거]
[1] 환불 절차 안내:
수령 후 30일 이내에 환불을 요청할 수 있다.

[질문]
돈을 돌려받고 싶어.
```

## 12. 답변이 이상할 때 확인 순서

```text
1. 검색기가 올바른 문서를 찾았는지 확인
2. Top-K 값 확인
3. 메타데이터 필터 확인
4. 거리 기준 확인
5. 문서 내용 확인
6. 검색이 정상이라면 프롬프트 개선
```

RAG에서는 생성 모델보다 검색 단계에서 문제가 발생하는 경우가 많음.

---

## 13. 전체 흐름

### 색인 단계

```text
문서
→ 임베딩 생성
→ 원문·벡터·메타데이터 저장
→ 벡터 인덱스 구성
```

### 질의 단계

```text
사용자 질문
→ 질문 임베딩
→ 메타데이터 필터
→ ANN 검색
→ 관련 문서 Top-K
→ 프롬프트에 근거 추가
→ LLM 답변 생성
```

## 핵심 요약

| 단계 | 핵심 내용 | ChromaDB에서 하는 일 |
|---|---|---|
| 목적 | LLM에 최신·비공개·전문 문서 제공 | 문서를 담을 컬렉션 생성 |
| 색인 | 문서를 임베딩해 미리 저장 | 문서·벡터·메타데이터 적재 |
| 질의 | 질문과 가까운 문서 검색 | 질문 벡터로 Top-K 검색 |
| 필터 | 조건에 맞는 문서만 검색 | 메타데이터 조건 사용 |
| 인덱스 | 검색 속도 향상 | HNSW 기반 근사 검색 |
| 거리 | 벡터 간 가까움 계산 | 코사인·L2·내적 방식 사용 |
| 생성 | 검색 문서를 근거로 답변 | 지시·근거·질문을 LLM에 전달 |

> **RAG 핵심:** 모델을 다시 학습하는 것이 아니라, 질문에 맞는 근거 문서를 찾아 프롬프트에 제공하는 방식.
