# 데이터베이스 설계 + SQL 조회·결합 — 실전 압축 정리

> 핵심 흐름: **구조를 먼저 설계 → 규칙을 걸어 저장 → 안전하게 수정 → 필요한 데이터만 조회 → 집계·결합해 리포트 생성**

---

## 0. 전체 흐름

```text
요구사항
→ ERD 설계
→ CREATE TABLE
→ 타입·제약조건·PK/FK 적용
→ INSERT
→ SELECT / WHERE
→ GROUP BY / HAVING
→ JOIN / LEFT JOIN
→ 서브쿼리
→ 리포트 저장·인덱스
```

데이터베이스는 단순 저장소가 아니라 **데이터 구조와 규칙을 함께 관리하는 장치**.

---

# 1. 데이터베이스 설계

## 1.1 테이블과 타입

- 한 테이블은 한 종류의 대상을 담당.
- 한 행 = 데이터 한 건.
- 한 열 = 대상의 속성.
- 타입은 **값의 의미**에 맞게 결정.

예:

```text
금액·수량      → int
이름·이메일    → text
전화번호·우편번호 → text
```

전화번호처럼 숫자로 계산하지 않는 값은 `int`보다 `text`가 적합.
`010...`을 숫자로 저장하면 앞의 `0`이 사라질 수 있음.

### SQLite 주의

SQLite는 기본적으로 타입을 강하게 검사하지 않음.

```sql
CREATE TABLE ... (
    ...
) STRICT;
```

`STRICT`를 붙여야 지정한 타입을 실제 규칙처럼 검사.

---

## 1.2 제약조건

| 규칙 | 역할 | 실전 예 |
|---|---|---|
| `NOT NULL` | 빈 값 금지 | 이름 필수 |
| `UNIQUE` | 중복 금지 | 이메일 중복 방지 |
| `CHECK` | 값 조건 제한 | `amount >= 0` |
| `DEFAULT` | 생략 시 기본값 | 가입일·재고 기본값 |
| `PRIMARY KEY` | 행 식별 | 고객 번호 |
| `REFERENCES` | 다른 테이블 참조 | 주문의 고객 번호 |

```sql
CREATE TABLE customers (
    id      integer PRIMARY KEY AUTOINCREMENT,
    name    text NOT NULL,
    email   text NOT NULL UNIQUE,
    city    text
) STRICT;
```

핵심:

```text
타입 = 어떤 종류의 값인가
제약조건 = 어떤 값까지 허용할 것인가
```

---

## 1.3 PK·FK와 관계

### PK

테이블 안에서 행 하나를 고유하게 식별.

```text
customers.id
```

### FK

다른 테이블의 PK를 참조.

```sql
customer_id int NOT NULL REFERENCES customers(id)
```

```text
orders.customer_id → customers.id
```

없는 고객 번호를 주문에 넣지 못하게 해서 **주인 없는 데이터**를 방지.

### 관계별 설계

```text
1:N → FK를 N쪽에 둠

customers 1 ── N orders
orders.customer_id → customers.id
```

```text
M:N → 중간 테이블로 분리

customers
    ↓
cart_items
    ↑
products
```

중간 테이블에는 관계 자체의 정보도 저장.

```text
customer_id
product_id
quantity
```

같은 조합의 중복을 막을 때 복합 PK 사용 가능.

```sql
PRIMARY KEY (customer_id, product_id)
```

---

## 1.4 ERD 설계 순서

```text
1. 저장할 대상 찾기
2. 각 대상의 속성 정하기
3. 대상끼리 관계 연결하기
4. 1:1 / 1:N / M:N 개수 정하기
```

ERD 구성:

```text
Entity       → 테이블
Attribute    → 열
Relationship → 테이블 사이 연결
```

### 실전 체크

- 한 칸에 여러 값을 몰아넣지 않기.
- 같은 사실을 여러 테이블에 중복 저장하지 않기.
- 모든 핵심 테이블에 식별 가능한 PK 두기.
- M:N을 발견하면 중간 테이블 검토.
- FK 이름은 역할이 보이게 작성.

예:

```text
customer_id
product_id
follower_id
following_id
```

---

## 1.5 삭제 규칙

부모 데이터를 자식이 참조하고 있으면 기본적으로 삭제가 막힐 수 있음.

| 옵션 | 부모 삭제 시 |
|---|---|
| 기본 `NO ACTION` | 삭제 거부 |
| `ON DELETE CASCADE` | 자식도 같이 삭제 |
| `ON DELETE SET NULL` | 자식은 남기고 FK만 `NULL` |

```sql
post_id int REFERENCES posts(id) ON DELETE CASCADE
```

`CASCADE`는 편하지만 연쇄 삭제 위험이 큼.

실무에서는 실제 삭제 대신:

```text
is_deleted = 1
```

처럼 표시만 남기는 **소프트 삭제**도 자주 사용.

# 2. 데이터 입력·수정·삭제

## 2.1 INSERT

```sql
INSERT INTO customers (name, email, city)
VALUES ('김민수', 'minsu@shop.com', '서울');
```

여러 행:

```sql
INSERT INTO products (name, list_price)
VALUES
    ('노트북', 1490000),
    ('마우스', 35000);
```

생성 결과 확인:

```sql
... RETURNING id, name;
```

### Python에서 값 넣기

문자열을 SQL에 직접 이어 붙이지 않고 **파라미터 바인딩** 사용.

```python
conn.execute(
    "INSERT INTO products (name, list_price) VALUES (?, ?)",
    (name, price),
)
```

여러 행은 `executemany()`.

---

## 2.2 UPDATE·DELETE 안전 규칙

가장 중요한 습관:

```text
1. 같은 WHERE로 SELECT
2. 대상 행 확인
3. BEGIN
4. UPDATE / DELETE
5. 결과 확인
6. 정상 → COMMIT
7. 문제 → ROLLBACK
```

### 수정

```sql
SELECT *
FROM orders
WHERE id = 4;

BEGIN;

UPDATE orders
SET amount = 300000
WHERE id = 4
RETURNING *;

COMMIT;
```

### 삭제

```sql
SELECT *
FROM orders
WHERE id = 4;

BEGIN;

DELETE FROM orders
WHERE id = 4
RETURNING *;

COMMIT;
```

**`WHERE`가 없으면 전체 행이 대상**.

```sql
UPDATE customers SET city = '서울';
DELETE FROM orders;
```

문법 오류가 아니라 정상 실행되는 위험한 SQL.

---

## 2.3 트랜잭션

```text
BEGIN
→ 변경 작업
→ 확인
├─ 정상: COMMIT
└─ 문제: ROLLBACK
```

여러 SQL을 하나의 작업으로 묶어:

```text
전부 성공
또는
전부 취소
```

를 보장할 때 사용.

`COMMIT` 뒤에는 `ROLLBACK`으로 되돌릴 수 없음.

---

## 2.4 ALTER TABLE

기존 테이블에 열 추가:

```sql
ALTER TABLE products
ADD COLUMN stock int NOT NULL DEFAULT 0;
```

기존 행이 있는 테이블에 `NOT NULL` 열을 추가할 때는 보통 **기존 행을 채울 기본값**이 필요.

# 3. SELECT — 필요한 데이터만 조회

## 3.1 기본 구조

```sql
SELECT 열
FROM 테이블
WHERE 조건
ORDER BY 정렬기준
LIMIT 개수
OFFSET 건너뛸개수;
```

역할:

```text
SELECT   → 어떤 열을 볼지
WHERE    → 어떤 행을 남길지
ORDER BY → 어떤 순서로 볼지
LIMIT    → 몇 개만 볼지
```

계산 열 + 별칭:

```sql
SELECT
    product,
    amount,
    amount * 1.1 AS amount_with_tax
FROM orders;
```

---

## 3.2 정렬

```sql
ORDER BY amount DESC
```

다중 정렬:

```sql
ORDER BY customer_id ASC, amount DESC
```

조회 결과 순서는 자동 보장되지 않음.
순서가 중요하면 반드시 `ORDER BY`.

---

## 3.3 조건식

| 목적 | 문법 |
|---|---|
| 조건 결합 | `AND`, `OR`, `NOT` |
| 범위 | `BETWEEN a AND b` |
| 목록 | `IN (...)` |
| 목록 제외 | `NOT IN (...)` |
| 문자열 패턴 | `LIKE` |
| 빈 값 | `IS NULL`, `IS NOT NULL` |
| 중복 제거 | `DISTINCT` |

```sql
WHERE (city = '서울' OR city = '부산')
  AND name <> '김민수';
```

`AND`가 `OR`보다 먼저 실행되므로 섞을 때는 괄호 사용.

### LIKE

```text
% → 글자 0개 이상
_ → 정확히 한 글자
```

```sql
WHERE product LIKE '%보드%'
```

### NULL

```sql
WHERE city = NULL      -- X
WHERE city IS NULL     -- O
```

`NULL`은 0이나 빈 문자열이 아니라 **값이 없음**을 뜻함.

# 4. 집계와 그룹

## 4.1 집계 함수

| 함수 | 역할 |
|---|---|
| `count(*)` | 전체 행 수 |
| `count(열)` | 해당 열이 `NULL`이 아닌 행 수 |
| `count(DISTINCT 열)` | 서로 다른 값 개수 |
| `sum()` | 합 |
| `avg()` | 평균 |
| `max()` | 최댓값 |
| `min()` | 최솟값 |

```sql
SELECT
    count(*) AS 주문수,
    sum(amount) AS 매출,
    avg(amount) AS 평균주문액
FROM orders;
```

---

## 4.2 GROUP BY

그룹별 통계:

```sql
SELECT
    customer_id,
    count(*) AS 주문건수,
    sum(amount) AS 매출
FROM orders
GROUP BY customer_id;
```

---

## 4.3 WHERE vs HAVING

```text
WHERE  → 그룹으로 묶기 전 행 필터
HAVING → 그룹으로 묶은 뒤 그룹 필터
```

```sql
SELECT
    customer_id,
    count(*) AS 주문건수
FROM orders
WHERE amount >= 30000
GROUP BY customer_id
HAVING count(*) >= 2;
```

### 논리적 실행 순서

```text
FROM
→ WHERE
→ GROUP BY
→ HAVING
→ SELECT
→ ORDER BY
→ LIMIT
```

따라서:

- 집계 조건 → `HAVING`
- `SELECT`에서 만든 별칭 → `WHERE`보다 `ORDER BY`에서 사용

# 5. JOIN — 여러 테이블을 한 줄로 연결

## 5.1 JOIN

짝이 있는 행만 연결.

```sql
SELECT
    c.name,
    o.product,
    o.amount
FROM customers c
JOIN orders o
    ON o.customer_id = c.id;
```

핵심 연결:

```text
orders.customer_id = customers.id
        FK                 PK
```

실무에서는 이름보다 **ID 키로 연결**하는 구조가 안정적.

---

## 5.2 LEFT JOIN

왼쪽 테이블의 행을 전부 유지.

```sql
SELECT
    c.name,
    count(o.id) AS 주문건수,
    coalesce(sum(o.amount), 0) AS 매출
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.id
GROUP BY c.id, c.name;
```

주문이 없는 고객도 남음.

### count 주의

```text
count(*)    → LEFT JOIN으로 생긴 행도 셈
count(o.id) → 실제 주문이 있는 행만 셈
```

주문 0건을 정확히 `0`으로 세려면 `count(o.id)`가 유용.

---

## 5.3 LEFT JOIN의 ON vs WHERE

요구사항:

```text
3월 주문만 집계
+
주문 없는 고객도 유지
```

기간 조건은 `ON`에 둠.

```sql
LEFT JOIN orders o
    ON o.customer_id = c.id
   AND o.ordered_at BETWEEN '2026-03-01' AND '2026-03-31'
```

반대로:

```sql
LEFT JOIN ...
WHERE o.ordered_at BETWEEN ...
```

처럼 `WHERE`에 두면 조인 후 `NULL` 행까지 제거되어 **주문 없는 고객이 사라질 수 있음**.

핵심:

```text
ON    → 어떤 행끼리 짝지을지
WHERE → 조인 완료 후 어떤 결과 행을 남길지
```

# 6. 서브쿼리

질의 안에 다른 `SELECT`를 넣는 방식.

## 값 하나

```sql
SELECT product, amount
FROM orders
WHERE amount > (
    SELECT avg(amount)
    FROM orders
);
```

## 목록

```sql
SELECT name
FROM customers
WHERE id IN (
    SELECT DISTINCT customer_id
    FROM orders
);
```

## 상관 서브쿼리

바깥 행 값을 안쪽에서 참조.

```sql
SELECT
    c.name,
    (
        SELECT count(*)
        FROM orders o
        WHERE o.customer_id = c.id
    ) AS 주문건수
FROM customers c;
```

바깥 행마다 안쪽 질의를 다시 계산하는 구조.

### `NOT IN` 주의

서브쿼리 결과 목록에 `NULL`이 섞이면 원하는 결과가 나오지 않을 수 있음.

```text
NOT IN 사용
→ 안쪽 열이 NOT NULL인지 확인
→ 필요하면 IS NOT NULL로 NULL 제거
```

# 7. 조회 결과 활용

## 7.1 집계 결과를 테이블로 저장

```sql
INSERT INTO sales_report (customer_id, total)
SELECT
    customer_id,
    sum(amount)
FROM orders
GROUP BY customer_id;
```

`INSERT INTO ... SELECT`는 조회 결과를 그대로 다른 테이블에 저장.

주의:

```text
INSERT 대상 열 순서
=
SELECT 결과 열 순서
```

---

## 7.2 인덱스

자주 검색하거나 조인하는 열에 만들어 두는 **찾아보기 구조**.

```sql
CREATE INDEX orders_customer_id_idx
ON orders(customer_id);
```

적합한 곳:

```text
WHERE에서 자주 거르는 열
JOIN에서 자주 연결하는 열
```

인덱스가 많으면 데이터 입력·수정 때 갱신 비용도 증가.
**필요한 열에만 생성**.

# 8. 실전 리포트 패턴

고객을 모두 남기면서 3월 주문만 집계:

```sql
SELECT
    c.name,
    count(o.id) AS 주문건수,
    coalesce(sum(o.amount), 0) AS 매출,
    avg(o.amount) AS 평균주문액
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.id
   AND o.ordered_at BETWEEN '2026-03-01' AND '2026-03-31'
GROUP BY c.id, c.name
ORDER BY 매출 DESC, c.name ASC;
```

이 한 쿼리에 들어간 핵심:

```text
LEFT JOIN  → 고객 전체 유지
ON         → 집계할 주문 범위 제한
count      → 주문 건수
sum / avg  → 매출 통계
coalesce   → 주문 없는 고객의 매출을 0으로
GROUP BY   → 고객별 집계
ORDER BY   → 리포트 정렬
```

# 9. 최종 실전 체크리스트

## 설계할 때

```text
□ 한 테이블이 한 대상을 담당하는가
□ 각 테이블에 PK가 있는가
□ 1:N의 FK가 N쪽에 있는가
□ M:N을 중간 테이블로 풀었는가
□ NOT NULL / UNIQUE / CHECK / DEFAULT가 필요한가
□ 삭제 시 자식 데이터를 어떻게 처리할지 정했는가
```

## 데이터를 바꿀 때

```text
□ UPDATE / DELETE 전에 같은 WHERE로 SELECT 했는가
□ 위험한 변경을 BEGIN으로 묶었는가
□ RETURNING 또는 SELECT로 결과를 확인했는가
□ 확인 뒤에만 COMMIT 했는가
```

## 조회할 때

```text
□ 필요한 열만 SELECT 했는가
□ 행 조건은 WHERE인가
□ 그룹 조건은 HAVING인가
□ NULL을 = NULL로 비교하지 않았는가
□ 순서가 필요하면 ORDER BY를 썼는가
```

## JOIN할 때

```text
□ 어떤 키로 연결하는지 명확한가
□ 없는 행도 유지해야 하면 LEFT JOIN인가
□ LEFT JOIN의 조건을 ON에 둘지 WHERE에 둘지 확인했는가
□ 주문 0건을 셀 때 count(*) 대신 count(오른쪽.id)를 써야 하는가
```

# 핵심 치트시트

| 목적 | 문법 |
|---|---|
| 표 생성 | `CREATE TABLE` |
| 열 추가 | `ALTER TABLE ... ADD COLUMN` |
| 행 추가 | `INSERT INTO ... VALUES` |
| 조회 | `SELECT` |
| 행 필터 | `WHERE` |
| 정렬 | `ORDER BY` |
| 일부 조회 | `LIMIT`, `OFFSET` |
| 그룹 | `GROUP BY` |
| 그룹 필터 | `HAVING` |
| 수정 | `UPDATE` |
| 삭제 | `DELETE` |
| 변경 시작 | `BEGIN` |
| 변경 확정 | `COMMIT` |
| 변경 취소 | `ROLLBACK` |
| 테이블 결합 | `JOIN`, `LEFT JOIN` |
| 내부 질의 | 서브쿼리 |
| 결과 저장 | `INSERT INTO ... SELECT` |
| 검색 최적화 | `CREATE INDEX` |

## 가장 중요한 구분

```text
PK       → 내 행을 식별
FK       → 다른 행을 참조
1:N      → FK는 N쪽
M:N      → 중간 테이블

WHERE    → 행을 거름
HAVING   → 그룹을 거름
ON       → JOIN할 짝을 정함

JOIN     → 짝 있는 행
LEFT JOIN→ 왼쪽 행 전부

BEGIN    → 변경 묶기
COMMIT   → 확정
ROLLBACK → 취소
```

## 전체 한 줄

```text
ERD로 구조를 먼저 정하고
→ 타입·제약조건·PK/FK로 데이터 품질을 막고
→ SELECT/WHERE로 필요한 데이터를 찾고
```
