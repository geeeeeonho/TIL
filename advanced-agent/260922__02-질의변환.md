# 질의 변환과 근거 검색

> Advanced RAG의 **Pre-retrieval(검색 전)** 단계.  
> 검색기를 바꾸기보다 **검색에 넣는 질문을 변환**해 검색 성능을 높이는 방식.

---

## 1. 전체 개념

기본 Hybrid Search는 그대로 유지한다.

```text
사용자 질문
   ↓
질의 변환
   ↓
BM25 + Dense Search
   ↓
RRF 결합
   ↓
실제 검색 원문
   ↓
LLM 답변
```

이 교안에서는 다음 5가지 질의 변환을 사용한다.

| 기법 | 핵심 역할 | 적합한 상황 |
|---|---|---|
| **Self-Query** | 검색어 + 메타데이터 조건 분리 | 연도·분류·페이지 등 조건 포함 |
| **HyDE** | 가상의 답변 문서를 만들어 Dense 검색 | 짧은 질문과 설명형 문서의 표현 차이가 큼 |
| **Multi-Query** | 같은 의미의 질문을 여러 표현으로 확장 | 질문과 원문의 표현이 다름 |
| **Step-back** | 구체 질문에서 상위 개념·원리 질문 생성 | 배경 원리까지 함께 필요 |
| **Decomposition** | 복합 질문을 여러 하위 질문으로 분리 | 서로 다른 정보 요구가 여러 개 포함 |

### 공통 원칙

```text
생성 질문 / 가상문서
        ↓
     검색에만 사용
        ↓
실제 검색된 원문
        ↓
   최종 답변 생성
```

**LLM이 만든 질의나 HyDE 가상문서를 답변 근거로 사용하지 않는다.**  
최종 답변은 실제 검색된 문서의 본문·메타데이터·출처 ID만 사용한다.

---

# 2. 공통 검색 환경

## Hybrid Search

교안에서는 BM25와 Dense Search를 동일한 비중으로 결합한다.

```python
TOP_K = 3

bm25 = BM25Retriever.from_documents(
    documents,
    preprocess_func=kiwi_tokenize,
    k=TOP_K,
)

dense = vector_store.as_retriever(
    search_kwargs={"k": TOP_K}
)

hybrid = EnsembleRetriever(
    retrievers=[bm25, dense],
    weights=[0.5, 0.5],
    c=60,
    id_key="source_id",
)
```

```text
질문
 ├─ BM25 ──┐
 │          ├─ RRF → 최종 문서
 └─ Dense ─┘
```

- `TOP_K = 3`: 검색기별 기본 후보 수
- `weights=[0.5, 0.5]`: BM25와 Dense 동일 비중
- `c=60`: RRF 순위 완화 상수
- `source_id`: 같은 원문을 식별하는 ID

---

## Recall 평가

질의 변환 전후에 정답 문서를 얼마나 찾았는지 비교한다.

```text
Recall = 찾은 정답 문서 수 / 전체 정답 문서 수
```

```python
def compare_recall(before, after, expected_ids):
    expected_ids = set(expected_ids)

    for stage, results in [("변환 전", before), ("변환 후", after)]:
        retrieved_ids = {doc.metadata["source_id"] for doc in results}

        recall = len(retrieved_ids & expected_ids) / len(expected_ids)
        missing_ids = expected_ids - retrieved_ids
```

> Recall은 **검색 단계 평가값**이다.  
> Recall이 높아져도 최종 답변 품질이 반드시 좋아지는 것은 아니므로 둘을 함께 확인해야 한다.

# 3. Self-Query

## 개념

**Self-Query Retrieval**은 자연어 질문에서 다음 두 요소를 분리한다.

```text
사용자 질문
   ↓
LLM 분석
   ├─ query  : 본문에서 검색할 내용
   └─ filter : 메타데이터 조건
```

예시:

```text
"2018년 이전 과학 분야에서 천체의 일생과 생물의 변화를 설명하는 책"

          ↓

query  = 천체의 일생과 생물의 변화
filter = category == "과학"
         year < 2018
```

### 적합한 경우

- 연도
- 문서 분류
- PDF 페이지
- 작성자
- 지역
- 상품 범주

처럼 **본문 의미 검색과 별도의 구조화된 조건**이 있을 때 유용하다.

문서에 해당 메타데이터 필드가 없다면 사용할 수 없다.

---

## 메타데이터 스키마 정의

```python
metadata_field_info = [
    AttributeInfo(
        name="category",
        description="장서 분류",
        type="string",
    ),
    AttributeInfo(
        name="year",
        description="출판 연도",
        type="integer",
    ),
]
```

LLM에게 사용할 수 있는 필드와 자료형을 명확히 알려준다.

---

## 검색어와 조건 추출

```python
parsed = self_query.query_constructor.invoke({
    "query": question
})

query_text, search_kwargs = (
    ChromaTranslator().visit_structured_query(parsed)
)

where = search_kwargs.get("filter")
```

### 실제 예시 결과

```text
검색어:
천체의 일생과 생물이 오랜 시간에 걸쳐 달라지는 과정

조건:
category == "과학"
year < 2018
```

검색 결과:

```text
book05 → 코스모스 우주와 별의 세계
book06 → 이기적 유전자 진화의 관점
```

# 4. 조건을 Hybrid Search 양쪽에 적용

Self-Query에서 추출한 조건은 Dense에만 적용하는 것이 아니라 **BM25와 Dense 모두에 동일하게 적용**한다.

```text
                  ┌─ BM25 검색 ─ 조건 필터 ─┐
query + filter ───┤                         ├─ RRF
                  └─ Dense 검색 + filter ───┘
```

교안의 BM25 흐름:

```text
전체 문서 BM25 점수 계산
        ↓
조건에 맞지 않는 문서 제거
        ↓
점수순 정렬
        ↓
상위 K개 선택
```

Dense Search:

```python
dense_results = vector_store.similarity_search(
    query,
    k=k,
    filter=where,
)
```

최종 결합:

```python
hybrid.weighted_reciprocal_rank([
    bm25_results,
    dense_results,
])[:k]
```

### PDF 실습 결과

질문:

```text
공통 분류이고 PDF 20쪽 이하인 문서에서
신청 자격, 승인 판단, 승인 후 유연근무 해제 절차를 찾아 주세요.
```

추출:

```text
query  = 신청 자격, 승인 판단, 승인 후 유연근무 해제 절차
filter = category == "공통"
         pdf_page <= 20
```

검색된 주요 원문:

```text
hr_eligibility → 적용대상자와 시행방법
hr_approval    → 신청과 승인 절차
hr_management  → 승인 후 업무관리
```

---

## ⚠️ 노트북 실행 순서 주의

원본 노트북의 Self-Query 뒤쪽 실행 결과 중 하나는 다음처럼 서로 다른 실습의 변수가 섞여 있다.

```text
원질문: 데이터 표를 이어 붙이는 방법, 항성의 일생, ...
검색어: 신청 자격, 승인 판단, 승인 후 유연근무 해제 절차
조건: 공통 / PDF 20쪽 이하
```

이는 `question`, `query_text`, `where`, `expected_ids` 같은 공용 변수명이 여러 셀에서 재사용되면서 **실행 순서에 따라 값이 덮어써진 결과**다.

실습할 때는 각 예제를 위에서부터 순서대로 실행하거나 다음처럼 변수명을 분리하는 편이 안전하다.

```python
self_query_question = ...
self_query_text = ...
self_query_where = ...
self_query_expected_ids = ...
```

# 5. HyDE

## 개념

**HyDE(Hypothetical Document Embeddings)**는 질문에 대한 **가상의 답변 문서**를 먼저 생성하고, 그 문서를 임베딩해 실제 원문을 찾는다.

원래 HyDE는 Dense 검색 기법이다.

교안에서는 Hybrid Search와 결합한다.

```text
원질문
 ├────────────→ BM25 ──────────────┐
 │                                  │
 └→ LLM → 가상 답변 문서 → Dense ──┤
                                    ↓
                                   RRF
                                    ↓
                               실제 원문
```

### 핵심

- BM25 → **원질문 사용**
- Dense → **가상문서 사용**
- 최종 답변 → **실제 검색 문서 사용**

---

## 가상문서 생성

```python
hypothetical_document = hyde_chain.invoke({
    "question": question
})
```

예시 질문:

```text
직원 설문에서 응답자 정보와 답변 표를 연결해 부서별 수치를 만들고,
일부 응답을 회사 전체 경향으로 해석할 때 주의할 점을 배우고 싶다.
```

생성된 가상문서에는 다음과 같은 전문 표현이 추가됐다.

```text
조인
집계
표본편향
대표성
표본오차
```

원질문의 일상적인 표현을 **실제 문서에서 등장할 가능성이 높은 용어**로 확장하는 효과가 있다.

---

## Hybrid 결합

```python
hyde_bm25_results = bm25.invoke(question)
hyde_dense_results = dense.invoke(hypothetical_document)

hyde_results = hybrid.weighted_reciprocal_rank([
    hyde_bm25_results,
    hyde_dense_results,
])[:TOP_K]
```

### 실습 결과

정답 문서:

```text
book02 → SQL / 조인·집계
book03 → 통계 / 표본오차·설문 해석
```

| 단계 | Recall |
|---|---:|
| 변환 전 | 0.5 |
| HyDE 적용 후 | **1.0** |

즉, 기존 검색에서 놓쳤던 `book02`까지 검색했다.

---

## HyDE의 한계

가상문서는 LLM이 생성하므로 원문에 없는 내용을 만들 수 있다.

실제 PDF 실습에서는 가상문서에 다음과 같은 표현도 생성됐다.

```text
성과개선계획(PIP)
심리적 안전감
관련 노동규정
```

하지만 검색된 실제 원문은 이 내용을 모두 보장하지 않는다.

따라서:

```text
가상문서 = 검색 힌트
실제 원문 = 답변 근거
```

을 반드시 분리해야 한다.

실제 PDF HyDE 실습에서는 Recall이 `0.5 → 0.5`로 동일했다.  
즉, **HyDE가 항상 검색 성능을 높이는 것은 아니다.**

# 6. Multi-Query

## 개념

**Multi-Query Retrieval**은 같은 의미의 질문을 여러 표현으로 다시 만든다.

```text
원질문
   ↓
LLM
   ├─ 질문 A
   ├─ 질문 B
   ├─ 질문 C
   └─ 원질문
        ↓
각 질문을 Hybrid Search
        ↓
검색 결과 합치기
        ↓
source_id 중복 제거
```

### 적합한 경우

```text
재택근무 ↔ 원격근무 ↔ 집에서 일하기
```

처럼 질문과 문서에서 같은 의미를 서로 다른 단어로 표현할 때 유용하다.

정확한 제품 번호·법령 번호·고유 키워드를 그대로 찾아야 하는 경우에는 불필요하게 검색 범위를 넓힐 수 있다.

---

## 질문 생성

```python
multi_query = MultiQueryRetriever.from_llm(
    retriever=hybrid,
    llm=llm,
    prompt=multi_prompt,
    include_original=True,
)
```

`include_original=True`이므로 생성 질문뿐 아니라 원질문도 함께 검색한다.

예시 생성 질문:

```text
1. 항성의 형성과 진화 및 생물 종의 장기적 변화를 다루는 책을 찾아 주세요.
2. 별의 탄생부터 소멸까지의 항성 진화와 생물 종의 시간에 따른 진화를 배울 수 있는 도서를 추천해 주세요.
3. 항성 생애 주기와 생물학적 진화 과정을 함께 설명하는 책들을 검색해 주세요.
```

---

## 중복 제거

여러 질문이 같은 문서를 찾을 수 있다.

```python
def unique_documents(documents):
    by_id = {}

    for doc in documents:
        source_id = doc.metadata["source_id"]

        if source_id not in by_id:
            by_id[source_id] = doc

    return list(by_id.values())
```

---

## 실습 결과

정답:

```text
book05 → 별의 탄생과 죽음
book06 → 진화·협력·이타 행동
```

| 단계 | Recall |
|---|---:|
| 원질문 검색 | 0.5 |
| Multi-Query | **1.0** |

PDF 실습:

| 단계 | Recall |
|---|---:|
| 변환 전 | 0.333 |
| Multi-Query | **0.667** |

즉, 표현을 여러 방식으로 바꾸면서 기존 검색에서 놓친 관련 문서를 추가로 찾았다.

# 7. Step-back

## 개념

**Step-back Prompting**은 구체적인 질문을 바로 다시 표현하는 것이 아니라 **그 문제를 이해하는 데 필요한 상위 원리·개념 질문**을 만든다.

```text
구체적인 원질문 ──────────────→ Hybrid Search
       │
       ↓
LLM → 배경 개념 질문 ─────────→ Hybrid Search
                                │
                       두 결과 합치기
                                ↓
                              답변
```

### Multi-Query와 차이

```text
Multi-Query
→ 같은 질문을 다른 표현으로 변경

Step-back
→ 구체 질문을 더 일반적인 배경 개념 질문으로 변경
```

---

## 예시

원질문:

```text
예측 모델의 오차를 줄이도록 내부 값을 바꾸는 과정을 구현하고,
미분이 왜 필요한지 이해하고 싶다.
```

Step-back 질문:

```text
경사 하강법과 미분은 함수의 오차를 줄이는
최적화 과정에서 어떤 역할을 하나요?
```

검색 결과:

```text
원질문 → book01 신경망 학습
배경질문 → book04 미적분 개념 추가
```

| 단계 | Recall |
|---|---:|
| 변환 전 | 0.5 |
| Step-back 결합 | **1.0** |

---

## 언제 사용?

다음처럼 **답뿐 아니라 이유·원리도 함께 설명해야 할 때** 적합하다.

```text
구체적인 방법
+
그 방법이 작동하는 이유
```

반대로 단순 사실 하나를 찾는 검색에는 검색 범위만 불필요하게 넓어질 수 있다.

# 8. Query Decomposition

## 개념

**Query Decomposition**은 하나의 질문 안에 서로 다른 정보 요구가 여러 개 있을 때 질문을 독립적인 하위 질문으로 나눈다.

```text
복합 질문
   ↓
LLM
   ├─ 하위 질문 1 → Hybrid Search
   ├─ 하위 질문 2 → Hybrid Search
   └─ 하위 질문 3 → Hybrid Search
                  ↓
            검색 결과 합치기
                  ↓
             중복 ID 제거
                  ↓
             원질문에 답변
```

### Multi-Query와 차이

```text
Multi-Query
→ 같은 정보 요구를 여러 표현으로 확장

Decomposition
→ 서로 다른 정보 요구를 각각 분리
```

---

## 구조화된 출력

```python
class SubQuestions(BaseModel):
    questions: list[str] = Field(
        min_length=2,
        max_length=3,
    )
```

LLM이 2~3개의 하위 질문을 생성하도록 스키마로 제한한다.

---

## 예시

원질문:

```text
데이터 표를 이어 붙이는 방법,
항성의 일생,
생물이 남을 돕는 이유를 각각 배울 책을 찾아 주세요.
```

분해 결과:

```text
1. 데이터 표를 이어 붙이는 방법을 배울 수 있는 책을 찾아 주세요.
2. 항성의 일생을 배울 수 있는 책을 찾아 주세요.
3. 생물이 남을 돕는 이유를 배울 수 있는 책을 찾아 주세요.
```

검색:

```python
subquestion_results = hybrid.batch(
    subquestions.questions
)
```

검색 결과를 하나의 목록으로 합친 뒤 `source_id`로 중복 제거한다.

### 실습 결과

| 단계 | Recall |
|---|---:|
| 원질문 검색 | 0.333 |
| Decomposition | **1.0** |

찾은 정답:

```text
book02 → SQL / 조인
book05 → 항성의 일생
book06 → 협력과 이타 행동
```

복합 질문 전체를 한 번에 검색하는 것보다 **정보 요구별로 검색하는 방식이 효과적**이었다.

---

# 9. 다섯 기법 비교

| 기법 | 무엇을 바꾸나 | 핵심 사용 상황 | 주의점 |
|---|---|---|---|
| **Self-Query** | 검색어 + 조건 분리 | 연도·분류·페이지 조건 | 메타데이터 필드 필요 |
| **HyDE** | 가상 답변 문서 생성 | 질문이 짧고 실제 문서는 설명형 | 가상 내용은 근거로 사용 금지 |
| **Multi-Query** | 같은 뜻의 표현 증가 | 표현 차이로 문서를 놓침 | 검색 후보와 비용 증가 |
| **Step-back** | 상위 개념 질문 생성 | 원리·정의까지 검색 | 단순 사실 검색에는 과도할 수 있음 |
| **Decomposition** | 서로 다른 요구 분리 | 복합 질문 | 독립적으로 나눌 수 있는 질문에 적합 |

---

# 10. 선택 기준

```text
질문에 명확한 조건이 있는가?
 └─ Yes → Self-Query

같은 뜻인데 문서와 표현이 다를 가능성이 큰가?
 └─ Yes → Multi-Query

질문이 짧고 설명형 문서를 잘 못 찾는가?
 └─ Yes → HyDE

구체적인 답과 배경 원리가 함께 필요한가?
 └─ Yes → Step-back

서로 다른 요구가 여러 개 섞였는가?
 └─ Yes → Decomposition
```

# 11. 기법 조합

기법은 하나만 사용해야 하는 것이 아니다.

예를 들어 복합 질문에 조건까지 있다면:

```text
원질문
   ↓
Decomposition
   ↓
하위 질문별 Self-Query
   ↓
query + filter
   ↓
Multi-Query
   ↓
각 질문에 같은 filter 적용
   ↓
Hybrid Search
   ↓
중복 제거
   ↓
실제 원문 기반 답변
```

다만 단계가 늘어날수록:

- LLM 호출 수 증가
- 검색 횟수 증가
- 응답 시간 증가
- 비용 증가
- 불필요한 후보 증가

가 발생한다.

따라서 **질문의 문제에 필요한 변환만 선택**하고, Recall과 최종 답변 품질을 함께 평가한다.

# 12. 핵심 코드 흐름

```python
# 1. 기본 Hybrid Search
hybrid = EnsembleRetriever(
    retrievers=[bm25, dense],
    weights=[0.5, 0.5],
    c=60,
    id_key="source_id",
)

# 2. 질의 변환
transformed_query = ...

# 3. 검색
results = hybrid.invoke(transformed_query)

# 또는 여러 질문
results_list = hybrid.batch(transformed_queries)

# 4. 실제 검색 원문만 답변 문맥으로 사용
context = format_context(results)

# 5. 원질문에 답변
answer = answer_chain.invoke({
    "question": original_question,
    "context": context,
})
```

질의 변환 방법은 달라도 최종 구조는 동일하다.

```text
질문 변환
   ↓
검색 성능 개선
   ↓
실제 원문 확보
   ↓
원질문에 근거 기반 답변
```

# 핵심 정리

```text
Self-Query
= 조건을 분리한다.

HyDE
= 답변처럼 생긴 가상문서로 검색한다.

Multi-Query
= 같은 뜻을 여러 표현으로 검색한다.

Step-back
= 구체 질문에서 배경 원리를 검색한다.

Decomposition
= 여러 요구를 각각 나눠 검색한다.
```

가장 중요한 원칙:

> **질의 변환은 검색을 돕기 위한 과정이다.**  
> 최종 답변의 근거는 반드시 **실제로 검색된 원문**이어야 한다.
