# Self-RAG 스타일: 답변 검토와 수정

## 1. 핵심 개념

교안 01의 CRAG가 **검색 근거를 평가하고 교정**했다면, 이번 교안은 그 뒤에 **생성한 답변을 다시 검토하고 수정**하는 단계를 추가함.

이번 실습은 정해진 LangGraph 경로 안에서 판단과 피드백을 사용하는 **자기검토 RAG 워크플로**.

```text
검색 근거 확보
→ 답변 초안 생성
→ 근거성·유용성 검토
→ 통과 / 수정 후 재검토 / 보류
```

전체적으로는 두 개의 사이클이 존재함.

```text
[검색 교정 사이클]
retrieve → grade
   ↑         │
   └ rewrite ┘
        │
        └ 필요 시 web_search

             ↓

[답변 검토 사이클]
generate → review
             ├─ 통과 → accept
             ├─ 수정 → revise → review
             └─ 한도 초과 → hold
```

검색 실패와 답변 실패를 **서로 다른 문제로 분리**해서 처리하는 것이 핵심.

---

## 2. RAG 평가의 대표 기준 4개

교안에서는 RAG 평가 기준을 다음 네 가지로 구분함.

| 구분 | 지표 | 의미 |
|---|---|---|
| 검색기 | **Context Precision** | 관련 컨텍스트가 상위에 잘 배치되었는가 |
| 검색기 | **Context Recall** | 정답에 필요한 근거를 빠짐없이 가져왔는가 |
| 생성기 | **Faithfulness** | 답변이 검색된 컨텍스트에 근거하는가 |
| 생성기 | **Response Relevancy** | 답변이 사용자 질문에 적절하게 응답하는가 |

이번 Self-RAG 스타일 실습은 특히 생성된 답변의 다음 두 기준을 직접 검토함.

### 근거성 `support`

답변의 사실·조건·인용이 제공된 근거와 실제로 일치하는지 확인.

```text
fully
→ 모든 주장·조건·인용이 근거로 뒷받침됨

partially
→ 일부 오류 또는 조건 누락

unsupported
→ 핵심 오류 또는 존재하지 않는 인용
```

### 유용성 `useful`

사용자가 요청한 내용을 실제로 충족했는지 확인.

- 답할 수 있는 요청을 빠뜨리지 않았는가
- 필수 조건·예외를 누락하지 않았는가
- 확인할 수 없는 내용은 한계를 밝혔는가
- 추가 확인 방법을 안내했는가

즉,

```text
근거성 = 이 답변이 원문에 맞는가?
유용성 = 이 답변이 질문에 제대로 답했는가?
```

## 3. 전체 Self-RAG 흐름

```text
START
  ↓
prepare_search
  ↓
retrieve
  ↓
grade
  ├─ 근거 충분 ─────────────────────→ generate
  │                                      ↓
  │                                    review
  │                                  ↙   ↓    ↘
  │                            accept  revise  hold
  │                              ↓       │      ↓
  │                             END      └→ review
  │
  ├─ 근거 부족 + 재작성 가능
  │        ↓
  │     rewrite
  │        ↓
  │     retrieve
  │
  └─ 재작성 한도 소진
           ↓
       web_search
           ↓
         grade
           ├─ 근거 있음 → generate
           └─ 근거 없음 → abstain → END
```

핵심은 `generate`가 끝이 아니라는 점.

```text
generate
→ review
→ 필요하면 revise
→ 다시 review
```

## 4. 상태(State)

CRAG 상태에 **답변 검토 결과와 이력**이 추가됨.

```python
class RAGState(TypedDict):
    # 입력과 한도
    question: str
    max_rewrites: int
    max_reviews: int

    # 검색
    search_query: str
    documents: list[Document]

    # 검색 근거 평가
    decision: Literal["", "correct", "ambiguous", "incorrect"]
    missing_info: str
    search_history: list[dict]
    feedback: str

    # 검색 보완
    rewrite_count: int
    web_searched: bool
    web_notice: str

    # 답변
    draft: str
    evidence_ids: list[str]
    status: Literal[
        "running",
        "generated",
        "partial",
        "accepted",
        "insufficient",
        "review_failed",
    ]

    # 답변 검토
    support: Literal["", "fully", "partially", "unsupported"]
    useful: bool
    review_count: int
    review_history: list[dict]
```

핵심 필드:

| 필드 | 역할 |
|---|---|
| `decision` | 검색 근거의 충분성 평가 |
| `missing_info` | 검색에서 확인하지 못한 내용 |
| `feedback` | 최근 검색 평가 또는 답변 검토 의견 |
| `draft` | 현재 답변 초안 |
| `evidence_ids` | 답변에서 실제 사용한 근거 ID |
| `support` | 답변의 근거성 |
| `useful` | 사용자 요청 충족 여부 |
| `review_count` | 완료한 답변 검토 횟수 |
| `review_history` | 초안·인용·판정·수정 의견 기록 |

기본 설정:

```python
"rewrite_count": 0,
"max_rewrites": 1,

"review_count": 0,
"max_reviews": 2,
```

`max_reviews=2`이면:

```text
첫 검토
→ 수정
→ 두 번째 검토
```

수정은 최대 1회 가능.

## 5. 검색 교정 노드

검색 부분은 교안 01의 CRAG 구조를 그대로 사용함.

### 5-1. `prepare_search`

원질문은 그대로 유지하고 검색에 사용할 영어 핵심어만 생성.

```python
def prepare_search(state):
    terms = lexical_chain.invoke({
        "question": state["question"]
    })

    return {
        "search_query": " ".join(terms.keywords)
    }
```

첫 검색 준비는 재검색이 아니므로 `rewrite_count`를 늘리지 않음.

---

### 5-2. `retrieve`

기존 근거와 새 검색 결과를 합침.

```python
def retrieve(state):
    found = search_documents(state["search_query"])

    return {
        "documents": merge_documents(
            state["documents"],
            found,
        )
    }
```

재검색하더라도 이전에 찾은 유효 근거를 유지함.

---

### 5-3. `grade`

검색 결과의 관련성과 충분성을 평가.

```python
class RetrievalReview(BaseModel):
    feedback: str
    useful_ids: list[str]
    sufficient: bool
```

판정:

```text
선택 근거 없음
→ incorrect

근거 있음 + 질문 전체를 답할 수 있음
→ correct

근거는 있지만 일부 정보 부족
→ ambiguous
```

검색에서 부족한 내용은 `missing_info`에 저장.

이 값은 이후 답변 생성과 수정 단계에서도 유지됨.

---

### 5-4. `rewrite`

검색 평가에서 발견한 부족한 정보를 이용해 검색어를 변경.

```python
def rewrite(state):
    query = rewrite_query(
        state["question"],
        state["search_query"],
        state["feedback"],
        search_language,
    )

    return {
        "search_query": query,
        "rewrite_count": state["rewrite_count"] + 1,
    }
```

```text
question     → 유지
search_query → 변경
feedback     → 부족한 정보 전달
```

---

### 5-5. `web_search`

내부 재검색으로도 부족하면 Tavily 웹 검색을 최대 1회 수행.

```python
def web_search(state):
    web_docs, notice = search_web(
        state["search_query"]
    )

    return {
        "documents": merge_documents(
            state["documents"],
            web_docs,
        ),
        "web_searched": True,
        "web_notice": notice,
    }
```

기존 내부 근거와 웹 근거를 합친 뒤 다시 `grade`에서 평가함.

## 6. 답변 생성

### `generate`

선택된 근거로 답변 초안을 생성.

```python
class GroundedAnswer(BaseModel):
    answer: str
    evidence_ids: list[str]
```

생성 시 지켜야 할 기준:

- 제공 근거가 직접 뒷받침하는 내용만 사용
- 사실마다 `[근거ID]` 표시
- `evidence_ids`와 실제 인용을 일치시킴
- 대상·조건·예외·절차 순서를 보존
- 확인되지 않은 사실은 만들지 않음
- 미확인 요청에는 추가 확인 방법 안내

```python
def generate(state):
    answer = generate_answer(
        state["question"],
        state["documents"],
        feedback=state["missing_info"],
    )

    status = (
        "generated"
        if state["decision"] == "correct"
        else "partial"
    )

    return {
        "draft": answer.answer,
        "evidence_ids": answer.evidence_ids,
        "status": status,
    }
```

검색 근거가 일부 부족해도 확인된 내용이 있으면 `partial` 답변을 생성함.

## 7. 답변 검토

### 7-1. `review`

생성된 답변을 원질문과 실제 근거에 다시 대조함.

```python
class AnswerReview(BaseModel):
    feedback: str
    support: Literal[
        "fully",
        "partially",
        "unsupported",
    ]
    useful: bool
```

검토 예시:

| 문제 | 판정 기준 |
|---|---|
| 근거에는 인물 정보가 있는데 제목만 답함 | 유용성 문제 |
| 원문에 없는 결말을 단정함 | 근거성 문제 |
| 존재하지 않는 ID를 인용함 | 근거성 문제 |
| 대상·기한·횟수·예외 조건 누락 | 근거성 + 유용성 문제 |

`review`는 모델 판정 외에도 `evidence_ids`를 직접 검사함.

```python
known_ids = {
    evidence_id(doc)
    for doc in state["documents"]
}

valid_ids = (
    bool(state["evidence_ids"])
    and set(state["evidence_ids"]).issubset(known_ids)
)
```

인용 ID가 없거나 실제 근거 목록 밖의 ID가 있으면 통과시키지 않음.

검토 결과는 이력에 계속 누적.

```python
entry = {
    "draft": state["draft"],
    "evidence_ids": state["evidence_ids"],
    "support": support,
    "useful": result.useful,
    "feedback": feedback,
}
```

## 8. 답변 수정

### `revise`

직전 초안과 검토 의견을 생성기에 다시 전달해 답변 수정.

```python
def revise(state):
    feedback = (
        state["feedback"]
        + "\n미확인 사항: "
        + state["missing_info"]
    )

    answer = generate_answer(
        state["question"],
        state["documents"],
        state["draft"],
        feedback,
    )

    return {
        "draft": answer.answer,
        "evidence_ids": answer.evidence_ids,
    }
```

수정 입력:

```text
원질문
+ 근거
+ 직전 초안
+ 검토 의견
+ 미확인 사항
```

단순히 같은 검토를 반복하는 것이 아니라 **검토 결과를 다음 생성 입력으로 전달**하는 구조.

## 9. 검토 후 조건 분기

```python
def route_after_review(state):
    if (
        state["support"] == "fully"
        and state["useful"]
    ):
        return "accept"

    if (
        state["review_count"]
        >= state["max_reviews"]
    ):
        return "hold"

    return "revise"
```

분기 우선순위:

| 순서 | 조건 | 이동 |
|---|---|---|
| 1 | `support == "fully"` + `useful=True` | `accept` |
| 2 | 미통과 + 검토 한도 도달 | `hold` |
| 3 | 미통과 + 검토 여유 있음 | `revise` |

**통과 여부를 검토 횟수보다 먼저 확인**해야 함.

마지막 허용 검토에서 통과했다면 `hold`가 아니라 `accept`로 이동함.

## 10. 종료 노드

### `accept`

답변 검토를 통과한 경우.

```python
def accept(state):
    return {
        "status": (
            "partial"
            if state["missing_info"]
            else "accepted"
        )
    }
```

검색 과정에서 미확인 정보가 남아 있으면 검토를 통과했더라도 `partial`.

---

### `hold`

검토 한도 안에 답변을 고치지 못한 경우.

```python
def hold(state):
    return {
        "status": "review_failed"
    }
```

마지막 초안과 검토 의견은 그대로 남겨 사람이 확인할 수 있게 함.

---

### `abstain`

검색 보완 후에도 사용할 근거 자체가 없는 경우.

```python
def abstain(state):
    return {
        "draft": (
            "제공 자료에서 답할 근거를 찾지 못했습니다. "
            + state["missing_info"]
        ),
        "evidence_ids": [],
        "status": "insufficient",
    }
```

`hold`와 `abstain`은 다름.

```text
abstain
→ 답변을 만들 근거 자체가 부족함

hold
→ 근거는 있지만 생성된 답변이 검토를 통과하지 못함
```

## 11. 검색 분기

검색 부분은 다음 규칙으로 동작함.

```python
def route_after_grade(state):
    if state["decision"] == "correct":
        return "generate"

    if state["web_searched"]:
        return (
            "generate"
            if state["documents"]
            else "abstain"
        )

    if (
        state["rewrite_count"]
        < state["max_rewrites"]
    ):
        return "rewrite"

    return "web_search"
```

정리:

```text
근거 충분
→ generate

근거 부족 + 재작성 가능
→ rewrite

재작성 한도 소진
→ web_search

웹 검색까지 끝남 + 근거 있음
→ generate

웹 검색까지 끝남 + 근거 없음
→ abstain
```

## 12. 전체 LangGraph 연결

```python
builder = StateGraph(RAGState)

builder.add_node("prepare_search", prepare_search)
builder.add_node("retrieve", retrieve)
builder.add_node("grade", grade)
builder.add_node("rewrite", rewrite)
builder.add_node("web_search", web_search)
builder.add_node("generate", generate)
builder.add_node("abstain", abstain)

builder.add_node("review", review)
builder.add_node("revise", revise)
builder.add_node("accept", accept)
builder.add_node("hold", hold)

builder.add_edge(START, "prepare_search")
builder.add_edge("prepare_search", "retrieve")
builder.add_edge("retrieve", "grade")

builder.add_conditional_edges(
    "grade",
    route_after_grade,
    {
        "generate": "generate",
        "rewrite": "rewrite",
        "web_search": "web_search",
        "abstain": "abstain",
    },
)

builder.add_edge("rewrite", "retrieve")
builder.add_edge("web_search", "grade")

builder.add_edge("generate", "review")

builder.add_conditional_edges(
    "review",
    route_after_review,
    {
        "accept": "accept",
        "hold": "hold",
        "revise": "revise",
    },
)

builder.add_edge("revise", "review")

builder.add_edge("accept", END)
builder.add_edge("hold", END)
builder.add_edge("abstain", END)

self_rag_app = builder.compile()
```

핵심만 보면:

```text
검색 교정
──────────────
prepare_search
      ↓
   retrieve
      ↓
    grade
   ↙  ↓   ↘
rewrite │ web_search
   │    │
   └────┴──→ grade
             ↓
          generate

답변 검토
──────────────
generate
   ↓
 review
 ├─ fully + useful → accept → END
 ├─ 수정 가능 → revise ─┐
 │                      │
 └─ 한도 도달 → hold    │
                        └→ review
```

## 13. 종료 상태

| 상태 | 의미 |
|---|---|
| `generated` | 초안 생성 완료 |
| `accepted` | 답변 검토까지 통과 |
| `partial` | 확인 가능한 내용만 답하고 미확인 사항을 남김 |
| `insufficient` | 답변에 사용할 근거가 없음 |
| `review_failed` | 검토 한도 내에 답변 수정 실패 |

특히 다음 두 개를 구분해야 함.

```text
status="partial"
→ 질문 일부를 자료에서 확인하지 못함

support="partially"
→ 생성된 답변 자체의 일부 주장이나 조건이 근거와 맞지 않음
```

따라서 **부분 답변이라도 확인된 사실만 정확하게 사용했다면 `support="fully"`가 가능**함.

## 14. 카메라 대여 안내 수정 실습

초기 답변:

```text
카메라는 3일 빌립니다.
반납 전날 18시까지 신청하면 2일 연장됩니다.
[space-01]
```

하지만 원문에는 추가 조건이 존재함.

```text
기본 대여: 3일
연장 신청: 반납 전날 18시까지
연장 조건: 다음 예약이 없을 때
연장 횟수: 1회
연장 기간: 2일
```

초안에는 다음 조건이 빠져 있음.

```text
다음 예약이 없음
1회만 연장 가능
```

따라서 흐름은 다음과 같음.

```text
review
→ 조건 누락 발견
→ revise
→ 누락 조건 추가
→ review
→ fully + useful
→ accept
```

실습용 수정 노드:

```python
def practice_revise(state):
    feedback = (
        state["feedback"]
        + "\n검색 문서 평가시 확인된 미확인 사항:"
        + state["missing_info"]
    )

    answer = generate_answer(
        state["question"],
        state["documents"],
        state["draft"],
        feedback,
    )

    return {
        "draft": answer.answer,
        "evidence_ids": answer.evidence_ids,
    }
```

실습은 검색 전체를 다시 돌리는 것이 아니라 **답변 검토 → 수정 → 재검토** 부분에 집중함.

---

## 15. 핵심 구분

### CRAG와 이번 Self-RAG 스타일

```text
CRAG
검색 결과가 부족한가?
→ 검색어를 바꾸고 다시 검색

Self-RAG 스타일
생성한 답변이 근거와 질문에 맞는가?
→ 답변을 수정하고 다시 검토
```

두 흐름을 합치면:

```text
검색 실패
→ 검색 교정

답변 실패
→ 답변 수정
```

각 사이클의 횟수도 따로 관리함.

```text
max_rewrites
→ 검색 보완 한도

max_reviews
→ 답변 검토 한도
```

답변 검토에 실패했다고 검색부터 다시 반복하지 않음.

## 16. 핵심 정리

1. **검색 평가와 답변 평가를 분리함.**
   - `grade`는 근거를 평가.
   - `review`는 생성된 답변을 평가.

2. **근거성과 유용성도 분리함.**
   - `support`: 답변이 원문에 맞는가.
   - `useful`: 사용자 요구를 충족했는가.

3. **검토 의견을 실제 수정 입력으로 사용함.**
   - `review → feedback → revise`.

4. **수정 후 반드시 다시 검토함.**
   - `revise → review`.

5. **인용 ID도 검증함.**
   - 실제 선택된 근거에 없는 ID는 통과시키지 않음.

6. **부분 답변과 부분 근거성을 구분함.**
   - 일부 요청을 확인하지 못해도 확인된 사실만 정확하면 `support="fully"` 가능.

7. **검색 보완과 답변 검토의 반복 한도는 별개임.**

8. **실패 상태도 구분함.**
   - 근거 없음 → `insufficient`.
   - 답변 검토 실패 → `review_failed`.

### 한 줄 요약

> 이번 Self-RAG 스타일 구조는 **검색된 근거로 답변을 생성한 뒤, 그 답변의 근거성과 유용성을 다시 평가하고 검토 의견을 이용해 수정·재검토하는 RAG 워크플로**임.
