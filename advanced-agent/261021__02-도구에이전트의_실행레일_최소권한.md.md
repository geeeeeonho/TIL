# 도구 에이전트의 실행 레일과 최소 권한 — 개념과 핵심 코드 문법

> **정리 원본:** `교안_02_도구_에이전트의_실행_레일과_최소_권한.ipynb`  
> **학습 순서:** 전체 구조 → 최소 권한 → 미들웨어 문법 → 사람 승인 → 결과 검사 → 유료·외부 도구 → 평가  
> **읽는 방법:** 코드에서 **무엇을 검사하는지**, **언제 실행하는지**, **통과·차단 시 무엇을 반환하는지**에 집중.  
> 코드의 함수·상수 상당수는 교안 프로젝트 `luna_agent/`에 정의되어 있음. **독립 실행 예제가 아니라 원본 코드의 핵심 발췌 및 구조 정리**이며, 생략한 부분은 별도로 표시. 출력 예시는 노트북에 저장된 실행 기록 중 필요한 부분만 사용.

## 1. 실행 레일의 개념과 전체 구조

**실행 레일(Execution Rail)**: 에이전트가 도구를 선택·실행하는 과정에서 **도구 노출, 호출 인자, 로그인 권한, 실행 결과**를 검사하는 장치.

교안 01의 챗봇은 앱이 정한 경로를 따라 조회·검색했다면, 교안 02의 에이전트는 **모델이 도구를 고르고 반복 호출**함. 따라서 입력과 최종 답변만 검사해서는 충분하지 않음.

| 구분 | 교안 01: 경로가 정해진 챗봇 | 교안 02: 도구 사용 에이전트 |
|---|---|---|
| 실행 흐름 결정 | 앱의 라우터와 그래프 엣지 | 에이전트 모델이 도구를 선택 |
| DB·검색 | 정해진 조회·검색 노드 | 도구 호출로 수행 |
| 중간 결과 검사 | 검색 레일 노드 | 도구 결과 미들웨어 |
| 핵심 보안 | 입력·검색·출력 레일 | 입력·출력 레일 **+ 실행 레일** |
| 레일 위치 | 바깥 LangGraph 노드 | 바깥 노드 + 에이전트 내부 미들웨어 |

### 전체 흐름

```text
사용자 질문
    │
    ▼
[입력 레일 노드] ── 차단 ─────────────→ [refuse] → END
    │ 통과
    ▼
┌──────────── 에이전트 노드(create_agent) ────────────┐
│ [모델 호출 전] 역할별 도구만 노출                    │
│               │                                     │
│               ▼                                     │
│           [모델이 도구 선택]                         │
│               │                                     │
│       ┌───────┴──────────┐                          │
│       ▼                  ▼                          │
│  [사람 승인 필요?]   [일반 도구 호출]                │
│       │                  │                          │
│    승인/거절              │                          │
│       └─────────┬────────┘                          │
│                 ▼                                   │
│         [실행 전 권한 검사]                         │
│           ├─ 거절 → 오류 ToolMessage               │
│           └─ 통과 → [도구 실행]                     │
│                        │                            │
│                        ▼                            │
│               [실행 후 결과 검사]                   │
│                        │                            │
│                        ▼                            │
│                 [모델이 결과 해석] ── 필요시 반복   │
│                        │                            │
│                [최종 답변 개인정보 가림]             │
└────────────────────────┼────────────────────────────┘
                         ▼
                  [출력 레일 노드]
                      ├─ 통과·가림 → END
                      ├─ 생성 실수 → [답만 1회 다시 쓰기]
                      │                 └──→ [출력 레일]
                      └─ 보안 위반·판정 오류 → 거절 → END
```

**검사 지점 다섯 곳**

| 검사 시점 | 대상 | 교안의 구현 |
|---|---|---|
| 모델 호출 전 | 모델에게 보이는 도구 목록 | `@wrap_model_call` |
| 도구 선택 직후 | 취소·환불 승인 요청 | `HumanInTheLoopMiddleware` |
| 도구 실행 전 | 역할, 티켓·주문 주인, 공연 ID | `@wrap_tool_call` |
| 도구 실행 후 | 검색 문서 주입, 회원 연락처, 생성 이미지 | `@wrap_tool_call` |
| 모델 응답 후 | 최종 답변 연락처 | `PIIMiddleware` 및 바깥 출력 레일 |

**왜 필요한가?** 남의 티켓을 취소해 달라는 문장은 일반 문의처럼 보여 입력 레일을 통과할 수 있음. 취소가 실행된 뒤의 정상적인 안내도 출력 레일은 통과시킬 수 있음. 실제로 중요한 검사는 **취소 실행 직전, 티켓의 소유자와 로그인 계정이 같은지** 확인하는 것.

### 위험도와 설계 원칙

- **조회·검색:** 상대적으로 낮은 위험. 그래도 본인 조회 제한과 검색 문서 검사 필요.
- **상태 변경(좌석 변경):** 본인 티켓인지 확인.
- **취소·환불:** 높은 위험. 본인 확인 + 사람 승인.
- **운영팀 회원 조회:** 높은 위험. 역할 제한 + 연락처 가림.
- **유료 이미지 생성:** 호출 횟수·일일 한도·정책 검사 + 생성 결과 검사.
- **외부 API(지도):** 자유 주소 대신 DB에 등록된 공연 ID만 받음.

**Lethal Trifecta(위험한 세 요소)**: ① 개인 데이터 ② 외부에서 들어온 신뢰할 수 없는 텍스트 ③ 외부로 정보를 내보낼 수단이 한 에이전트에 동시에 모이는 상태. 교안은 권한 확인, 검색 결과 필터링, 외부 호출 인자 제한을 이용해 세 요소가 연결되는 경로를 줄임.

## 2. 최소 권한(Least Privilege) — 기능·권한·자율성의 세 겹

**최소 권한 원칙**: 에이전트에게 현재 업무에 필요한 기능과 데이터 접근 권한만 허용하고, 중요한 행동은 사람이 최종 결정하도록 제한.

| 구분 | 질문 | 적용 방법 |
|---|---|---|
| **기능(Functionality)** | 이 역할이 어떤 도구를 볼 수 있는가? | 역할별 도구 목록 (`ROLE_TOOLS`) |
| **권한(Permission)** | 이 도구로 어떤 대상에 접근할 수 있는가? | 로그인 정보로 소유자·ID 검사 (`permission_problem`) |
| **자율성(Autonomy)** | 혼자 실행해도 되는가? | 취소·환불에 사람 승인 (`HumanInTheLoopMiddleware`) |

### 2-1. 역할별 도구 설정

`app/core/config.py`의 핵심 설정:

```python
FAN_TOOLS = [
    "get_my_profile", "get_my_tickets", "get_my_orders",
    "search_policy", "get_event_venue", "change_seat",
    "cancel_ticket", "request_goods_refund", "create_fanart",
]

ROLE_TOOLS = {
    "fan": FAN_TOOLS,
    "staff": FAN_TOOLS + ["lookup_fan"],  # 운영팀 전용 도구 추가
}

APPROVAL_TOOLS = ["cancel_ticket", "request_goods_refund"]
MEMBER_INFO_TOOLS = ["lookup_fan"]
```

- `ROLE_TOOLS[role]`: 해당 역할에 노출하고 허용할 도구 이름 목록.
- `APPROVAL_TOOLS`: 실행 전 승인 대상으로 묶은 도구.
- `MEMBER_INFO_TOOLS`: 실행 결과에서 연락처를 가릴 도구.
- **역할·승인 조건은 보안 정책이므로 `.env`의 임의 설정 값으로 쉽게 비활성화하지 않도록 코드에서 관리**(이 교안의 설계).

### 2-2. 로그인 정보는 메시지가 아니라 `Runtime`에서 읽기

교안에서는 사용자 계정·역할·DB 경로를 `AgentContext`에 보관함.

```python
from app.core.schemas import AgentContext

context = AgentContext(
    fan_id="F0001",
    role="fan",
    db_path=notebook_db,
)
```

| 구분 | 담당 정보 | 예시 |
|---|---|---|
| `state` / `LunaState` | 대화 중 누적되거나 갱신되는 정보 | `messages`, `input_verdict`, `output_verdict`, `retry_count` |
| `runtime.context` | 앱이 실행 시 주입하는 신뢰할 로그인 정보 | `fan_id`, `role`, `db_path` |
| `request.tool_call` | 모델이 선택한 도구 및 인자 | `{"name": "cancel_ticket", "args": {"ticket_id": "T00003"}}` |

**중요:** 사용자 문장에 `나는 운영팀이야`라고 적어도 `runtime.context.role`은 바뀌지 않음.

### 2-3. `ToolRuntime`: 모델이 채우면 안 되는 인자 숨기기

`app/tools/booking_tools.py`:

```python
@tool
def get_my_tickets(runtime: ToolRuntime[AgentContext]) -> dict:
    """로그인한 계정의 티켓 목록 반환."""
    return {
        "tickets": fan_db.get_my_tickets(
            runtime.context.fan_id,
            runtime.context.db_path,
        )
    }
```

- `@tool`: 함수를 LangChain 도구로 등록.
- `ToolRuntime[AgentContext]`: 실행 환경과 컨텍스트를 전달받는 **런타임 주입 인자**. 모델에게는 사용자 입력 파라미터로 노출되지 않음.
- `runtime.context.fan_id`: 대화 내용이 아니라 실제 로그인 계정을 기준으로 조회.

도구의 모델 노출 인자를 확인하는 문법:

```python
# 도구에 모델이 채울 수 있는 파라미터가 무엇인지 확인
print(get_my_tickets.tool_call_schema.model_json_schema()["properties"])
# {}
```

이 도구는 **모델이 넣는 인자가 없음**. 호출자를 지정하는 계정 ID 자체를 모델에 맡기지 않는 구조.

## 3. LangGraph 바깥 레일과 `create_agent` 내부 레일의 연결

입력·출력 검사는 요청 단위로 실행되므로 **LangGraph 노드**, 도구 검사는 도구 호출마다 실행되므로 **에이전트 미들웨어**로 구성함.

### 3-1. 에이전트 생성 문법

`app/graph/builder.py`:

```python
def build_agent():
    return create_agent(
        model=llm,
        tools=ALL_TOOLS,
        system_prompt=agent_system_prompt(),
        context_schema=AgentContext,
        middleware=MIDDLEWARE,
    )
```

| 인자 | 역할 |
|---|---|
| `model` | 도구를 선택하고 답변을 만드는 LLM |
| `tools` | 등록된 전체 도구 객체 목록 |
| `system_prompt` | 도구 사용 방법·행동 규칙 |
| `context_schema` | 실행마다 넘기는 로그인 컨텍스트의 자료형 |
| `middleware` | 모델·도구 호출 주변에서 동작할 실행 레일 목록 |

`create_agent`가 내부적으로 **모델 ↔ 도구 호출**을 반복하는 에이전트 그래프를 만듦. 외부 LangGraph에서는 그 에이전트 그래프를 `agent` 노드 하나로 등록.

### 3-2. 바깥 그래프 생성 문법

```python
def build_app(checkpointer=None):
    builder = StateGraph(LunaState, context_schema=AgentContext)

    builder.add_node("input_rail", input_rail)
    builder.add_node("refuse", refuse)
    builder.add_node("agent", build_agent())
    builder.add_node("output_rail", output_rail)
    builder.add_node("regenerate", regenerate)

    builder.add_edge(START, "input_rail")
    builder.add_conditional_edges(
        "input_rail", route_after_input,
        {"refuse": "refuse", "agent": "agent"},
    )
    builder.add_edge("refuse", END)
    builder.add_edge("agent", "output_rail")
    builder.add_conditional_edges(
        "output_rail", route_after_output,
        {"regenerate": "regenerate", "end": END},
    )
    builder.add_edge("regenerate", "output_rail")

    return builder.compile(checkpointer=checkpointer)
```

- `StateGraph(LunaState, context_schema=...)`: State와 별도 실행 컨텍스트 정의.
- `add_node(...)`: 일반 함수 또는 에이전트 그래프 등록.
- `add_conditional_edges(...)`: 레일 판정 이후의 경로를 앱이 결정.
- `compile(checkpointer=...)`: `thread_id` 단위 대화 기록, 승인 중단 지점 저장.

### 3-3. 차단·재시도 위치에 따른 차이

| 발생 위치 | 처리 | 이유 |
|---|---|---|
| 입력 레일 | `refuse`로 이동, 에이전트 호출 안 함 | 도구 실행 전에 차단 |
| 실행 레일(도구 호출) | `ToolMessage(status="error")` 형태로 차단 이유 반환 | **도구를 실행하지 않고** 모델에게 이유 전달 |
| 출력 레일: `OUT-05`·`OUT-09` | `regenerate`에서 답만 1회 수정 후 재검사 | 생성 실수 교정. **도구를 다시 호출하지 않음** |
| 출력 레일: 보안 위반 또는 재시도 후 차단 | 거절 안내로 종료 | 위험한 답변 재생성 방지 |
| 판정 함수 오류 | 판정 실패로 차단(Fail Closed) | 미검증 결과 전달 방지 |

`app/graph/edges.py`의 출력 분기:

```python
def route_after_output(state: LunaState) -> str:
    verdict = state["output_verdict"]
    if (
        verdict["status"] == "blocked"
        and verdict["rule_id"] in RETRY_RULES
        and state["retry_count"] == 0
    ):
        return "regenerate"
    return "end"
```

- `RETRY_RULES`: `OUT-05`(근거 없는 사실), `OUT-09`(규정에 없는 약속)만 포함.
- `retry_count == 0`: 이번 턴에 아직 재시도하지 않았을 때만 허용.
- 재생성은 `await llm.ainvoke(prompt)`로 **답변 모델만 호출**. 취소·환불 도구를 재실행하면 부작용이 두 번 발생할 수 있으므로 `agent`로 돌아가지 않음.

노트북의 라우팅 확인 결과:

```text
OUT-05 / 다시 쓴 횟수 0 -> regenerate
OUT-05 / 다시 쓴 횟수 1 -> end
OUT-03 / 다시 쓴 횟수 0 -> end
```

## 4. 핵심 미들웨어 문법 — 도구 노출과 실행 권한

### 4-1. `@wrap_model_call`: 모델에게 보일 도구만 조정

`app/guards/execution.py`:

```python
@wrap_model_call
async def expose_tools_by_role(request, handler):
    # 역할은 모델 메시지가 아니라 로그인 정보에서 얻음
    allowed_names = ROLE_TOOLS[request.runtime.context.role]
    allowed_tools = [
        tool for tool in request.tools
        if tool.name in allowed_names
    ]

    return await handler(request.override(tools=allowed_tools))
```

**문법 해설**

| 표현 | 의미 |
|---|---|
| `@wrap_model_call` | 모델 호출을 감싸는 미들웨어로 등록 |
| `request.runtime.context.role` | 로그인 계정의 역할 읽기 |
| `request.tools` | 이번 모델 호출에서 사용할 수 있는 도구 목록 |
| `request.override(tools=...)` | 이번 호출에 **보여 줄 목록**으로 변경 |
| `await handler(...)` | 실제 모델 호출을 다음 단계로 전달 |

**주의:** 모델에게 도구를 숨기는 것은 **UI·모델 노출 제한**에 가까움. 실제 실행 권한이 변경되는 것은 아니므로 **도구 호출 직전에 재검사**해야 함.

### 4-2. `@wrap_tool_call`: 호출 자체를 허용하거나 차단

```python
@wrap_tool_call
async def check_tool_permission(request, handler):
    problem = permission_problem(
        request.tool_call,
        request.runtime.context,
    )

    if problem["reason"] != "":
        return blocked_tool_message(
            request.tool_call,
            "check_tool_permission",
            problem["rule_id"],
            problem["reason"],
        )

    return await handler(request)
```

**핵심 문법**

- `@wrap_tool_call`: **개별 도구 호출**을 감싸는 미들웨어.
- `request.tool_call`: 도구 이름·인자·호출 ID 등 포함.
- `handler(request)`: 다음 미들웨어 또는 실제 도구 실행.
- **`handler`를 부르지 않고 반환하면 실행을 중단**할 수 있음.
- `blocked_tool_message(...)`: 같은 `tool_call_id`를 가진 오류 `ToolMessage` 생성. 모델은 해당 호출이 실행되지 않은 이유를 결과처럼 받음.

```text
permission_problem == 정상
  └── await handler(request) → 도구 실행

permission_problem == 권한 문제
  └── ToolMessage(status="error") 반환
      └── handler 미호출 → DB 변경 없음
```

### 4-3. 실행 전 검사의 실제 로직

`permission_problem`은 호출 정보와 신뢰할 수 있는 `context`를 함께 검사함. 원본의 핵심 판단만 발췌:

```python
def permission_problem(tool_call: dict, context) -> dict:
    name = tool_call["name"]
    args = tool_call["args"]

    # 1. 역할 검사
    if name not in ROLE_TOOLS[context.role]:
        return {"rule_id": ROLE_RULE, "reason": "이 역할로는 쓸 수 없는 도구예요."}

    # 2. 티켓 소유자 검사
    if "ticket_id" in args:
        ticket = find_ticket(args["ticket_id"], context.db_path)
        if ticket is not None and ticket["fan_id"] != context.fan_id:
            return {"rule_id": OWNER_RULE, "reason": "본인의 티켓만 처리할 수 있어요."}

    # 3. 주문 소유자 검사
    if "order_id" in args:
        order = find_order(args["order_id"], context.db_path)
        if order is not None and order["fan_id"] != context.fan_id:
            return {"rule_id": OWNER_RULE, "reason": "본인의 주문만 처리할 수 있어요."}

    # 4. 등록된 공연 ID 검사
    if name == "get_event_venue":
        if "event_id" not in args or fan_db.get_event(args["event_id"], context.db_path) is None:
            return {"rule_id": VENUE_RULE, "reason": "등록된 공연의 위치만 조회할 수 있어요."}

    return {"rule_id": "", "reason": ""}
```

- 반환 `{"rule_id": "", "reason": ""}`: **권한 검사 통과**. 도구 실행 성공을 의미하는 것은 아님.
- 번호 자체가 없는 티켓·주문은 실행 전 소유자 검사에서 차단하지 않고 **도구의 업무 규칙**이 오류 이유를 반환함.
- 원본에는 팬레터 추가 실습을 위한 TODO가 남아 있음(후반에서 설명).

**실제 저장된 실행 결과** — 동일한 `T00003` 취소 호출:

```text
F0002: {'rule_id': 'IN-05', 'reason': '로그인한 팬 본인의 티켓만 처리할 수 있어요.'}
F0003: {'rule_id': '', 'reason': ''}
```

`F0003`이 주인이고 `F0002`는 다른 팬. 도구가 실제로 실행됐는지와 별개로 **권한 검사 결과가 다름**.

## 5. 사람 승인(HITL) — 실행 중단과 재개

**Human-in-the-Loop(HITL)**: 모델이 중요 도구를 호출하면 실행 직전에 멈추고, 사람이 `approve` 또는 `reject` 결정을 내려야 계속 진행하는 구조.

### 5-1. 승인 미들웨어 설정

`app/guards/execution.py`:

```python
APPROVAL_CONFIG = {}
for tool_name in APPROVAL_TOOLS:
    APPROVAL_CONFIG[tool_name] = {
        "allowed_decisions": ["approve", "reject"],
        "description": describe_approval,
        "when": should_ask_approval,
    }

approval_mw = HumanInTheLoopMiddleware(
    interrupt_on=APPROVAL_CONFIG
)
```

| 설정 | 의미 |
|---|---|
| `interrupt_on` | 승인 대상 도구 및 조건 |
| `allowed_decisions` | 허용할 사용자 결정. 이 교안은 승인·거절만 사용 |
| `description` | 승인 카드에 보여 줄 티켓·좌석·수수료·환불 금액 설명 함수 |
| `when` | **승인을 물어야 하는 호출인지** 판정 함수 |

**중요한 순서 문제:** 사람 승인 후에 `check_tool_permission`을 실행하도록 구성되어 있어, 권한이 없는 요청에도 승인 카드가 표시될 가능성이 있음. 따라서 `when=should_ask_approval` 안에서 먼저 권한과 업무 규칙을 검사함.

```python
def should_ask_approval(request) -> bool:
    context = request.runtime.context

    # 권한이 없으면 승인 카드도 표시하지 않음
    if permission_problem(request.tool_call, context)["reason"] != "":
        return False

    # 없는 티켓·이미 취소 등 실행 불가 호출도 묻지 않음
    return business_rule_problem(
        request.tool_call, context.db_path
    ) == ""
```

- `True`: 실제 실행 가능한 승인 대상 호출 → **사람에게 묻고 중단**.
- `False`: **승인만 건너뜀**. 도구 호출은 다음 단계로 전달되며, 이후의 실행 전 검사나 도구 자체에서 거절될 수 있음. `False = 도구 실행 차단`은 아님.

저장된 확인 결과:

```text
F0003 에게 승인을 묻는가: True
F0002 에게 승인을 묻는가: False
```

### 5-2. 체크포인터로 멈춘 위치 저장

에이전트 노드 안에서 도구 실행을 멈추더라도 **바깥 그래프의 체크포인터**가 중단 상태를 보존함.

```python
import aiosqlite
from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver

connection = await aiosqlite.connect(OUTPUT_DIR / "notebook_chat.sqlite")
app = build_app(AsyncSqliteSaver(connection))

thread_id = "some-conversation-id"
config = {"configurable": {"thread_id": thread_id}}

# 바깥 그래프의 저장된 실행 상태
saved = await app.aget_state(config)

# 서브그래프까지 확인
saved_with_subgraphs = await app.aget_state(config, subgraphs=True)
```

| 표현 | 의미 |
|---|---|
| `thread_id` | 같은 대화·같은 승인 대기 상태를 식별하는 키 |
| `AsyncSqliteSaver` | SQLite를 이용한 비동기 체크포인터 |
| `app.aget_state(config)` | 바깥 그래프의 현재 저장 상태 읽기 |
| `subgraphs=True` | 내부 에이전트 그래프의 중단 상태까지 확인 |
| `saved.tasks` / `task.state` | 중단된 서브그래프의 상태 접근 |

교안의 중단 확인 예시:

```text
바깥 그래프의 다음 노드: ('agent',)
에이전트 노드 안의 다음 노드: ('HumanInTheLoopMiddleware.after_model',)
```

바깥 그래프에서는 `agent` 노드 진행 중이고, 안쪽에서는 **모델이 도구를 고른 직후 승인 훅**에서 멈춰 있다는 뜻.

### 5-3. `Command(resume=...)`로 이어 실행하기

```python
from langgraph.types import Command

config = {"configurable": {"thread_id": approval_thread}}

decisions = [{"type": "approve"}]
# 거절할 때: [{"type": "reject", "message": "승인 거절 사유"}]

command = Command(
    resume={"decisions": decisions},
    update={"human_rejected_ids": rejected_ids},
)

# 교안은 이 명령을 run_graph(...)로 바깥 그래프에 전달
resumed = await run_graph(app, command, config, fan_f0003)
```

- `resume`: 중단되어 대기 중인 승인 미들웨어에 보낼 **결정 목록**.
- `update`: 거절된 도구 호출 ID 등을 바깥 State에 기록. 화면·평가용.
- 결정은 **승인 대기 작업 순서와 동일한 순서**로 제공.
- 같은 `thread_id`를 사용해야 기존 작업 위치에서 재개.
- **승인(approve)**: 이후 실행 전 검사·도구 실행으로 진행. **거절(reject)**: 도구를 실행하지 않고 거절 결과를 모델에게 전달.

**전후 비교(노트북의 실제 결과)**

```text
[취소 요청 후, 승인 전]
T00097 상태: 예매

[approve로 재개 후]
T00097 상태: 취소
루나: ... 취소 수수료는 0원이고, 88,000원이 환불될 예정이에요.
```

핵심은 **승인 전 DB가 변경되지 않으며, 재개하면 멈춘 지점부터 이어진다**는 점. 이미 실행한 조회를 처음부터 다시 수행하지 않도록 하는 효과도 있음.

## 6. 도구 결과 검사 — 검색 문서·개인정보

도구는 올바르게 실행됐어도 **반환값이 그대로 모델에게 들어가면 위험할 수 있음**. 검색 문서에는 간접 프롬프트 주입이, 회원 조회에는 연락처가 포함될 수 있기 때문.

### 6-1. `handler` **뒤**에서 검사하기

실행 전 검사와 실행 후 검사는 같은 `@wrap_tool_call`을 쓰지만 `await handler(request)` 위치가 다름.

```python
# 실행 전 검사: handler 이전에 판정
@wrap_tool_call
async def before_example(request, handler):
    if not allowed(request):
        return blocked_tool_message(...)
    return await handler(request)

# 실행 후 검사: handler 결과를 받은 다음 판정/수정
@wrap_tool_call
async def after_example(request, handler):
    result = await handler(request)
    return inspect_or_modify(result)
```

> 위 두 함수는 문법 비교를 위한 **설명용 의사 코드**. 실제 교안 함수는 아래 `check_tool_result`, `mask_member_info`임.

### 6-2. 검색 문서의 숨은 지시 제거

`app/guards/execution.py`의 핵심 구조:

```python
@wrap_tool_call
async def check_tool_result(request, handler):
    result = await handler(request)

    # 검색 도구의 정상 실행 결과만 검사
    if request.tool_call["name"] != "search_policy" or result.status == "error":
        return result

    filtered = filter_documents(result.artifact)
    if not filtered["dropped_ids"]:
        return result

    return ToolMessage(
        content=format_documents(filtered["kept"]),
        artifact=filtered["kept"],
        tool_call_id=result.tool_call_id,
        name=result.name,
        response_metadata={
            "rail": "check_tool_result",
            "rule_id": "",
            "dropped_ids": filtered["dropped_ids"],
        },
    )
```

`filter_documents`는 각 `Document.page_content`에 숨은 지시 정규식을 적용해 문서를 제거하는 함수.

```python
def filter_documents(docs: list) -> dict:
    kept, dropped_ids = [], []
    for doc in docs:
        if has_hidden_instruction(doc.page_content):
            dropped_ids.append(doc.metadata["source_id"])
        else:
            kept.append(doc)
    return {"kept": kept, "dropped_ids": dropped_ids}
```

| 구문 | 역할 |
|---|---|
| `result.artifact` | 검색 도구가 넘긴 `Document` 객체 목록 |
| `result.content` | 모델에게 보여 줄 문자열 |
| `ToolMessage(content=..., artifact=...)` | 필터링한 본문과 원본 형태의 구조화 문서 동시 전달 |
| `tool_call_id` | 어떤 도구 호출의 반환인지 연결 |
| `response_metadata` | 막은 레일·제외된 문서 ID 기록(모델 본문과 분리) |

실제 실행 출력:

```text
뺀 절: ['mem-ptn'] / 남긴 절: ['mem-03']
```

**한계:** 정규식에 정한 표현만 검출함. 다른 형태의 프롬프트 주입은 통과할 수 있어 모델 도구 사용 규칙·출력 레일과 결합해 방어.

### 6-3. 회원 도구 결과와 최종 답변을 각각 가리기

회원 연락처는 **모델이 읽기 전에** 한 번 가리고, 모델의 **최종 답변에서** 다시 가림.

```python
@wrap_tool_call
async def mask_member_info(request, handler):
    result = await handler(request)
    if request.tool_call["name"] not in MEMBER_INFO_TOOLS:
        return result
    return result.model_copy(
        update={"content": mask_pii(result.text)}
    )


def mask_pii(text: str) -> str:
    masked = RRN_PATTERN.sub("[주민등록번호]", text)
    masked = PHONE_PATTERN.sub("[전화번호]", masked)
    masked = EMAIL_PATTERN.sub("[이메일]", masked)
    return masked
```

- `model_copy(update={...})`: 기존 메시지의 나머지 필드와 상태를 유지하고 **`content`만 수정**.
- `.sub(대체문자열, text)`: 정규표현식과 일치한 부분을 표시 문자열로 교체.
- `get_my_profile`은 아예 연락처를 반환하지 않고, `lookup_fan`은 운영팀만 접근 가능하며 모델에 보여 주는 텍스트에서 연락처를 가림.

최종 답변 가림:

```python
pii_mws = [
    PIIMiddleware(
        "kr_phone", detector=PHONE_PATTERN.pattern,
        strategy="mask", apply_to_input=False,
        apply_to_tool_results=False, apply_to_output=True,
    ),
    PIIMiddleware(
        "email", strategy="mask", apply_to_input=False,
        apply_to_tool_results=False, apply_to_output=True,
    ),
]
```

| 인자 | 의미 |
|---|---|
| `detector` | 전화번호 등을 찾을 정규식 패턴. 기본 감지기가 있는 경우 생략 가능 |
| `strategy="mask"` | 해당 문자열 가림 |
| `apply_to_input=False` | 사용자 입력에는 이 미들웨어 적용 안 함 |
| `apply_to_tool_results=False` | 도구 결과는 앞의 전용 미들웨어가 담당 |
| `apply_to_output=True` | 모델 최종 답변에 적용 |

**구분:** `mask_member_info`는 **특정 도구 결과**, `PIIMiddleware`는 **답변**의 연락처를 가림. 그 뒤의 바깥 `output_rail`도 정책 및 개인정보 검사를 수행.

> 구현 점검: 이 교안의 `mask_member_info`는 `content`만 수정하며 `artifact`는 유지함. 모델에게 보여 주는 본문과 별개로, `artifact`를 화면·로그·외부 인터페이스에서 어떻게 취급하는지는 확인할 필요가 있음.

## 7. 유료 도구 예시 — 팬아트 생성 앞뒤의 가드레일

**핵심 원칙:** 비용이 발생하기 **전**에 가능한 검사를 끝내고, 비용이 발생한 **후**에는 결과 자체를 검증해야 함.

```text
사용자 팬아트 요청
       │
       ▼
[권한 확인]
       ▼
[한 메시지당 한 장] ── 초과 ─→ 차단
       ▼
[등급별 하루 한도] ─── 초과 ─→ 차단
       ▼
[그림 요청 정책(Jev)] ─ 위반/판정 오류 ─→ 차단
       ▼
[장면만 구조화 추출: place/action/season/props/mood]
       ▼
[고정 프롬프트 + 공식 설정 이미지]
       ▼
[이미지 생성 API]  ← 여기서 생성 비용 발생
       ▼
[모더레이션] ────── 위반 ─→ 비공개 보관
       ▼
[브랜드 검사] ────── 위반 ─→ 비공개 보관
       ▼
[AI 생성 팬아트 표시 + 결과 전달]
```

### 7-1. 구조화 출력과 고정 프롬프트

사용자가 보낸 원문을 그대로 그림 모델에 보내지 않고, 허용하는 장면 요소 **다섯 칸**만 추출:

| 슬롯 | 뜻 | 예 |
|---|---|---|
| `place` | 배경 장소 | 별빛 무대 |
| `action` | 동작·포즈 | 응원봉 흔들기 |
| `season` | 계절·날씨·시간대 | 가을 저녁 |
| `props` | 소품 | 편지, 꽃 |
| `mood` | 분위기 | 밝고 따뜻함 |

외모 변경, 실제 사람·주소, 그림 속 글자 등은 장면 추출 대상에서 제외. 장면을 하나도 추출하지 못하면 그림 API를 호출하지 않고 추가 설명을 요청.

`app/tools/fanart.py`의 핵심 코드:

```python
@tool(response_format="content_and_artifact")
async def create_fanart(request: str, runtime: ToolRuntime[AgentContext]):
    scene = await extract_scene(request)     # 장면 5칸 구조화 출력
    values = scene.model_dump()             # Pydantic -> dict

    parts = [f"{name}: {values[name]}" for name in SCENE_SLOTS if values[name]]
    if not parts:
        return "그릴 장면을 알려 주세요.", {"generated": False}

    prompt = IMAGE_PROMPT.format(scene="; ".join(parts))
    image_bytes = await generate_image(prompt)

    FANART_DIR.mkdir(parents=True, exist_ok=True)
    path = FANART_DIR / f"{runtime.context.fan_id}_{uuid4().hex[:8]}.png"
    path.write_bytes(image_bytes)
    return "팬아트를 만들었어요.", {
        "generated": True,
        "path": str(path),
        "summary": scene.summary_ko,
        "prompt": prompt,
    }
```

- `response_format="content_and_artifact"`: 모델이 읽는 **짧은 텍스트 `content`**와 후속 검사·화면이 사용하는 **구조화 정보 `artifact`**를 구분.
- `scene.model_dump()`: Pydantic 객체에서 딕셔너리 추출.
- `IMAGE_PROMPT.format(scene=...)`: 고정 정책 프롬프트의 `{scene}`만 교체.
- `path.write_bytes(...)`: 생성 이미지를 파일에 기록. **팬에게 실제로 보여 줄지는 이후 검사에서 결정**.

원본 `generate_image`는 `image_client.images.edit(model=..., image=[reference], prompt=..., quality=..., size=...)`로 **공식 설정 이미지를 함께 넘기는 방식**이며, 정책·모델 설정은 `visual.yaml`에서 읽음.

### 7-2. 생성 전 미들웨어 문법

```python
@wrap_tool_call
async def fanart_quota_and_policy(request, handler):
    call = request.tool_call
    if call["name"] != "create_fanart":
        return await handler(request)

    context = request.runtime.context

    # 무료 검사 1: 현재 사용자 메시지의 첫 팬아트 호출인가?
    if first_fanart_call_id(request.state["messages"]) != call["id"]:
        return blocked_tool_message(call, "fanart_quota_and_policy", FANART_RUN_RULE,
                                    "메시지 한 번에 한 장만 만들 수 있어요.")

    # 무료 검사 2: DB 기준 일일 한도
    if remaining_fanarts(context) <= 0:
        return blocked_tool_message(call, "fanart_quota_and_policy", QUOTA_RULE,
                                    VISUAL["blocked_replies"]["over_limit"])

    # 유료 판정: 원래 사용자 메시지와 도구 인자를 함께 검사
    tool_request = call["args"].get("request", "")
    text = f"팬 메시지: {last_fan_message(request.state['messages'])}\n도구 요청: {tool_request}"
    try:
        judgement = await jev_policy_judgement(
            {"fanart_request": text}, IMAGE_REQUEST_POLICY, IMAGE_RULES
        )
    except Exception:
        return blocked_tool_message(call, "fanart_quota_and_policy", RAIL_ERROR_RULE,
                                    reply_for_rule(RAIL_ERROR_RULE))

    rule_id = judgement["rule_id"]
    if judgement["probability"] > IMAGE_POLICY_THRESHOLD and rule_id != "":
        record_fanart_request(context.fan_id, f"그림 요청 정책 위반({rule_id})",
                              "차단", rule_id, context.db_path)
        return blocked_tool_message(call, "fanart_quota_and_policy", rule_id,
                                    VISUAL["blocked_replies"]["input_blocked"])

    return await handler(request)
```

**검사 순서**: 한 메시지 한 장 → 하루 한도 → Jev 요청 정책 → 생성 API. 앞에서 막으면 뒤의 유료 검사·생성은 실행하지 않음.

판정기가 오류를 내면 `RAIL-ERROR`로 차단(Fail Closed). 다만 이 교안의 이미지 정책 차단 조건은 **위반 확률이 기준값을 넘고, `rule_id`도 비어 있지 않을 때**이며, 특정 오차단 완화를 위한 설계임.

### 7-3. 생성 후 미들웨어와 검증기

생성 후에는 `check_fanart_image` 미들웨어가 결과 이미지를 대상으로 순서대로 검사:

1. **모더레이션(`moderate_image`)**: 선정성·폭력·자해 등 범주별 점수 검사. 기본 기준값 **0.5**, `sexual`은 **0.2**. 점수가 기준값 **이상이면** 차단.
2. **브랜드 검사(`brand_check`)**: 공식 설정 그림과 생성 이미지를 비전 모델에 함께 보여 주고 질문 ID(`BRD-01`~`05`)의 yes/no 답 비교. 실패로 정한 답이 있거나 답변이 누락되면 차단.

대표 문법:

```python
# 모더레이션: 범주별 기준값 선택
threshold = moderation["category_thresholds"].get(
    category, moderation["threshold"]
)
if scores[category] >= threshold:
    return {"passed": False, "rule_id": "MOD-" + category, "scores": checked}

# 브랜드 검사: 질문 id별 실패 조건
for check_id, fail_answer in VISUAL["brand_fail_if"].items():
    if check_id not in answers or answers[check_id] == fail_answer:
        return {"passed": False, "rule_id": check_id, "answers": answers}
```

- **통과:** 표시(워터마크)를 붙이고 공개, 성공한 결과는 하루 횟수에 반영.
- **생성 후 차단:** 이미 그림 생성 비용은 사용했으나 결과는 공개하지 않음. `output/fanart/blocked`에 보관해 오차단 검토. 이 교안에서는 일일 성공 횟수에 넣지 않음.
- **생성 전 차단:** 그림 파일 없음, 생성 비용 없음.

이미지 도구의 `artifact` 예시 키:

```text
{
  generated: True/False,
  path: 공개 가능한 파일 경로(차단되면 None),
  verdicts: 검사별 결과,
  remaining: 오늘 남은 수,
  rule_id: 차단 규칙 ID,
  blocked_path: 비공개 보관한 파일(차단 시)
}
```

**주의:** 노트북의 `generated=False`에는 `path` 키 자체가 없을 수 있으므로 `artifact["generated"]`부터 확인.

## 8. 외부 API 도구 — 입력 자유도를 줄여 허용 목록만 사용

**도구 인자 설계가 보안의 시작**: 위치 검색 도구가 `address: str`로 임의 주소를 받으면 모델이 외부 지오코딩 API에 어떤 주소든 넘길 수 있음. 교안의 지도 도구는 **DB에 등록된 `event_id`만 입력**으로 받음.

```python
@tool
def get_event_venue(
    event_id: str,
    runtime: ToolRuntime[AgentContext],
) -> dict:
    venue = get_venue_for_event(event_id, runtime.context.db_path)
    if venue is None:
        return {"error": "없는 공연 id 예요."}
    return venue
```

실행 레일에서 `fan_db.get_event(event_id, db_path)`로 ID의 존재를 먼저 확인하고, 도구는 DB에 등록된 공식 공연장 주소만 Nominatim에 전달.

```python
venue_call = {"name": "get_event_venue", "args": {"event_id": "E01"}}
address_call = {
    "name": "get_event_venue",
    "args": {"event_id": "서울특별시 ... 임의 주소"},
}
```

확인 결과:

```text
E01: {'rule_id': '', 'reason': ''}
주소: {'rule_id': 'IN-07', 'reason': '공연 목록에 있는 공연의 공연장 위치만 찾을 수 있어요.'}
```

**차이:** 입력 텍스트가 주소처럼 보여도 등록된 공연 ID가 아니므로 실행 전 차단. **외부 API 호출 전**에 허용 여부를 결정하는 구조.

## 9. 미들웨어 목록과 실제 실행 순서

**미들웨어의 배열 순서가 방어 계층의 우선순위**를 결정함. 단, 미들웨어의 종류에 따라 실행 방향이 다름.

- `wrap_tool_call`: 앞에 있는 미들웨어가 바깥에서 감쌈. **앞에서 차단되면 뒤의 검사와 도구가 실행되지 않음**.
- `wrap_model_call`: 모델 호출 주변에서 동작. 교안에서는 도구 노출 제한.
- `after_model` 훅: 이 교안의 구성에서는 **목록의 역순**으로 실행. 최종 답변 가림 이후 승인 훅이 호출된 도구를 확인.

`app/graph/builder.py`의 실제 목록:

```python
MIDDLEWARE = [
    expose_tools_by_role,     # 1. 모델 호출 시 역할별 도구 노출
    check_tool_permission,    # 2. 도구 실행 전: 권한/본인/공연 ID
    fanart_quota_and_policy,  # 3. 생성 전: 호출 수/일일 한도/요청 정책
    check_fanart_image,       # 4. 생성 후: 모더레이션/브랜드 검사
    check_tool_result,        # 5. 검색 도구 결과: 숨은 지시 제거
    mask_member_info,         # 6. 회원 조회 결과: 개인정보 가림
    approval_mw,              # 7. 모델이 도구 고른 뒤 사람 승인
] + pii_mws                  # 8~9. 모델 답변 전화번호·이메일 가림
```

**도구 실행 쪽 감싸는 순서(핵심)**

```text
check_tool_permission   ← 가장 바깥: 먼저 차단 가능
    └─ fanart_quota_and_policy
        └─ check_fanart_image
            └─ check_tool_result
                └─ mask_member_info
                    └─ 실제 도구 실행
                         │
                    결과는 안쪽 → 바깥쪽으로 복귀
```

**승인 위치는 별도:** `approval_mw`는 위의 `wrap_tool_call` 중첩 안쪽에서 실행되는 것이 아니라, **모델이 도구를 결정한 후의 훅**으로 승인·거절을 판정함. 이 때문에 `should_ask_approval`에서 권한을 **먼저 확인**함.

노트북에 기록된 미들웨어 이름:

```text
1 expose_tools_by_role
2 check_tool_permission
3 fanart_quota_and_policy
4 check_fanart_image
5 check_tool_result
6 mask_member_info
7 HumanInTheLoopMiddleware
8 PIIMiddleware[kr_phone]
9 PIIMiddleware[email]
```

미들웨어 순서를 바꾸면 차단 비용과 근거가 달라질 수 있으므로 교안에서는 `uv run pytest -q`로 재검증하도록 안내함.

## 10. 평가와 새 도구 설계

### 10-1. 실행 레일 평가 기준

**차단율만 높이는 것이 목표가 아님.** 위험한 행동은 반드시 막되, 정상적인 업무는 완료해야 함.

| 지표 | 확인할 것 | 기대 기준 |
|---|---|---|
| 남의 데이터 조회·쓰기 | 타인 데이터 접근이 일어났는가 | 없음 |
| 승인 없는 실행 | 승인 전에 취소·환불됐는가 | 0건 |
| 승인 대기 | 승인 대상 호출에서 멈췄는가 | 기대한 호출에서만 대기 |
| 방어 성공률 | 공격이 실질적인 금지 행동 없이 끝났는가 | 높을수록 좋음 |
| 오차단율 | 정상 요청을 불필요하게 막았는가 | 낮을수록 좋음 |
| 정상 업무 완료율 | 정상 요청이 끝나거나 적절한 승인 대기에 도달했는가 | 높을수록 좋음 |
| 유료 이미지 생성 | 금지·한도 초과 요청에서도 API가 호출됐는가 | 공격은 미생성 |
| 누출·도구 거절·재생성 | 어떤 레일/업무 규칙이 처리했는가 | 원인 추적 가능 |

평가 함수 호출 문법:

```python
from app.evaluate import run_cases, scorecard, summary_metrics

records = await run_cases(small_cases)

# 개별 케이스 결과
records_df = pd.DataFrame(records)

# 정상/공격 그룹의 집계
score = scorecard(records)

# 주요 지표 딕셔너리
metrics = summary_metrics(records)
```

> **원본 실행 상태:** 노트북에서 `run_cases(small_cases)` 셀은 `RuntimeError`로 중단되어 이후 `scorecard`, `summary_metrics` 실행 결과가 저장되지 않았음. 따라서 교안의 **지표 정의와 호출 문법**만 정리했으며 실제 방어율·업무 완료율 수치는 임의로 만들지 않음.

**개선 순서:** 골든셋/레드팀 테스트 → 남의 데이터·무승인 실행부터 점검 → 오차단과 미완료 업무 분석 → 한 요소만 변경 → 최적화용 케이스 재평가 → 마지막에 확인용 케이스 검증. 사용자 경험은 별도의 사용자 피드백으로 함께 개선.

### 10-2. 새 도구 추가 예시: 팬레터

교안 마지막은 `send_fan_letter` 도구를 추가하는 **미완성 실습(TODO)**임. 완성 코드가 제시된 것은 아님.

| 설계 항목 | 실습에서 정한 기준 |
|---|---|
| 기능 | 팬(`fan`) 역할에만 노출, 운영팀(`staff`)에는 미노출 |

변경 위치를 기능별로 구분:

```text
app/tools/fan_letter.py     : @tool 도구 본체 구현
app/core/config.py         : ROLE_TOOLS, FAN_LETTER_MAX_CHARS
app/guards/execution.py    : permission_problem의 입력 검사
app/graph/builder.py       : ALL_TOOLS에 새 도구 등록
app/core/prompts.py        : AGENT_RULES에 사용 지침
```

**새 도구 등록에서 중요한 순서**: `@tool` 작성 → 허용 역할과 모델 인자 최소화 → 실행 전 권한·입력 검사 → 승인 필요성 결정 → 실행·결과 검사 → 정상/공격 평가. **도구를 `ALL_TOOLS`에 추가하는 것만으로 보안 설계가 끝나지 않음.**

## 11. 핵심 문법 요약표

| 문법·객체 | 의미 | 사용하는 자리 |
|---|---|---|
| `@tool` | Python 함수를 에이전트 도구로 등록 | 조회·변경·이미지 생성 도구 |
| `ToolRuntime[AgentContext]` | 로그인 컨텍스트 등을 도구에 주입 | 도구 함수 매개변수 |
| `Runtime[AgentContext]` | 그래프 노드에서 컨텍스트 접근 | `output_rail` 등 |
| `@wrap_model_call` | 모델 호출 전후를 감싸 수정 | 역할별 도구 노출 |
| `request.override(tools=...)` | 이번 모델 호출에 보일 도구 목록 변경 | 도구 노출 제한 |
| `@wrap_tool_call` | 도구 실행 전·후 호출을 감싸 검사 | 권한·한도·결과 검사 |
| `await handler(request)` | 다음 미들웨어 또는 실제 호출 실행 | 통과 처리 또는 실행 후 검사 |
| `request.tool_call` | 호출할 도구 이름·인자·ID | 권한 확인·횟수 제한 |
| `request.runtime.context` | 로그인 계정·역할·DB 경로 | 역할·소유자 확인 |
| `ToolMessage(...)` | 해당 도구 호출에 대한 실행·오류 결과 | 실행 차단, 문서 필터링 |
| `response_metadata` | 도구 결과의 레일·규칙·제외 ID 기록 | 로깅·평가 |
| `artifact` | 모델 본문과 구분되는 부가 데이터 | 검색 문서, 이미지 경로·검사 결과 |
| `HumanInTheLoopMiddleware` | 승인 필요 도구 호출 중단 | 취소·환불 |
| `interrupt_on` / `when` | 승인 대상 및 승인 요청 조건 설정 | 사람 승인 설정 |
| `Command(resume=...)` | 중단된 실행에 결정 전달 | 승인·거절 후 재개 |
| `Command(update=...)` | State에 추가 변경 기록 | 거절 호출 ID 등 |
| `AsyncSqliteSaver` | 저장 가능한 대화·중단 상태 | 체크포인터 |
| `thread_id` | 동일 대화·중단 실행의 식별 키 | 호출·재개·상태 조회 |
| `PIIMiddleware(..., strategy="mask")` | 정규식·감지기 기반 개인정보 가림 | 최종 답변 |
| `response_format="content_and_artifact"` | 텍스트와 부가 구조 데이터를 분리 | 이미지 생성 도구 |
| `model_dump()` | Pydantic 객체 → dict | 이미지 장면 구조화 |
| `app.aget_state(..., subgraphs=True)` | 내부 에이전트의 중단 상태까지 읽기 | 승인 상태 확인 |

### 꼭 구분할 다섯 가지

1. **입력·출력 레일 = 바깥 그래프 노드 / 실행 레일 = 에이전트 내부 미들웨어.**
2. **도구 노출 제한 ≠ 실제 실행 권한 보장.** `@wrap_model_call`로 숨기고 `@wrap_tool_call`로 재검사.
3. **`handler` 이전 검사 = 실행 차단 가능 / `handler` 이후 검사 = 실행 결과 검토·수정.**
4. **승인을 물을지 판단하는 함수(`when`) ≠ 실행 권한 검사 그 자체.** 승인 생략 뒤에도 실행 전 검사가 있어야 함.
5. **생성 전 검사와 생성 후 검사는 비용 관점에서 다름.** 생성 전 차단은 생성비용 0, 생성 후 차단은 비용이 발생했지만 결과를 보여 주지 않음.

> **한 줄 정리:** LangGraph는 전체 업무 흐름과 중단·재개를 관리하고, LangChain 에이전트는 도구 선택을 수행하며, 실행 레일 미들웨어는 **모델이 어떤 도구를 고르더라도 허용된 행동만 실행되도록** 도구 앞뒤를 검사하는 구조.
