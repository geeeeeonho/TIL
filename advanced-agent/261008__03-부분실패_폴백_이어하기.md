# LangGraph 운영 복구: 부분 실패 · 폴백 · 이어 하기

> 멀티에이전트 실행에서 일부 작업이 실패했을 때 **전체를 멈출지, 축소해서 계속할지, 다른 경로로 대체할지, 실패 지점부터 다시 시작할지**를 제어하는 방법 정리.

---

# 1. 전체 흐름

이번 내용은 실패를 한 종류로 보지 않고 **실패 범위와 복구 방식**을 나눠 처리하는 것이 핵심이다.

```text
작업 실행
   │
   ├─ 병렬 작업 하나만 실패
   │      ↓
   │   실패 격리
   │      ↓
   │   findings / failures 기록
   │      ↓
   │   진행 판단
   │      ├─ completed → 정상 진행
   │      ├─ degraded  → 일부 누락을 밝히고 진행
   │      ├─ held      → 발행 보류
   │      └─ failed    → 중단
   │
   ├─ 단독 노드가 재시도까지 실패
   │      ↓
   │   error_handler
   │      ↓
   │   폴백 노드로 이동
   │
   └─ 실행이 중간에 멈춤
          ↓
       checkpoint
          ↓
       invoke(None, config)
          ↓
       실패 지점부터 이어 하기
```

이어 하기나 fork에서는 같은 노드가 다시 실행될 수 있으므로, 게시·메일·결제처럼 외부 상태를 바꾸는 작업에는 **멱등성**도 같이 고려해야 한다.

# 2. 병렬 분기의 부분 실패

## 2-1. 왜 병렬 작업 하나의 실패가 전체 실패가 되는가

`Send`로 여러 작업을 동시에 실행하면 같은 **superstep**에서 처리된다.

```text
planner
   ↓
┌───────────────┐
│ researcher    │ → prices
│ researcher    │ → news
│ researcher    │ → reviews
└───────────────┘
   ↓
synthesizer
   ↓
writer
```

문제 상황:

```text
prices  → 성공
news    → 성공
reviews → KeyError
```

격리하지 않으면:

```text
reviews의 예외
   ↓
같은 단계 전체 실패
   ↓
prices / news 결과도 반영되지 않음
   ↓
synthesizer 실행 안 됨
   ↓
브리핑 없음
```

즉, **병렬 작업 하나의 예외가 팀 전체 실행을 막을 수 있음**.

# 3. 병렬 결과를 모으는 State

작업별 성공 결과와 실패 결과를 따로 저장한다.

```python
def merge_results(old: dict, new: dict) -> dict:
    merged = dict(old)
    merged.update(new)
    return merged
```

```python
class BriefingState(TypedDict):
    week: str
    tasks: list[str]

    findings: Annotated[
        dict[str, str],
        merge_results
    ]

    failures: Annotated[
        dict[str, str],
        merge_results
    ]

    summary: str
    briefing: str
    post_id: str
```

구조:

```text
findings
{
    "prices": "...",
    "news": "..."
}

failures
{
    "reviews": "KeyError: 'reviews'"
}
```

`findings`와 `failures`를 분리하는 이유:

- 성공 자료는 이후 종합에 사용
- 실패 자료는 누락 사실을 표시
- 어떤 작업이 실패했는지 trace와 최종 State에 남김
- 실패한 자료를 LLM이 추측하지 않게 함

# 4. `Send`로 조사 작업 분배

```python
from langgraph.types import Send
```

```python
def planner(state: BriefingState):

        "tasks": [

            "reviews",
```

작업마다 `researcher`로 보냄.

```python
def assign_research(state: BriefingState):
    return [
        Send(
            "researcher",
            {"source": source},
        )
        for source in state["tasks"]
    ]
```

```text
planner
   │
   ├─ Send("researcher", {"source": "prices"})
   ├─ Send("researcher", {"source": "news"})
   └─ Send("researcher", {"source": "reviews"})
```

# 6. 실패 격리: `researcher_safe`

영구 오류를 **예외로 끝내지 않고 실패 결과로 변환**한다.

```python
async def researcher_safe(payload):
    source = payload["source"]

    try:
        items = await fetch_source(source)

    except ConnectionError:
        # 일시 오류
        # RetryPolicy가 처리하도록 다시 올림
        raise

    except Exception as error:
        # 영구 오류
        # 실패 자체를 정상 결과로 기록
        return {
            "failures": {
                source:
                f"{type(error).__name__}: {error}"
            }
        }

    memo = await summary_chain.ainvoke({
        "source": SOURCE_NAMES[source],
        "our_product": OUR_PRODUCT,
        "items": format_items(items),
    })

    return {
        "findings": {
            source: memo.text
        }
    }
```

핵심 구분:

| 예외 | 처리 |
|---|---|
| `ConnectionError` | 다시 `raise` → `RetryPolicy` |
| 그 밖의 영구 오류 | `failures`에 기록 후 정상 반환 |

```text
일시 오류
→ 다시 시도하면 성공 가능
→ RetryPolicy

영구 오류
→ 다시 해도 동일한 실패
→ failures에 기록
```

# 8. 실패 뒤에는 진행 여부도 판단해야 함

실패를 격리했다고 해서 **항상 다음 단계로 가면 안 됨**.

예:

```text
고객 리뷰 실패
→ 일부 정보만 없음
→ 브리핑 작성 가능
```

반면:

```text
이번 주 가격 실패
→ 시장 브리핑의 핵심 정보 없음
→ 발행 보류 필요
```

따라서 자료를 필수/선택으로 나눈다.

| 자료 | 구분 |
|---|---|
| 경쟁사 가격 `prices` | 필수 |
| 업계 뉴스 `news` | 선택 |
| 고객 리뷰 `reviews` | 선택 |

---

# 9. 진행 결과 `outcome`

```python
class DecisionState(BriefingState):
    outcome: str
    outcome_reason: str
```

교안의 네 가지 결과:

| 결과 | 의미 | 다음 처리 |
|---|---|---|
| `completed` | 실패 없음 | 정상 진행 |
| `degraded` | 선택 자료만 실패 | 누락을 밝히고 진행 |
| `held` | 필수 자료 실패 | 발행 보류 |
| `failed` | 모든 조사 실패 | 중단 |

```text
조사 완료
   ↓
decide_after_research
   │
   ├─ completed ─→ synthesizer → writer
   ├─ degraded  ─→ synthesizer → writer
   ├─ held      ─→ END
   └─ failed    ─→ END
```

---

# 10. `decide_after_research`

```python
REQUIRED_SOURCES = ["prices"]
```

```python
def decide_after_research(
    state: DecisionState,
) -> Command[
    Literal["synthesizer", "__end__"]
]:

    failures = state["failures"]

    # 1. 실패 없음
    if not failures:
        return Command(
            goto="synthesizer",
            update={
                "outcome": "completed",
                "outcome_reason":
                    "실패한 조사 없음",
            },
        )

    # 2. 모든 조사 실패
    if len(failures) == len(state["tasks"]):
        return Command(
            goto=END,
            update={
                "outcome": "failed",
                "outcome_reason":
                    f"모든 조사 실패: "
                    f"{failure_note(failures)}",
            },
        )

    # 3. 필수 자료 실패
    for source in REQUIRED_SOURCES:
        if source in failures:
            return Command(
                goto=END,
                update={
                    "outcome": "held",
                    "outcome_reason":
                        "필수 자료 실패: "
                        f"{SOURCE_NAMES[source]}, "
                        "발행 보류 후 사람 확인",
                },
            )

    # 4. 선택 자료만 실패
    return Command(
        goto="synthesizer",
        update={
            "outcome": "degraded",
            "outcome_reason":
                "선택 자료 실패: "
                f"{failure_note(failures)}, "
                "누락을 밝히고 진행",
        },
    )
```

### 판단 순서 주의

`모든 조사 실패`를 `필수 자료 실패`보다 먼저 검사한다.

```text
모든 조사 실패
→ prices도 당연히 failures에 있음
```

필수 자료부터 검사하면 실제로는 `failed`여야 하는 상황이 `held`로 분류될 수 있음.

---

# 11. `held`와 `failed`는 예외가 아님

중요한 점:

```text
held
failed
```

둘 다 **정상 종료**다.

즉:

```text
예외 없음
≠
성공적으로 업무 완료
```

실행 후 반드시 `outcome`을 확인해야 한다.

```python
print(result["outcome"])
print(result["outcome_reason"])
```

예:

```text
outcome: held

이유:
필수 자료 실패:
경쟁사 가격,
발행 보류 후 사람 확인
```

이 경우 `synthesizer`와 `writer`는 실행하지 않으므로:

```python
summary == ""
briefing == ""
```

상태로 끝남.

# 12. 폴백 경로

부분 실패와 별개로 **하나의 노드 자체가 재시도를 모두 소진한 경우**에는 대체 경로로 보낼 수 있다.

```text
이번 주 가격 수집
   ↓
실패
   ↓
RetryPolicy 재시도
   ↓
여전히 실패
   ↓
error_handler
   ↓
지난주 가격 사용
   ↓
보고 작성
```

LangGraph 1.2 교안 기준:

```python
add_node(
    ...,
    error_handler=handler,
)
```

# 13. `error_handler`

```python
from langgraph.errors import NodeError
```

```python
def price_fallback(
    state: PriceReportState,
    error: NodeError,
) -> Command[Literal["use_last_week"]]:

    note = (
        f"{error.node} 실패"
        f"({type(error.error).__name__}: "
        f"{error.error}), "
        "지난주 가격 사용"
    )

    return Command(
        goto="use_last_week",
        update={
            "price_note": note
        },
    )
```

`NodeError`에서 확인할 수 있는 값:

```text
error.node
→ 실패한 노드 이름

error.error
→ 실제 발생한 예외
```

# 15. `error_handler`에서는 `Command(goto=...)`가 중요

잘못된 예:

```python
def price_fallback_dict(
    state,
    error,
):
    return {
        "price_note":
            "collect_this_week 실패, "
            "지난주 가격 사용"
    }
```

State 값은 바뀌지만 다음 노드를 지정하지 않음.

```text
collect_this_week 실패
       ↓
error_handler
       ↓
price_note 수정
       ↓
끝
```

따라서:

```python
report == ""
```

가 됨.

### 이유

핸들러가 실행되면 원래 고정 엣지:

```text
collect_this_week
→ make_report
```

는 사용되지 않음.

따라서 폴백을 계속 실행하려면:

```python
return Command(
    goto="use_last_week",
    update={...},
)
```

처럼 다음 노드를 명시해야 한다.

# 16. 부분 실패와 `error_handler` 차이

교안의 구분:

```text
병렬 분기
→ 노드 내부 try/except
→ failures 기록
```

```text
단독 노드
→ RetryPolicy
→ error_handler
→ fallback
```

교안에서 사용하는 LangGraph 1.2.9 기준으로는 같은 단계에 다른 작업이 있는 병렬 상황에서 `error_handler`를 쓰면 핸들러 실행 후에도 예외가 다시 올라올 수 있으므로, 병렬 분기는 `researcher_safe` 방식으로 처리함.

# 17. 체크포인트로 실패 지점부터 이어 하기

**이어 하기(resume)**는 실패한 전체 실행을 처음부터 다시 돌리지 않고, 저장된 상태에서 실패한 지점부터 계속 실행하는 방식.

필요 조건:

```text
checkpointer
+
같은 thread_id
```

컴파일:

```python
from langgraph.checkpoint.memory import InMemorySaver
```

```python
publish_app = builder.compile(
    checkpointer=InMemorySaver()
)
```

```python
resumed = await publish_app.ainvoke(
```

# 21. `thread_id`와 Langfuse Session

이어 하기에서는 두 가지 식별자를 구분한다.

```text
thread_id
→ LangGraph checkpoint에서
  이전 실행 상태를 찾는 기준
```

```text
langfuse_session_id
→ Langfuse에서
  관련 trace들을 한 세션으로 묶는 기준
```

같은 값을 사용할 수 있지만 역할은 다름.

```text
같은 thread_id
→ 같은 실행 상태에서 이어 하기

같은 langfuse_session_id
→ Langfuse 화면에서 실패 실행과 재개 실행을 같이 보기
```

---

# 22. 이어 하기는 실패 노드를 다시 실행함

중요한 문제:

```text
게시 요청
   ↓
게시판에는 실제 글 등록 완료
   ↓
응답만 끊김
   ↓
LangGraph는 실패로 판단
```

이후 이어 하기:

```text
publisher 다시 실행
   ↓
같은 글 다시 게시
```

즉 외부 시스템에는 중복 작업이 생길 수 있음.

```text
게시 2번
메일 2번
결제 2번
```

이 문제를 막는 것이 **멱등성**.

---

# 23. 멱등성

멱등성:

> 같은 요청을 여러 번 실행해도 최종 결과가 한 번 실행한 것과 같도록 만드는 성질.

게시 예:

```python
def publish_once(state: PostState):
    key = f"weekly-{state['week']}"

    return {
        "post_id":
            post_briefing(
                state["briefing"],
                key=key,
            )
    }
```

게시 API는 동일 key가 이미 있으면 새 글을 만들지 않고 기존 글 번호를 반환.

```text
첫 요청
key = weekly-2026-41
→ POST-001 생성

응답 끊김
→ LangGraph는 실패로 인식

이어 하기
key = weekly-2026-41
→ 이미 존재함
→ POST-001 반환
→ 새 글 생성 X
```

---

# 24. 멱등 키가 없으면

```text
1차 publisher
→ 글 생성
→ 응답 끊김

이어 하기
→ publisher 다시 실행
→ 글 또 생성
```

결과:

```text
post_briefing 호출 수 = 2
게시판 글 수 = 2
```

멱등 키 사용:

```text
post_briefing 호출 수 = 2
게시판 글 수 = 1
```

### 핵심

체크포인터가 보장하는 것:

```text
성공한 노드를 다시 실행하지 않음
```

체크포인터가 보장하지 못하는 것:

```text
실패한 노드 안에서
이미 발생한 외부 부작용
```

따라서 부작용 노드가 다시 실행될 수 있다면 멱등 키 필요.

---

# 25. 멱등 키 설계 예

주간 브리핑:

```python
key = f"weekly-{week}"
```

버전이 필요하면:

```text
weekly-2026-41-v1
weekly-2026-41-v2
```

실행 단위로 구분하고 싶다면 `thread_id` 등을 포함할 수도 있음.

# 26. 과거 결정에서 다시 실행: Fork

이어 하기는 **실패한 곳부터 계속 실행**하는 것.

Fork는:

```text
과거의 특정 체크포인트로 돌아감
   ↓
State 값 일부를 수정
   ↓
새 실행 경로를 만듦
```

예:

```text
route_channel
   ↓
channel = email_all   ← 잘못된 결정
   ↓
send_email_all
```

과거 결정 수정:

```text
route_channel 직후 checkpoint
   ↓
channel = board 로 수정
   ↓
post_board
```

기존 실행은 지워지지 않고 새 갈래가 생성된다.

---

# 27. Fork 전체 흐름

```text
1. get_state_history()
        ↓
2. 잘못된 결정 직후 checkpoint 찾기
        ↓
3. update_state()
        ↓
4. 수정된 checkpoint 생성
        ↓
5. invoke(None, 새 config)
        ↓
6. 해당 지점 이후만 새 경로로 실행
```

---

# 28. 결정은 State에 남겨야 수정하기 쉬움

예:

```python
class DeliveryState(TypedDict):
    briefing: str
    channel: str
    sent: Annotated[
        list[str],
        operator.add
    ]
```

결정 노드:

```python
def route_channel(
    state: DeliveryState
):
    return {
        "channel": "email_all"
    }
```

라우팅 함수:

```python
def pick_channel(
    state: DeliveryState
):
    if state["channel"] == "board":
        return "post_board"

    return "send_email_all"
```

연결:

```python
builder.add_conditional_edges(
    "route_channel",
    pick_channel,
    [
        "post_board",
        "send_email_all",
    ],
)
```

이 구조에서는 `channel` 값만 수정하면 조건부 엣지가 다시 계산될 수 있음.

# 29. 과거 체크포인트 찾기

```python
for snapshot in delivery_app.get_state_history(
    fork_config
):
    print(
        snapshot.metadata["step"],
        snapshot.metadata["source"],
        snapshot.next,
        snapshot.values.get("channel"),
    )
```

기록은 최신부터 반환됨.

`metadata["source"]`:

| 값 | 의미 |
|---|---|
| `input` | 시작 입력 |
| `loop` | 노드 실행 |
| `update` | `update_state()` |

잘못된 결정 직후:

```python
wrong_snapshot = None

for snapshot in delivery_app.get_state_history(
    fork_config
):
    if snapshot.next == (
        "send_email_all",
    ):
        wrong_snapshot = snapshot
        break
```

---

# 30. `update_state()`

잘못된 channel만 수정.

```python
branch_config = (
    delivery_app.update_state(
        wrong_snapshot.config,
        {
            "channel": "board"
        },
        as_node="route_channel",
    )
)
```

`as_node` 의미:

```text
이 값을
route_channel 노드가 쓴 것으로 처리
```

따라서 `route_channel` 뒤 조건부 엣지가 다시 계산됨.

```text
수정 전
next = send_email_all

수정 후
next = post_board
```

```python
{
```

```text

```

새 갈래:

```text

→ post_board
```

# 32. Fork의 중요한 한계

Fork는 **State와 실행 경로를 다시 만드는 기능**이지 외부 시스템을 되돌리는 기능이 아님.

예:

```text
원래 갈래
→ 전체 메일 발송 완료

fork
→ board로 다시 실행
```

이미 나간 전체 메일:

```text
취소되지 않음
```

즉:

```text
State 되돌리기
≠
외부 부작용 되돌리기
```

또 fork 지점 뒤의 노드는 다시 실행될 수 있으므로 게시·메일·결제 노드에는 **멱등성**이 여전히 중요함.

---

# 33. `Command(goto=...)` 결정과 Fork

나중에 수정 가능해야 하는 결정이라면:

```text
결정 결과를 State에 저장
+
조건부 엣지가 State를 읽음
```

구조가 적합함.

```text
route_channel
→ {"channel": ...}

pick_channel
→ state["channel"]로 분기
```

반대로 결정 노드가:

```python
return Command(
    goto="send_email_all"
)
```

처럼 다음 노드만 직접 정하면, 나중에 `update_state()`로 값을 바꿔도 분기를 다시 계산하기 어려움.

즉:

```text
수정 가능성이 있는 결정
→ State 필드로 남김
→ conditional edge로 분기
```

# 34. 복구 방법 비교

| 상황 | 핵심 장치 |
|---|---|
| 병렬 작업 일부 실패 | 노드 내부 `try/except` + `failures` |
| 일시 오류 | `RetryPolicy` |
| 선택 자료만 실패 | `degraded` |
| 필수 자료 실패 | `held` |
| 모든 자료 실패 | `failed` |
| 단독 노드 재시도 소진 | `error_handler` |
| 대체 데이터 사용 | `Command(goto="fallback")` |
| 중간 실행 실패 | checkpointer |
| 실패 지점부터 재실행 | `invoke(None, config)` |
| 부작용 중복 방지 | 멱등 키 |
| 과거 결정 수정 | `get_state_history()` + `update_state()` |
| 수정된 과거에서 새 실행 | fork |

# 35. 실패 처리 계층

이번 교안을 하나의 계층으로 보면 다음과 같다.

```text
[1] Retry
일시 오류
→ 같은 작업 다시 시도

        ↓ 실패 지속

[2] Isolation
병렬 작업의 영구 오류
→ failures로 기록

        ↓

[3] Decision
실패 범위를 확인
→ completed / degraded / held / failed

        ↓

[4] Fallback
대체 값이 있으면
→ 다른 노드로 이동

        ↓

[5] Resume
실행 자체가 멈췄으면
→ checkpoint부터 다시 실행

        ↓

[6] Fork
과거 판단 자체가 잘못됐으면
→ 과거 State를 수정해 새 갈래 실행
```

# 37. 사람에게 넘길 상황

자동 복구가 가능하다고 해서 모두 자동 처리하면 안 됨.

교안의 예:

| 상황 | 처리 |
|---|---|
| 라운드 상한 도달 | 사람 확인 |
| 같은 반려 사유 반복 | 사람 확인 |
| 필수 자료 실패 | `held` 후 사람 확인 |
| 지난주 데이터로 폴백한 상태에서 게시 직전 | 사람 확인 |
| 외부 메일·결제 등 되돌리기 어려운 행동 직전 | 사람 승인 |

필요하면 `interrupt()`로 그래프를 멈추고 사람의 결정을 받은 뒤 이어 갈 수 있음.

## 한 줄 기준

- **부분 실패 격리** → 병렬 작업 하나의 영구 오류를 `failures`에 기록해 다른 작업을 살림
- **`degraded`** → 선택 자료만 빠진 상태로 누락을 밝히고 진행
- **`held`** → 필수 자료가 빠져 발행 보류
- **`failed`** → 모든 조사 실패로 중단
- **`error_handler`** → 재시도 소진 뒤 폴백 경로 선택
- **`Command(goto=...)`** → 핸들러 이후 실행할 노드를 명시
- **checkpoint** → 실행 상태 저장
- **`invoke(None, config)`** → 저장된 위치부터 이어 실행
- **멱등 키** → 재실행돼도 외부 부작용은 한 번만 발생하게 함
- **fork** → 과거 체크포인트의 State를 수정해 새로운 실행 갈래를 만듦
