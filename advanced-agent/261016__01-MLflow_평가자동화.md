# MLflow 평가 기록과 인용 검증 — 개념·코드 문법 정리

> 정리 기준: `교안_01_MLflow_평가기록과_인용검증.ipynb`  
> 범위: MLflow 실행·기록, RAG 인용 답변, 골든셋, DeepEval 채점 함수, 인용 검증, 평가 결과 확인  
> **핵심:** DeepEval과 코드 채점 함수가 **무엇이 맞는지 판정**하고, MLflow는 **평가 실행·기록·추적·비교**를 담당함.

## 1. 전체 개념과 평가 구조

### 주요 용어

| 용어 | 의미 | 핵심 포인트 |
|---|---|---|
| **골든셋(Golden Set)** | 고정해 둔 질문·정답 답변의 평가 데이터 | 변경 전후를 같은 질문으로 평가해 회귀(regression) 확인 |
| **Experiment** | 같은 대상의 실행 기록을 묶는 실험 | 하나의 실험 안에 여러 run 존재 |
| **Run** | 실험을 한 번 수행한 기록 | 설정, 지표, 산출물, 평가 결과 저장. 고유한 `run_id`로 식별 |
| **Trace** | 질문 한 건이 처리된 실행 과정 | 답변 함수 호출 및 내부 검색 단계 등 추적 |
| **Span** | Trace 내부의 개별 작업 단계 | 검색 함수 등 작업 단위의 입력·출력 확인 |
| **Scorer** | 답변 하나를 판정하는 채점 함수 | `@scorer`, `Feedback(value, rationale)` 사용 |
| **Metric** | 평가 결과의 수치 | 예: `correctness/mean` |
| **Artifact** | Run에 첨부해 저장하는 파일 | 실패 사례 JSON 등 |

### 전체 흐름

```text
골든셋(JSONL)
   ↓  to_records()
[ {inputs: ..., expectations: ...}, ... ]
   ↓
mlflow.genai.evaluate(data, predict_fn, scorers)
   ├── predict_fn(**inputs) → RAG 답변 생성
   │      ├── 문서 검색                 [RETRIEVER span]
   │      └── 구조화 답변·인용 생성      [Trace 기록]
   ├── correctness()      → 정답 판정 (DeepEval G-Eval)
   ├── faithfulness()     → 검색 근거 판정 (DeepEval Faithfulness)
   └── citation_valid()   → 인용 검사 (Python 코드)
   ↓
MLflow Run
   ├── metrics   : 채점 함수별 평균
   ├── result_df : 질문별 판정·이유·응답
   └── traces    : 질문별 실행 단계
```

- **정답 판정:** 답변이 골든셋의 정답 사실을 충족하는가?
- **검색 근거 판정:** 답변 내용이 이번에 검색한 문서로 뒷받침되는가?
- **인용 검증:** 표시한 근거 ID와 인용 문구가 실제 검색 문서의 원문과 일치하는가?
- 세 검사는 서로 다름. `faithfulness=True`여도 엉뚱한 문서를 인용했다면 `citation_valid=False` 가능.

## 2. MLflow 기본 문법: 실험과 Run 기록

### 2-1. 설정·기록 함수

| 코드 | 역할 |
|---|---|
| `mlflow.set_tracking_uri(uri)` | 기록을 저장하거나 읽을 위치 설정 |
| `mlflow.set_experiment(name)` | 실험 선택·생성 |
| `mlflow.start_run(run_name=...)` | 새 Run 시작 |
| `mlflow.start_run(run_id=...)` | 기존 Run을 다시 열어 기록 추가 |
| `mlflow.log_param(key, value)` | 실행 조건 한 개 저장 |
| `mlflow.log_params({...})` | 실행 조건 여러 개 저장 |
| `mlflow.log_metric(key, value)` | 수치 지표 한 개 저장 |
| `mlflow.log_metrics({...})` | 수치 지표 여러 개 저장 |
| `mlflow.set_tag(key, value)` | 분류·검토 상태 등 태그 기록 |
| `mlflow.log_dict(data, "file.json")` | 사전 데이터를 JSON 산출물로 기록 |
| `mlflow.get_run(run_id)` | 저장된 Run 메타데이터·설정·지표 조회 |
| `mlflow.artifacts.load_dict(uri)` | 저장된 JSON 산출물 다시 읽기 |

**기본 패턴**

```python
import mlflow
from pathlib import Path

# 로컬 SQLite를 기록 저장소로 사용
mlflow.set_tracking_uri(f"sqlite:///{Path('.') / 'mlflow.db'}")
mlflow.set_experiment("library-rag-eval")

with mlflow.start_run(run_name="baseline") as run:
    mlflow.log_param("top_k", 3)
    mlflow.log_params({"prompt_version": "v1", "app_model": "gpt-4.1"})
    mlflow.log_metric("correctness", 0.875)
    mlflow.set_tag("review", "pending")
    mlflow.log_dict({"lib-12": "오답"}, "failures.json")

run_id = run.info.run_id
```

- `with` 블록이 끝나면 Run 종료. `run.info.run_id`는 같은 Run을 다시 찾는 고유 ID.
- **Param:** 같은 Run에서 이미 기록한 키의 값을 다른 값으로 바꿀 수 없음.
- **Metric:** 숫자 기록. **Tag:** 문자열 등 식별·분류용으로 수정 가능.
- **Artifact:** 결과를 파일로 보관. `mlflow.db`는 기록 저장소이고, 산출물 파일은 별도 아티팩트 경로에도 저장됨.

**기존 Run 재사용 및 읽기**

```python
with mlflow.start_run(run_id=run_id):
    mlflow.set_tag("review", "확인함")

saved = mlflow.get_run(run_id)
print(saved.data.params)
print(saved.data.metrics)
print(saved.data.tags["review"])

failures = mlflow.artifacts.load_dict(f"runs:/{run_id}/failures.json")
```

**MLflow 화면 실행(단원 폴더에서)**

```bash
uv run mlflow server --backend-store-uri sqlite:///mlflow.db --port 5050
```

- 접속 주소: `http://127.0.0.1:5050`
- 노트북과 서버가 **동일한 `mlflow.db`**를 가리켜야 같은 기록이 표시됨.
- 교안에서는 `mlflow.langchain.autolog(disable=True)` 및 `mlflow.openai.autolog(disable=True)`로 자동 추적을 끄고, `@mlflow.trace`로 수동 추적함. 이는 교안의 MLflow 3.14 실습 환경에서 추적 완료 지연 문제를 피하기 위한 설정.

## 3. RAG 답변과 Trace: 검색·구조화 출력·인용

### 3-1. 검색 함수와 추적

```python
from langchain_chroma import Chroma

vector_store = Chroma(
    collection_name="library_docs",
    embedding_function=embedding_model,
    persist_directory=str(data_dir / "본실습" / "chroma"),
)

@mlflow.trace(span_type="RETRIEVER")
def search_documents(search_query, top_k=3):
    return vector_store.similarity_search(search_query, k=top_k)
```

| 문법 | 의미 |
|---|---|
| `Chroma(..., persist_directory=...)` | 미리 저장한 문서 벡터 컬렉션 사용 |
| `.similarity_search(query, k=top_k)` | 질문과 유사한 문서 `top_k`개 반환 |
| `@mlflow.trace(span_type="RETRIEVER")` | 함수를 검색 단계(span)로 기록 |
| `doc.page_content` | 검색된 문서 본문 |
| `doc.metadata["source_id"]` | 답변에서 사용할 근거 ID |

검색 문서를 프롬프트에 넣을 때 근거 ID와 본문을 함께 표시해야 모델이 해당 ID를 인용할 수 있음.

### 3-2. 답변 형식: Segment와 Citation

답변 전체를 한 문자열로만 저장하지 않고 **문장(부분)별로 근거를 연결**함.

```text
CitedAnswer
└── segments: list[Segment]
      ├── text: "신간은 7일 대출 가능"
      └── citations: list[Citation]
            ├── evidence_id: "loan-new-books"
            └── quote: "...7일 동안 빌릴 수 있으며..."
```

**Pydantic 스키마 문법**

```python
from pydantic import BaseModel, Field

class Citation(BaseModel):
    evidence_id: str = Field(description="근거 문서 ID")
    quote: str = Field(description="원문에서 그대로 복사한 구절")

class Segment(BaseModel):
    text: str = Field(description="답변의 한 부분")
    citations: list[Citation] = Field(description="이 부분의 인용 목록")

class CitedAnswer(BaseModel):
    segments: list[Segment]
```

- `BaseModel`: 반환 데이터의 필드·자료형 지정.
- `list[Citation]`: 인용 객체를 여러 개 담는 리스트.
- `Field(description=...)`: 각 필드의 의미를 모델에 안내.

**프롬프트·체인 구성**

```python
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "제공된 문서만 사용하고 사실을 쓴 부분마다 근거 ID와 원문 구절을 인용하세요."),
    ("human", "질문: {question}\n문서: {context}"),
])

chain = prompt | llm.with_structured_output(CitedAnswer)
result = chain.invoke({"question": question, "context": context})
output = result.model_dump()
```

- `prompt | llm`: 프롬프트와 모델을 연결하는 LangChain 파이프 문법.
- `.with_structured_output(CitedAnswer)`: 모델 출력을 지정한 Pydantic 구조로 받음.
- `.invoke({...})`: 체인 실행. `{question}`, `{context}`와 같은 템플릿 변수에 값을 전달.
- `.model_dump()`: Pydantic 객체를 일반 Python `dict`로 변환.

### 3-3. 답변 함수의 반환 규약

```python
@mlflow.trace
def answer_with_citations(question, top_k=3):
    docs = search_documents(question, top_k)
    structured = chain.invoke({
        "question": question,
        "context": format_documents(docs),
    })

    output = structured.model_dump()
    output["answer"] = " ".join(s["text"] for s in output["segments"])
    output["searched_ids"] = [d.metadata["source_id"] for d in docs]
    return output
```

- `@mlflow.trace`: 답변 함수 호출을 상위 Trace로 기록. 내부 검색 함수의 RETRIEVER span을 함께 확인 가능.
- 반환 `dict`의 핵심 키는 **`segments`, `answer`, `searched_ids`**.
- `segments`: 부분별 `text`와 `citations`; `answer`: 사용자용 완성 문장; `searched_ids`: **이번 질문에서 실제 검색한** 문서 ID.
- `searched_ids`는 문서 전체의 ID와 다름. 인용이 *검색하지 않은 문서*를 가리키는지 검사할 때 필요.

> 위의 코드 조각은 핵심 문법만 추출한 예시. `llm`, `embedding_model`, `data_dir`, `format_documents()` 및 Chroma 데이터는 교안의 앞선 준비 코드가 있다고 가정함.

## 4. 골든셋과 MLflow 평가 입력 형식

골든셋은 **같은 질문을 반복 평가해 변경으로 인한 품질 하락을 찾아내는 기준 데이터**.

| 골든셋 필드 | 역할 |
|---|---|
| `case_id` | 고정 사례 ID. 다른 평가 Run에서 동일 질문끼리 비교할 때 사용 |
| `input` | 질문 |
| `expected_output` | 정답 답변(자료에 없으면 확인 불가 안내) |
| `context` | 정답을 뒷받침하는 원문 구절 |
| `relevant_doc_ids` | 정답 근거 문서 ID |
| `smoke` | 빠른 대표 사례 평가에 사용할지 여부 |

**JSONL 읽기** (`.jsonl`: 한 줄에 JSON 객체 하나)

```python
import json

def read_jsonl(name):
    rows = []
    for line in (data_dir / name).read_text(encoding="utf-8").splitlines():
        if line.strip():
            rows.append(json.loads(line))
    return rows

library_golden = read_jsonl("본실습/golden.jsonl")
```

**`evaluate`에 넣는 형식으로 변환**

```python
def to_records(cases):
    return [
        {
            "inputs": {"question": c["input"]},
            "expectations": {
                "case_id": c["case_id"],
                "expected_output": c["expected_output"],
            },
        }
        for c in cases
    ]
```

```python
# 변환된 레코드 한 건의 구조
{
    "inputs": {"question": "대출 기간은?"},
    "expectations": {
        "case_id": "lib-01",
        "expected_output": "정답 답변 문자열",
    },
}
```

- **`inputs`는 필수.** `predict_fn(**inputs)` 방식으로 전달되므로 `"question"`은 답변 함수의 `question` 인자와 일치해야 함.
- **`expectations`는 정답 판정에서 사용.** 이 교안에서는 `expected_output`과 `case_id`를 담음.
- `case_id`로 결과를 정렬해야 함. 평가 결과의 행 순서는 입력 순서와 달라질 수 있음.

## 5. 채점 함수(Scorer)와 DeepEval 평가

### 5-1. `@scorer`와 `Feedback`

```python
from mlflow.genai.scorers import scorer
from mlflow.entities import Feedback

@scorer
def citation_valid(outputs):
    # 판정 로직
    return Feedback(value=True, rationale="검사 통과")
```

- `@scorer`: 일반 Python 함수를 MLflow 평가용 채점 함수로 등록.
- `Feedback(value=..., rationale=...)`: 결과값(`True`/`False` 등)과 판정 이유 반환.
- **함수 이름이 지표·열 이름의 기준**: `citation_valid/mean`, `citation_valid/value`, `citation_valid/rationale`.

**Scorer에서 사용하는 인자 이름(중요)**

| 허용 인자 | 전달 내용 |
|---|---|
| `inputs` | 해당 행의 질문 등 입력값 |
| `outputs` | 답변 함수의 반환값 |
| `expectations` | 해당 행의 정답·사례 ID |
| `trace` | 해당 질문 처리의 실행 기록 |
| `session` | 대화 전체의 Trace 묶음(세션 단위 평가용) |

- 필요한 인자만 선언. `correctness(inputs, outputs, expectations)`와 `citation_valid(outputs)` 모두 가능.
- `question`, `answer`처럼 **임의의 인자명으로 바꾸면 자동 연결되지 않음**.
- 교안의 세션 Scorer에서는 `session`과 질문 단위 `inputs`·`outputs`·`trace`를 함께 받지 않음.

### 5-2. DeepEval 판사 2종

| 채점 함수 | 사용하는 DeepEval 지표 | 판정 내용 | 교안 기준 |
|---|---|---|---|
| `correctness` | `GEval` | 정답 답변의 사실·조건·숫자가 실제 답변에 들어 있는지 | `threshold=0.7` |
| `faithfulness` | `FaithfulnessMetric` | 실제 답변의 주장이 검색한 문서에 의해 뒷받침되는지 | `threshold=0.7` |

**정답 판정 코드 문법**

```python
from deepeval.metrics import GEval
from deepeval.test_case import LLMTestCase, SingleTurnParams

@scorer
def correctness(inputs, outputs, expectations):
    metric = GEval(
        name="정답 판정",
        evaluation_steps=CORRECTNESS_STEPS,
        evaluation_params=[
            SingleTurnParams.INPUT,
            SingleTurnParams.ACTUAL_OUTPUT,
            SingleTurnParams.EXPECTED_OUTPUT,
        ],
        model=judge_llm,
        threshold=0.7,
        async_mode=False,
    )
    case = LLMTestCase(
        input=inputs["question"],
        actual_output=outputs["answer"],
        expected_output=expectations["expected_output"],
    )
    metric.measure(case, _show_indicator=False)
    return Feedback(value=metric.success, rationale=metric.reason)
```

- `evaluation_steps`: G-Eval이 적용할 구체적인 판단 규칙(숫자·기간·예외 포함, 자료에 없는 질문 처리 등).
- `SingleTurnParams`: 평가에 사용할 `LLMTestCase` 항목 지정.
- `.measure(case)`: 실제 평가 실행. `.success`는 기준 통과 여부, `.reason`은 이유.
- 실습은 동시 채점 환경에서 충돌을 줄이려고 호출마다 `GEval`을 만들고 `async_mode=False`로 설정함.

**검색 근거 판정 코드의 핵심 차이**

```python
from deepeval.metrics import FaithfulnessMetric

retrieval_context = [library_texts[doc_id] for doc_id in outputs["searched_ids"]]

metric = FaithfulnessMetric(
    model=judge_llm,
    threshold=0.7,
    async_mode=False,
    penalize_ambiguous_claims=True,
)
case = LLMTestCase(
    input=inputs["question"],
    actual_output=outputs["answer"],
    retrieval_context=retrieval_context,
)
metric.measure(case, _show_indicator=False)
```

- `retrieval_context`: **이번에 검색한** 근거 문서들의 원문 목록.
- `penalize_ambiguous_claims=True`: 문서에 명시되지 않은 주장(`borderline`)도 불통과로 계산.
- 교안은 `FaithfulnessTemplate.generate_reason()`을 상속·재정의한 `KoreanFaithfulnessTemplate`을 `evaluation_template=`에 전달해 판정 이유를 한국어로 작성하도록 유도함.
- `correctness`와 `faithfulness`의 `measure()` 이후 결과는 동일하게 `Feedback(value=metric.success, rationale=metric.reason)`으로 반환.

### 5-3. 인용 검증: 근거 ID → 원문 문구 대조

**검사 순서**

```text
citation = {evidence_id, quote}
   │
   ├── evidence_id가 원문 사전에 없음 → "없는 근거 ID"
   ├── 이번 검색 문서가 아님         → "검색하지 않은 문서"
   ├── quote가 해당 원문에 없음      → "원문에 없는 문구"
   └── 모든 조건 통과              → "확인"
```

**정규화 및 검증 함수**

```python
def normalize(text):
    for mark in ["･", "∙", "・", "•"]:
        text = text.replace(mark, "·")
    return " ".join(text.split())  # 줄바꿈·연속 공백을 공백 하나로


def check_citation(citation, source_texts, searched_ids):
    cited_id = citation["evidence_id"]
    if cited_id not in source_texts:
        return "없는 근거 ID"
    if cited_id not in searched_ids:
        return "검색하지 않은 문서"
    if normalize(citation["quote"]) not in normalize(source_texts[cited_id]):
        return "원문에 없는 문구"
    return "확인"
```

- `source_texts`: `{문서 ID: 원문 문자열}` 딕셔너리.
- `text.replace(a, b)`: 특정 표기를 통일. `" ".join(text.split())`: 공백·줄바꿈 정규화.
- `A not in B`: **문자열 포함 여부** 또는 **딕셔너리 키/리스트 멤버십** 확인. `A`가 없으면 `True`.
- 유사도가 아니라 원문 부분 문자열 일치를 검사함. `14일`을 `30일`로 잘못 인용하면 실패해야 하기 때문.

**Scorer로 연결**

```python
@scorer
def citation_valid(outputs):
    problems = []
    for segment in outputs["segments"]:
        for citation in segment["citations"]:
            status = check_citation(citation, library_texts, outputs["searched_ids"])
            if status != "확인":
                problems.append(f"{status}: {citation['evidence_id']}")

    if not problems:
        return Feedback(value=True, rationale="인용 검증 통과")
    return Feedback(value=False, rationale="; ".join(problems))
```

**검증 범위에 주의**

- 인용 ID와 문구가 실제 문서에 있는지만 확인. **그 인용이 답변 주장을 의미적으로 뒷받침하는지는 검사하지 않음**.
- 인용이 **전혀 없는 답변도** `citation_valid=True`. 인용 검증 단독으로는 답변 품질을 보장할 수 없으므로 `correctness`·`faithfulness`와 함께 읽어야 함.

## 7. 따라하기 응용 및 실수하기 쉬운 부분

| 구분 | 도서관 실습 | HR 매뉴얼 따라하기 |
|---|---|---|
| 원문 문서 | 15개 | 44개 |
| 골든 사례 | 16건 | 24건(근거 없는 질문 4건) |
| 검색 함수 | `search_documents(..., top_k=3)` | `search_manual(..., top_k=4)` |
| 원문 사전 | `library_texts` | `hr_texts` |
| 인용 Scorer | `citation_valid` | `hr_citation_valid` |
| 평가 Scorer | 정답·검색 근거·인용 검사 | 정답·인용 검사(검색 근거 평가 생략) |

**교안 코드 교정 사항**

HR 실습의 `hr_answer()` 본문에는 도서관용 `search_documents(question)`이 들어 있음. 앞 절의 HR 검색 함수를 호출하도록 수정해야 매뉴얼 문서가 검색됨.

```python
@mlflow.trace
def hr_answer(question):
    docs = search_manual(question)  # 수정: search_documents → search_manual
    result = hr_chain.invoke({
        "question": question,
        "context": format_documents(docs),
    })
    output = result.model_dump()
    output["answer"] = " ".join(s["text"] for s in output["segments"])
    output["searched_ids"] = [d.metadata["source_id"] for d in docs]
    return output
```

추가로 기억할 점:

- `predict_fn`의 인자명과 `inputs`의 키가 일치해야 함. 예: `answer_with_citations(question)` ↔ `{"inputs": {"question": ...}}`.
- `@scorer`의 인자명은 정해진 이름(`inputs`, `outputs`, `expectations` 등)을 사용해야 함.
- 반환값 `outputs`에 `searched_ids`가 없으면 **이번에 검색하지 않은 문서**를 인용했는지 검증 불가.
- PDF에서 추출한 원문은 단어 사이 공백 문제로 문구 비교가 실패할 수 있음. 원문 표기 문제와 잘못된 인용을 구별해야 함.
- **이 교안의 범위는 평가 실행과 결과 기록까지.** 승인 기준선과의 자동 비교, pytest·CI를 통한 품질 하락 차단은 다음 교안의 범위.
