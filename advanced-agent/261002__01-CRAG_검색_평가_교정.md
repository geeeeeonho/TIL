# CRAG: 검색 근거 평가와 교정

## 1. CRAG 핵심 개념

### Agentic RAG

LLM이 질문과 검색 결과를 보고 **검색 여부·검색어·추가 행동**을 판단하는 RAG 방식.

### CRAG

**CRAG(Corrective Retrieval Augmented Generation)**는 검색 결과를 평가하고, 근거가 부족하면 검색을 교정해 다시 보완하는 구조.

이번 실습의 핵심은 다음 두 기준을 분리하는 것.

| 기준 | 의미 |
|---|---|
| **관련성** | 해당 문서가 질문의 일부라도 답하는 데 도움이 되는가 |
| **충분성** | 선택한 문서를 합치면 질문의 모든 요구를 답할 수 있는가 |

관련 문서가 있어도 질문 전체를 답하지 못하면 재검색이 필요함.

### 전체 흐름

```text
START
  ↓
prepare_search
  ↓
retrieve
  ↓
grade
  ├─ 충분함 ─────────────────────→ generate → END
  ├─ 부족 + 재작성 가능 ─────────→ rewrite → retrieve
  └─ 부족 + 재작성 한도 소진 ───→ web_search → grade
                                      ├─ 근거 있음 → generate → END
                                      └─ 근거 없음 → abstain → END
```

검색 순서:

```text
내부 검색
→ 근거 평가
→ 검색어 재작성 + 내부 재검색
→ 그래도 부족하면 웹 검색
→ 최종 답변 또는 확인 불가
```

재작성과 웹 검색은 각각 최대 1회 사용.

## 2. 검색기 구성

영화 문서를 대상으로 **BM25 + Dense 검색**을 결합하고 RRF로 결과를 합침.

```python
bm25 = BM25Retriever.from_documents(
    movie_documents,
    preprocess_func=tokenize,
    k=6,
)

dense = vector_store.as_retriever(search_kwargs={"k": 6})

hybrid = EnsembleRetriever(
    retrievers=[bm25, dense],
    weights=[0.3, 0.7],
    c=60,
    id_key="chunk_id",
)


def search_documents(search_query, top_k=4):
    return hybrid.invoke(search_query)[:top_k]
```

- BM25 후보: 6개
- Dense 후보: 6개
- RRF로 결합
- 최종 평가 후보: 상위 4개

웹 검색은 내부 검색으로 근거가 부족할 때만 Tavily를 사용.

```dotenv
TAVILY_API_KEY=발급받은_키
```

## 3. CRAG 상태(State)

노드는 전체 상태를 다시 만드는 것이 아니라 **변경할 필드만 반환**함.

```python
class RAGState(TypedDict):
    question: str
    search_query: str
    documents: list[Document]

    decision: Literal["", "correct", "ambiguous", "incorrect"]
    feedback: str
    missing_info: str
    search_history: list[dict]

    rewrite_count: int
    max_rewrites: int

    web_searched: bool
    web_notice: str

    draft: str
    evidence_ids: list[str]
    status: Literal["running", "generated", "partial", "insufficient"]
```

핵심 상태값:

| 필드 | 역할 |
|---|---|
| `question` | 사용자의 원질문. 재검색해도 변경하지 않음 |
| `search_query` | 실제 검색에 사용하는 표현 |
| `documents` | 현재까지 선택·보존한 근거 |
| `decision` | 근거 평가 결과 |
| `feedback` | 평가 이유와 부족한 정보 |
| `missing_info` | 아직 확인하지 못한 내용 |
| `rewrite_count` | 검색어 재작성 횟수 |
| `web_searched` | 웹 검색을 시도했는지 여부 |
| `search_history` | 검색어·후보·판정 기록 |

초기 상태에서는 문서와 기록을 비우고 재작성 횟수를 0으로 시작.

## 4. 핵심 노드

### 4-1. `prepare_search` — 첫 검색어 준비

한국어 원질문은 보존하고, 검색용 영어 핵심어만 생성.

```python
def prepare_search(state):
    terms = lexical_chain.invoke({"question": state["question"]})
    return {"search_query": " ".join(terms.keywords)}
```

첫 검색어 준비는 실패 후 재검색이 아니므로 `rewrite_count`를 증가시키지 않음.

---

### 4-2. `retrieve` — 내부 검색

기존 근거와 새 검색 결과를 합쳐 사용.

```python
def merge_documents(kept, found):
    merged = {evidence_id(doc): doc for doc in kept}
    merged.update({evidence_id(doc): doc for doc in found})
    return list(merged.values())


def retrieve(state):
    found = search_documents(state["search_query"])
    return {
        "documents": merge_documents(state["documents"], found)
    }
```

핵심은 **재검색 시 기존 유효 근거를 버리지 않는 것**.

복합 질문에서는 첫 검색에서 찾은 근거와 재검색에서 찾은 근거를 합쳐야 전체 질문을 답할 수 있음.

---

### 4-3. `grade` — 검색 근거 평가

구조화 출력으로 관련 문서와 충분성을 평가.

```python
class RetrievalReview(BaseModel):
    feedback: str
    useful_ids: list[str]
    sufficient: bool
```

평가 기준:

```text
useful_ids 없음
→ incorrect

관련 문서 있음 + 모든 요청을 충족
→ correct

관련 문서는 있지만 일부 요구가 부족
→ ambiguous
```

```python
def grade_documents(question, docs):
    if not docs:
        return [], "incorrect", "검색된 문서가 없습니다."

    review = grade_chain.invoke({
        "question": question,
        "context": format_documents(docs),
    })

    # 실제 후보 안에 있는 ID만 선택
    ...

    if not kept:
        decision = "incorrect"
    elif review.sufficient and valid_selection:
        decision = "correct"
    else:
        decision = "ambiguous"

    return kept, decision, feedback
```

`grade` 노드는 평가 결과와 함께 검색 기록도 저장.

```python
entry = {
    "search_query": state["search_query"],
    "candidate_ids": [...],
    "kept_ids": [...],
    "decision": decision,
    "feedback": feedback,
}
```

즉, 단순 점수보다 **질문의 요구를 실제 근거가 얼마나 충족하는지**를 평가함.

---

### 4-4. `rewrite` — 검색어 교정

원질문은 유지하고 `feedback`에 나온 부족한 정보를 검색어에 반영.

```python
def rewrite(state):
    query = rewrite_query(
        state["question"],
        state["search_query"],
        state["feedback"],
        search_language,
    )

    return {
        "search_query": query,
        "rewrite_count": state["rewrite_count"] + 1,
    }
```

핵심:

```text
question      → 유지
search_query  → 수정
feedback      → 부족한 정보 반영
```

확인되지 않은 사실이나 추측한 정답을 검색어에 추가하지 않음.

---

### 4-5. `web_search` — 외부 검색 보완

내부 재검색으로도 부족한 경우 Tavily 웹 검색을 1회 수행.

```python
def web_search(state):
    web_docs, notice = search_web(state["search_query"])

    return {
        "documents": merge_documents(state["documents"], web_docs),
        "web_searched": True,
        "web_notice": notice,
    }
```

`web_searched=True`는 **검색 성공 여부가 아니라 검색을 시도했다는 의미**.

웹 검색에 실패해도 계속 호출하지 않고, 기존 근거가 있다면 부분 답변으로 진행 가능.

---

### 4-6. `generate` — 근거 기반 답변 생성

선택된 근거와 미확인 사항을 함께 전달해 답변 생성.

```python
class GroundedAnswer(BaseModel):
    answer: str
    evidence_ids: list[str]
```

```python
def generate(state):
    answer = generate_answer(
        state["question"],
        state["documents"],
        feedback=state["missing_info"],
    )

    status = (
        "generated"
        if state["decision"] == "correct"
        else "partial"
    )

    return {
        "draft": answer.answer,
        "evidence_ids": answer.evidence_ids,
        "status": status,
    }
```

상태:

| 상태 | 의미 |
|---|---|
| `generated` | 질문 전체를 답할 근거가 있음 |
| `partial` | 일부만 확인 가능. 미확인 사항도 함께 안내 |

부분 답변에서는 다음을 구분함.

```text
확인된 내용
+ 미확인 사항
+ 추가 확인 방법
```

---

### 4-7. `abstain` — 확인 불가 처리

모든 보완 후에도 사용할 근거가 없을 때만 실행.

```python
def abstain(state):
    return {
        "draft": (
            "제공 자료에서 답할 근거를 찾지 못했습니다. "
            + state["missing_info"]
            + "\n추가 확인: 질문에 해당하는 원문 자료를 제공하거나 "
              "관련 담당자에게 확인해 주세요."
        ),
        "evidence_ids": [],
        "status": "insufficient",
    }
```

관련 근거가 조금이라도 남아 있으면 `abstain`이 아니라 `generate`에서 부분 답변을 생성.

## 5. 평가 후 조건 분기

`grade`는 상태를 평가하고, `route_after_grade`가 다음 노드를 선택.

```python
def route_after_grade(state):
    if state["decision"] == "correct":
        return "generate"

    if state["web_searched"]:
        return "generate" if state["documents"] else "abstain"

    if state["rewrite_count"] < state["max_rewrites"]:
        return "rewrite"

    return "web_search"
```

분기 우선순위:

| 순서 | 조건 | 이동 |
|---|---|---|
| 1 | 근거 충분 | `generate` |
| 2 | 웹 검색까지 완료 + 근거 있음 | `generate` → 부분 답변 가능 |
| 3 | 웹 검색까지 완료 + 근거 없음 | `abstain` |
| 4 | 아직 재작성 가능 | `rewrite` |
| 5 | 재작성 한도 소진 | `web_search` |

## 6. LangGraph 구성

```python
builder = StateGraph(RAGState)

builder.add_node("prepare_search", prepare_search)
builder.add_node("retrieve", retrieve)
builder.add_node("grade", grade)
builder.add_node("rewrite", rewrite)
builder.add_node("web_search", web_search)
builder.add_node("generate", generate)
builder.add_node("abstain", abstain)

builder.add_edge(START, "prepare_search")
builder.add_edge("prepare_search", "retrieve")
builder.add_edge("retrieve", "grade")

builder.add_conditional_edges(
    "grade",
    route_after_grade,
    {
        "generate": "generate",
        "rewrite": "rewrite",
        "web_search": "web_search",
        "abstain": "abstain",
    },
)

builder.add_edge("rewrite", "retrieve")
builder.add_edge("web_search", "grade")
builder.add_edge("generate", END)
builder.add_edge("abstain", END)

crag_app = builder.compile()
```

구조를 간단히 보면:

```text
prepare_search
      ↓
   retrieve
      ↓
    grade
   ↙  ↓   ↘
rewrite │ web_search
   │    │    │
   └→ retrieve
        │
        └────→ grade

충분 → generate → END
근거 없음 → abstain → END
```

## 7. 실행과 기록

```python
result = crag_app.invoke(
    make_initial_state(question),
    config={"recursion_limit": 30},
)
```

`recursion_limit`은 LangGraph의 **super-step 실행 한도**이며 `max_rewrites`와는 다른 개념.

최종 상태에는 다음 정보가 남음.

```text
최종 답변
선택된 근거
실제 인용 ID
검색어 변경 기록
평가 결과
미확인 사항
웹 검색 여부
```

`search_history`를 확인하면 재검색이 실제로 새로운 근거를 찾았는지 추적할 수 있음.

## 8. VPN 문의 실습: 내부 문서 전용 CRAG

두 번째 실습은 회사 VPN 도움말을 대상으로 웹 검색 없이 동일한 핵심 구조를 적용.

```text
START
  ↓
retrieve
  ↓
grade
  ├─ 충분 → generate
  ├─ 부족 + 재작성 가능 → rewrite → retrieve
  └─ 보완 종료
       ├─ 근거 있음 → generate
       └─ 근거 없음 → abstain
```

한국어 업무 문서는 Kiwi로 명사·외국어·숫자를 추출해 BM25 검색.

```python
def kiwi_tokenize(text):
    return [
        token.form.lower()
        for token in kiwi.tokenize(text)
        if token.tag.startswith("N") or token.tag in {"SL", "SN"}
    ]
```

검색어 재작성도 한국어로 수행.

```python
def practice_rewrite(state):
    query = rewrite_query(
        state["question"],
        state["search_query"],
        state["feedback"],
        "한국어",
    )

    return {
        "search_query": query,
        "rewrite_count": state["rewrite_count"] + 1,
    }
```

실습 마지막 저장 코드는 결과 변수에 맞춰 다음처럼 사용하는 것이 맞음.

```python
practice_result = practice_app.invoke(make_initial_state(query))
show_result(practice_result)
save_brief("lesson01_helpdesk_brief", practice_result)
```

## 9. 핵심 정리

1. **관련성과 충분성은 다름.**
   - 관련 문서가 있어도 질문 전체의 근거가 부족하면 재검색 필요.

2. **원질문과 검색어를 분리함.**
   - `question`은 유지.
   - `search_query`만 평가 결과에 따라 수정.

3. **기존 근거를 보존함.**
   - 재검색 결과만 사용하면 이미 찾은 유효 근거를 잃을 수 있음.

4. **검색 → 평가 → 교정 → 재평가 구조가 핵심.**

5. **웹 검색은 마지막 보완 수단.**
   - 내부 검색 → 내부 재검색 → 웹 검색 순서.

6. **근거가 일부 있으면 부분 답변을 생성함.**
   - 전부 없을 때만 `abstain`.

7. **검색 이력을 남김.**
   - 검색어, 후보 근거, 선택 근거, 판정, 부족한 정보를 기록해 추적 가능하게 함.

### 한 줄 요약

> CRAG는 검색 결과를 바로 답변에 쓰지 않고, **근거의 관련성과 충분성을 평가한 뒤 부족하면 검색을 교정하고 다시 검증하는 RAG 구조**임.
