# 슈퍼바이저와 워커

> 여러 도구를 하나의 에이전트에 몰아넣는 대신, 역할별 **Worker**와 전체 흐름을 조정하는 **Supervisor**로 나누는 구조.
>
> 핵심은 `Supervisor → Worker → 보고 → Supervisor` 반복과 `Command(goto, update)`를 이용한 동적 이동.

---

## 1. 핵심 개념

### 멀티 에이전트 구조

하나의 에이전트가 주문 조회, 규정 검색, 환불 처리, 답변 작성까지 모두 맡으면 도구와 지시가 많아져 판단이 복잡해짐.

역할별로 에이전트를 분리하면 각 Worker가 자기 업무와 도구에만 집중할 수 있음.

```text
[단일 Agent]
사용자
  ↓
Agent
  ├─ 주문 조회
  ├─ 규정 검색
  ├─ 환불 처리
  └─ 답변 작성


[Supervisor + Workers]
사용자
  ↓
Supervisor
  ├─ order_worker  → 주문·배송 조회
  ├─ policy_worker → 규정 검색
  ├─ refund_worker → 환불·교환 처리
  └─ reply_writer  → 고객 답변 작성
```

멀티 에이전트가 항상 좋은 것은 아님.

- 도구가 적고 단일 에이전트로 충분한 경우
- 속도와 비용이 중요한 경우
- 실행 순서가 항상 같은 경우

이런 상황은 단일 Agent 또는 고정된 `StateGraph`가 더 단순함.

### Router와 Supervisor

| 구분 | Router | Supervisor |
|---|---|---|
| 판단 시점 | 처음 문의를 받을 때 | Worker가 돌아올 때마다 |
| 기준 | 최초 입력 | 최초 입력 + 누적된 Worker 보고 |
| 실행 형태 | 보통 한 번 분기 | 여러 Worker를 반복 호출 |
| 적합한 상황 | 담당이 처음부터 명확함 | 앞 단계 결과에 따라 다음 담당이 달라짐 |

예시 문의:

```text
"ORD-1024 블루투스 이어폰 한쪽이 안 들려요. 환불해 주세요."
```

Router라면 `환불`이라는 단어만 보고 바로 환불 담당으로 보낼 수 있음.

Supervisor는 앞의 보고를 계속 읽음.

```text
사용자 문의
   ↓
Supervisor
   ↓
order_worker
   └─ "배송 후 9일, 개봉"
   ↓
Supervisor
   ↓
policy_worker
   └─ "초기 불량은 30일 이내, 증빙 필요"
   ↓
Supervisor
   ↓
order_worker
   └─ "불량 사진 2장 첨부"
   ↓
Supervisor
   ↓
refund_worker
   └─ "89,000원 환불 처리"
   ↓
Supervisor
   ↓
reply_writer
   └─ 고객 답변
   ↓
FINISH
```

### ReAct Agent와 Supervisor

둘 다 **결과를 읽고 다음 행동을 다시 선택**한다는 점은 같음.

차이는 무엇을 선택하느냐임.

| 구조 | 선택 대상 | 특징 |
|---|---|---|
| ReAct Agent | Tool | 하나의 Agent가 여러 Tool 중 선택 |
| Supervisor | Worker | Supervisor가 역할별 Agent 중 선택 |

Supervisor 구조에서는 반복이 두 겹으로 생김.

```text
바깥 반복
Supervisor
   ↓ Worker 선택

안쪽 반복
Worker Agent
   ↓ Tool 선택
   ↓ Tool 실행
   ↓ Worker 보고

다시 Supervisor
```

## 2. `Command`: State 업데이트와 다음 노드 이동

LangGraph의 노드는 일반적으로 State에 쓸 `dict`를 반환함.

`Command`를 사용하면 **State 업데이트와 다음 노드 선택을 동시에** 처리할 수 있음.

```python
Command(
    goto="다음_노드",
    update={"state_key": "새 값"}
)
```

- `goto`: 다음 실행 노드
- `update`: State에 반영할 값

### 조건부 엣지 방식

```text
START
  ↓
classify
  ↓
route_by_category()
  ├─ order_desk
  └─ policy_desk
       ↓
      END
```

```python
import re
from typing import Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command


class DeskState(TypedDict):
    question: str
    category: str
    order_id: str
    answer: str


def classify(state: DeskState):
    question = state["question"]
    order_id = re.search(r"ORD-\d+", question).group()

    if "환불" in question or "교환" in question:
        category = "환불·교환"
    else:
        category = "배송·주문"

    return {
        "category": category,
        "order_id": order_id,
    }


def route_by_category(
    state: DeskState,
) -> Literal["order_desk", "policy_desk"]:

    if state["category"] == "환불·교환":
        return "policy_desk"

    return "order_desk"


def order_desk(state: DeskState):
    return {
        "answer": (
            f"order_desk가 받은 값: "
            f"{state['category']} {state['order_id']}"
        )
    }


def policy_desk(state: DeskState):
    return {
        "answer": (
            f"policy_desk가 받은 값: "
            f"{state['category']} {state['order_id']}"
        )
    }
```

그래프 연결:

```python
edge_builder = StateGraph(DeskState)

edge_builder.add_node("classify", classify)
edge_builder.add_node("order_desk", order_desk)
edge_builder.add_node("policy_desk", policy_desk)

edge_builder.add_edge(START, "classify")

edge_builder.add_conditional_edges(
    "classify",
    route_by_category,
    ["order_desk", "policy_desk"],
)

edge_builder.add_edge("order_desk", END)
edge_builder.add_edge("policy_desk", END)

edge_app = edge_builder.compile()
```

### `Command` 방식

분류와 이동을 하나의 노드에서 처리함.

```text
START
  ↓
classify
  ├─ Command(goto="order_desk")
  └─ Command(goto="policy_desk")
           ↓
          END
```

```python
def classify_and_go(
    state: DeskState,
) -> Command[Literal["order_desk", "policy_desk"]]:

    question = state["question"]
    order_id = re.search(r"ORD-\d+", question).group()

    if "환불" in question or "교환" in question:
        next_desk = "policy_desk"
        category = "환불·교환"
    else:
        next_desk = "order_desk"
        category = "배송·주문"

    return Command(
        goto=next_desk,
        update={
            "category": category,
            "order_id": order_id,
        },
    )
```

그래프에는 `classify` 이후의 분기 엣지를 직접 등록하지 않음.

```python
command_builder = StateGraph(DeskState)

command_builder.add_node("classify", classify_and_go)
command_builder.add_node("order_desk", order_desk)
command_builder.add_node("policy_desk", policy_desk)

command_builder.add_edge(START, "classify")
command_builder.add_edge("order_desk", END)
command_builder.add_edge("policy_desk", END)

command_app = command_builder.compile()
```

비교:

| 구분 | 조건부 엣지 | `Command` |
|---|---|---|
| 다음 노드 결정 | 별도 라우팅 함수 | 현재 노드 반환값 |
| State 변경 | 노드의 `dict` 반환 | `update` |
| 이동 | `add_conditional_edges()` | `goto` |
| 적합한 구조 | 규칙 기반 분기 | 노드의 판단이 곧 다음 실행 대상일 때 |

Supervisor가 Worker를 직접 선택하는 구조에서는 `Command`가 잘 맞음.

## 3. CS Supervisor 팀 설계

예제는 쇼핑몰 환불·교환 처리 팀.

### Worker 역할과 Tool

| Worker | 역할 | Tool |
|---|---|---|
| `order_worker` | 주문·배송 / 불량 접수 조회 | `get_order`, `get_defect_report` |
| `policy_worker` | 환불·교환 규정 검색 | `search_policy` |
| `refund_worker` | 환불 실행 / 교환 접수 | `issue_refund`, `request_exchange` |
| `reply_writer` | 고객 답변 작성 | `get_reply_template` |

핵심은 **Worker마다 필요한 Tool만 제공**하는 것.

예를 들어 `reply_writer`에는 `issue_refund`가 없으므로 답변 작성 Worker가 직접 환불을 실행할 수 없음.

```text
Supervisor
  │
  ├─ order_worker
  │    ├─ get_order
  │    └─ get_defect_report
  │
  ├─ policy_worker
  │    └─ search_policy
  │
  ├─ refund_worker
  │    ├─ issue_refund
  │    └─ request_exchange
  │
  └─ reply_writer
       └─ get_reply_template
```

### 전체 Supervisor 그래프

Worker끼리는 직접 대화하지 않음.

`instruction`과 `results`를 State에 남겨 Supervisor를 통해 전달함.

```text
                 ┌─────────────────┐
                 │    Supervisor   │
                 └────────┬────────┘
                          │ Command(goto)
          ┌───────────────┼────────────────┐
          ↓               ↓                ↓
   order_worker     policy_worker    refund_worker
          │               │                │
          └───────┬───────┴────────────────┘
                  │ 보고(results)
                  ↓
             Supervisor
                  │
                  ├─ reply_writer
                  │      ↓
                  │    고객 답변
                  │
                  └─ FINISH → END
```

### Tool 정의

주문 Worker의 조회 Tool:

```python
@tool
def get_order(order_id: str) -> dict:
    """주문 정보와 배송 후 지난 날수를 조회합니다."""

    if order_id not in ORDERS:
        return {"안내": "없는 주문번호입니다."}

    order = dict(ORDERS[order_id])

    delivered = date.fromisoformat(order["배송 완료일"])
    order["배송 후 지난 날수"] = (
        date.fromisoformat(TODAY) - delivered
    ).days

    return order


@tool
def get_defect_report(order_id: str) -> dict:
    """불량 접수 내용과 사진 첨부 여부를 조회합니다."""

    if order_id not in DEFECT_REPORTS:
        return {"안내": "접수된 불량 신고가 없습니다."}

    return DEFECT_REPORTS[order_id]
```

규정 Worker의 검색 Tool:

```python
@tool
def search_policy(keyword: str) -> list[dict]:
    """제목이나 내용에 keyword가 포함된 규정을 찾습니다."""

    found = []

    for policy in POLICIES:
        if (
            keyword in policy["제목"]
            or keyword in policy["내용"]
        ):
            found.append(policy)

    return found
```

환불 Worker의 실행 Tool:

```python
REFUND_LOG = []


@tool
def issue_refund(order_id: str, reason: str) -> str:
    """주문의 결제 금액 전액을 환불합니다."""

    amount = ORDERS[order_id]["결제 금액"]

    REFUND_LOG.append({
        "order_id": order_id,
        "amount": amount,
        "reason": reason,
    })

    return (
        f"환불 승인: {order_id} "
        f"{amount:,}원, 사유: {reason}"
    )


@tool
def request_exchange(order_id: str) -> str:
    """같은 상품의 새 제품으로 교환을 접수합니다."""

    return (
        f"교환 접수: {order_id} 새 제품 발송, "
        "회수 기사 1~2일 안에 방문"
    )
```

```python
@tool
```

```python
    system_prompt=(
        "쇼핑몰 CS 팀의 답변 작성 담당입니다. "
        "양식을 도구로 확인하고, 전달받은 보고에 있는 사실만으로 "
        "고객에게 보낼 한국어 답변을 쓰세요. "
        "금액·기간·날짜는 보고에 적힌 값만 사용하세요."
    ),
)
```

### Team State

Supervisor와 Worker가 공유하는 상태.

```python
class TeamState(TypedDict):
    # 최초 입력
    request: str
    max_turns: int

    # Supervisor가 관리
    instruction: str
    visits: list[str]
    turn: int

    # Worker 보고
    results: list[dict]
```

각 필드의 역할:

| 필드 | 역할 |
|---|---|
| `request` | 고객 문의 원문 |
| `max_turns` | Worker 호출 최대 횟수 |
| `instruction` | 이번 Worker에게 줄 지시 |
| `visits` | 호출한 Worker 순서 |
| `turn` | Worker를 호출한 횟수 |
| `results` | Worker가 반환한 보고 목록 |

`results`에는 별도 reducer가 없음.

따라서 새 보고 하나만 반환하지 않고 **기존 목록 + 새 보고** 전체를 반환해야 함.

### Supervisor의 구조화 출력

Supervisor는 다음 Worker 이름과 지시를 구조화 출력으로 생성함.

```python
WORKER_GUIDE = (
    "order_worker: 주문·배송 정보 조회, 불량 접수 조회. "
    "policy_worker: 환불·교환 규정 검색. "
    "refund_worker: 환불 실행, 교환 접수. "
    "reply_writer: 확인된 내용으로 고객 답변 작성."
)


TEAM_RULES = (
    "처리 원칙: "
    "1) 환불·교환은 판단에 필요한 사실이 모두 확인된 뒤에만 "
    "refund_worker에게 맡깁니다. "
    "2) 필요한 사실이 아직 보고에 없으면 그 사실을 알아낼 Worker에게 맡깁니다. "
    "이미 보고된 내용은 다시 시키지 않습니다. "
    "3) 규정 조건을 채우지 못하면 환불·교환하지 말고 "
    "reply_writer에게 고객이 해야 할 일을 안내하게 합니다. "
    "4) 고객에게 보낼 답변이 나오면 FINISH를 고릅니다."
)


class Route(BaseModel):
    next: Literal[
        "order_worker",
        "policy_worker",
        "refund_worker",
        "reply_writer",
        "FINISH",
    ] = Field(
        description="다음에 일을 맡길 Worker"
    )

    instruction: str = Field(
        description=(
            "다음 Worker에게 줄 지시. "
            "필요한 앞 보고도 함께 포함"
        )
    )
```

프롬프트와 Chain:

```python
supervisor_prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        "쇼핑몰 CS 환불·교환 팀의 팀장입니다. "
        "직접 조회하거나 처리하지 않고 Worker에게 맡깁니다. "
        + WORKER_GUIDE
        + " "
        + TEAM_RULES
        + " 문의와 지금까지 보고를 읽고 "
          "다음 Worker 한 명과 지시를 정하세요.",
    ),
    (
        "human",
        "고객 문의: {request}\n\n"
        "지금까지 보고:\n{results}",
    ),
])


supervisor_chain = (
    supervisor_prompt
    | llm.with_structured_output(
        Route,
        strict=True,
    )
)
```

### 보고 정리 함수와 Supervisor 노드

```python
def format_results(results):
    """Worker 보고 목록을 Supervisor가 읽을 문자열로 변환."""

    if not results:
        return "아직 없음"

    lines = []

    for row in results:
        lines.append(
            f"[{row['worker']}] {row['result']}"
        )

    return "\n\n".join(lines)
```

Supervisor는 보고를 읽고 `Command`로 다음 Worker를 선택함.

```python
def supervisor(
    state: TeamState,
) -> Command[
    Literal[
        "order_worker",
        "policy_worker",
        "refund_worker",
        "reply_writer",
        END,
    ]
]:
    # 처리 상한
    if state["turn"] >= state["max_turns"]:

        # 이미 reply_writer까지 갔다면 종료
        if "reply_writer" in state["visits"]:
            return Command(goto=END)

        # 답변이 없다면 상담원 연결 안내만 작성
        return Command(
            goto="reply_writer",
            update={
                "instruction": (
                    "처리 상한에 닿았습니다. "
                    "환불·교환을 약속하지 말고, "
                    "지금까지 확인한 내용과 함께 "
                    "'상담원 확인 필요'로 안내하세요."
                ),
                "visits": (
                    state["visits"]
                    + ["reply_writer"]
                ),
                "turn": state["turn"] + 1,
            },
        )

    # 현재 문의 + 누적 보고를 보고 다음 Worker 결정
    route = supervisor_chain.invoke({
        "request": state["request"],
        "results": format_results(
            state["results"]
        ),
    })

    if route.next == "FINISH":
        return Command(goto=END)

    return Command(
        goto=route.next,
        update={
            "instruction": route.instruction,
            "visits": (
                state["visits"]
                + [route.next]
            ),
            "turn": state["turn"] + 1,
        },
    )
```

핵심 흐름:

```text
results 확인
    ↓
Supervisor LLM
    ↓
Route(next, instruction)
    ↓
Command(
    goto=next,
    update={instruction, visits, turn}
)
```

### Worker 실행 함수

Worker는 고객 문의, Supervisor 지시, 기존 보고를 받아 자기 Agent를 실행함.

```python
def run_worker(
    agent,
    worker,
    state,
):
    message = (
        f"고객 문의: {state['request']}\n\n"
        f"지시: {state['instruction']}\n\n"
        "팀이 지금까지 확인한 내용:\n"
        f"{format_results(state['results'])}"
    )

    reply = agent.invoke({
        "messages": [{
            "role": "user",
            "content": message,
        }]
    })

    return (
        state["results"]
        + [{
            "worker": worker,
            "result": reply["messages"][-1].text,
        }]
    )
```

Worker 노드는 모두 같은 패턴.

```python
def order_worker(
    state: TeamState,
) -> Command[Literal["supervisor"]]:

    results = run_worker(
        order_agent,
        "order_worker",
        state,
    )

    return Command(
        goto="supervisor",
        update={"results": results},
    )


def policy_worker(
    state: TeamState,
) -> Command[Literal["supervisor"]]:

    results = run_worker(
        policy_agent,
        "policy_worker",
        state,
    )

    return Command(
        goto="supervisor",
        update={"results": results},
    )


def refund_worker(
    state: TeamState,
) -> Command[Literal["supervisor"]]:

    results = run_worker(
        refund_agent,
        "refund_worker",
        state,
    )

    return Command(
        goto="supervisor",
        update={"results": results},
    )


def reply_writer(
    state: TeamState,
) -> Command[Literal["supervisor"]]:

    results = run_worker(
        reply_agent,
        "reply_writer",
        state,
    )

    return Command(
        goto="supervisor",
        update={"results": results},
    )
```

각 Worker는 일을 끝내면 항상 `supervisor`로 돌아감.

```text
Supervisor
   ↓
Worker
   ↓ 보고 저장
Supervisor
   ↓
다음 Worker
```

## 5. 처리 상한과 상담원 연결

Supervisor 구조는 Worker를 계속 호출할 수 있으므로 반복 제한이 필요함.

`max_turns`는 Supervisor가 Worker에게 일을 맡길 수 있는 최대 횟수.

예를 들어 `max_turns=2`:

```text
1턴
Supervisor → order_worker
              └─ 배송 후 9일, 개봉

2턴
Supervisor → policy_worker
              └─ 초기 불량 30일 이내, 증빙 필요

상한 도달
Supervisor
   ↓
refund_worker 호출 금지
   ↓
reply_writer
   └─ "상담원 확인 필요"

END
```

실행:

```python
REFUND_LOG.clear()

guard_input = {
    "request": TICKETS["ORD-1024"],
    "max_turns": 2,
    "instruction": "",
    "visits": [],
    "turn": 0,
    "results": [],
}

guard_result = team_app.invoke(
    guard_input
)

print(
    "방문 순서:",
    " -> ".join(
        guard_result["visits"]
    ),
)

print(
    "환불 기록:",
    len(REFUND_LOG),
    "건",
)
```

핵심은 상한에 도달한 상태에서 `refund_worker`를 추가 호출하지 않는 것.

환불을 약속하지 않고 사람 상담원에게 이어지도록 답변을 생성함.

## 6. Worker를 Tool로 호출하는 Supervisor Agent

앞에서는 Supervisor 자체를 LangGraph 노드로 구현함.

다른 방식은 **Supervisor Agent가 Worker를 Tool처럼 호출**하는 구조.

```text
사용자
  ↓
supervisor_agent
  ↓
ask_worker(
    worker="order_worker",
    instruction="..."
)
  ↓
order_agent
  ↓
보고 문자열
  ↓
supervisor_agent
  ↓
다음 ask_worker(...)
  ↓
최종 답변
```

이 방식에서는 `supervisor_agent`가 직접 `Command(goto)`를 반환하지 않음.

`ask_worker`라는 Tool을 통해 어떤 Worker를 실행할지 결정함.

### `ask_worker` Tool

```python
WORKER_AGENTS = {
    "order_worker": order_agent,
    "policy_worker": policy_agent,
    "refund_worker": refund_agent,
    "reply_writer": reply_agent,
}

ASK_LOG = []


@tool
def ask_worker(
    worker: Literal[
        "order_worker",
        "policy_worker",
        "refund_worker",
        "reply_writer",
    ],
    instruction: str,
) -> str:
    """Worker 한 명에게 지시하고 최종 보고만 반환."""

    ASK_LOG.append(worker)

    reply = WORKER_AGENTS[
        worker
    ].invoke({
        "messages": [{
            "role": "user",
            "content": instruction,
        }]
    })

    return reply["messages"][-1].text
```

중요한 차이:

Worker는 다른 Worker의 보고를 자동으로 공유받지 않음.

따라서 Supervisor Agent가 `instruction` 안에 필요한 앞 보고를 직접 포함해야 함.

### Supervisor Agent 생성

```python
from langchain.agents.middleware import (
    ModelCallLimitMiddleware,
)


supervisor_llm = ChatOpenAI(
    model=model_name,
    use_responses_api=True,
    model_kwargs={
        "parallel_tool_calls": False,
    },
)


supervisor_agent = create_agent(
    supervisor_llm,
    tools=[ask_worker],
    system_prompt=(
        "쇼핑몰 CS 환불·교환 팀의 팀장입니다. "
        "직접 조회하거나 처리하지 않고 "
        "ask_worker로 Worker에게 맡깁니다. "
        + WORKER_GUIDE
        + " "
        + TEAM_RULES
        + " Worker는 다른 Worker의 보고를 모르므로 "
          "지시에 필요한 앞 보고를 넣으세요. "
          "reply_writer의 고객 답변을 받으면 "
          "그 답변을 최종 답으로 내세요."
    ),
    middleware=[
        ModelCallLimitMiddleware(
            run_limit=10,
            exit_behavior="end",
        )
    ],
)
```

`parallel_tool_calls=False`를 사용해 한 번에 여러 Worker를 동시에 호출하지 않도록 구성함.

### 실행

```python
REFUND_LOG.clear()
ASK_LOG.clear()

supervisor_reply = (
    supervisor_agent.invoke({
        "messages": [{
            "role": "user",
            "content": TICKETS["ORD-1024"],
        }]
    })
)

print(
    "Worker 호출 순서:",
    " -> ".join(ASK_LOG),
)

print(
    "환불:",
    REFUND_LOG,
)

print(
    supervisor_reply[
        "messages"
    ][-1].text
)
```

## 7. 두 Supervisor 방식 비교

| 구분 | Supervisor 노드 | Supervisor Agent |
|---|---|---|
| 다음 Worker 선택 | `Command(goto)` | `ask_worker` Tool 호출 |
| 구조 | `StateGraph` 직접 설계 | `create_agent` 중심 |
| 상태 공유 | `TeamState` | Agent 대화 문맥 |
| Worker가 받는 앞 정보 | `run_worker`가 `results` 전체 전달 | Supervisor가 `instruction`에 직접 포함 |
| 반복 제한 | `max_turns` + 노드의 `if` | `ModelCallLimitMiddleware` |
| 상한 이후 행동 | 코드로 다음 노드 지정 가능 | 실행을 그 자리에서 종료 |
| 순서 제어 | 코드 수준에서 제어 가능 | 주로 Prompt 지시 |
| 적합한 상황 | 확인·승인 순서가 중요한 업무 | Worker 조합을 빠르게 구성하는 업무 |

핵심 차이:

```text
[Supervisor 노드 방식]

Supervisor Node
   ↓ Command(goto)
Worker Node
   ↓ Command(goto="supervisor")
Supervisor Node

→ 그래프의 이동 자체를 코드로 관리


[Supervisor Agent 방식]

Supervisor Agent
   ↓ Tool Call
ask_worker()
   ↓
Worker Agent
   ↓
보고 반환
Supervisor Agent

→ Worker 호출을 Agent의 Tool 사용으로 관리
```

## 핵심 정리

- **Router**는 최초 입력을 보고 보통 한 번 분기함.
- **Supervisor**는 Worker의 보고를 읽고 다음 Worker를 반복해서 선택함.
- Supervisor 구조에서는 Worker마다 필요한 Tool만 제공해 역할과 권한을 분리함.
- `Command(goto, update)`는 **다음 노드 이동 + State 업데이트**를 동시에 처리함.
- Worker는 일을 마친 뒤 보고를 `results`에 추가하고 다시 Supervisor로 돌아감.
- Supervisor는 누적된 `results`를 보고 다음 Worker를 선택함.
- 반복 그래프에는 `max_turns` 같은 처리 상한을 두고, 상한에 닿으면 사람에게 넘기는 구조를 만들 수 있음.
- Supervisor를 LangGraph 노드로 직접 만들 수도 있고, Worker를 Tool로 호출하는 `create_agent` 방식으로 만들 수도 있음.
- 실행 순서와 승인 흐름을 코드로 강하게 제어해야 하면 **Supervisor 노드 방식**이 더 적합함.
