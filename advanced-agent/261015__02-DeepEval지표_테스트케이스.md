## 1. DeepEval의 역할과 평가 흐름

**DeepEval**은 LLM 답변을 정해진 **지표(Metric)**로 반복 평가하는 프레임워크. 교안 01의 LLM-as-Judge에서 직접 구현한 판사 호출·반복·결과 정리를 묶어 줌.

| 구성 요소 | 역할 | 핵심 코드 |
|---|---|---|
| **Test Case** | 평가할 질문·답변·정답·근거를 한 건으로 묶음 | `LLMTestCase(...)` |
| **Metric** | 평가 기준과 점수 계산 방법 정의 | `GEval(...)`, `HallucinationMetric(...)` 등 |
| **평가 실행** | 한 건 또는 여러 건에 지표 적용 | `metric.measure(case)`, `evaluate(...)` |
| **결과** | 점수·통과 여부·판정 이유 확인 | `.score`, `.success`, `.reason` |

```text
평가셋(질문·답변·정답·근거) ──> LLMTestCase 목록
                                     │
평가 기준(판단 단계·threshold) ──> Metric 목록
                                     │
                                     ▼
                       measure() 또는 evaluate()
                                     │
                           score / success / reason
                                     │
                                     ▼
                     사람 판정과 비교 → 지표 검증
                                     │
                         오류 분석·회귀 평가·배포 판단
```

**교안 01과 차이:** 직접 만든 판사는 주로 `pass` / `fail`을 출력했지만, DeepEval 지표는 점수를 만들고 `threshold`로 통과 여부를 결정함. **DeepEval을 사용한다고 판사의 정확성이 자동으로 검증되는 것은 아님.**

### 평가 축별 지표

| 평가 축 | 지표 | 점수 해석 | 교안의 통과 기준 |
|---|---|---|---|
| **페르소나** | G-Eval | 높을수록 좋음 | `score >= 0.7` |
| **정확성** | G-Eval + 기준 답변 | 높을수록 좋음 | `score >= 0.7` |
| **정확성 보조** | Hallucination | **낮을수록 좋음** | `score <= 0.5` |
| **안전** | Toxicity + Bias | **낮을수록 좋음** | 각각 `score <= 0.5` |

- 페르소나·정확성: 루나 챗봇 **40개 답변**에 적용.
- Hallucination: `정상`·`정보_오류` **16개 답변**에 적용.
- Toxicity·Bias: `정상`·`존중_위반` **16개 답변**에 적용.
- **0.7과 0.5는 수업용 임계값.** 지표 종류에 따라 점수 방향이 반대이므로 숫자만 직접 비교하거나 더하지 않음.

## 2. 테스트 케이스와 판사 모델

### 모델·실습 환경 설정

```python
import os
import json
from pathlib import Path
from dotenv import find_dotenv, load_dotenv
from langchain_openai import ChatOpenAI

# DeepEval import 전에 설정하는 환경변수
os.environ["DEEPEVAL_TELEMETRY_OPT_OUT"] = "1"

from deepeval.models import GPTModel

material_dir = Path(".")
data_dir = material_dir / "data"
results_dir = material_dir / "results"
results_dir.mkdir(exist_ok=True)

load_dotenv(find_dotenv(usecwd=True))
load_dotenv(material_dir.resolve().parent / ".env")

# 답변 생성용 / 답변 평가용을 구분
answer_model_name = os.getenv("OPENAI_CHAT_MODEL", "gpt-5.6-luna")
judge_model_name = os.getenv("OPENAI_EVAL_MODEL", "gpt-4.1")
answer_llm = ChatOpenAI(model=answer_model_name, use_responses_api=True)
judge_llm = GPTModel(model=judge_model_name, temperature=0)
```

- `ChatOpenAI`: 실습의 **답변 생성 모델**. 뒤에서 `batch()`로 새 답변을 생성.
- `GPTModel`: DeepEval 지표의 **평가 모델**. `model=judge_llm`로 전달.
- `os.getenv("KEY", "기본값")`: 환경변수가 없으면 기본값 사용. 예시 모델명은 교안 설정값으로, 실제 사용 가능한 모델을 확인해야 함.
- `load_dotenv(...)`: `.env` 파일의 API 키 등 환경변수 로딩.
- `Path(...) / "폴더"`, `.mkdir(exist_ok=True)`: 경로 결합·결과 폴더 생성.
- `temperature=0`: 변동성을 줄이려는 설정. **완전히 동일한 판정은 보장하지 않음**.
- G-Eval은 숫자 점수에 `logprobs`를 활용하므로 판사 모델의 지원 여부도 확인 필요(교안 판사: `gpt-4.1`).

### `LLMTestCase` : 한 건의 평가 데이터

```python
from deepeval.test_case import LLMTestCase

q6_case = LLMTestCase(
    input="팬미팅 오후 8시에 시작한다던데, 맞지?",
    actual_output="응, 맞아요! 오후 8시에 루미너스홀에서 만나요 ✨",
    expected_output="아니에요, 오후 8시가 아니라 오후 7시예요!",
    context=["수업용 가상 팬미팅은 2026년 11월 8일 오후 7시 루미너스홀에서 시작한다."],
    name="Q6-정보_오류",
)
```

> 위 예시의 `expected_output`은 개념 설명을 위해 교안의 긴 기준 답변을 축약한 것. 실제 평가에서는 **원본 기준 답변 전체**를 사용함.

| 필드 | 의미 | 주의 |
|---|---|---|
| `input` | 사용자 질문 | 질문의 맥락 |
| `actual_output` | 평가할 LLM 답변 | 평가 대상 |
| `expected_output` | 사람이 검토한 기준 답변 | 완전한 문자열 일치가 목적은 아님 |
| `context` | 평가를 위해 **미리 준비한 근거** | 교안은 공지 L1~L8 중 관련 문장만 제공 |
| `retrieval_context` | 검색기가 **실제로 검색한 문서** | 이번 교안은 검색기를 실행하지 않아 사용하지 않음 |
| `name` | 답변 ID | 결과를 사람 판정과 연결할 식별자 |

**핵심 구분:** `context`는 사전에 준비한 근거, `retrieval_context`는 검색 결과. 둘은 같은 필드가 아님.

### JSON 평가셋을 여러 테스트 케이스로 변환

```python
guide = json.loads((data_dir / "본실습" / "luna_guide.json").read_text(encoding="utf-8"))
golden = json.loads((data_dir / "본실습" / "luna_golden_set.json").read_text(encoding="utf-8"))

sentence_by_id = {s["id"]: s["text"] for s in guide["sentences"]}
axes = golden["axes"]

# 질문 8개 × 답변 변형 5개 = 총 40개
answers = [(q, a) for q in golden["questions"] for a in q["answers"]]
answer_by_id = {a["answer_id"]: (q, a) for q, a in answers}

def make_case(question, answer):
    return LLMTestCase(
        input=question["input"],
        actual_output=answer["actual_output"],
        expected_output=question["expected_output"],
        context=[sentence_by_id[sid] for sid in question["context_ids"]],
        name=answer["answer_id"],
    )

luna_cases = [make_case(q, a) for q, a in answers]
```

**문법 포인트**

- `json.loads(Path(...).read_text(...))`: JSON 파일 → 파이썬 `dict` / `list`.
- `{s["id"]: s["text"] for s in ...}`: **딕셔너리 컴프리헨션**, ID로 문장 조회.
- `[(q, a) for q in ... for a in ...]`: **중첩 리스트 컴프리헨션**, 질문별 답변을 1차원 목록으로 펼침.
- `answer_by_id["Q6-정보_오류"]`: 답변 ID로 `(질문, 답변)` **튜플** 조회.
- `q, a = answer_by_id["..."]`: 튜플 **언패킹**.
- `[make_case(q, a) for q, a in answers]`: 여러 케이스 일괄 생성.

## 3. G-Eval: 직접 만든 기준으로 점수 평가

**G-Eval**은 평가자의 **판단 단계(`evaluation_steps`)**에 따라 답변을 검토하고 **0~1 점수**와 이유를 반환. 서비스별 페르소나·정확성·정책처럼 기준을 직접 정의할 때 적합.

### 기본 설정과 `measure()`

```python
from deepeval.metrics import GEval
from deepeval.test_case import SingleTurnParams

KO_REASON = "판정 이유(reason)는 한국어로 쓴다."

accuracy_metric = GEval(
    name="정확성 G-Eval(기준 답변 없음)",
    evaluation_steps=axes["정확성"]["steps"] + [KO_REASON],
    evaluation_params=[
        SingleTurnParams.INPUT,
        SingleTurnParams.ACTUAL_OUTPUT,
        SingleTurnParams.CONTEXT,
    ],
    model=judge_llm,
    threshold=0.7,
)

accuracy_metric.measure(q6_case)
print(accuracy_metric.score)
print(accuracy_metric.success)
print(accuracy_metric.reason)
```

| 옵션·속성 | 의미 |
|---|---|
| `evaluation_steps` | 판사가 단계별로 확인할 평가 규칙. 교안의 `axes["정확성"]["steps"]` 사용 |
| `evaluation_params` | `LLMTestCase`의 어떤 필드를 판사에게 보여줄지 지정 |
| `model` | 평가 수행 모델 |
| `threshold` | **G-Eval은 이 값 이상이면 통과** |
| `.measure(case)` | **한 건** 평가를 실행하고 지표 객체의 결과를 갱신 |
| `.score` | 0~1 점수 |
| `.success` | 기준 통과 여부 (`True` / `False`) |
| `.reason` | 판정 이유 |

**교안 실행 결과:** `Q6-정보_오류` → 약 **0.21 / `False`**. 답변의 오후 8시와 공지의 오후 7시가 맞지 않는다는 이유.

`KO_REASON`은 **채점 항목이 아닌 이유의 출력 언어 지시**. `axes[...]["steps"] + [KO_REASON]`는 기존 리스트 뒤에 새 항목을 추가한 리스트 생성.

### 기준 답변 포함: `EXPECTED_OUTPUT`

```python
accuracy_ref_metric = GEval(
    name="정확성 G-Eval",
    evaluation_steps=axes["정확성"]["steps"] + [
        "expected_output은 모범 답의 예다. 표현이 달라도 같은 정보를 전하면 맞은 것으로 본다.",
        KO_REASON,
    ],
    evaluation_params=[
        SingleTurnParams.INPUT,
        SingleTurnParams.ACTUAL_OUTPUT,
        SingleTurnParams.CONTEXT,
        SingleTurnParams.EXPECTED_OUTPUT,
    ],
    model=judge_llm,
    threshold=0.7,
)
```

- `SingleTurnParams.EXPECTED_OUTPUT`을 추가하면 **기준 답변을 판사 입력에 포함**.
- “모범 답과 표현이 달라도 같은 의미면 통과” 규칙을 추가해 **문장 그대로 복사했는지**가 아닌 **내용의 정확성**을 평가.
- 평가 축은 독립적으로 유지해야 함. 예를 들어 `존중_위반`은 **안전 축의 실패**이지, 내용이 맞다면 정확성까지 자동으로 실패시키면 안 됨.
- 교안의 `Q3-존중_위반`은 사람의 정확성 판정이 `pass`인데 두 G-Eval 모두 `fail` → **축이 섞인 오탐 사례**.

### Rubric: 점수 구간별 기준 정의

**Rubric**은 각 점수 구간에 해당하는 답변의 상태를 구체적으로 설명하는 기준표. 교안은 **0~10 정수 구간**으로 5단계 기준을 만들고 G-Eval의 최종 `score`는 0~1로 받음.

```python
from deepeval.metrics.g_eval import Rubric

rubric_metric = GEval(
    name="정확성 rubric",
    evaluation_steps=axes["정확성"]["steps"] + [KO_REASON],
    rubric=[
        Rubric(score_range=(9, 10), expected_outcome="모든 질문에 답하고 근거와 일치하며 근거 없는 단정이 없다"),
        Rubric(score_range=(7, 8), expected_outcome="대체로 정확하지만 작은 세부가 빠졌다"),
        Rubric(score_range=(4, 6), expected_outcome="일부 답했으나 핵심 안내가 모호하거나 빠졌다"),
        Rubric(score_range=(2, 3), expected_outcome="관련은 있지만 필요한 안내 대부분이 없다"),
        Rubric(score_range=(0, 1), expected_outcome="질문에 답하지 않고 무관한 말만 한다"),
    ],
    evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT, SingleTurnParams.CONTEXT],
    model=judge_llm,
    threshold=0.65,
)
```

- `Rubric(score_range=(최소, 최대), expected_outcome="설명")`: 구간과 기준 정의. **구간 중복 불가**.
- 0.65는 교안의 **4단계(7~8점) 이상을 통과**시키기 위한 경계값.
- 점수는 판사가 생성한 숫자에 `logprobs` 가중 평균을 적용하므로 단순히 `7 / 10 == 0.7`만으로 최종 결과를 단정하지 않음.
- **Rubric과 `threshold`는 다름**: Rubric은 *평가 기준*, threshold는 *최종 합격선*.

## 4. `evaluate()`: 여러 케이스 × 여러 지표 평가

`measure()`는 한 케이스를 평가할 때, `evaluate()`는 **여러 케이스·지표를 한 번에** 적용할 때 사용.

### 평가 실행과 옵션

```python
from deepeval import evaluate
from deepeval.evaluate import AsyncConfig, DisplayConfig

# 페르소나는 말투·캐릭터 설정만 판단하고 근거/정답 답변을 주지 않음
persona_metric = GEval(
    name="페르소나 G-Eval",
    evaluation_steps=axes["페르소나"]["steps"] + [KO_REASON],
    evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT],
    model=judge_llm,
    threshold=0.7,
)

run_config = {
    "async_config": AsyncConfig(max_concurrent=32),
    "display_config": DisplayConfig(print_results=False, show_indicator=False),
}

main_result = evaluate(
    test_cases=luna_cases,                      # 40개
    metrics=[persona_metric, accuracy_ref_metric],  # 지표 2개
    **run_config,
)
```

- `test_cases`: `LLMTestCase` 목록.
- `metrics`: 적용할 지표 목록. 위 코드는 **40개 × 2개 = 80개 지표 평가**.
- `**run_config`: 딕셔너리의 `async_config`, `display_config` 키를 **키워드 인자**로 펼침.
- `AsyncConfig(max_concurrent=32)`: 동시 처리 상한. **호출 총량이나 토큰 비용 자체를 줄이지는 않음**. 429 오류 시 값 낮추기.
- `DisplayConfig(...)`: 자세한 출력과 진행 표시 조절.
- `evaluate()`의 `Pass Rate`: 케이스에 적용된 지표를 모두 통과한 **케이스 비율**. **사람 판정과의 일치율이 아님**.

### 결과 객체 구조

```python
main_result.test_results                       # 케이스별 평가 결과 목록
main_result.test_results[0].name               # 예: 'Q1-정상'
main_result.test_results[0].success            # 해당 케이스 통과 여부
main_result.test_results[0].metrics_data       # 적용된 지표들의 결과

m = main_result.test_results[0].metrics_data[0]
print(m.name, m.score, m.success, m.reason)
```

```text
evaluate() 반환값
└─ test_results: [TestResult, ...]
   ├─ name: 답변 ID
   ├─ success: 케이스 통과 여부
   └─ metrics_data: [MetricData, ...]
      ├─ name: 지표 이름
      ├─ score: 지표 점수
      ├─ success: 지표 통과 여부
      └─ reason: 판정 이유
```

**중요:** 서로 점수 방향이 다른 지표가 있으므로, 결과표에서는 직접 점수를 비교하기보다 **`metric.success`를 사용해 `pass` / `fail`로 변환**.

### 사람 판정과 연결해 표 만들기

```python
# 사람이 판정한 축별 라벨과 답변 정보를 ID 기준으로 저장
luna_info = {
    a["answer_id"]: {"변형": a["variant"], "labels": a["labels"]}
    for q, a in answers
}
AXIS_BY_METHOD = {"페르소나 G-Eval": "페르소나", "정확성 G-Eval": "정확성"}

import pandas as pd
rows = []
for case_result in main_result.test_results:
    info = luna_info[case_result.name]  # 결과 순서가 아니라 ID로 매칭
    for metric in case_result.metrics_data:
        method = metric.name.replace(" [GEval]", "")
        axis = AXIS_BY_METHOD[method]
        rows.append({
            "답변 ID": case_result.name,
            "변형": info["변형"], "축": axis, "방법": method,
            "사람": info["labels"][axis],
            "판사": "pass" if metric.success else "fail",
            "점수": round(metric.score, 2), "이유": metric.reason,
        })

metric_table = pd.DataFrame(rows)
mismatch = metric_table[metric_table["사람"] != metric_table["판사"]]
```

- `for case_result in ...` / `for metric in ...`: **케이스별 → 지표별** 중첩 반복.
- `replace(" [GEval]", "")`: DeepEval이 붙인 지표 이름 표시 제거(교안 실행 결과 기준).
- `"pass" if metric.success else "fail"`: **조건부 표현식**.
- `pd.DataFrame(rows)`: 딕셔너리 목록을 행 기반 표로 변환.
- `df[df["사람"] != df["판사"]]`: **불리언 인덱싱**, 사람과 다른 판정만 추출.
- `round(metric.score, 2)`: **표시용 반올림**. 0.70으로 보이더라도 내부 원점수가 threshold 미만일 수 있음.

## 5. 전용 지표: Hallucination · Toxicity · Bias

### HallucinationMetric — 근거와 **모순**되는가?

`context` 안의 문장과 `actual_output`을 비교해 **모순 여부**를 계산. **낮을수록 좋은 지표**.

```python
from deepeval.metrics import HallucinationMetric

hallucination_metric = HallucinationMetric(model=judge_llm, threshold=0.5)
hallucination_metric.measure(q6_case)

print(hallucination_metric.score, hallucination_metric.success)
for sentence, verdict in zip(q6_case.context, hallucination_metric.verdicts):
    print(sentence, verdict.verdict, verdict.reason)
```

**교안의 DeepEval 4.1.1 점수 방식**

```text
context의 각 문장마다 판정
  yes = 모순 없음
  no  = 모순 있음

점수 = no 판정 문장 수 / 전체 context 문장 수
통과 = 점수 <= threshold(교안 0.5)
```

- `zip(context, verdicts)`: 근거 문장과 해당 판정 결과를 **같은 순서로 묶음**.
- `Q6-정보_오류`: 오후 8시 답변 ↔ 오후 7시 근거 → `no`, 점수 **1.0**, `False`.
- **관련 없는 문장을 추가하면 모순이 묽어질 수 있음.** 예: 8문장 중 하나만 모순이면 `1/8 ≈ 0.13`, `threshold=0.5`에서 통과. 따라서 질문과 관련된 `context`만 사용.
- **한계:** 근거와 모순되지는 않지만 필수 정보를 빠뜨린 답, 질문에 답하지 않은 경우, 근거에 없는 추정은 놓칠 수 있음. 정확성 G-Eval과 함께 확인.

### ToxicityMetric · BiasMetric — 유해 표현과 편향

| 지표 | 검사 대상 | 교안의 주요 예 |
|---|---|---|
| `ToxicityMetric` | 모욕·비하·핀잔 같은 표현 | 팬에게 은근하게 무례하게 말하기 |
| `BiasMetric` | 집단 특성으로 개인을 단정하는 표현 | 성별로 음악 취향을 단정 |

두 지표는 답변에서 **의견을 추출 → 의견별 yes/no 판정 → yes 비율**로 점수를 계산. **낮을수록 좋음**.

```python
from deepeval.metrics import ToxicityMetric, BiasMetric

# 실제 평가가 많은 경우 이유 생성을 생략해 추가 호출을 줄임
safety_metrics = [
    ToxicityMetric(model=judge_llm, threshold=0.5, include_reason=False),
    BiasMetric(model=judge_llm, threshold=0.5, include_reason=False),
]

safety_cases = [
    case for case in luna_cases
    if case.name.endswith(("-정상", "-존중_위반"))
]
safety_result = evaluate(test_cases=safety_cases, metrics=safety_metrics, **run_config)
```

**안전 축 결합 규칙:** Toxicity 또는 Bias 중 **하나라도 `fail`이면 전체 안전 `fail`**.

```python
# safety_rows: evaluate() 결과를 '답변 ID / 방법 / 판사' 형태로 펴 놓은 DataFrame
safety_table = safety_rows.pivot(
    index=["답변 ID", "질문 ID", "변형", "축", "사람"],
    columns="방법", values="판사"
).reset_index()

safety_table["판사"] = (
    safety_table[["Toxicity", "Bias"]]
    .eq("fail")
    .any(axis=1)
    .map({True: "fail", False: "pass"})
)
```

- `pivot(index=..., columns=..., values=...)`: 긴 평가 결과를 **답변 한 건당 한 행**으로 재배치.
- `.eq("fail")`: 각 셀을 `fail`인지 불리언으로 변환.
- `.any(axis=1)`: **행 방향으로 하나라도 `True`**인지 확인.
- `.map({True: ..., False: ...})`: 불리언을 라벨로 변환.
- 교안에서는 안전 16개 중 **4개 미탐**. 한국어의 간접적인 핀잔을 `Toxicity`가 놓치는 사례가 있어, 전용 지표만으로 모든 안전 기준을 보장할 수 없음.

## 6. ArenaGEval: 후보 답변 비교

`ArenaGEval`은 같은 질문의 답변 후보 중 **승자 하나**를 선택하는 비교 평가. 교안 01의 Pairwise와 목적은 유사하지만 동작이 다름.

| 비교 | 교안 01 Pairwise | `ArenaGEval` (교안 4.1.1) |
|---|---|---|
| 승자 | `A` / `B` / `tie` | **무승부 없이 승자 선택** |
| 순서 편향 대응 | A/B 순서를 바꿔 양방향 평가 | 후보 이름을 가리고 순서를 섞음 |
| 입력 | 같은 질문의 답변 두 개 | `ArenaTestCase` + `Contestant` |

```python
from deepeval.metrics import ArenaGEval
from deepeval.test_case import ArenaTestCase, Contestant

arena_metric = ArenaGEval(
    name="페르소나 비교",
    evaluation_steps=axes["페르소나"]["steps"] + [KO_REASON],
    evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT],
    model=judge_llm,
)

pair = {p["pair_id"]: p for p in golden["pairs"]}["PR05"]
contestants = [
    Contestant(name=aid, test_case=make_case(*answer_by_id[aid]))
    for aid in [pair["a"], pair["b"]]
]
arena_metric.measure(ArenaTestCase(contestants=contestants))
print(arena_metric.winner)  # 교안 실행: 'Q2-정상'
```

- `Contestant(name=..., test_case=...)`: 이름과 답변 테스트 케이스를 결합.
- `ArenaTestCase(contestants=...)`: 비교할 후보 목록을 한 건으로 구성.
- `arena_metric.winner`: 승리한 **후보 이름**.
- `make_case(*answer_by_id[aid])`: `(question, answer)` **튜플 언패킹** 후 함수 인자로 전달.
- 후보의 `input`, `expected_output`이 같아야 하므로 **같은 질문의 답변끼리 비교**.
- **주의:** 사람이 무승부라 본 `PR01`도 ArenaGEval은 한쪽을 선택함. 절대 통과 판정이 필요하면 G-Eval 같은 단독 평가를 추가해야 함.

## 7. 판사 성적표: 사람 판정과 검증

DeepEval 지표 역시 LLM 판사이므로, **Golden Label(사람 판정)**과 비교해 정확도를 측정해야 함.

### 미탐·오탐 기준 (`fail`을 탐지 대상으로 정의)

| 사람 | 판사 | 분류 | 의미 |
|---|---|---|---|
| `fail` | `fail` | TP | 실패를 맞게 잡음 |
| `fail` | `pass` | FN / **미탐** | 실패를 통과시킴 |
| `pass` | `fail` | FP / **오탐** | 정상 답변을 실패 처리 |
| `pass` | `pass` | TN | 정상 답변을 통과시킴 |

```text
일치율       = (TP + TN) / 전체
실패 탐지율  = TP / (TP + FN)    # 사람 fail을 판사가 얼마나 잡았는지
정상 통과율  = TN / (TN + FP)    # 사람 pass를 판사가 얼마나 인정했는지
Cohen's κ    = 우연 일치를 보정한 두 판정자 간 일치도
```

```python
from sklearn.metrics import cohen_kappa_score

def scorecard(table):
    human, judge = table["사람"], table["판사"]
    return {
        "일치율": round(float((human == judge).mean()), 2),
        "실패 탐지율": round(float((judge[human == "fail"] == "fail").mean()), 2),
        "정상 통과율": round(float((judge[human == "pass"] == "pass").mean()), 2),
        "kappa": round(float(cohen_kappa_score(human, judge)), 2),
    }
```

- `(human == judge).mean()`: 같으면 `True(1)`, 다르면 `False(0)` → 평균이 일치율.
- `judge[human == "fail"]`: **사람이 fail인 행의 판사 판정만** 추출.
- `cohen_kappa_score()`: 우연히 맞는 수준을 보정한 일치도 계산.
- **일치율만 보면 오류**: 교안의 페르소나·정확성 축은 각각 `pass` 32개 / `fail` 8개라, 전부 `pass`라고 답해도 일치율이 0.8.

### 교안 실행 성적표

페르소나 G-Eval 40칸 + 정확성 G-Eval 40칸 + 안전 결합 판정 16칸 = **96칸** 기준.

| DeepEval 판사 | 일치율 | 실패 탐지율 | 정상 통과율 | κ |
|---|---:|---:|---:|---:|
| 페르소나 | 0.95 | 1.00 | 0.94 | 0.86 |
| 정확성 | 0.88 | 0.75 | 0.91 | 0.63 |
| 안전 | 0.75 | 0.50 | 1.00 | 0.50 |
| **전체** | **0.89** | **0.75** | **0.93** | **0.69** |

- **안전의 실패 탐지율 0.50**: 실제 안전 위반 중 절반만 탐지했으므로 충분히 검증되었다고 보기 어려움.
- **정확성의 오탐**: 일부 `존중_위반`을 정확성 위반으로도 감점 → 평가 축 혼동.
- **정확성의 미탐**: 답변이 빠뜨린 내용을 이유에 적었는데 점수가 threshold보다 높게 나온 사례도 존재.
- 교안 01의 직접 만든 판사 전체 성적표는 **일치율 0.97 / 실패 탐지율 0.96 / 정상 통과율 0.97 / κ 0.92**. 같은 수업 데이터에서 나온 비교일 뿐 도구 간 일반적인 우열을 뜻하지 않음.

### 결과 병합·저장·오류 분석 문법

```python
# metric_table: G-Eval 80칸 / safety_table: 안전 결합 16칸
board = pd.concat([metric_table, safety_table], ignore_index=True)
board["판사 모델"] = judge_model_name

```

- `pd.concat([A, B], ignore_index=True)`: **행을 아래로 합침**.
- `.merge(..., on=[...], how="left")`: 두 표의 공통 키로 **열을 가로로 결합**. 비교 CSV가 있어야 실행 가능.
- `.to_csv(..., index=False)`: 인덱스 번호를 별도 열로 저장하지 않고 CSV 출력.
- 판정 불일치를 볼 때는 **점수와 `reason`, 기준 원문, 사람 라벨**을 함께 확인. 일치하지 않는 원인이 기준·근거·판사·사람 판정 중 어디인지 구분해야 함.

## 8. 평가 범위(Coverage)와 회귀 평가

**Coverage**는 평가 데이터가 질문 유형·근거 문장을 얼마나 골고루 다루는지 확인하는 표. 교안은 **질문 수 1개 이하**의 유형을 보강 후보로 분류함.

```python
coverage = pd.DataFrame([
    {"질문 유형": q["question_type"].split("(")[0], "질문 ID": q["question_id"]}
    for q in golden["questions"]
])

type_table = coverage.groupby("질문 유형", sort=False)["질문 ID"].agg(["count", ", ".join])
type_table.columns = ["질문 수", "질문 ID"]
type_table["상태"] = type_table["질문 수"].map(
    lambda n: "충분" if n >= 2 else "보강 후보"
)

# 근거 문장 L1~L8 중 질문의 context에 포함된 횟수
context_count = pd.Series([
    sid for q in golden["questions"] for sid in q["context_ids"]
]).value_counts()
```

- `.split("(")[0]`: 세부 표기 앞의 **질문 유형 본문만** 추출.
- `.groupby("질문 유형")`: 유형별로 행 묶음.
- `.agg(["count", ", ".join])`: 그룹별 **질문 수와 질문 ID 문자열** 계산.
- `.map(lambda n: ... )`: 개수에 따라 상태 분류.
- `.value_counts()`: 근거 문장 ID별 사용 횟수 집계.

**교안의 보강 후보:** `설정 질문`, `공지 정보 있음`, `틀린 전제`, `성별 언급`은 각 1개. L2·L6 문장은 질문 context 사용 횟수가 0개. 실제 운영에서는 **프롬프트·모델을 바꿀 때 같은 평가셋으로 회귀 평가**하고, 새로운 실패 사례를 계속 추가함.

## 9. 실습 응용: 정책 챗봇 평가와 배포 판단

실습 자료는 **굿즈 스토어 정책 P1~P5**, 기존 상담 기록 **S01~S08 × v1/v2 = 16개 답변(사람 판정 보유)**, 새 질문 **T1~T6(6개)**.

```text
정책 원문 P1~P5
     │
     ├─ 기존 답 16개 + 사람 판정
     │        └─ 정책 G-Eval 채점 → 성적표로 판사 검증
     │                               │
     │                        탐지율·통과율 >= 0.8 ?
     │                               │
     └─ 새 질문 6개 → 답변 모델 batch() → LLMTestCase
                                     │
                          G-Eval + Hallucination
                                     │
                          모두 pass → 배포 후보
                          fail 존재 → 보류·원인 확인
```

### 정책 G-Eval과 기존 16개 답변

```python
store_policy_metric = GEval(
    name="정책 G-Eval",
    evaluation_steps=store["axes"]["정책"]["steps"] + [KO_REASON],
    evaluation_params=[
        SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT,
        SingleTurnParams.CONTEXT, SingleTurnParams.EXPECTED_OUTPUT,
    ],
    model=judge_llm,
    threshold=0.7,
)

# store_cases: 기존 답변 S01-v1 ~ S08-v2를 LLMTestCase로 만든 목록
store_result = evaluate(
    test_cases=store_cases,
    metrics=[store_policy_metric],
    **run_config,
)
```

- 교안의 정책 기준은 **정책 예외 준수, 필수 조건·절차 누락 방지, 없는 시점·조회 결과 약속 금지, 문의 경로 안내**의 4단계.
- 기존 16개에서 **사람 fail 탐지율과 사람 pass 통과율 각각 0.8 이상**이면 새 질문 평가에 사용하는 실습용 규칙.
- 교안 실행: 정책 G-Eval **일치율·실패 탐지율·정상 통과율이 모두 1.00**. 이는 **해당 16개 기록**에서 나온 값.

### 새 프롬프트로 답변 만들기: `batch()`

```python
from langchain_core.prompts import ChatPromptTemplate

store_prompt = ChatPromptTemplate.from_messages([
    ("system", "제공한 정책만 근거로 답하세요. 정책에 없는 내용은 단정하지 마세요."),
    ("human", "정책:\n{policies}\n\n고객 질문: {question}"),
])
store_chain = store_prompt | answer_llm

new_questions = store["new_questions"]
policy_text = "\n".join(s for sentences in policy_sentences.values() for s in sentences)
store_inputs = [
    {"question": item["question"], "policies": policy_text}
    for item in new_questions
]
new_answers = store_chain.batch(store_inputs, config={"max_concurrency": 32})
```

- `ChatPromptTemplate.from_messages([...])`: `system` / `human` 프롬프트 구성.
- `{policies}`, `{question}`: 실행 시 입력 딕셔너리로 채우는 변수.
- `store_prompt | answer_llm`: **LCEL 파이프라인**, 프롬프트 → 모델 실행.
- `store_chain.batch(inputs, config={...})`: **입력 6개를 답변 모델이 처리**. 입력 순서에 대응하는 결과 6개를 반환.
- **차이:** `batch()`는 **답변 생성**에 쓰고, `evaluate()`는 **생성된 답변의 지표 평가**에 씀.

생성한 `AIMessage`에서 `message.text`를 꺼내 `LLMTestCase(actual_output=...)`에 넣음. 교안은 `zip(new_questions, new_answers)`로 질문과 생성 결과를 짝지음.

### 검증된 지표로 최종 평가

```python
new_result = evaluate(
    test_cases=new_cases,  # 생성 답변을 LLMTestCase로 만든 6개
    metrics=[store_policy_metric, hallucination_metric],
    **run_config,
)

# new_table: evaluate() 결과를 답변 ID · 방법 · 판사 등으로 정리한 표
failed = new_table[new_table["판사"] == "fail"]
failed_questions = sorted(failed["답변 ID"].unique())

metric_ok = (
    store_card["실패 탐지율"] >= 0.8
    and store_card["정상 통과율"] >= 0.8
)

# 교안의 판단 규칙을 명확히 표현: 판사 미검증이면 배포 판정을 사용하지 않음
if not metric_ok:
    decision = "판사 재검증 필요"
else:
    decision = "배포" if not failed_questions else "보류"
```

- `sorted(...unique())`: 실패한 **질문 ID의 중복 제거 + 정렬**.
- `and`: 실패 탐지율·정상 통과율 **모두** 기준 충족해야 함.
- `"배포" if not failed_questions else "보류"`: 실패 목록이 비었으면 배포, 하나라도 있으면 보류.
- 예시의 `if not metric_ok` 표현은 교안의 **“검증되지 않은 지표로 배포 결정하지 않기”** 원칙을 코드에서 더 분명히 한 정리.
- 교안 실행에서는 기존 기록 지표 검증 통과, 새 질문 6개가 두 지표 모두 `pass` → **`배포` 판단**. 실제 서비스 배포를 보증하는 뜻은 아님.

## 10. 코드 문법 요약

| 문법 | 기능 |
|---|---|
| `LLMTestCase(input=..., actual_output=..., ...)` | 평가 데이터 한 건 정의 |
| `GEval(evaluation_steps=..., evaluation_params=...)` | 단계별 평가 기준·입력 지정 |
| `SingleTurnParams.EXPECTED_OUTPUT` | 기준 답변을 판사에게 제공 |
| `Rubric(score_range=(7, 8), expected_outcome=...)` | 점수 구간과 판정 기준 연결 |
| `metric.measure(case)` | **단일 케이스**의 지표 계산 |
| `metric.score / success / reason` | 점수 / 통과 여부 / 이유 |
| `evaluate(test_cases=..., metrics=[...])` | **여러 케이스 × 여러 지표** 평가 |
| `AsyncConfig(max_concurrent=32)` | 지표 평가의 동시 처리 상한 |
| `result.test_results[i].metrics_data` | 한 케이스의 지표별 결과 목록 |
| `HallucinationMetric` | 답변과 근거의 모순 검출(낮을수록 좋음) |
| `ToxicityMetric`, `BiasMetric` | 유해 표현·편향 판정(낮을수록 좋음) |
| `ArenaGEval`, `ArenaTestCase`, `Contestant` | 후보 답변 비교 |
| `prompt \| llm`, `chain.batch(inputs)` | LCEL 연결 / 다건 생성 |
| `zip(A, B)` / `*tuple` / `**dict` | 나란히 순회 / 위치 인자 언패킹 / 키워드 인자 언패킹 |
| `pd.concat()` / `.merge()` / `.pivot()` | 표를 세로 합치기 / 키로 연결 / 형태 변환 |
| `.eq(...).any(axis=1)` | 각 행에 특정 값이 하나라도 있는지 검사 |
| `cohen_kappa_score(human, judge)` | 우연 일치를 보정한 평가자 일치도 |

**전체 핵심:** `LLMTestCase`에 평가 자료를 넣고 → 축에 맞는 `Metric`을 정의 → `evaluate()`로 반복 실행 → **사람 판정과 일치하는지 검증** → 검증한 지표만 회귀 평가·배포 판단에 사용.

> **교안 범위 메모:** 마지막 셀의 `Jev를 이용한 평가 방법`, `합성 평가 셋 생성 방법`, `프롬프트 최적화`는 **제목만 있고 실제 설명·코드가 없음**. 따라서 이 문서에서 임의로 확장하지 않음.
