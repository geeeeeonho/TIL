# LightRAG — 색인과 검색 핵심 정리

> **핵심:** 문서에서 **개체(Entity)·관계(Relationship)**를 추출해 **지식 그래프 + 벡터**로 저장한다. 검색 시에는 질문의 **구체 키워드 → 개체**, **주제 키워드 → 관계**를 찾고, 필요하면 원문 청크까지 결합한다. Microsoft GraphRAG와 달리 **커뮤니티 보고서를 생성하지 않는다.**
>
> 교안 기준: 곡성·구례 관광 안내문 32편 색인, 추가 문서 1편, 골드 질문 12개. 뒤쪽 실습은 장애 보고서 20편과 질문 8개를 사용한다.

## 1. LightRAG의 개념과 색인 구조

### 1-1. 무엇이 다른가?

LightRAG는 **비정형 문서에서 LLM이 그래프를 자동 추출하는 GraphRAG 방식**이다. 사람이 미리 노드·관계 종류를 설계하고 Cypher로 조회하는 **도메인 지식 그래프**와 구별한다.

| 비교 | Microsoft GraphRAG(교안 01) | LightRAG |
|---|---|---|
| 색인 | 개체·관계 추출 → 커뮤니티 생성 → 커뮤니티 보고서 작성 | 개체·관계 추출 → 그래프·벡터 저장 |
| 전역 검색 | 커뮤니티 보고서를 대상으로 넓은 범위 요약 | **관계 벡터 검색**으로 관련 주제 탐색 |
| 관계 표현 | 개체와 관계·커뮤니티 중심 | **관계 키워드·설명** 중심(정해진 관계 이름 없음) |
| 기본 저장 | GraphRAG의 색인 결과물 | 그래프·벡터·문서 상태를 로컬 파일에 저장 |
| 문서 갱신 | 색인 파이프라인 기준 | 새 문서 `ainsert`, 삭제 `adelete_by_doc_id` |

- **색인 부담 감소:** 커뮤니티 보고서 작성 단계가 없다. 교안의 미리 만든 *관광 문서 32편 색인 사례*에서는 LightRAG 약 **34회**, Microsoft GraphRAG 약 **147회** LLM 호출. **이 실습의 비교값**이며 일반적인 호출 수 비율은 아님.
- **관계는 이름 대신 의미:** `등산로, 연결`과 같은 `keywords`, 관계 내용인 `description`을 붙여 벡터 검색한다. Cypher의 `:LOCATED_IN` 같은 확정된 관계 유형 필터와는 다름.
- **그래프 DB 필수 아님:** 기본은 GraphML·JSON 파일. 필요하면 Neo4j 등 다른 저장소로 교체 가능.

### 1-2. 색인(Indexing) 과정

```text
[원문 문서]
    │  문서 분할
    ▼
[텍스트 청크]
    │
    ▼
[LLM: 개체·관계 추출 및 설명 생성]
    │
    ├─ [지식 그래프] ─ 개체 / 개체 사이 연결 / 관계 키워드·설명
    │
    ├─ [개체 벡터] ─ 개체 이름 + 설명
    ├─ [관계 벡터] ─ 관계 키워드 + 양 끝 개체 + 설명
    └─ [청크 벡터] ─ 원문 청크
                │
                ▼
       [문서·청크·처리 상태 저장]
```

기본 저장 구조(`working_dir/workspace`):

| 주요 파일 | 내용 | 검색에서의 역할 |
|---|---|---|
| `graph_chunk_entity_relation.graphml` | 개체와 관계 | 연결된 이웃 개체·관계 탐색 |
| `vdb_entities.json` | 개체 임베딩 | `local`의 출발점 |
| `vdb_relationships.json` | 관계 임베딩 | `global`의 출발점 |
| `vdb_chunks.json` | 청크 임베딩 | `naive`·`mix` 직접 검색 및 관련 청크 선택 |
| `kv_store_*.json` | 원문·청크·문서 처리 상태 | 문맥 복원, 중복 문서 확인 |

> 기본 그래프에서 `source` / `target`은 **관계 방향을 뜻하지 않는다.** 관계는 방향 없이 저장된다. 또한 개체·관계의 설명은 LLM이 추출·요약한 내용이며, 원문 자체와 동일하지 않다.

## 2. 검색(Search) 원리 — 가장 중요한 부분

### 2-1. 질문을 두 수준의 키워드로 분해

`naive`를 제외한 모드는 LLM으로 질문을 읽고 두 종류의 키워드를 추출한다.

| 키워드 | 의미 | 검색 대상 | 예시 |
|---|---|---|---|
| `ll_keywords` (low-level) | 고유명사·구체 대상 | **개체 벡터** | `곡성`, `구례`, `화엄사계곡` |
| `hl_keywords` (high-level) | 주제·의도·관계 맥락 | **관계 벡터** | `생태 관찰`, `유학 교육 장소` |

```text
[질문]
   │
   ├─ LLM 키워드 추출 ─┬─ 구체 키워드 → 개체 벡터 → 연결 관계·청크
   │                  └─ 주제 키워드 → 관계 벡터 → 양 끝 개체·청크
   │
   └─ 질문 자체의 임베딩 ───────────────→ 청크 벡터 (naive·mix)
                                            │
                       [문맥 후보 병합·중복 제거]
                                            │
                          [선택적 청크 리랭킹]
                                            │
                         [chunk_top_k개 선택]
                                            │
                     [개체·관계·청크 → 답변 LLM]
```

**중요:** 키워드는 문자열 일치/BM25 검색에 쓰이는 게 아니다. LLM이 뽑은 키워드를 **임베딩한 후 벡터 유사도 검색**한다. 매번 LLM이 키워드를 다르게 뽑을 수 있으며, `QueryParam`으로 직접 고정 가능.

### 2-2. 검색 모드 5가지

| 모드 | 무엇을 벡터 검색하나? | 주요 처리 | 적합한 질문 |
|---|---|---|---|
| `naive` | **청크** | 질문 임베딩 → 관련 원문 청크 | 단일 사실·수치 |
| `local` | **개체** | 구체 키워드 → 개체 → 그래프의 인접 관계·청크 | 특정 개체 주변 정보 |
| `global` | **관계** | 주제 키워드 → 관계 → 양 끝 개체·청크 | 주제에 맞는 대상 탐색 |
| `hybrid` | **개체 + 관계** | `local` + `global` 후보 결합·중복 제거 | 대상과 주제가 함께 있는 질문 |
| `mix` | **개체 + 관계 + 청크** | `hybrid` + 질문 기반 직접 청크 검색 | 멀티홉·여러 근거 결합 |

- `naive`: 별도 키워드 추출 없음. **그래프를 사용하지 않고** 청크를 직접 검색.
- `local`: 개체 벡터에서 `top_k`개를 찾은 뒤 그래프 연결을 따라 관련 내용을 수집.
- `global`: 관계 벡터에서 `top_k`개를 찾음. **Microsoft GraphRAG Global과 달리 커뮤니티 보고서를 조회하지 않는다.**
- `hybrid`: **BM25 + Dense 하이브리드 검색이 아님.** LightRAG의 개체 경로와 관계 경로를 합치는 뜻.
- `mix`: `hybrid`에 **원문 청크 벡터 직접 검색**을 추가한 모드이며 `QueryParam`의 기본 모드.

모든 모드에서 수집한 원문 후보는 중복을 제거한 뒤 필요한 경우 **청크에만** 리랭킹을 적용하고, 최종 `chunk_top_k`개로 제한한다. 개체·관계 설명은 별도로 답변 문맥에 포함될 수 있다.

**검색 한계:** LightRAG `global`은 자료 전체를 전수 조사하는 모드가 아니다. 전역 질문이라도 관련 근거가 선택된 관계와 청크 범위 밖에 있으면 항목이 누락될 수 있다. `mix`도 이 한계를 완전히 없애지는 못한다.

## 3. 핵심 코드 문법

아래 코드는 **교안에서 사용한 주요 API만 남긴 Jupyter 비동기 코드 예시**다. 실행에는 `lightrag`, `langchain-openai` 등의 설치와 API 키, 문서 파일이 필요하다. 실습의 `tracker`, `rag` 등은 순서대로 정의하는 전제.

### 3-1. LLM·임베딩 함수 연결

LightRAG는 모델 객체 자체보다 **비동기 호출 함수**(`llm_model_func`, `embedding_func`)를 전달받는다.

```python
import os
import numpy as np
from langchain_openai import OpenAIEmbeddings
from lightrag.llm.openai import openai_complete_if_cache
from lightrag.utils import EmbeddingFunc, TokenTracker

model_name = os.getenv("OPENAI_CHAT_MODEL", "gpt-5.6-luna")
tracker = TokenTracker()                 # LLM 호출 수·토큰 집계

embedding_model = OpenAIEmbeddings(
    model="text-embedding-3-large", dimensions=768
)

async def course_llm(prompt, **kwargs):
    return await openai_complete_if_cache(
        model_name, prompt, token_tracker=tracker, **kwargs
    )

async def course_embed(texts):
    vectors = await embedding_model.aembed_documents(texts)
    return np.array(vectors)

embedding_func = EmbeddingFunc(
    embedding_dim=768, func=course_embed
)
```

- `**kwargs`: LightRAG가 전달하는 추가 인자(시스템 프롬프트 등)를 그대로 전달.
- `EmbeddingFunc(embedding_dim=768, ...)`: 실제 임베딩 모델 출력 차원과 맞춰야 함.
- `TokenTracker`: 학습용 호출량 측정. `tracker.reset()` 후 특정 작업의 사용량 확인.

### 3-2. LightRAG 생성과 색인

```python
from pathlib import Path
from lightrag import LightRAG

rag = LightRAG(
    working_dir="output/lightrag",  # 저장 상위 폴더
    workspace="tour",               # 색인별 작업 공간
    llm_model_func=course_llm,
    embedding_func=embedding_func,
    addon_params={
        "language": "Korean",
        "entity_types_guidance": "장소, 인물, 단체, 행사 중 하나로 분류한다. 맞는 것이 없으면 Other."
    },
    entity_extract_max_gleaning=0,  # 추가 추출 단계를 끈 실습 설정
    enable_llm_cache=False,        # 검색 호출량을 재기 위한 실습 설정
)

await rag.initialize_storages()    # 색인·검색 전에 저장소 열기

paths = sorted(Path("data/본실습/docs").glob("*.txt"))
# 실제 교안에서는 '추가 시연용 1편'을 이 목록에서 제외해 32편만 넣는다.
texts = [p.read_text(encoding="utf-8") for p in paths]
file_paths = [p.name for p in paths]

await rag.ainsert(texts, file_paths=file_paths)
```

| 문법 | 역할 |
|---|---|
| `LightRAG(...)` | 저장 위치, 모델 함수, 색인·검색 설정 지정 |
| `addon_params` | 추출·요약 프롬프트의 한국어/개체 유형 안내 |
| `initialize_storages()` | 그래프·벡터·문서 저장소 초기화 |
| `ainsert(texts, file_paths=...)` | 문서 색인(개체·관계 추출 및 저장) |
| `workspace="tour"` | 다른 색인(예: `incident`)과 저장 폴더 분리 |

`ainsert()`로 기존 문서를 재입력해도 새 문서로 처리되지 않을 수 있다. **같은 커널에서 저장 폴더만 삭제해 재실행하는 방식은 피한다.** 교안에서는 재색인 시 커널 재시작을 안내한다.

### 3-3. `QueryParam`으로 검색 조건 지정

```python
from lightrag import QueryParam

question = "선비가 공부하던 곳은 어디인가?"  # 개념 설명용 질문

param = QueryParam(
    mode="mix",               # naive | local | global | hybrid | mix
    chunk_top_k=5,            # 답변 문맥에 넣을 원문 청크 상한
    enable_rerank=False,      # 리랭킹 적용 여부
)

# 검색만 수행: 답변을 생성하지 않음
search_result = await rag.aquery_data(question, param=param)

entities = search_result["data"]["entities"]
relationships = search_result["data"]["relationships"]
chunks = search_result["data"]["chunks"]
keywords = search_result["metadata"]["keywords"]

print(len(entities), len(relationships), len(chunks))
print(keywords["high_level"], keywords["low_level"])

# 같은 키워드로 다른 모드를 비교하면 LLM 키워드 추출 차이를 통제할 수 있음
fixed_param = QueryParam(
    mode="local", chunk_top_k=5, enable_rerank=False,
    hl_keywords=keywords["high_level"],
    ll_keywords=keywords["low_level"],
)
fixed_result = await rag.aquery_data(question, param=fixed_param)
```

- `top_k`: `local`의 개체 / `global`의 관계 등 **그래프 검색 출발 후보** 수(교안 설명의 기본값 40).
- `chunk_top_k`: **답변에 넘기는 청크**의 최종 상한(기본 20, 교안은 5).
- `aquery_data()`: 검색 결과의 개체·관계·청크를 확인. `naive`를 제외하면 키워드 추출에 LLM을 사용할 수 있지만, **답변 LLM 호출은 없음**.
- `hl_keywords`, `ll_keywords`: 수동 키워드 지정으로 재추출을 생략하고 모드를 비교할 때 사용.

### 3-4. 검색 + 답변 생성과 근거 문서 확인

```python
param = QueryParam(
    mode="mix", chunk_top_k=5,
    response_type="한국어로 한두 문장. 근거에 없으면 모른다고 답한다",
    enable_rerank=False,
)

result = await rag.aquery_llm(question, param=param)
answer = result["llm_response"]["content"]

# 근거는 LLM 요약(개체·관계 설명)이 아니라 '원문 청크'의 문서로 판정
source_doc_ids = sorted({
    chunk["file_path"].removesuffix(".txt")
    for chunk in result["data"]["chunks"]
})

print(answer)
print("넘긴 근거 문서:", source_doc_ids)
```

**`aquery_data()` vs `aquery_llm()`**

| API | 반환 | LLM 사용(교안 설정) |
|---|---|---|
| `aquery_data()` | 검색 문맥의 개체·관계·청크 | 보통 키워드 추출 1회(`naive`·고정 키워드 제외) |
| `aquery_llm()` | 검색 문맥 + 생성 답변 | `naive` 답변 1회 / 나머지 키워드 추출 + 답변 약 2회 |

`### References`의 파일명도 답변 근거 추적에 활용한다. 다만 **LLM이 답을 만들었다는 것과 정답 근거 문서가 실제로 전달되었다는 것은 별개**이므로 청크의 `file_path`를 직접 비교한다.

### 3-5. 문서 추가·삭제와 그래프 확인

```python
import networkx as nx

# 새 문서만 색인. 삭제할 수 있도록 IDs를 명시해 관리
await rag.ainsert(
    new_text,
    ids="INC-0922",
    file_paths="INC-0922.txt",
)

# 문서·청크·해당 문서에만 속한 개체·관계 정리
result = await rag.adelete_by_doc_id("INC-0922")
print(result.status)

# 기본 GraphML 저장소의 개체·관계를 확인
G = nx.read_graphml(
    "output/lightrag/tour/graph_chunk_entity_relation.graphml"
)
print(G.number_of_nodes(), G.number_of_edges())

# 모든 작업을 마친 뒤 저장소 닫기
await rag.finalize_storages()
```

`new_text`는 추가할 문서 본문 문자열이다. **수정할 문서 = 기존 ID 삭제 → 수정한 본문을 다시 추가.** 중복 개체는 기존 그래프와 병합되고, 삭제 시 다른 문서에도 등장하는 개체는 남긴다(설명을 재구성할 수 있음).

## 4. 실습 응용 — 리랭킹·라우팅·평가

### 4-1. 리랭킹(Reranking)

임베딩 검색으로 찾은 **청크 후보의 순서를 Cross-Encoder가 다시 정한다.** 이미 빠진 정답 근거를 새로 검색하는 기능은 아니다.

```text
[개체·관계·청크에서 후보 수집]
          ↓
[청크 후보 병합·중복 제거]
          ↓
[Cross-Encoder: 질문 + 청크를 함께 평가]  ← 선택적
          ↓
[점수순으로 정렬 → chunk_top_k개]
```

교안의 장애 실습은 `Qwen/Qwen3-Reranker-0.6B`를 로컬에서 사용하고, 아래와 같은 함수 형식을 LightRAG에 연결한다.

```python
from langchain_community.cross_encoders import HuggingFaceCrossEncoder

cross_encoder = HuggingFaceCrossEncoder(
    model_name="Qwen/Qwen3-Reranker-0.6B",
    model_kwargs={"device": "cpu", "max_length": 1024},
)

async def practice_rerank(query, documents, top_n=None, **kwargs):
    scores = cross_encoder.score([(query, doc) for doc in documents])
    order = sorted(range(len(documents)), key=lambda i: scores[i], reverse=True)
    if top_n is not None:
        order = order[:top_n]
    return [
        {"index": i, "relevance_score": float(scores[i])}
        for i in order
    ]

# LightRAG 생성 시 연결(별도 incident 색인을 만드는 경우)
practice_rag = LightRAG(
    working_dir="output/lightrag", workspace="incident",
    llm_model_func=course_llm, embedding_func=embedding_func,
    rerank_model_func=practice_rerank,
)
```

- 실제 사용: `QueryParam(mode="mix", enable_rerank=True, chunk_top_k=5)`.
- **`enable_rerank=True`만으로는 작동하지 않음.** 생성 시 `rerank_model_func`를 연결해야 한다.
- 리랭커는 **청크만** 재정렬하며, 후보에 이미 포함된 정답 근거가 상위 5개에서 밀린 경우 등에 효과.
- 교안의 CPU 실습은 질문당 시간이 많이 들 수 있어 Q5·Q6만 비교. 켬/끔 비교 시 **추출 키워드를 동일하게 고정**해야 함.

### 4-2. 질문별 모드 라우팅(Jev)

실습에서는 Jev의 `TypeSafeClassifier`가 질문 성격을 보고 `naive`, `local`, `global`, `mix` 중 하나를 선택한다. `hybrid`는 라우팅 후보에서 제외한다.

```python
from langchain_typesafe import Choice, TypeSafeClassifier

router = TypeSafeClassifier(
    model=os.getenv("TYPESAFE_MODEL", "jev-1.13.0")
)

route_question = Choice(
    instructions="질문에 맞는 LightRAG 검색 모드를 고른다.",
    criteria={
        "naive": "한 문서에서 단일 사실을 찾는 질문",
        "local": "특정 개체와 바로 이어진 내용을 묻는 질문",
        "global": "주제에 해당하는 대상을 찾는 질문",
        "mix": "여러 문서를 잇거나 전체에서 항목·유형을 정리하는 질문",
    },
)

decision = router.invoke({
    "state": question,
    "questions": {"route": route_question},
})
route = decision.choices["route"].choice

param = QueryParam(mode=route, chunk_top_k=5, enable_rerank=False)
```

`route`는 검색 경로를 고르는 **별도 분류 결과**다. 전역 질문이라도 근거를 폭넓게 모으기 위해 `mix`로 보낼 수 있다. 분류 확률이 비슷하면 모드 선택이 불안정할 수 있다.

### 4-3. 성능 비교: 정답 근거 포함률

교안에서 정답을 미리 연결한 질문을 **골드 질문(Gold Question)**이라 하며, 각 질문에는 `gold_doc_ids`가 있다.

```python
gold_ids = question_row["gold_doc_ids"]   # 미리 지정한 정답 근거 문서
retrieved_ids = source_doc_ids             # LLM에 실제 전달한 청크의 문서

hit_docs = sum(doc_id in retrieved_ids for doc_id in gold_ids)
all_hit = int(hit_docs == len(gold_ids))
```

| 지표 | 의미 |
|---|---|
| `docs_given` | 실제 넘긴 원문 문서 수(중복 제거) |
| `gold_docs` | 정답 근거로 지정한 문서 수 |
| `hit_docs` | 실제 넘긴 문서 중 정답 근거와 일치한 수 |
| `hit_docs / gold_docs` | 정답 근거 문서 포함률 |
| `all_hit` | 정답 근거를 전부 넘겼으면 1, 아니면 0 |
| `llm_calls`, `input_tokens`, `output_tokens`, `seconds` | 호출 비용·시간 비교 |

**근거 포함률은 답변 정확도 자체가 아니다.** 맞는 문서를 넘겨도 답변이 틀릴 수 있고, 그래프 개체·관계 요약에 일부 사실이 담겨 답변에 반영될 수도 있다. 교안에서는 **원문 청크 문서 기준**으로 비교한다.

## 5. 최종 핵심 요약

1. **색인:** LLM이 개체·관계를 추출하고 그래프·개체 벡터·관계 벡터·청크 벡터를 저장. **커뮤니티 보고서는 생성하지 않음.**
2. **검색:** `low-level → 개체(local)`, `high-level → 관계(global)`, `mix → 개체 + 관계 + 원문 청크`.
3. **주의:** LightRAG의 `global` ≠ Microsoft GraphRAG의 Global. `hybrid` ≠ BM25 + Dense 검색.
4. **주요 문법:** `LightRAG(...)` → `initialize_storages()` → `ainsert()` → `aquery_data()`/`aquery_llm()` → `finalize_storages()`.
5. **갱신:** `ainsert(..., ids=...)`로 추가하고 `adelete_by_doc_id(...)`로 삭제. 문서 수정 시 삭제 후 재추가.
6. **검증:** `QueryParam(mode=..., chunk_top_k=...)`, 원문 `file_path` 확인, 필요하면 리랭킹과 질문 유형 라우팅 적용.
