# RAG 검색 아키텍처 선정 — 임베딩·검색 전략·벡터 저장소

> 원본: `교안_01_임베딩_모델_선택.ipynb` + `교안_02_검색_전략과_벡터_저장소_종합_선정.ipynb`  
> 정리 방식: **핵심 개념 → 주요 코드 문법 → 비교 결과 → 선정 원칙**. 반복 실습·이미지·긴 실행 출력은 생략.  
> 실습 자료: 관광지 **388건**, 평가 질문 **75개**(묘사·이름·조건·관계·집계 각 15개). 임베딩 모델 평가에는 **30문항(묘사·이름)**, 검색 전략 평가에는 **45문항(묘사·이름·조건)** 사용.

## 1. 전체 구조와 선정 원칙

### 무엇을 선택하는가

| 구성 요소 | 역할 | 주요 후보 |
|---|---|---|
| **임베딩 모델** | 문서·질문을 같은 벡터 공간으로 변환 | OpenAI, E5, KURE |
| **검색 전략** | 질문에 맞는 문서를 어떤 방식으로 찾는가 | BM25 / Dense / Hybrid |
| **벡터 저장소** | 벡터 색인·검색, 필터 및 구조화 질의 지원 | Chroma / pgvector / Neo4j Vector |

```text
[문서] → 임베딩 모델 선정 → 문서 벡터 생성 → 벡터 저장소에 색인

[질문] → 질문 유형 확인
       ├─ 묘사·이름·조건 → 검색 전략(BM25/Dense/Hybrid) → 관련 문서
       │                                     └─ 조건 검색: 필요한 필터 추가
       └─ 관계·집계     → 구조화 질의(SQL/Cypher)     → 관계·집계 결과

선정: 동일 평가셋으로 정확도 비교 → 지연·비용·저장 공간 검토
     → 제약 적용 → 후보 순위 결정 → ADR 기록
```

- **네 평가 축:** 정확도(높을수록 좋음), 지연·비용·저장 공간(낮을수록 좋음).
- **선택 순서:** 먼저 서비스 요구·제약으로 후보를 거르고, 남은 후보를 동일 조건에서 비교.
- **ADR(Architecture Decision Record):** `제목 / 상태 / 맥락 / 결정 / 결과(재검토 조건)`을 기록. 모델 교체는 전체 문서 재임베딩, 저장소 교체는 색인·검색 코드 이전 비용이 발생할 수 있음.

## 2. 임베딩 모델 선택 (교안 1)

### 핵심 개념과 평가 지표

- **MTEB:** 임베딩 벤치마크. 전체 순위보다 **한국어 + Retrieval + 유사 도메인 데이터셋**을 기준으로 후보를 좁힘. 실제 선정은 자체 평가셋으로 진행.
- **Recall@K:** 정답 문서 전체 중 검색 결과 상위 K개에서 찾은 비율. 교안은 `Recall@5` 사용.
- **MRR:** 검색 결과에서 *처음 등장한 정답 문서*의 순위 역수를 질문별로 평균. 1위면 1, 2위면 0.5.
- **맞힌 문항:** 상위 5개에 정답이 **하나라도** 있으면 1문항으로 계산. 정답 문서가 여러 개면 Recall@5와 값이 다를 수 있음.
- **입력 잘림 비율(`truncated_ratio`):** 모델 최대 토큰 길이를 초과한 문서 비율. 토크나이저·접두어 규칙에 따라 달라짐.
- **정확 검색:** 모든 문서 벡터를 직접 비교해 HNSW 근사 검색의 오차를 배제하고 모델만 평가.

| 비교 모델 | 차원 | 최대 입력(교안 기준) | 입력 규칙 |
|---|---:|---:|---|
| `text-embedding-3-small` | 1536 | 8192토큰 | 질문·문서 그대로 |
| `text-embedding-3-large` | 768 또는 3072 | 8192토큰 | `dimensions`로 차원 설정 |
| `multilingual-e5-small` | 384 | 512토큰 | 문서 `passage: `, 질문 `query: ` |
| `KURE-v1` | 1024 | 8192토큰 | 접두어 없음 |
| `BM25` | 벡터 없음 | 해당 없음 | 비교용 키워드 검색 기준선 |

### 핵심 코드: 모델 로드와 벡터 생성

```python
from langchain_openai import OpenAIEmbeddings
from langchain_huggingface import HuggingFaceEmbeddings
from sentence_transformers import SentenceTransformer

# OpenAI API (환경 변수 OPENAI_API_KEY 필요)
api = OpenAIEmbeddings(
    model="text-embedding-3-large",
    dimensions=768,
    check_embedding_ctx_length=False,  # 긴 문서 자동 분할 비활성화
)
doc_vecs = api.embed_documents(["문서 A", "문서 B"])  # 여러 문서
query_vec = api.embed_query("질문")                    # 질문 하나

# 로컬 모델: SentenceTransformers 사용
kure = SentenceTransformer("nlpai-lab/KURE-v1")
kure_docs = kure.encode(["문서 A", "문서 B"], normalize_embeddings=True)
kure_query = kure.encode("질문", normalize_embeddings=True)

e5 = SentenceTransformer("intfloat/multilingual-e5-small")
e5_docs = e5.encode(["passage: 문서 A"], normalize_embeddings=True)
e5_query = e5.encode("query: 질문", normalize_embeddings=True)

# LangChain 벡터 저장소에 바로 연결할 때는 Embeddings 래퍼 사용
embedding_model = HuggingFaceEmbeddings(
    model_name="nlpai-lab/KURE-v1",
    encode_kwargs={"normalize_embeddings": True},
)
```

- `.embed_documents(list[str])` / `.embed_query(str)`: LangChain 임베딩 인터페이스.
- `.encode(..., normalize_embeddings=True)`: SentenceTransformer 임베딩 및 벡터 정규화.
- `dimensions=768`: 출력 차원을 조절. 차원 감소는 저장 공간 절감과 정확도 손실 사이의 절충.
- **문서·질문은 반드시 같은 모델·차원·입력 규약으로 벡터화.** 모델을 바꾸면 기존 문서 벡터 재생성 필요.

### 핵심 코드: 유사도 계산·평가

```python
import numpy as np

# 질문 여러 개, 문서 여러 개를 각각 같은 모델로 임베딩했다고 가정
def normalize(vectors):
    vectors = np.asarray(vectors, dtype=np.float32)
    return vectors / np.linalg.norm(vectors, axis=1, keepdims=True)


def search_top_ids(question_vectors, doc_vectors, doc_ids, k=10):
    scores = normalize(question_vectors) @ normalize(doc_vectors).T
    return [[doc_ids[i] for i in np.argsort(-row)[:k]] for row in scores]


def recall_at_k(predicted, relevant, k=5):
    return sum(doc_id in relevant for doc_id in predicted[:k]) / len(relevant)


def mrr(predicted, relevant):
    for rank, doc_id in enumerate(predicted, start=1):
        if doc_id in relevant:
            return 1 / rank
    return 0.0
```

- `np.linalg.norm(..., axis=1, keepdims=True)`: 행마다 벡터 길이를 계산. 정규화 후 **내적(`@`) = 코사인 유사도**.
- `.T`: 행렬 전치. `np.argsort(-row)[:k]`: 점수가 높은 상위 K개 선택.
- `predicted`: 검색 결과 문서 ID를 **순위순**으로 저장. `relevant`: 정답 ID 목록.
- 정확도만 보지 않고 문서 임베딩 시간(`time.perf_counter()`), 질문당 지연, 토큰 잘림도 함께 기록.

**교안 1의 관광지 30문항 결과** (기록된 실습값. 재실행한 값 아님)

| 후보 | 맞힌 문항 | Recall@5 | 잘림 비율 | 판정 |
|---|---:|---:|---:|---|
| BM25 | 20 | 0.667 | 0 | 기준선 |
| 3-small (1536) | 13 | 0.433 | 0 | 정확도 부족 |
| 3-large (768) | 13 | 0.433 | 0 | 정확도 부족 |
| 3-large (3072) | 16 | 0.533 | 0 | 정확도 부족 |
| E5-small (384) | **22** | **0.733** | 0.046 | 잘림 1% 초과 |
| **KURE-v1 (1024)** | **21** | **0.700** | **0** | **채택** |

**교안 선정 규칙:** `최고 맞힌 문항 - 2` 이내 후보 → 잘림 비율 `<= 0.01` → 로컬 우선·질문 처리 시간 짧은 모델. 따라서 **ADR-001 = KURE-v1**. 최다 정답인 E5를 선택하지 않은 이유는 입력 잘림 제약 때문.

## 3. 질문 유형별 검색 전략 (교안 2)

### 질문 유형과 처리 방식

| 질문 유형 | 필요한 처리 | 검색 전략 평가에 포함? |
|---|---|---|
| **묘사** | 표현이 달라도 의미가 가까운 문서 검색 | O |
| **이름** | 고유명사·정확한 명칭 검색 | O |
| **조건** | 검색 + 지역·날짜 등 메타데이터 필터 | O (교안 측정에서는 **필터 없이** 검색) |
| **관계** | 테이블 JOIN 또는 그래프 관계 탐색 | X |
| **집계** | `COUNT(*)` 등 구조화 질의 | X |

- **BM25:** 형태소 기반 키워드 검색. 고유명사에 강점.
- **Dense:** 임베딩 벡터 유사도 검색. 다른 표현으로 묻는 질문에 대응.
- **Hybrid:** BM25 + Dense 결과를 **RRF(Reciprocal Rank Fusion)**로 병합. 교안은 동일 가중치 사용.
- **Self-Query:** 질문에서 지역 같은 메타데이터 필터를 추출하는 단계. 검색 방식의 정확도 비교와 구분.

### 핵심 코드: BM25·Dense·Hybrid 구성

```python
import json
from pathlib import Path
from kiwipiepy import Kiwi
from langchain_core.documents import Document
from langchain_community.retrievers import BM25Retriever
from langchain_chroma import Chroma
from langchain_classic.retrievers import EnsembleRetriever

# 교안 자료의 한 문서 = 한 벡터
folder = Path("data/본실습")
spots = [json.loads(x) for x in (folder / "spots.jsonl").read_text(encoding="utf-8").splitlines()]
questions = json.loads((folder / "questions.json").read_text(encoding="utf-8"))
search_questions = [q for q in questions if q["question_type"] in ("묘사", "이름", "조건")]

documents = [
    Document(id=s["doc_id"], page_content=s["title"] + "\n" + s["text"],
             metadata={"source_id": s["doc_id"]})
    for s in spots
]

kiwi = Kiwi()
def kiwi_tokenize(text):
    return [t.form.lower() for t in kiwi.tokenize(text.replace("･", "·"))
            if t.tag.startswith("N") or t.tag in {"SL", "SN"}]

bm25 = BM25Retriever.from_documents(documents, preprocess_func=kiwi_tokenize, k=10)
vector_store = Chroma(collection_name="travel_spots", embedding_function=embedding_model)
vector_store.add_documents(documents)  # embedding_model: 앞 절의 KURE-v1 래퍼

dense = vector_store.as_retriever(search_kwargs={"k": 10})
hybrid = EnsembleRetriever(
    retrievers=[bm25, dense], weights=[0.5, 0.5], c=60, id_key="source_id"
)
found = hybrid.invoke("희귀한 야생화를 볼 수 있는 산속 명소")
found_ids = [doc.metadata["source_id"] for doc in found]
```

| 문법 | 기능 |
|---|---|
| `Document(page_content=..., metadata=...)` | 문서 본문과 원문 ID 보관 |
| `BM25Retriever.from_documents(...)` | 토큰화한 문서로 BM25 색인 생성 |
| `Chroma(..., embedding_function=...)` | 로컬 벡터 저장소에 임베딩 모델 연결 |
| `.add_documents(documents)` | 문서 임베딩 및 저장 |
| `.as_retriever(search_kwargs={"k": 10})` | 벡터 DB를 검색기 인터페이스로 변환 |
| `EnsembleRetriever(..., c=60, id_key="source_id")` | 검색기 순위 RRF 결합·동일 문서 병합 |
| `.invoke(question)` | 검색 실행, `Document` 목록 반환 |

> 교안 실습에서는 매번 같은 Chroma 컬렉션을 비우기 위해 `reset_collection()`을 사용함. 해당 메서드는 **기존 컬렉션 데이터를 삭제**하므로 운영 환경에서는 주의.

### 유형별 정확도 평가 문법 및 결과

```python
import pandas as pd

retrievers = {"bm25": bm25, "dense": dense, "hybrid": hybrid}
rows = []
for q in search_questions:
    for strategy, retriever in retrievers.items():
        found = retriever.invoke(q["question"])
        ids = [doc.metadata["source_id"] for doc in found]
        rows.append({
            "type": q["question_type"], "strategy": strategy,
            "recall_at_5": recall_at_k(ids, q["relevant_doc_ids"], 5),
        })

type_table = pd.DataFrame(rows).pivot_table(
    index="type", columns="strategy", values="recall_at_5"
)
routed_plan = type_table.idxmax(axis=1).to_dict()  # 유형별 1위 전략
```

**교안 2의 45문항 Recall@5** (각 유형 15문항)

| 전략 | 묘사 | 이름 | 조건(필터 없음) | 전체 |
|---|---:|---:|---:|---:|
| BM25 | 0.333 | 1.000 | 0.853 | 0.729 |
| Dense (KURE) | 0.400 | 1.000 | 0.816 | 0.739 |
| **Hybrid** | **0.533** | **1.000** | **0.849** | **0.794** |
| 유형별 최적 라우팅 | 0.533 | 1.000 | 0.853 | 0.795 |

- 유형별 최적 라우팅은 **질문 유형을 항상 정확히 아는 경우의 상한**. Hybrid 하나와 차이 `0.001`이므로 라우터를 추가하지 않음.
- **ADR-002 = Hybrid 단일 전략.** 임베딩 평가의 30문항 점수와 전략 평가의 45문항 점수는 평가셋이 달라 직접 비교하지 않음.

## 4. 벡터 저장소와 저장 형식 (교안 2)

### 저장소는 '필요한 질의를 처리할 수 있는가'로 선택

| 필요한 질의 | Chroma | PostgreSQL + pgvector | Neo4j Vector |
|---|---|---|---|
| 벡터 유사도 검색 | 지원 | 지원 | 지원 |
| 키워드 점수 기반 검색 | 별도 BM25 필요 | 전문 검색 + 한국어 분석 처리 | 전문 인덱스 |
| 메타데이터 필터 | `where` | `WHERE` | 인덱스 필터 |
| 관계 탐색 | 외부 코드/DB 필요 | `JOIN` | `MATCH` |
| 집계 | 밖에서 계산 | `COUNT(*)` | `count(n)` |

- **Chroma:** 간단한 로컬 벡터 검색에 적합. 교안 기준 로컬 Chroma의 문서 포함 필터는 BM25 순위 검색 대체 불가.
- **pgvector:** 이미 PostgreSQL을 운영하고 필터·한 단계 관계·집계를 SQL로 처리할 때 유리. 한국어 키워드 순위 검색은 PostgreSQL 전문 검색과 애플리케이션 형태소 분석의 조합이 필요.
- **Neo4j Vector:** 여러 단계의 관계 탐색에 유리하지만 기존 인프라가 PostgreSQL뿐이면 DB를 추가로 운영해야 함.
- **ADR-003 = pgvector 선택.** 여행지 실습은 기존 PostgreSQL + 지역 필터 + 간단한 근처 관계·집계가 선정 근거.

### 핵심 SQL/Python 문법: pgvector

```sql
-- PostgreSQL / Supabase (교안은 extensions 스키마 사용)
CREATE EXTENSION IF NOT EXISTS vector WITH SCHEMA extensions;
CREATE TABLE spot_vectors (
    doc_id text PRIMARY KEY,
    embedding vector(1024)
);
CREATE INDEX spot_vectors_embedding_hnsw
ON spot_vectors USING hnsw (embedding vector_cosine_ops);

-- 코사인 거리(<=>) 오름차순 검색은 아래 Python 코드에서 실행
-- 질문 벡터는 1024개 숫자를 포함한 값으로 매개변수 전달
```

```python
import os
import psycopg2
from psycopg2.extras import execute_values

connection = psycopg2.connect(os.environ["SUPABASE_DB_URL"])
connection.autocommit = True

# Chroma에 저장한 문서 벡터를 꺼내 재임베딩 없이 옮김
stored = vector_store.get(include=["embeddings"])
vector_literal = lambda v: "[" + ",".join(map(str, v)) + "]"
rows = [(doc_id, vector_literal(vec))
        for doc_id, vec in zip(stored["ids"], stored["embeddings"])]
with connection.cursor() as cur:
    execute_values(cur, "INSERT INTO spot_vectors VALUES %s", rows,
                   template="(%s, %s::vector)", page_size=100)

# 질문도 같은 KURE-v1로 임베딩해 코사인 거리 순위 검색
query_vec = embedding_model.embed_query("희귀한 야생화를 볼 수 있는 장소")
with connection.cursor() as cur:
    cur.execute(
        "SELECT doc_id FROM spot_vectors ORDER BY embedding <=> %s::vector LIMIT 5",
        (vector_literal(query_vec),),
    )
    found_ids = [doc_id for (doc_id,) in cur.fetchall()]
connection.close()
```

- `psycopg2.connect(...)`: PostgreSQL 직접 접속. `SUPABASE_DB_URL`은 `.env`로 관리.
- `execute_values(..., page_size=100)`: 원격 DB에 다량의 행을 묶어서 INSERT.
- `vector(1024)`: 1024차원 float32 벡터 열. `vector_cosine_ops`: 코사인 거리용 인덱스.
- `<=>`: 코사인 거리(작을수록 가까움). `pg_column_size`: 데이터 값 크기, `pg_relation_size`: 인덱스 등 객체 크기.
- **HNSW + `WHERE` 필터**는 사후 필터로 결과가 요청 개수보다 적어질 수 있음. 필요 시 `hnsw.iterative_scan` 사용 및 결과 개수 확인.
- 위 SQL은 핵심 문법 예시이며, 실제 실행에는 정상 차원의 벡터 전체 값·테이블 초기화·스키마 경로 등이 필요.

### 벡터 정밀도(양자화)와 저장 공간

```sql
-- float32 → float16 또는 binary 사본 변환
embedding::halfvec(1024)                       -- float16
binary_quantize(embedding)::bit(1024)          -- 부호 기반 1비트

-- 검색 연산자
-- vector / halfvec : <=> (코사인 거리)
-- bit              : <~> (해밍 거리)
```

**교안의 KURE-v1 1024차원, 벡터 100만 개 기준 결과**

| 저장 형식 | pgvector 열 타입 | 실측 벡터 1개 | 100만 개 | 맞힌 문항(45개) | Recall@5 |
|---|---|---:|---:|---:|---:|
| **float32** | `vector` | 약 4,100B | **4.100GB** | **35** | **0.739** |
| float16 | `halfvec` | 약 2,052B | 2.052GB | 35 | 0.739 |
| binary | `bit` | 약 136B | 0.136GB | 33 | 0.679 |

- 기본 벡터 계산: `벡터 수 × 차원 × 4바이트`(float32). KURE-v1의 100만 벡터 원시 크기 ≈ **4.096GB**.
- 교안에서 측정한 **원시 벡터 + HNSW 인덱스 ≈ 원시 벡터 3.0배**. 이는 388건 실측으로 만든 **규모 추정용 배수**이지 고정 규칙이 아님.
- 64GB 메모리 제약 안에 float32가 들어가므로 **float32 유지**. 메모리가 부족하면 평가상 손실이 없던 float16부터 검토.
- binary는 값만 사용 시 손실 발생. 필요하면 **binary로 후보 검색 → 원본 float32로 재순위화** 방식 검토(해당 방식의 성능은 교안에서 직접 측정하지 않음).

## 5. 네 축으로 최종 아키텍처 선정

### 측정·비용·선정 절차

| 평가 축 | 교안의 계산 방식 |
|---|---|
| 정확도 | 검색 질문 45개의 전체 `Recall@5` |
| 지연 | 실측 평균 검색 시간 + 100만 건 검색 지연 **30ms(가정)** |
| 비용 | `색인 1회 비용 / 12 + 월 질문 검색 비용` = 월 운영비 |
| 저장 공간 | 벡터 원시 크기 × 인덱스 배수 + BM25 색인 크기(추정) |

- 교안의 규모 가정: **문서 100만 건 / 월 질문 1만 건**, 장비 **$0.70/시간**, 재색인 주기 **12개월**.
- **비용은 색인 1회 / 월 질의 / 재색인으로 구분.** 재색인 1회 비용은 새 문서 전체를 임베딩할 때의 색인 비용으로 봄.
- **선정 순서:** `1) 제약으로 탈락 → 2) 파레토 지배 후보 제거 → 3) 고정 기준 가중 점수 → 4) 민감도 확인`.
- **파레토 지배:** 다른 후보가 모든 축에서 같거나 더 좋고, 적어도 한 축에서 더 좋으면 해당 후보는 지배당함.
- **민감도 분석:** 가중치를 하나씩 ±20% 바꿨을 때도 같은 후보가 1위인지 검사.

### 주요 코드: 제약과 고정 기준 점수

```python
# candidates: candidate, accuracy, latency_ms, cost_usd, storage_gb 열이 있는 DataFrame
limits = {"latency_ms": 300, "storage_gb": 64}
weights = {"accuracy": 0.7, "latency_ms": 0.1,
           "cost_usd": 0.1, "storage_gb": 0.1}
references = {"latency_ms": 300.0, "cost_usd": 1000.0,
              "storage_gb": 64.0}

# 1. 한도 위반 후보 제거
passed = candidates[
    (candidates["latency_ms"] <= limits["latency_ms"])
    & (candidates["storage_gb"] <= limits["storage_gb"])
].copy()

# 2. 파레토 지배 제거: 모든 축에서 더 좋은 후보가 있으면 제외
axes = {"accuracy": "max", "latency_ms": "min",
        "cost_usd": "min", "storage_gb": "min"}
def remove_dominated(df, axes):
    records = df.to_dict("records")
    keep, dominated = [], {}
    for row in records:
        winners = []
        for other in records:
            if other["candidate"] == row["candidate"]:
                continue
            diffs = [(other[axis] - row[axis]) * (1 if direction == "max" else -1)
                     for axis, direction in axes.items()]
            if all(d >= 0 for d in diffs) and any(d > 0 for d in diffs):
                winners.append(other["candidate"])
        if winners:
            dominated[row["candidate"]] = winners
        else:
            keep.append(row)
    return pd.DataFrame(keep), dominated

front, dominated = remove_dominated(passed, axes)

# 3. 후보 추가·삭제에 영향받지 않는 고정 기준 점수
# 정확도는 그대로, 작을수록 좋은 축은 max(0, 1 - 값 / 기준)
def score(row):
    return weights["accuracy"] * row["accuracy"] + sum(
        weights[axis] * max(0, 1 - row[axis] / references[axis])
        for axis in references
    )

front["score"] = front.apply(score, axis=1)
ranking = front.sort_values("score", ascending=False)
```

> 위 코드는 **선정 핵심 문법만 발췌**한 예시. `candidates` 후보표 생성과 가중치 민감도 반복은 생략. `min-max`처럼 후보 집합의 최솟값·최댓값으로 점수를 계산하면 후보 추가 시 기존 점수가 바뀌므로 교안은 고정 기준을 사용.

**교안 2의 종합 선정 결과** (문서 100만 건, 지연 300ms·메모리 64GB 제약)

| 후보 | 전략 | 정확도 | 검색 메모리(추정) | 가중 점수 | 순위 |
|---|---|---:|---:|---:|---:|
| A | Dense | 0.739 | 12.288GB | 0.783 | 3 |
| **B** | **Hybrid** | **0.794** | **13.127GB** | **0.820** | **1** |
| C | BM25 | 0.729 | 0.839GB | 0.799 | 2 |

- 세 후보 모두 제약을 통과하고, 파레토 지배로 탈락한 후보도 없음.
- 정확도 가중치가 **0.7**이어서 Hybrid가 1위. 가중치 8개 변형(각 축 ±20%)에서도 1위 유지.
- 문서가 **1,000만 건**이면 현 메모리 제약에서 벡터를 쓰는 A·B는 탈락. 데이터 규모 변경 시 양자화·저장소·검색 전략을 다시 비교해야 함.

### 결정 기록(ADR) — 최종 요약

| ADR | 교안에서 채택한 결정 | 바뀌면 재검토할 조건 |
|---|---|---|
| **001** | 임베딩 **KURE-v1 (1024차원)** | 문서 길이·보안 규칙·자체 평가셋이 바뀜 |
| **002** | 검색 전략 **Hybrid (BM25 + Dense, RRF)** | 질의 유형 분포·검색 정확도 변화 |
| **003** | 저장소 **pgvector + float32 + HNSW** | 메모리 한계·복잡한 관계 질의 증가·키워드 엔진 전환 |
| **004** | 종합 구성 **KURE-v1 + Hybrid + pgvector** | 문서 규모·실제 지연·선정 가중치가 바뀜 |

**주의할 점:** 교안의 Hybrid 정확도는 **파이썬 `BM25Retriever`**로 측정됨. 최종 아키텍처의 PostgreSQL 전문 검색(`ts_rank` 등)은 별개 구현이므로 교체한 뒤 **Hybrid Recall@5 재평가가 필요**. 관계·집계 질의 역시 저장소 처리 가능성을 비교한 것이지, 본 실습에서 끝까지 실행·평가한 것은 아님.

**한 줄 결론:** 리더보드나 제품 인기만으로 결정하지 않고 **우리 질문에 대한 정확도 → 구현 제약 → 지연·비용·저장 공간 → 결정 재검토 조건** 순서로 RAG 검색 구성을 선택.
