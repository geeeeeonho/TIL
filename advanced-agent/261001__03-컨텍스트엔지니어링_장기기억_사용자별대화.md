## 1. 컨텍스트 엔지니어링 핵심

**컨텍스트(Context)** = LLM에게 이번 요청을 처리하도록 전달하는 정보.

주요 구성 요소:

- 시스템 프롬프트
- 현재 질문을 포함한 대화 내역
- 장기기억
- Tool / MCP 정보
- 구조화 출력 스키마
- 환경에 따라 Skill 정보

**컨텍스트 엔지니어링** = 필요한 정보를 골라 적절한 형태와 분량으로 모델에 전달하는 설계.

```text
[저장된 전체 정보]
        ↓ 필요한 것만 선택
┌─────────────────────────────┐
│ 시스템 지시                │
│ 사용자 기억                │
│ 이전 대화 요약             │
│ 최근 대화 + 현재 질문      │
└─────────────────────────────┘
        ↓ 입력 예산 조절
      [LLM 호출]
```

정보를 많이 넣는 것이 항상 좋은 것은 아님.

- 불필요한 정보가 많으면 답변 품질이 떨어질 수 있음
- 입력 토큰과 비용 증가
- 오래된 내용과 최신 변경이 충돌할 수 있음

교안의 흐름:

```text
프롬프트 엔지니어링
        ↓
컨텍스트 엔지니어링
        ↓
하네스 엔지니어링
```

핵심 질문은 두 가지.

1. **무엇을 넣을 것인가?**
2. **얼마나 넣을 것인가?**

### 주요 조절 방법

| 방법 | 역할 | 주의점 |
|---|---|---|
| 검색 | 현재 질문과 관련된 기억 선택 | 저장돼도 검색되지 않을 수 있음 |
| 트리밍 | 입력 한도에 맞춰 일부 메시지만 선택 | 오래된 합의가 빠질 수 있음 |
| 요약 | 오래된 대화의 핵심을 압축 | 숫자·조건이 누락될 수 있음 |
| 토큰 예산 | 입력 요소별 사용 분량 배분 | 근사 토큰과 실제 사용량은 다를 수 있음 |

**State에 저장된 전체 대화와 실제 모델 입력은 다를 수 있음.**

## 2. 최근 대화만 사용할 때의 문제

### 기본 준비

```python
from langchain_core.messages import HumanMessage, convert_to_messages
from langchain_core.messages.utils import (
    count_tokens_approximately,
    trim_messages,
)

history = convert_to_messages(history_data)
conversation = [
    *history,
    HumanMessage(content=question),
]

print(count_tokens_approximately(conversation))
```

### 결과

```text
대화의 근사 토큰 수: 344
```

교안 실습에서는 모델 최대 입력 한도와 별개로 압축 과정을 보기 위한 입력 예산을 설정.

```python
input_budget = 1200
summary_trigger = 240
keep_recent = 3
```

- `input_budget`: 지시 + 기억 + 요약 + 최근 대화에 사용할 목표 예산
- `summary_trigger`: 대화 요약 시작 기준
- `keep_recent`: 요약하지 않고 원문으로 남길 최근 메시지 수

### 최근 메시지만 선택

```python
recent_only = trim_messages(
    conversation,
    max_tokens=120,
    token_counter=count_tokens_approximately,
    strategy="last",
    start_on="human",
    allow_partial=False,
)
```

```text
전체 대화
├─ 오래된 합의
├─ 중간 변경
├─ 최신 변경
└─ 현재 질문

        trim_messages(strategy="last")
                    ↓
최근 대화
├─ 최신 변경
└─ 현재 질문
```

### 결과

```text
원본 메시지 수: 15
선택한 메시지 수: 5

전체 대화 입력 근사 토큰: 430
최근 대화만 입력 근사 토큰: 183
```

최근 대화만 사용하면 입력은 줄지만 **초기의 중요한 합의가 빠질 수 있음.**

> Tool을 사용하는 대화에서는 Tool Call과 Tool Result가 서로 짝을 이루도록 남겨야 함.

## 3. 기억 + 요약 + 최근 대화로 입력 구성

단순 트리밍 대신 다음 구조 사용.

```text
                 ┌─ 짧은 대화 ─────────────┐
[사용자 질문] → [기억 조회] ───────────────→ [답변]
                 │                          ↑
                 └─ 긴 대화 → [누적 요약] ─┘

모델 입력 = 시스템 지시 + 장기기억 + 누적 요약 + 최근 대화
```

### State와 사용자 Context

```python
from typing import Annotated
from typing_extensions import TypedDict
from langchain_core.messages import AnyMessage
from langgraph.graph.message import add_messages

class ContextState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    summary: str
    recalled_memories: list[str]
    input_tokens: int
```

```python
from dataclasses import dataclass

@dataclass
class UserContext:
    user_id: str
```

- `messages`: 현재 thread의 대화
- `summary`: 오래된 대화의 핵심 합의
- `recalled_memories`: 사용자 장기기억
- `input_tokens`: 실제 답변에 구성한 근사 입력량
- `user_id`: 어떤 사용자의 기억을 읽을지 결정

---

### 3-1. 장기기억 조회

교안에서는 `profile`과 `episodes`를 다르게 사용.

```text
profile
└─ 매 상담마다 필요한 사용자 환경 → get()

episodes
└─ 현재 질문과 관련된 과거 경험 → search()
```

```python
from langgraph.runtime import Runtime

def recall_memories(state: ContextState, runtime: Runtime[UserContext]):
    user_id = runtime.context.user_id

    item = runtime.store.get(
        ("customers", user_id, "profile"),
        "work_context",
    )

    memories = (
        ["매 상담에 참고할 사용자 정보(업무 환경): " + item.value["text"]]
        if item else []
    )

    episodes = runtime.store.search(
        ("customers", user_id, "episodes"),
        query=state["messages"][-1].text,
        filter={"speaker": "user"},
        limit=1,
    )

    memories.extend(
        "이번 질문에 관련된 과거 경험(사용자 발화): " + item.value["text"]
        for item in episodes
    )

    return {"recalled_memories": memories}
```

핵심:

- 항상 필요한 정보 → `get()`
- 질문과 관련된 기억 → `search()`
- 과거 경험은 참고 사례이며 현재 합의로 간주하지 않음

### 3-2. 오래된 대화 누적 요약

기존 요약과 새로 압축할 대화를 같이 전달해야 이전 합의가 유지됨.

```python
def summarize_history(state: ContextState):
    old_messages = state["messages"][:-keep_recent]

    summary = summary_chain.invoke({
        "summary": state.get("summary", ""),
        "messages": old_messages,
    }).text

    return {
        "summary": summary,
        "messages": [
            RemoveMessage(id=message.id)
            for message in old_messages
        ],
    }
```

```text
기존 summary
     +
오래된 새 대화
     ↓
새 summary

최근 3개 메시지 → 원문 유지
```

`RemoveMessage`는 **현재 State에서 메시지를 제거**하며 과거 체크포인트 기록 자체를 삭제하는 것은 아님.

### 3-3. 입력 예산에 맞춰 최종 모델 입력 생성

```python
def answer_consultation(state: ContextState):
    fixed_messages = context_prompt.format_messages(
        memories="\n".join(state["recalled_memories"]),
        summary=state.get("summary", ""),
    )

    history_budget = (
        input_budget
        - count_tokens_approximately(fixed_messages)
    )

    latest_question = state["messages"][-1]

    if history_budget < count_tokens_approximately([latest_question]):
        return {
            "messages": [AIMessage(
                content="현재 입력 예산을 넘었습니다. 자료나 질문을 나누어 보내 주세요."
            )],
            "input_tokens": 0,
        }

    recent = trim_messages(
        state["messages"],
        max_tokens=history_budget,
        token_counter=count_tokens_approximately,
        strategy="last",
        start_on="human",
    )

    model_input = [*fixed_messages, *recent]
    response = llm.invoke(model_input)

    return {
        "messages": [response],
        "input_tokens": count_tokens_approximately(model_input),
    }
```

핵심 계산:

```text
전체 입력 예산
    - 시스템 지시
    - 장기기억
    - 누적 요약
────────────────
최근 대화에 사용 가능한 예산
```

현재 질문조차 담을 수 없으면 모델을 호출하지 않음.

## 4. 조건부 요약 LangGraph

### 라우팅

```python
def route_context(state: ContextState):
    needs_summary = (
        count_tokens_approximately(state["messages"])
        > summary_trigger
    )

    if needs_summary and len(state["messages"]) > keep_recent:
        return "summarize_history"

    return "answer_consultation"
```

### 그래프 구성

```python
builder = StateGraph(ContextState, context_schema=UserContext)

builder.add_node("recall_memories", recall_memories)
builder.add_node("summarize_history", summarize_history)
builder.add_node("answer_consultation", answer_consultation)

builder.add_edge(START, "recall_memories")

builder.add_conditional_edges(
    "recall_memories",
    route_context,
    {
        "summarize_history": "summarize_history",
        "answer_consultation": "answer_consultation",
    },
)

builder.add_edge("summarize_history", "answer_consultation")
builder.add_edge("answer_consultation", END)

graph = builder.compile(
    checkpointer=checkpointer,
    store=store,
)
```

### 실행 흐름

```text
START
  ↓
recall_memories
  ↓
route_context
  ├─ 짧음 → answer_consultation → END
  │
  └─ 김   → summarize_history
                         ↓
                answer_consultation → END
```

### 결과 예시

짧은 대화:

```text
실행 노드:
recall_memories
→ answer_consultation
```

긴 대화:

```text
실행 노드:
recall_memories
→ summarize_history
→ answer_consultation

현재 State 메시지 수: 4
답변 입력 근사 토큰: 297 / 예산: 1200
```

비교:

| 방식 | 입력 근사 토큰 |
|---|---:|
| 전체 대화 | 430 |
| 최근 대화만 | 183 |
| 기억 + 요약 + 최근 대화 | 297 |

**최근 대화만 쓰는 것보다 입력은 늘지만, 오래된 합의와 사용자 기억을 유지할 수 있음.**

같은 `thread_id`로 후속 질문을 보내면 기존 State를 이어서 사용.

```python
followup = (
    "제안 검토 예산 상한만 550만 원으로 변경합니다. "
    "이전에 합의한 나머지 범위와 제외 기능을 유지해서 다시 정리해 주세요."
)

graph.stream(
    {"messages": [HumanMessage(content=followup)]},
    config,
    context=UserContext(user_id="client-a"),
)
```

최신 변경과 이전 합의를 함께 유지해야 하므로 **요약 + 최근 메시지**를 같이 읽음.

## 5. Middleware로 컨텍스트 조절

LangChain Agent에서는 별도 노드 대신 Middleware로 모델 호출 전후 처리를 연결할 수 있음.

### 5-1. `SummarizationMiddleware`

대화가 기준을 넘으면 오래된 부분을 자동 요약.

```python
summary_agent = create_agent(
    model=llm,
    tools=[],
    middleware=[
        SummarizationMiddleware(
            model=llm,
            trigger=("messages", 8),
            keep=("messages", 3),
            summary_prompt="...",
        )
    ],
    checkpointer=checkpointer,
)
```

```text
메시지 8개 이상
      ↓
오래된 대화 요약
      ↓
최근 3개 원문 유지
      ↓
모델 호출
```

---

### 5-2. `wrap_model_call`

State는 유지하고 **이번 모델 호출에 전달할 메시지만** 줄임.

```python
@wrap_model_call
def trim_request(request, handler):
    recent = trim_messages(
        request.messages,
        max_tokens=180,
        token_counter=count_tokens_approximately,
        strategy="last",
        start_on="human",
    )

    return handler(
        request.override(messages=recent)
    )
```

```text
[전체 State]
    ↓ 유지
[wrap_model_call]
    ↓ 이번 호출만 변경
[최근 메시지]
    ↓
[LLM]
```

`request.override()`는 이번 모델 요청만 변경. State의 원문은 삭제하지 않음.

---

### 5-3. `PIIMiddleware`

모델 입력 전 이메일 같은 개인정보를 가릴 수 있음.

```python
pii_agent = create_agent(
    model=llm,
    tools=[],
    middleware=[
        PIIMiddleware(
            "email",
            strategy="redact",
            apply_to_input=True,
        )
    ],
)
```

- `apply_to_input=True` → 사용자 입력 검사
- `apply_to_output=True` → 모델 출력 검사
- `apply_to_tool_results=True` → Tool 결과 검사

주의:

> 별도로 호출하는 Mem0나 외부 로그까지 자동으로 가려주는 것은 아님.

# 6. 장기기억 방식 선택

교안 부록에서는 **Store / Mem0 / LLM Wiki**를 서로 다른 방식으로 구분.

```text
사용자·작업에서 계속 필요한 정보
            ↓
    ┌───────┼──────────┐
    ↓       ↓          ↓
  Store    Mem0     LLM Wiki
 직접관리  대화기억   문서지식
```

| 방식 | 핵심 | 적합한 경우 |
|---|---|---|
| **Store** | 저장할 내용·형식·조회 방식을 직접 관리 | 기억 구조와 갱신 로직을 직접 통제할 때 |
| **Mem0** | 대화에서 기억 추출·저장·검색 | 기억 추출 기능까지 활용할 때 |
| **LLM Wiki** | 작업 결과를 Markdown 지식으로 연결·갱신 | 프로젝트·팀 단위 지식을 축적할 때 |

**같은 사용자 기억을 Store와 Mem0 양쪽에 중복 저장할 필요는 없음.**

### Store

직접 설계할 것:

- 어떤 내용을 기억할지
- 어떤 namespace에 저장할지
- 언제 추가/수정/삭제할지
- `get()` / `search()` 중 무엇을 사용할지

### Mem0

직접 설계할 것:

- 기억 추출 지침
- `profile / episodes` 구분
- add / update / delete / keep 기준

### LLM Wiki

특정 라이브러리가 아니라 **Markdown 기반 지식 관리 설계 방식**.

```text
project/
├── raw/          # 원본 자료. 읽기 전용
├── wiki/         # LLM이 정리한 지식 문서
│   ├── index.md  # 전체 목차·링크·요약
│   └── log.md    # 작업 기록
└── AGENTS.md     # LLM 작업 규칙
```

원본은 보존하고 Wiki에서 출처를 연결.

```text
[현재 요청]
     ↓
[필요한 Wiki 문서 선택]
     ↓
[읽기 / 작업 수행]
     ↓
[결과 검토]
     ↓
[Wiki 갱신]
```

특징:

- 개인 사용자 기억 저장 전용 방식은 아님
- 프로젝트·팀 작업 지식 축적에 적합
- 임베딩·Graph DB·Obsidian은 필수 아님
- 파일을 모아 두는 것만으로 자동 관리되지는 않음

## 7. `user_id`와 `thread_id` 분리

한 사용자는 여러 대화를 가질 수 있음.

```text
user_id = 사용자
│
├─ thread_id A → 대화 A의 State
├─ thread_id B → 대화 B의 State
└─ thread_id C → 대화 C의 State

user_id
└─ Store / Mem0 → 여러 대화에서 공유할 장기기억
```

### 앱 관리 DB

| 테이블 | 저장 정보 |
|---|---|
| `users` | `user_id`, 표시 이름 |
| `conversations` | `thread_id`, 소유 `user_id`, 제목, 생성 시각 |

- 새 대화마다 충돌하지 않는 `thread_id` 발급
- ID 문자열만으로 권한이 보장되는 것은 아님
- 앱에서 현재 로그인 사용자와 thread의 소유 관계를 확인해야 함

### 요청 처리 흐름

```text
[로그인 사용자 확인]
         ↓
     user_id
         ↓
[thread 소유권 확인]
         ↓
     thread_id
         │
         ├─ Checkpointer → 현재 대화 State
         │
         └─ user_id → Store / Mem0 장기기억
                         ↓
                [현재 질문과 조합]
                         ↓
                       LLM
```

핵심 구분:

| ID | 역할 |
|---|---|
| `thread_id` | 대화별 State 연결 |
| `user_id` | 사용자별 장기기억 연결 |

Store에서 다음처럼 namespace를 만들 수 있으면 별도 Store ID 매핑이 필요하지 않음.

```python
("counseling", user_id)
```

외부 기억 ID나 Wiki 위치가 별도라면 앱 DB에 연결 정보를 추가.

### 권장 구성

```text
앱 관리 DB
  └─ user_id ↔ thread_id

Checkpointer
  └─ thread별 대화 State

Store 또는 Mem0
  └─ 사용자별 장기기억

[선택]
LLM Wiki
  └─ 프로젝트 결정·근거·산출물
```

# 8. 종합 실습: 기억을 갱신하는 주간 업무 보고서 Agent

교안 마지막 실습은 앞의 내용을 하나의 Agent에 통합.

```text
사용자 입력
   ↓
① 이메일 가리기
   ↓
② 기존 장기기억 조회
   ↓
③ 긴 대화면 누적 요약
   ↓
④ 입력 예산에 맞게 Context 구성
   ↓
⑤ 보고서 생성
   ↓
⑥ 현재 사용자 발화로 기억 갱신
   ↓
결과 반환
```

### 정보별 저장 위치

| 정보 | 위치 | 사용 방식 |
|---|---|---|
| 지속적인 보고서 작성 기준 | Mem0 `profile` | 매 요청 전체 조회 |
| 실제 과거 보고서 피드백 | Mem0 `episodes` | 현재 요청과 관련된 경험 검색 |
| 이번 회의 작업·담당자·기한 | Checkpointer `messages`, `summary` | 현재 thread 안에서 유지 |
| 이번 모델 입력 | `wrap_model_call` 지역 변수 | 예산에 맞게 구성 |

---

## 8-1. Agent State

```python
class ReportState(AgentState):
    user_message: NotRequired[str]
    summary: NotRequired[str]
    profile_memories: NotRequired[list[str]]
    recalled_memories: NotRequired[list[str]]
    memory_events: NotRequired[list[dict]]
```

`user_message`를 별도로 보관하는 이유:

```text
사용자 발화
  ↓ 저장
user_message
  ↓
답변 생성 과정에서 messages가 변경돼도
  ↓
after_agent에서 원래 사용자 발화 기준으로 기억 판단
```

## 8-2. `before_agent`: 개인정보 가리기 + 기억 조회

### 이메일 가리기

```python
@before_agent(state_schema=ReportState)
def redact_report_emails(state, runtime):
    replacements = []

    for message in state["messages"]:
        safe_text = email_pattern.sub("[EMAIL]", message.text)
        if safe_text != message.text:
            replacements.append(
                message.model_copy(update={"content": safe_text})
            )

    return {
        "messages": replacements,
        "user_message": email_pattern.sub(
            "[EMAIL]",
            state["messages"][-1].text,
        ),
    }
```

### 기억 조회

```python
@before_agent(state_schema=ReportState)
def recall_report_memories(state, runtime):
    user_id = runtime.context.user_id

    profile_items = report_memory.get_all(
        filters={
            "user_id": user_id,
            "memory_space": "profile",
        },
        top_k=50,
    )["results"]

    feedback_items = report_memory.search(
        state["user_message"],
        filters={
            "user_id": user_id,
            "memory_space": "episodes",
        },
        top_k=2,
    )["results"]

    return {
        "profile_memories": [x["memory"] for x in profile_items],
        "recalled_memories": [x["memory"] for x in feedback_items],
        "memory_events": [],
    }
```

```text
profile → get_all()
        → 현재 작성 기준 전체

episodes → search(현재 발화)
         → 관련 과거 피드백만
```

## 8-3. `before_model`: 누적 요약

```python
@before_model(state_schema=ReportState)
def summarize_report(state, runtime):
    old_messages = state["messages"][:-report_keep_recent]

    if (
        len(state["messages"]) < report_summary_trigger
        or not old_messages
    ):
        return None

    summary = report_summary_chain.invoke({
        "summary": state.get("summary", ""),
        "messages": old_messages,
    }).text

    return {
        "summary": summary,
        "messages": [
            RemoveMessage(id=m.id)
            for m in old_messages
        ],
    }
```

요약에는 다음만 유지.

- 작업
- 담당자
- 최신 기한
- 미결 사항
- 기존 요약에서 아직 유효한 결정

보고서 형식 같은 장기 선호는 Mem0에서 관리하므로 회의 요약에서는 분리.

## 8-4. `wrap_model_call`: 최종 Context 구성

```python
@wrap_model_call(state_schema=ReportState)
def compose_report_context(request, handler):
    state = request.state

    fixed = SystemMessage(
        content=(
            request.system_message.text
            + "\n이전 요청까지 저장된 작성 기준:\n"
            + "\n".join(state.get("profile_memories", []))
            + "\n사용자가 전한 과거 피드백:\n"
            + "\n".join(state.get("recalled_memories", []))
            + "\n이번 회의의 누적 요약:\n"
            + state.get("summary", "")
        )
    )

    history_budget = (
        report_input_budget
        - count_tokens_approximately([fixed])
    )

    recent = trim_messages(
        request.messages,
        max_tokens=history_budget,
        token_counter=count_tokens_approximately,
        strategy="last",
        start_on="human",
        allow_partial=False,
    )

    return handler(
        request.override(
            system_message=fixed,
            messages=recent,
        )
    )
```

```text
[시스템 지시]
      +
[profile]
      +
[관련 episodes]
      +
[회의 summary]
      ↓
  고정 Context
      ↓
남은 토큰 예산 계산
      ↓
[최근 대화 선택]
      ↓
    LLM 호출
```

## 8-5. `after_agent`: 장기기억 갱신

Mem0 기억 변경은 네 가지로 판단.

```text
add     → 새 지속 기준 / 새 실제 피드백
update  → 같은 기준의 값이 변경됨
delete  → 기존 기준이 명확히 종료됨
keep    → 반복, 일회성, 모호함, 기억할 필요 없음
```

구조화 출력:

```python
class ReportMemoryChange(BaseModel):
    action: Literal["add", "update", "delete", "keep"]
    memory_space: Literal["profile", "episodes"]
    memory_id: str | None
    new_text: str | None
    reason: str
```

갱신 흐름:

```text
현재 user_id의 기억 조회
        ↓
현재 사용자 발화와 비교
        ↓
add / update / delete / keep 판단
        ↓
ID·공간·중복 작업 검증
        ↓
Mem0 반영
```

```python
@after_agent(state_schema=ReportState)
def update_report_memory(state, runtime):
    user_id = runtime.context.user_id
    message = state["user_message"]

    # 현재 사용자의 기억 후보 조회
    candidates = {...}

    plan = report_memory_chain.invoke({
        "message": message,
        "memories": json.dumps(candidates, ensure_ascii=False),
    })

    # 검증 후 Mem0에 반영
    ...

    return {"memory_events": events}
```

중요:

- 마지막 AI 답변이 아니라 **보관한 현재 사용자 발화**로 기억을 판단
- 다른 사용자의 기억 ID 수정 금지
- 이번 회의의 담당자·기한 같은 정보는 장기기억에 저장하지 않음
- “이번 보고서만 표로” 같은 일회성 요청도 장기기억 변경 대상이 아님

## 9. 같은 사용자 + 새 대화

### 같은 `thread_id`

```text
같은 회의 계속
→ 기존 messages / summary 복원
→ 최신 변경을 이어서 처리
```

### 새 `thread_id` + 같은 `user_id`

```text
새 회의
→ 이전 회의 State는 가져오지 않음
→ 사용자 장기기억은 재사용
```

예시:

```python
next_report_config = {
    "configurable": {
        "thread_id": str(uuid4())
    }
}

next_report = report_agent.invoke(
    {"messages": [HumanMessage(content=next_report_request)]},
    next_report_config,
    context=ReportContext(user_id=report_user_id),
)
```

```text
이전 회의 담당자·기한      X
이전 회의 summary           X

현재 사용자 작성 기준       O
관련 과거 피드백             O
```

즉,

```text
thread_id = 현재 대화의 기억
user_id   = 여러 대화에서 공유하는 사용자 기억
```

# 10. 전체 구조 최종 정리

```text
                    ┌─────────────────────────┐
                    │       App 관리 DB        │
                    │ user_id ↔ thread_id     │
                    └────────────┬────────────┘
                                 │
                  ┌──────────────┴──────────────┐
                  ↓                             ↓
        ┌─────────────────┐            ┌─────────────────┐
        │  Checkpointer   │            │ Store / Mem0    │
        │ 대화별 State    │            │ 사용자 장기기억 │
        │ messages        │            │ profile         │
        │ summary         │            │ episodes        │
        └────────┬────────┘            └────────┬────────┘
                 │                              │
                 └──────────────┬───────────────┘
                                ↓
                     ┌────────────────────┐
                     │ Context Engineering│
                     │ 지시               │
                     │ 기억               │
                     │ 요약               │
                     │ 최근 대화          │
                     │ 토큰 예산          │
                     └──────────┬─────────┘
                                ↓
                              [LLM]
                                ↓
                         [현재 요청 결과]

[선택]
LLM Wiki → 프로젝트 결정·근거·작업 결과를 Markdown 지식으로 축적
```

## 핵심만 기억

1. **저장된 전체 정보 ≠ 모델에 전달할 Context**
2. 최근 대화만 자르면 오래된 합의가 빠질 수 있음
3. **장기기억 + 누적 요약 + 최근 대화**를 함께 조합하면 이를 보완 가능
4. `Checkpointer`는 **thread별 대화 State** 관리
5. `Store / Mem0`는 **user별 장기기억** 관리
6. `thread_id`와 `user_id`는 역할이 다름
7. `wrap_model_call`은 **State를 유지하면서 이번 모델 입력만 조절** 가능
8. 장기기억에는 지속적으로 재사용할 정보만 저장
9. 일회성 요청·현재 작업의 기한은 장기기억과 분리
10. 프로젝트 단위 장기 지식은 필요하면 **LLM Wiki**로 별도 관리
