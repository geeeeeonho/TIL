# LangGraph 운영 실패 제어: 핑퐁 · 재시도 · 타임아웃

> 멀티에이전트가 **끝나지 않거나**, **결과 없이 끝나거나**, **외부 API가 잠깐 실패하거나**, **응답하지 않는 상황**을 제어하는 방법 정리.

---

## 1. 전체 개념

멀티에이전트는 그래프 설계가 맞아도 실행 중 여러 형태로 실패할 수 있음.

| 실패 유형 | 예시 | 관측 신호 | 주요 대응 |
|---|---|---|---|
| 무한 반복 · 핑퐁 | writer ↔ reviewer 반복 | 같은 노드가 계속 반복됨 | `recursion_limit`, 라운드 가드, `RemainingSteps` |
| 에러 없는 중단 | 필요한 갈래가 실행되지 않음 | 예외는 없지만 결과 필드가 비어 있음 | 엣지 구조 점검, `defer=True` |
| 일시 오류 | API 연결 끊김 | 같은 요청을 다시 하면 성공 가능 | `RetryPolicy` |
| 영구 오류 | 응답 형식 변경 | 다시 시도해도 같은 오류 | 재시도하지 않음 |
| 응답 없음 | API가 무한 대기 | 노드가 끝나지 않음 | 노드 `timeout` |
| 겹친 재시도 | SDK + 노드가 모두 재시도 | 실제 요청 수가 곱으로 증가 | 재시도 계층 한 곳으로 통일 |

전체 흐름은 다음처럼 볼 수 있음.

```text
그래프 실행
   │
   ├─ 계속 반복되는가?
   │      ├─ 마지막 안전장치 → recursion_limit
   │      └─ 정상 종료 유도 → 라운드 가드 / RemainingSteps
   │
   ├─ 예외 없이 결과가 비었는가?
   │      └─ 병렬 갈래 + 합류 엣지 구조 확인
   │
   ├─ 외부 호출이 실패했는가?
   │      ├─ 일시 오류 → RetryPolicy
   │      └─ 영구 오류 → 즉시 실패 처리
   │
   └─ 외부 호출이 응답하지 않는가?
          └─ timeout + 필요한 경우 RetryPolicy
```

# 2. 실습용 실패 API

교안에서는 실제 외부 API 대신 일부러 실패하도록 만든 함수를 사용함.

```python
CALLS = {
    "fetch_prices": 0,
    "fetch_news": 0,
    "fetch_reviews": 0,
}

FAULTS = {
    "price_failures": 0,
    "news_hangs": 0,
}
```

## 가격 API: 일시 오류

처음 몇 번만 실패하고 이후 성공함.

```python
def fetch_prices():
    CALLS["fetch_prices"] += 1

    if CALLS["fetch_prices"] <= FAULTS["price_failures"]:
        raise ConnectionError("가격 API 연결 끊김")

    return COMPETITOR_PRICES
```

```text
price_failures = 2

1번째 호출 → ConnectionError
2번째 호출 → ConnectionError
3번째 호출 → 정상 반환
```

→ **재시도에 적합한 오류**

---

## 뉴스 API: 응답 없음

```python
async def fetch_news():
    CALLS["fetch_news"] += 1

    if CALLS["fetch_news"] <= FAULTS["news_hangs"]:
        await asyncio.sleep(30)

    return NEWS
```

`asyncio.sleep()`으로 대기하므로 LangGraph의 노드 `timeout`으로 중단 가능함.

---

## 리뷰 API: 영구 오류

API 응답 구조가 바뀌었는데 예전 키를 계속 읽는 상황.

```python
def fetch_reviews():
    CALLS["fetch_reviews"] += 1
    response = REVIEW_API_RESPONSE

    return response["reviews"]
```

실제 응답은 다음 구조임.

```python
{
    "data": {
        "items": [...]
    }
}
```

따라서 항상 `KeyError` 발생.

```text
1번째 → KeyError
2번째 → KeyError
3번째 → KeyError
...
```

→ 다시 호출해도 해결되지 않으므로 **재시도 대상이 아님**

# 3. 핑퐁과 반복 제어

## 3-1. 핑퐁이 생기는 구조

작성자와 검토자의 규칙이 동시에 만족될 수 없으면 두 노드가 계속 왕복할 수 있음.

```text
START
  ↓
writer
  ↓
reviewer
  ├─ 통과 → END
  └─ 반려 → writer
               ↑
               └──── 반복
```

예제의 검토 규칙:

```python
def review_reason(draft):
    if len(draft) > 300:
        return "300자를 넘습니다"

    missing = []

    for item in COMPETITOR_PRICES:
        if item["회사"] not in draft:
            missing.append(item["회사"])

    if missing:
        return "빠진 경쟁사가 있습니다"

    return "통과"
```

writer는 반려 사유에 따라 서로 다른 초안을 만듦.

```python
def draft_writer(state: DraftState) -> Command[Literal["reviewer"]]:
    if state["feedback"] == "300자를 넘습니다":
        # 짧게 만들지만 경쟁사가 빠짐
        draft = price_paragraph(COMPETITOR_PRICES[:3])
    else:
        # 모든 경쟁사를 넣지만 300자를 넘음
        draft = price_paragraph(COMPETITOR_PRICES)

    return Command(
        goto="reviewer",
        update={"draft": draft},
    )
```

reviewer는 실패 시 다시 writer로 보냄.

```python
def draft_reviewer(
    state: DraftState,
) -> Command[Literal["writer", "__end__"]]:

    reason = review_reason(state["draft"])

    if reason == "통과":
        return Command(
            goto=END,
            update={"feedback": reason},
        )

    return Command(
        goto="writer",
        update={"feedback": reason},
    )
```

결과적으로 다음 패턴 반복.

```text
writer
  ↓
"300자를 넘습니다"
  ↓
writer가 3개 경쟁사만 작성
  ↓
"빠진 경쟁사가 있습니다"
  ↓
writer가 8개 경쟁사 작성
  ↓
"300자를 넘습니다"
  ↓
...
```

# 4. `recursion_limit`: 최종 단계 상한

`recursion_limit`은 그래프가 실행할 수 있는 단계 수의 상한.

```python
config = {
    "recursion_limit": 10,
}
```

상한을 넘으면:

```text
GraphRecursionError
```

발생.

예제에서는 실행 궤적을 직접 모음.

```python
def stream_trail(app, inputs, config, trail):
    final = None

    for mode, chunk in app.stream(
        inputs,
        config,
        stream_mode=["updates", "values"],
    ):
        if mode == "updates":
            for node_name in chunk:
                trail.append(node_name)

        else:
            final = chunk

    return final
```

실행:

```python
trail = []

try:
    stream_trail(
        pingpong_app,
        {"draft": "", "feedback": ""},
        pingpong_config,
        trail,
    )

except GraphRecursionError as error:
    print("예외:", type(error).__name__)

print("방문 수:", len(trail))
print("방문 순서:", " -> ".join(trail))
```

예상 형태:

```text
예외: GraphRecursionError

방문 순서:
writer -> reviewer
-> writer -> reviewer
-> writer -> reviewer
-> writer -> reviewer
-> writer -> reviewer

방문 수: 10
```

### 핵심

`recursion_limit`은 반복의 **원인을 해결하는 장치가 아님**.

```text
핑퐁 발생
   ↓
상한까지 실행
   ↓
GraphRecursionError
```

즉, 전체 그래프에 두는 **최후의 안전장치**에 가까움.

LLM 노드가 반복되면 호출 비용도 계속 발생하므로 기본값에 맡기지 않고 직접 상한을 지정하는 편이 안전함.

# 5. 라운드 가드: 정상 경로로 반복 탈출

`recursion_limit`에 걸리면 예외로 끝남.

반면 State에 반복 횟수와 반려 사유를 저장하면 **예외 전에 정상 경로로 빠져나갈 수 있음**.

```python
MAX_ROUNDS = 4
```

State:

```python
class GuardState(TypedDict):
    draft: str
    feedback: str

    # 지금까지 반려한 횟수
    rounds: int

    # 지금까지 발생한 반려 사유
    reasons: Annotated[list[str], operator.add]

    # 종료 이유
    status: str
```

검토 노드:

```python
def guarded_reviewer(
    state: GuardState,
) -> Command[Literal["writer", "escalate", "__end__"]]:

    reason = review_reason(state["draft"])

    # 정상 통과
    if reason == "통과":
        return Command(
            goto=END,
            update={"status": "통과"},
        )

    # 같은 실패가 반복됨
    if reason in state["reasons"]:
        return Command(
            goto="escalate",
            update={
                "status": f"같은 반려 사유 반복: {reason}"
            },
        )

    # 반복 횟수 상한
    if state["rounds"] >= MAX_ROUNDS:
        return Command(
            goto="escalate",
            update={
                "status": f"라운드 상한 {MAX_ROUNDS} 도달"
            },
        )

    # 계속 수정
    return Command(
        goto="writer",
        update={
            "feedback": reason,
            "rounds": state["rounds"] + 1,
            "reasons": [reason],
        },
    )
```

`escalate`:

```python
def escalate(state: GuardState):
    return {
        "status": "사람 확인 필요: " + state["status"]
    }
```

구조:

```text
writer
  ↓
reviewer
  ├─ 통과 ─────────────→ END
  │
  ├─ 새로운 반려 사유 ─→ writer
  │
  ├─ 같은 사유 반복 ───→ escalate → END
  │
  └─ 라운드 상한 ──────→ escalate → END
```

### 차이

```text
recursion_limit
→ 너무 오래 돌면 예외 발생

라운드 가드
→ 문제 상황을 State로 감지
→ 정상적인 분기(escalate)로 종료
```

# 6. `RemainingSteps`: 남은 실행 단계로 탈출

반복 구조를 정확히 알기 어려운 경우에는 `RemainingSteps` 사용 가능.

```python
from langgraph.managed import RemainingSteps
```

State 타입에 넣으면 별도 입력 없이 LangGraph가 현재 남은 단계 수를 채움.

```python
class StepBudgetState(TypedDict):
    draft: str
    feedback: str
    status: str

    remaining_steps: RemainingSteps
```

검토 노드:

```python
def budget_reviewer(
    state: StepBudgetState,
) -> Command[Literal["writer", "escalate", "__end__"]]:

    # 상한 직전에는 정상 탈출
    if state["remaining_steps"] <= 2:
        return Command(
            goto="escalate",
            update={
                "status":
                f"남은 단계 {state['remaining_steps']}에서 멈춤"
            },
        )

    reason = review_reason(state["draft"])

    if reason == "통과":
        return Command(
            goto=END,
            update={"feedback": reason},
        )

    return Command(
        goto="writer",
        update={"feedback": reason},
    )
```

`2`단계를 남기는 이유:

```text
현재 reviewer
   ↓
escalate 실행에 1단계 필요
   ↓
END
```

상한 직전에 바로 `GraphRecursionError`가 발생하지 않도록 탈출할 여유를 남겨두는 것.

---

## 반복 제어 비교

| 방법 | 멈추는 기준 | 종료 형태 | 적합한 상황 |
|---|---|---|---|
| `recursion_limit` | 전체 단계 수 | `GraphRecursionError` | 모든 그래프의 마지막 안전장치 |
| 라운드 가드 | 반복 횟수 / 같은 원인 반복 | `escalate`로 정상 종료 | 반복 구조를 알고 있을 때 |
| `RemainingSteps` | 남은 단계 수 | `escalate`로 정상 종료 | 반복 구조를 미리 예측하기 어려울 때 |

보통 다음처럼 같이 사용함.

```text
구체적인 반복 감지
라운드 가드
      │
      ├──────────────┐
      ↓              ↓
RemainingSteps   recursion_limit
                  최종 안전장치
```

# 7. 에러 없는 중단: 대기 엣지

실패는 항상 예외로 나타나는 것이 아님.

병렬 갈래를 잘못 합치면 그래프가 **예외 없이 정상 종료됐지만 필요한 노드가 실행되지 않을 수 있음**.

예제 구조:

```text
             ┌─ prices
START ───────┤
             └─ news_fetch → news_summary

뉴스를 생략하면:
START → skip_news
```

---

## 7-1. 대기 엣지

```python
builder.add_edge(
    ["prices", "news_summary"],
    "assemble",
)
```

뜻:

```text
prices 완료
AND
news_summary 완료
        ↓
    assemble
```

뉴스를 생략하는 경우:

```text
prices 완료
skip_news 완료

news_summary 실행 안 됨
        ↓
대기 엣지 조건 불충족
        ↓
assemble 실행 안 됨
        ↓
예외 없이 그래프 종료
```

즉:

```text
Error 없음 ≠ 원하는 결과 생성
```

`briefing`이 비어 있는지, `assemble` 노드가 실행됐는지 궤적을 확인해야 함.

# 8. 보통 엣지의 문제

모든 갈래에서 `assemble`로 일반 엣지를 연결할 수도 있음.

```python
builder.add_edge("prices", "assemble")
builder.add_edge("news_summary", "assemble")
builder.add_edge("skip_news", "assemble")
```

이 경우 어느 하나의 앞 노드가 끝날 때마다 `assemble`이 실행될 수 있음.

```text
prices 완료
   ↓
assemble 실행

news_summary 완료
   ↓
assemble 다시 실행
```

뉴스를 사용하는 주에는 `assemble`이 너무 일찍 실행되어 아직 뉴스 요약이 없는 결과를 먼저 만들 수 있음.

# 9. `defer=True`: 마지막에 한 번 합치기

합치는 노드를 다음처럼 등록.

```python
builder.add_node(
    "assemble",
    assemble,
    defer=True,
)
```

전체 코드:

```python
builder = StateGraph(CollectState)

add_collect_branches(builder)

builder.add_node(
    "assemble",
    assemble,
    defer=True,
)

builder.add_edge("prices", "assemble")
builder.add_edge("news_summary", "assemble")
builder.add_edge("skip_news", "assemble")

builder.add_edge("assemble", END)

defer_app = builder.compile()
```

`defer=True`는 해당 노드를 그래프 실행이 끝나기 직전까지 미룸.

```text
prices ──────────┐
                 │
news_fetch       │
    ↓            │
news_summary ────┼─→ [마지막] assemble → END
                 │
skip_news ───────┘
```

따라서 뉴스 수집 여부와 관계없이 `assemble`을 마지막에 한 번 실행 가능.

### 비교

```text
대기 엣지
["prices", "news_summary"] → assemble

문제:
news_summary가 아예 실행되지 않으면 assemble도 실행되지 않음
```

```text
보통 엣지
prices → assemble
news_summary → assemble
skip_news → assemble

문제:
assemble이 여러 번 또는 너무 일찍 실행될 수 있음
```

```text
보통 엣지 + defer=True

장점:
실행 가능한 갈래를 모두 마친 뒤 마지막에 assemble 실행
```

# 10. 일시 오류와 재시도

## 일시 오류

같은 요청을 조금 뒤에 다시 보내면 성공할 가능성이 있는 오류.

예:

```text
네트워크 연결 끊김
서버 일시 과부하
일부 5xx
일시적인 timeout
```

## 영구 오류

같은 요청을 그대로 다시 보내도 결과가 바뀌지 않는 오류.

예:

```text
잘못된 인자
잘못된 응답 형식
KeyError
ValueError
코드 버그
```

핵심 원칙:

```text
일시 오류 → 재시도
영구 오류 → 재시도하지 않음
```

# 11. `RetryPolicy`

재시도는 노드 함수 안에 직접 작성하지 않고 `add_node()`에서 정책으로 붙일 수 있음.

노드:

```python
def collect_prices(state: PriceState):
    return {
        "prices": fetch_prices()
    }
```

재시도 없음:

```python
builder.add_node(
    "collect_prices",
    collect_prices,
)
```

첫 실패에서 전체 그래프 종료.

```text
가격 API 호출 1
→ ConnectionError
→ 그래프 종료
```

---

## 재시도 적용

```python
from langgraph.types import RetryPolicy
```

```python
builder.add_node(
    "collect_prices",
    collect_prices,
    retry_policy=RetryPolicy(
        max_attempts=3,
        initial_interval=0.5,
        retry_on=ConnectionError,
    ),
)
```

실행 흐름:

```text
1차 시도
  ↓
ConnectionError
  ↓
0.5초 대기

2차 시도
  ↓
ConnectionError
  ↓
1초 대기

3차 시도
  ↓
성공
```

`max_attempts=3`은 **재시도 3번이 아니라 첫 시도를 포함하여 총 3번**임.

---

## 주요 인자

| 인자 | 의미 |
|---|---|
| `max_attempts` | 첫 시도를 포함한 최대 시도 횟수 |
| `initial_interval` | 첫 재시도 전 대기 시간 |
| `backoff_factor` | 다음 대기 시간 증가 배수 |
| `max_interval` | 대기 시간 최대값 |
| `jitter` | 여러 요청이 동시에 재시도되는 것을 줄이기 위한 무작위 지연 |
| `retry_on` | 어떤 예외를 재시도할지 지정 |

기본적인 backoff:

```text
0.5초
  ↓ ×2
1초
  ↓ ×2
2초
  ↓ ×2
4초
...
```

---

# 12. 영구 오류는 재시도하지 않기

리뷰 API는 응답 구조가 바뀌어 항상 `KeyError` 발생.

```python
def collect_reviews(state: ReviewState):
    return {
        "reviews": fetch_reviews()
    }
```

```python
builder.add_node(
    "collect_reviews",
    collect_reviews,
    retry_policy=RetryPolicy(
        max_attempts=3,
    ),
)
```

교안의 기본 판정에서는 `KeyError`가 재시도 대상이 아니므로 실제 API 호출은 한 번만 발생.

```text
max_attempts = 3

하지만

1번째 호출
  ↓
KeyError
  ↓
영구 오류로 판단
  ↓
즉시 종료
```

### 핵심

`RetryPolicy`를 붙였다고 모든 예외를 무조건 반복하는 것은 아님.

특히 직접 정책을 정의할 때는 가능한 한:

```python
retry_on=ConnectionError
```

처럼 **일시 오류만 명시적으로 선택**하는 것이 안전함.

# 13. 노드 타임아웃

외부 API가 예외조차 내지 않고 계속 기다리는 경우에는 재시도만으로 해결할 수 없음.

먼저 **현재 시도를 끊을 시간 제한**이 필요함.

```python
from langgraph.errors import NodeTimeoutError
```

비동기 노드:

```python
async def collect_news(state: NewsState):
    return {
        "news": await fetch_news()
    }
```

노드에 2초 timeout 지정:

```python
builder.add_node(
    "collect_news",
    collect_news,
    timeout=2,
)
```

흐름:

```text
collect_news 시작
      ↓
외부 API 무응답
      ↓
2초 경과
      ↓
NodeTimeoutError
      ↓
그래프 종료
```

교안의 API는 30초 동안 기다리도록 만들었지만 실제 그래프는 약 2초 뒤 중단됨.

---

# 14. 타임아웃 + 재시도

일시적인 무응답은 한 번 끊은 뒤 다시 호출하면 성공할 수도 있음.

따라서 같은 노드에 timeout과 RetryPolicy를 함께 설정 가능.

```python
builder.add_node(
    "collect_news",
    collect_news,

    timeout=2,

    retry_policy=RetryPolicy(
        max_attempts=2,
        initial_interval=0.5,
        retry_on=NodeTimeoutError,
    ),
)
```

흐름:

```text
1차 시도
   ↓
2초 동안 무응답
   ↓
NodeTimeoutError
   ↓
0.5초 + jitter 대기
   ↓
2차 시도
   ↓
정상 응답
```

---

# 15. 재시도 예산

타임아웃과 재시도를 함께 사용하면 **최악의 총 대기 시간**을 생각해야 함.

교안의 계산:

```text
최악 대기
=
시도 수 × timeout
+ 시도 사이의 대기 시간 합
+ jitter 최대값
```

예:

```text
시도 수       = 2
timeout       = 2초
재시도 대기   = 0.5초
jitter 최대   = 1초
```

```text
2 × 2
+ 0.5
+ 1
= 5.5초
```

즉 최악의 경우 약 **5.5초**를 사용할 수 있음.

실제 두 번째 시도가 바로 성공하면 이보다 짧게 끝남.

# 16. 타임아웃과 재시도 설정 기준

| 설정 | 기준 |
|---|---|
| `timeout` | 정상 응답 시간보다 넉넉하게 설정 |
| `max_attempts` | 일시 오류를 복구할 정도로만 설정 |
| `initial_interval` | 외부 서비스가 회복할 시간을 조금 제공 |
| `backoff_factor` | 재시도 간격을 점점 늘림 |
| `retry_on` | 일시 오류만 지정 |
| 전체 예산 | 사용자가 기다릴 수 있는 최대 시간 안으로 제한 |

너무 짧은 timeout:

```text
정상 호출도 강제로 끊김
```

너무 긴 timeout:

```text
장애 발생 시 사용자 대기 증가
```

재시도 횟수가 너무 많으면:

```text
장애 상태의 API에 요청을 더 많이 보냄
→ 복구를 방해할 수도 있음
```

# 17. 겹친 재시도

재시도는 LangGraph에만 있는 것이 아님.

`ChatOpenAI` 내부의 OpenAI Python SDK도 자체 재시도 기능을 가짐.

교안 확인 코드:

```python
print(
    "ChatOpenAI max_retries:",
    llm.max_retries,
)

print(
    "OpenAI 클라이언트 max_retries:",
    llm.root_client.max_retries,
)
```

교안 설정에서는:

```text
ChatOpenAI max_retries: None
OpenAI 클라이언트 max_retries: 2
```

SDK의 `max_retries=2`는:

```text
첫 요청 1번
+ 재시도 2번
= 최대 HTTP 요청 3번
```

---

## 노드 재시도까지 겹치면

예를 들어:

```text
SDK 최대 시도 = 3
LangGraph 노드 최대 시도 = 3
```

노드가 매번 SDK 호출까지 다시 시작하므로 최악의 실제 요청 수는:

```text
3 × 3 = 9번
```

구조:

```text
LangGraph Node
│
├─ 1차 노드 시도
│    └─ SDK: 요청 → 재시도 → 재시도
│
├─ 2차 노드 시도
│    └─ SDK: 요청 → 재시도 → 재시도
│
└─ 3차 노드 시도
     └─ SDK: 요청 → 재시도 → 재시도
```

이처럼 서로 다른 계층에서 같은 오류를 재시도하면 요청 수와 대기 시간이 곱으로 증가할 수 있음.

# 19. 재시도는 한 계층에서 관리

교안의 실무 원칙:

```text
재시도 로직은 가능하면 한 계층에서 관리
```

방법 1:

```text
OpenAI SDK 재시도 사용
LangGraph 노드 재시도는 모델 오류에 적용하지 않음
```

방법 2:

```text
ChatOpenAI(max_retries=0)
        ↓
SDK 재시도 비활성화
        ↓
```

```python
llm = ChatOpenAI(

    max_retries=0,

```

이유:

```text
재시도 횟수 예측 가능
대기 시간 계산 가능
API 호출 수 계산 가능
장애 원인 추적 쉬움
```

# 20. 운영 실패를 보는 순서

멀티에이전트 실행이 이상할 때 다음 순서로 보면 됨.

```text
1. 실행이 끝났는가?
   │
   ├─ 아니오
   │    ├─ 노드가 반복됨 → 핑퐁 확인
   │    └─ 특정 노드에서 멈춤 → timeout 확인
   │
   └─ 예
        ↓
2. 예외가 발생했는가?
   │
   ├─ GraphRecursionError
   │      → 반복 구조 확인
   │
   ├─ ConnectionError
   │      → 일시 오류라면 RetryPolicy
   │
   ├─ NodeTimeoutError
   │      → timeout + 필요 시 재시도
   │
   └─ KeyError / ValueError 등
          → 영구 오류 가능성 확인

3. 예외가 없는데 결과가 비어 있는가?
   ↓
병렬 갈래와 합류 엣지 확인

4. 재시도가 너무 많은가?
   ↓
SDK / LangGraph 등 여러 계층의 재시도 중복 확인
```

# 22. 최종 정리

```text
[반복 문제]

writer ↔ reviewer ↔ writer ↔ reviewer ...
             │
             ├─ 라운드 가드
             ├─ RemainingSteps
             └─ recursion_limit
```

```text
[병렬 합류 문제]

branch A ──┐
           ├─ assemble
branch B ──┘

필수 갈래가 항상 실행되는가?
→ 아니면 대기 엣지 사용에 주의

마지막에 한 번 합치고 싶음
→ defer=True
```

```text
[외부 API 실패]

호출 실패
   │
   ├─ 일시 오류
   │      → RetryPolicy
   │
   ├─ 영구 오류
   │      → 재시도 X
   │
   └─ 응답 없음
          → timeout
             ↓
       필요하면 RetryPolicy
```

```text
[재시도 계층]

LangGraph RetryPolicy
        ↓
Node
        ↓
LLM SDK Retry
        ↓
HTTP 요청

여러 계층이 동시에 재시도하면
실제 요청 횟수와 대기 시간이 곱으로 증가함.

→ 재시도 책임을 가능한 한 한 계층에 둠.
```

---

## 한 줄 기준

- `recursion_limit` → **그래프 전체의 마지막 실행 상한**
- 라운드 가드 → **알고 있는 반복 패턴을 State로 직접 차단**
- `RemainingSteps` → **남은 실행 예산을 보고 정상 경로로 탈출**
- `defer=True` → **합치는 노드를 실행 마지막까지 미룸**
- `RetryPolicy` → **다시 하면 성공할 수 있는 일시 오류만 재시도**
- `timeout` → **응답하지 않는 한 번의 실행을 시간으로 중단**
- 재시도 예산 → **timeout × 시도 수 + 대기 시간을 미리 계산**
- 겹친 재시도 → **SDK와 노드가 동시에 재시도하지 않도록 책임 분리**
