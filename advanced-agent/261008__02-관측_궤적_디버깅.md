# Langfuse 관측과 궤적 디버깅

> 목표: 멀티에이전트 실행을 **궤적(trajectory)** 으로 남기고, LangGraph 스트리밍과 Langfuse trace를 이용해 **증상에서 원인까지 역추적**하는 방법 정리.

---

## 1. 전체 흐름

멀티에이전트는 최종 답변만 보면 어떤 에이전트가 무엇을 받고 무엇을 넘겼는지 알기 어려움.

```text
사용자 요청
   ↓
supervisor
   ↓ 지시
claim_worker ── get_claim
   ↓ 보고
supervisor
   ↓ 지시
terms_worker ── search_terms ── Retriever
   ↓ 보고
supervisor
   ↓ 지시
reply_writer ── get_reply_template
   ↓ 답변
supervisor
   ↓
  END
```

여기서 확인해야 할 것은 최종 답변 하나가 아니라 **각 단계의 입력과 출력**임.

```text
실행
 ↓
궤적 기록
 ↓
이상 징후 발견
 ↓
문제가 보인 단계의 입력 확인
 ↓
이전 단계로 역추적
 ↓
정보가 사라진 지점 발견
 ↓
코드 수정
 ↓
v1 / v2 trace 비교
```

---

# 2. 핵심 개념

## 2-1. 궤적(Trajectory)

**한 번의 실행에서 어떤 노드·에이전트·도구가 어떤 순서로 실행됐고, 무엇을 입력받아 무엇을 출력했는지 남긴 기록.**

단일 에이전트는 메시지 흐름만 확인해도 되지만, 슈퍼바이저 구조는 실행이 두 겹으로 존재함.

```text
[바깥 흐름]
supervisor → worker → supervisor → worker ...

[워커 내부]
model → tool → model → ...
```

따라서 멀티에이전트 디버깅에서는 두 흐름을 같이 봐야 함.

---

## 2-2. 증상과 원인은 다를 수 있음

잘못된 답변이 나온 노드가 반드시 원인 노드는 아님.

예시:

```text
사용자 요청
"땅콩 알레르기가 있음"
       ↓
supervisor 지시
"저녁 메뉴를 찾아줘"
       ↓
알레르기 정보 소실 ← 실제 원인
       ↓
검색 worker
땅콩 메뉴 검색
       ↓
답변 worker
땅콩 메뉴 추천 ← 증상
```

따라서 디버깅은 아래처럼 **뒤에서 앞으로** 진행함.

```text
최종 답변
  ↑
답변 worker 입력
  ↑
검색 worker 출력
  ↑
supervisor 지시
  ↑
원래 사용자 요청
```

핵심 질문:

> **필요한 정보가 이 단계의 입력에 존재하는가?**

있던 정보가 다음 단계에서 사라졌다면, 그 사이가 원인 지점임.

# 3. 실습 구조

교안에서는 여행자 보험 청구 심사 팀을 사용함.

| 노드 | 역할 | 도구 |
|---|---|---|
| `supervisor` | 다음 작업 결정 | 없음 |
| `claim_worker` | 청구 내용 조회 | `get_claim` |
| `terms_worker` | 약관 검색 | `search_terms` |
| `reply_writer` | 고객 답변 작성 | `get_reply_template` |

약관 검색은 BM25 + Dense 검색을 결합한 하이브리드 검색 구조.

```text
질문
 ├─ BM25 검색
 └─ Dense 검색
       ↓
EnsembleRetriever(RRF)
       ↓
상위 약관 반환
```

# 5. 워커 도구와 에이전트

## 5-1. 청구 조회 도구

```python
from langchain_core.tools import tool

@tool
def get_claim(claim_id: str) -> dict:
    """청구번호로 청구 정보를 조회한다."""
    if claim_id not in CLAIMS:
        return {"안내": "없는 청구번호입니다."}

    return CLAIMS[claim_id]
```

## 5-2. 약관 검색 도구

```python
@tool
def search_terms(query: str) -> list[dict]:
    """관련 약관 상위 3개를 검색한다."""
    found = terms_retriever.invoke(query)[:3]

    return [
        {
            "id": doc.metadata["id"],
            "제목": doc.metadata["제목"],
            "내용": doc.page_content,
        }
        for doc in found
    ]
```

`search_terms` 내부에서는 하이브리드 Retriever가 실행됨.

```python
terms_retriever = EnsembleRetriever(
    retrievers=[bm25, dense],
    weights=[0.5, 0.5],
    c=60,
    id_key="id",
)
```

# 6. 팀 State와 Supervisor

## 6-1. 공유 State

```python
from typing_extensions import TypedDict

class TeamState(TypedDict):
    request: str
    max_turns: int
    instruction: str
    visits: list[str]
    turn: int
    results: list[dict]
```

각 필드의 의미:

| 필드 | 역할 |
|---|---|
| `request` | 원래 심사 요청 |
| `instruction` | supervisor가 현재 worker에 준 지시 |
| `visits` | 지금까지 호출된 worker 순서 |
| `turn` | worker 호출 횟수 |
| `results` | 각 worker가 반환한 보고 목록 |
| `max_turns` | 무한 반복 방지 상한 |

---

## 6-2. 구조화된 라우팅 결과

```python
from typing import Literal
from pydantic import BaseModel, Field

class Route(BaseModel):
    next: Literal[
        "claim_worker",
        "terms_worker",
        "reply_writer",
        "FINISH",
    ] = Field(description="다음 worker")

    instruction: str = Field(
        description="다음 worker에게 전달할 지시"
    )
```

Supervisor는 단순 문자열이 아니라 다음 두 값을 구조화해서 반환함.

```text
next        → 어느 노드로 갈지
instruction → 그 노드에 무엇을 시킬지
```

---

## 6-3. Supervisor 체인

```python
from langchain_core.prompts import ChatPromptTemplate

supervisor_prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        "보험 청구 심사 팀의 팀장입니다. "
        "심사 요청과 지금까지 보고를 읽고 다음 worker를 정하세요."
    ),
    (
        "human",
        "심사 요청: {request}\n\n"
        "지금까지 보고:\n{results}"
    ),
])

supervisor_chain = (
    supervisor_prompt
    | llm.with_structured_output(Route, strict=True)
)
```

# 7. 보고 전달 함수와 핵심 버그

교안의 v1에서는 토큰 절약을 위해 worker 보고를 **앞 60자만 전달**함.

```python
def format_results(results):
    if not results:
        return "아직 없음"

    lines = []

    for row in results:
        summary = row["result"][:60]
        lines.append(f"[{row['worker']}] {summary}")

    return "\n\n".join(lines)
```

처음에는 단순한 압축처럼 보이지만 실제로는 이후 디버깅의 원인이 됨.

```text
claim_worker 전체 보고
[청구번호 / 청구인 / 사고 종류 / 지연 사유 / 청구액 / 증빙]
                         ↓ 앞 60자만 사용
Supervisor가 받는 보고
[청구번호 / 청구인 / 사고 종류 ...]
                         ↓
지연 사유·청구액·증빙 손실
```

# 8. Supervisor 노드

```python
from langgraph.types import Command
from langgraph.graph import END


def supervisor(state: TeamState) -> Command:
    # 처리 상한 도달
    if state["turn"] >= state["max_turns"]:
        if "reply_writer" in state["visits"]:
            return Command(goto=END)

        return Command(
            goto="reply_writer",
            update={
                "instruction": (
                    "처리 상한에 닿았습니다. "
                    "지급을 약속하지 말고 심사 담당자 확인 필요로 안내하세요."
                ),
                "visits": state["visits"] + ["reply_writer"],
                "turn": state["turn"] + 1,
            },
        )

    route = supervisor_chain.invoke({
        "request": state["request"],
        "results": format_results(state["results"]),
    })

    if route.next == "FINISH":
        return Command(goto=END)

    return Command(
        goto=route.next,
        update={
            "instruction": route.instruction,
            "visits": state["visits"] + [route.next],
            "turn": state["turn"] + 1,
        },
    )
```

### 핵심

`Command`가 두 작업을 동시에 수행함.

```text
goto   → 다음 노드 지정
update → State 갱신
```

따라서 별도의 조건부 엣지 없이 supervisor가 실행 흐름을 직접 결정함.

# 9. Worker 공통 실행 함수

```python
def run_worker(agent, worker, state):
    message = (
        f"심사 요청: {state['request']}\n\n"
        f"지시: {state['instruction']}\n\n"
        f"팀이 지금까지 확인한 내용:\n"
        f"{format_results(state['results'])}"
    )

    reply = agent.invoke({
        "messages": [
            {"role": "user", "content": message}
        ]
    })

    return state["results"] + [{
        "worker": worker,
        "result": reply["messages"][-1].text,
    }]
```

각 worker 노드는 같은 구조를 사용함.

```python
def claim_worker(state: TeamState) -> Command:
    results = run_worker(claim_agent, "claim_worker", state)
    return Command(
        goto="supervisor",
        update={"results": results},
    )


def terms_worker(state: TeamState) -> Command:
    results = run_worker(terms_agent, "terms_worker", state)
    return Command(
        goto="supervisor",
        update={"results": results},
    )


def reply_writer(state: TeamState) -> Command:
    results = run_worker(reply_agent, "reply_writer", state)
    return Command(
        goto="supervisor",
        update={"results": results},
    )
```

흐름:

```text
supervisor
   ↓ instruction
worker
   ↓ results 추가
supervisor
```

# 10. 그래프 조립

```python
from langgraph.graph import StateGraph, START

team_builder = StateGraph(TeamState)

team_builder.add_node("supervisor", supervisor)
team_builder.add_node("claim_worker", claim_worker)
team_builder.add_node("terms_worker", terms_worker)
team_builder.add_node("reply_writer", reply_writer)

team_builder.add_edge(START, "supervisor")

team_app = team_builder.compile()
```

고정 엣지는 시작점 하나뿐임.

```text
START → supervisor
```

그 뒤 이동은 각 노드가 반환하는 `Command(goto=...)`가 결정함.

# 11. LangGraph Streaming으로 궤적 보기

Langfuse 없이도 `stream()`으로 현재 실행을 바로 볼 수 있음.

핵심 옵션:

```python
app.stream(
    inputs,
    stream_mode="updates",
    subgraphs=True,
)
```

## `stream_mode="updates"`

노드가 끝날 때마다 해당 노드가 State에 변경한 값만 반환.

## `subgraphs=True`

worker 안에서 실행되는 `create_agent`의 내부 `model`, `tools` 이벤트까지 반환.

반환 형태:

```python
(namespace, event)
```

예시:

```text
namespace = ()
→ 팀 그래프 이벤트

namespace = ('terms_worker:<작업 id>',)
→ terms_worker 내부 agent 이벤트
```

---

## 11-1. 이벤트 위치 표시

```python
def event_place(namespace):
    names = ["팀"]

    for part in namespace:
        names.append(part.split(":")[0])

    return "/".join(names)
```

예:

```text
()                              → 팀
('claim_worker:abc...',)         → 팀/claim_worker
('terms_worker:def...',)         → 팀/terms_worker
```

---

## 11-2. 이벤트의 핵심 값 추출

```python
from langchain_core.messages import AIMessage, ToolMessage


def update_lines(update):
    if update is None:
        return ["State 변경 없음"]

    lines = []

    if "instruction" in update:
        lines.append(
            f"지시({update['visits'][-1]}): {update['instruction']}"
        )

    if "results" in update:
        last = update["results"][-1]
        lines.append(
            f"보고({last['worker']}): {last['result']}"
        )

    if "messages" in update:
        for message in update["messages"]:
            if isinstance(message, ToolMessage):
                lines.append(
                    f"도구 결과({message.name}): {message.content}"
                )

            elif isinstance(message, AIMessage) and message.tool_calls:
                for call in message.tool_calls:
                    lines.append(
                        f"도구 호출: {call['name']} {call['args']}"
                    )

            elif isinstance(message, AIMessage):
                lines.append(f"에이전트 답: {message.text}")

    return lines
```

## 11-3. 궤적 출력

```python
def print_trajectory(app, inputs):
    step = 0

    for namespace, event in app.stream(
        inputs,
        stream_mode="updates",
        subgraphs=True,
    ):
        place = event_place(namespace)

        for node, update in event.items():
            step += 1
            print(f"[{step}] {place} > {node}")

            for line in update_lines(update):
                one_line = line.replace("\n", " / ")
                print("    ", one_line[:120])
```

실행:

```python
print_trajectory(team_app, make_input("CLM-2101"))
```

출력은 대략 다음 구조로 읽음.

```text
[1] 팀 > supervisor
    지시(claim_worker): CLM-2101 청구를 조회하세요.

[2] 팀/claim_worker > model
    도구 호출: get_claim {'claim_id': 'CLM-2101'}

[3] 팀/claim_worker > tools
    도구 결과(get_claim): {...}

[4] 팀/claim_worker > model
    에이전트 답: ...

[5] 팀 > claim_worker
    보고(claim_worker): ...
```

### Streaming의 장단점

장점:
- 현재 실행을 바로 확인 가능
- 어떤 노드가 반복되는지 확인하기 쉬움
- worker 내부 tool 호출까지 볼 수 있음

한계:
- 노트북을 닫으면 기록이 사라짐
- 토큰·비용·지연 시간 비교가 어려움
- 과거 실행과 수정 후 실행 비교가 어려움

→ 운영 관측에는 Langfuse 사용.

# 12. Langfuse의 기록 단위

## 12-1. Trace / Observation / Session

| 단위 | 의미 | 예 |
|---|---|---|
| **Trace** | 요청 1회의 전체 실행 | `team_app.invoke()` 한 번 |
| **Observation** | Trace 내부 단계 하나 | supervisor, tool 호출 등 |
| **Session** | 관련된 여러 Trace 묶음 | 같은 청구 작업의 여러 실행 |

구조:

```text
Session
 ├─ Trace 1
 │   ├─ Observation
 │   ├─ Observation
 │   └─ Observation
 │
 └─ Trace 2
     ├─ Observation
     └─ Observation
```

---

## 12-2. Observation 종류

| 종류 | 의미 | 예 |
|---|---|---|
| `agent` | 모델·도구 호출을 반복하는 agent 실행 | `claim_agent` |
| `chain` | 코드가 정한 흐름 실행 | `claim-team`, `supervisor` |
| `generation` | LLM 호출 1회 | `ChatOpenAI` |
| `tool` | Tool 호출 | `get_claim` |
| `retriever` | 검색기 호출 | `EnsembleRetriever` |

구분:

```text
agent
 ├─ generation
 ├─ tool
 └─ generation

chain
 └─ 정해진 코드 흐름
```

# 13. Langfuse 실행 설정

```python
from langfuse.langchain import CallbackHandler


def make_config(session_id, thread_id, tags):
    return {
        "callbacks": [CallbackHandler()],
        "run_name": "claim-team",
        "recursion_limit": 30,
        "configurable": {
            "thread_id": thread_id,
        },
        "metadata": {
            "langfuse_session_id": session_id,
            "langfuse_tags": tags,
        },
    }
```

## 핵심 설정

| 설정 | 역할 |
|---|---|
| `callbacks` | Langfuse에 실행 기록 전송 |
| `run_name` | Trace 이름 |
| `thread_id` | LangGraph 작업 식별자 |
| `langfuse_session_id` | Langfuse Session 묶음 |
| `langfuse_tags` | 실행 분류 및 필터링 |
| `recursion_limit` | 그래프 단계 상한 |

# 14. `thread_id`와 `session_id` 차이

둘은 비슷해 보이지만 역할이 다름.

| | `thread_id` | `langfuse_session_id` |
|---|---|---|
| 시스템 | LangGraph | Langfuse |
| 위치 | `configurable` | `metadata` |
| 역할 | State/체크포인터 작업 식별 | Trace 묶음 |
| 없을 때 | 체크포인터 사용 시 문제 | Trace는 남지만 Session 없음 |

교안에서는 단순하게 다음처럼 맞춤.

```text
작업 하나 = thread 하나 = session 하나
```

즉:

```python
run_id = "claim-review-2026-10-08-CLM-2101"

config = make_config(
    session_id=run_id,
    thread_id=run_id,
    tags=["day56", "v1"],
)
```

중요:

> `thread_id`만 넣는다고 Langfuse Session이 생성되는 것은 아님.

Session은 반드시 `metadata["langfuse_session_id"]`로 설정함.

# 18. 실제 원인: `format_results()` 정보 손실

먼저 `claim_worker`의 원본 보고에는 필요한 정보가 존재함.

```python
results_2102 = claim_runs["CLM-2102"]["results"]

claim_report = ""

for row in results_2102:
    if row["worker"] == "claim_worker":
        claim_report = row["result"]
        break

print(claim_report)
```

그러나 supervisor에 전달하기 전에 아래 함수를 거침.

```python
summary = row["result"][:60]
```

결과:

| 단계 | 정보 상태 |
|---|---|
| `claim_worker` 출력 | 전체 정보 존재 |
| `format_results()` | 60자로 잘림 |
| supervisor 입력 | 지연 사유·청구액·증빙 누락 |
| supervisor 판단 | 조회가 안 끝난 것으로 판단 |
| `claim_worker` | 다시 호출 |
| 반복 | 처리 상한 도달 |

즉 최종 답변 노드가 문제가 아니라 **에이전트 사이의 정보 전달 함수**가 원인임.

```text
증상
같은 worker 반복 + 결론 없는 답변

원인
format_results()가 보고를 60자로 자름
```

# 19. 수정 코드

보고를 자르지 않도록 변경.

```python
def format_results(results):
    """worker 보고를 자르지 않고 전달한다."""
    if not results:
        return "아직 없음"

    lines = []

    for row in results:
        lines.append(
            f"[{row['worker']}] {row['result']}"
        )

    return "\n\n".join(lines)
```

Supervisor와 `run_worker()`가 실행 시점에 `format_results`라는 이름을 다시 찾으므로, 교안에서는 같은 이름으로 재정의한 뒤 기존 `team_app`을 다시 실행함.

|---|---|---|
| Session | 같은 작업의 Trace 묶음 | 실행 `metadata` |

## 21-1. `sample_rate`

```python

```

의미:


# 22. 개인정보 Masking

Trace에는 Tool 입력/출력도 남으므로 개인정보가 포함될 수 있음.

교안에서는 휴대전화 번호를 전송 전에 가림.

```python
import re

PHONE_PATTERN = re.compile(
    r"01[016789]-\d{3,4}-\d{4}"
)


def mask_phone(*, data, **kwargs):
    if isinstance(data, str):
        return PHONE_PATTERN.sub(
            "***-****-****",
            data,
        )

    if isinstance(data, dict):
        return {
            key: mask_phone(data=value)
            for key, value in data.items()
        }

    if isinstance(data, list):
        return [
            mask_phone(data=value)
            for value in data
        ]

    return data
```

클라이언트 생성 시 설정:

```python
from langfuse import Langfuse

langfuse = Langfuse(
    mask=mask_phone,
    sample_rate=0.2,
    environment="production",
)
```

### 주의

`mask`는 클라이언트 생성 시점에 지정함.

이미 `get_client()`로 클라이언트를 생성한 뒤가 아니라, 초기 설정 단계에서 적용해야 함.

# 23. Streaming과 Langfuse 비교

| 구분 | LangGraph Streaming | Langfuse |
|---|---|---|
| 목적 | 현재 실행 확인 | 실행 기록·분석 |
| 저장 | 일시적 | 서버 저장 |
| 내부 worker 확인 | `subgraphs=True` | Trace Tree |
| 반복 노드 확인 | 출력 직접 확인 | Graph/Aggregated |
| 모델 Input/Output | 일부 확인 | 상세 확인 |
| Token/Cost/Latency | 제한적 | 확인 가능 |
| 수정 전후 비교 | 어려움 | Tag로 비교 |

둘 중 하나를 고르는 구조가 아니라 용도가 다름.

```text
개발 중 즉시 흐름 확인
→ Streaming

실행을 저장하고 과거와 비교
→ Langfuse
```

# 24. 디버깅 절차 정리

멀티에이전트에서 오류가 발생하면 다음 순서로 확인.

```text
1. 최종 결과에서 증상 확인
       ↓
2. Graph에서 반복된 노드 확인
       ↓
3. 문제 노드의 Input 확인
       ↓
4. 필요한 정보가 있는지 확인
       ↓
5. 이전 노드 Output 확인
       ↓
6. 정보가 사라진 경계 찾기
       ↓
7. 해당 전달 코드 수정
       ↓
8. 새 Tag로 재실행
       ↓
9. v1 / v2 Trace 비교
```

핵심은 **증상이 보이는 노드를 바로 수정하지 않는 것**.

```text
잘못된 답변
≠
답변 worker가 항상 원인
```

실제 원인은 그보다 앞의:

- 잘못된 supervisor 지시
- 정보 전달 누락
- 잘못된 검색 결과
- Tool 호출 인자 오류
- 반복/종료 조건 오류

일 수 있음.

# 26. 최종 정리

- **궤적** = 실행 과정 전체의 입력·출력 기록.
- 멀티에이전트는 **팀 그래프 + worker 내부 agent 그래프**가 겹치므로 실행을 계층적으로 봐야 함.
- `stream(..., stream_mode="updates", subgraphs=True)`로 현재 실행의 내부 단계까지 확인 가능.
- Langfuse에서는 요청 한 번이 **Trace**, 내부 단계 하나가 **Observation**, 관련 Trace 묶음이 **Session**.
- `thread_id`는 LangGraph 작업 식별자이고 `langfuse_session_id`는 Langfuse에서 Trace를 묶는 값.
- `CallbackHandler()`를 실행 config의 `callbacks`에 넣어 LangGraph 실행을 기록.
- 오류 디버깅은 **최종 증상 → 입력 확인 → 이전 출력 확인** 순서로 역추적.
- 교안의 핵심 버그는 `format_results()`가 worker 보고를 60자로 잘라 중요한 정보가 supervisor에 전달되지 않은 것.
- 수정 전후 실행은 `v1`, `v2-full-report` 같은 **Tag**를 달아 비교.
- 운영에서는 `sample_rate`, `mask`, `environment`, `release`까지 함께 설계.
