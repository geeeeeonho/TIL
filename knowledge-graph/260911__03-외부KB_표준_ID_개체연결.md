# 외부 KB의 표준 ID에 개체 연결하기 핵심 정리

> 기준: `부록_외부_KB의_표준_ID에_개체_연결하기.ipynb`  
> 목적: **Entity Linking 개념 · 핵심 문법 · 저장 및 활용 흐름** 중심으로 압축 정리

---

## 0. 전체 흐름

이 부록의 목표는 **내 그래프의 개체를 Wikidata의 같은 대상과 연결**하는 것이다.

```text
내부 개체
→ 이름·별칭으로 Wikidata 후보 검색
→ 후보 상세 정보 비교
→ LLM이 같은 대상 선택
→ 선택한 Q-ID 검증
→ 내부 노드에 외부 ID 저장
→ Q-ID로 Wikidata 상세 정보 조회
→ SPARQL로 연결된 다른 항목 탐색
```

핵심:

```text
standard_id = 내 프로젝트의 식별자
external_id = 외부 KB의 식별자
source_kb   = 외부 ID의 출처
```

> 기존 `standard_id`를 외부 ID로 바꾸는 작업이 아님.  
> **내부 ID를 유지한 채 외부 ID를 추가**하는 작업이다.

---

# 1. 내부 ID와 외부 ID

## 1-1. Entity Linking

**개체 연결(Entity Linking)**은 문서나 그래프의 개체가 외부 지식베이스의 어떤 항목과 같은 대상인지 연결하는 작업이다.

이 부록에서는 외부 KB로 **Wikidata**를 사용한다.

Wikidata의 항목 ID:

```text
Q117340550
```

처럼 `Q`로 시작하며 **Q-ID**라고 부른다.

---

## 1-2. ID 역할 구분

| 속성 | 역할 | 예 |
|---|---|---|
| `standard_id` | 내 프로젝트의 노드 식별 | `framework:langchain` |
| `external_id` | Wikidata 항목 식별 | `Q117340550` |
| `source_kb` | 외부 ID의 출처 | `wikidata` |

연결 전:

```text
(:SoftwareFramework {
    standard_id: "framework:langchain"
})
```

연결 후:

```text
(:SoftwareFramework {
    standard_id: "framework:langchain",
    external_id: "Q...",
    source_kb: "wikidata"
})
```

Wikidata의 노드와 관계를 내 그래프에 그대로 복사하는 것이 아니라, **기존 노드에 연결 정보만 추가**한다.

# 2. Wikidata 후보 검색

## 2-1. 내부 개체 정보

후보를 찾기 전에 내 개체를 설명할 정보를 준비한다.

```python
local_entity = {
    "standard_id": "framework:langchain",
    "canonical_name": "LangChain",
    "aliases": ["랭체인"],
    "entity_type": "SoftwareFramework",
    "context": "언어 모델 애플리케이션을 만드는 프레임워크",
    "official_website": "https://langchain.com/",
}
```

핵심 필드:

```text
canonical_name   = 대표 이름
aliases          = 다른 표기
entity_type      = 내 그래프의 개체 타입
context          = 어떤 대상인지 설명하는 문맥
official_website = 공식 사이트
```

이름만으로 같은 대상을 판단하지 않고 **종류·설명·공식 사이트**도 함께 사용한다.

---

## 2-2. 제공 조회 함수

교안의 `kb_lookup.py`가 Wikidata 조회를 담당한다.

```python
from kb_lookup import (
    search_candidates,
    candidate_rows,
)
```

### `search_candidates()`

```python
search_candidates(검색어_목록)
```

- 이름·별칭으로 Wikidata 검색
- 검색어당 최대 5개 후보
- 같은 Q-ID 중복 제거
- `{Q-ID: 검색 결과}` 사전 반환

### `candidate_rows()`

```python
candidate_rows(Q_ID_목록)
```

각 후보의 상세 정보를 비교 가능한 형태로 반환한다.

대표 정보:

```text
qid
name
type
description
websites
```

# 3. 후보 상세 정보 비교

후보 Q-ID를 상세 조회한다.

```python
candidate_table = pd.DataFrame(
    candidate_rows(
        list(candidates_by_id)
    )
)
```

`list(candidates_by_id)`는 사전의 **키인 Q-ID 목록**을 꺼낸다.

비교 기준:

```text
이름
종류
설명
공식 사이트
```

Wikidata 속성 예:

```text
P31  = 종류
P856 = 공식 사이트
```

`websites=[]`는 공식 사이트 정보가 Wikidata에 등록되지 않았다는 뜻이다.

> 타입 표현이 정확히 같지 않다는 이유만으로 바로 제외하지 않는다.  
> 예: `SoftwareFramework`와 더 넓은 타입인 `Software`.

# 4. LLM으로 같은 대상 선택

## 4-1. 역할 분리

Prompt는 다음처럼 나눈다.


판정 결과:

# 6. 선택한 Q-ID 검증

LLM이 `linked`를 반환했다고 바로 저장하지 않는다.

## 6-1. 허용 후보 ID 만들기

```python
allowed_qids = {
    row["qid"]
    for row in candidate_records
}
```

즉 LLM에게 실제 전달했던 Q-ID만 허용한다.

---

## 6-2. 선택 검증

```python
reason = link_decision.reason.strip()

selected_qid = None
review_reason = (
    reason
    or "판정 이유가 없어 추가 확인이 필요합니다."
)

if link_decision.status == "linked":
    if (
        link_decision.qid in allowed_qids
        and reason
    ):
        selected_qid = link_decision.qid
        review_reason = None
    else:
        review_reason = (
            "후보 목록의 ID와 선택 이유를 "
            "다시 확인해야 합니다."
        )
```

`linked`로 인정하려면:

```text
1. status == "linked"
2. qid가 실제 후보 목록 안에 있음
3. reason이 비어 있지 않음
```

하나라도 만족하지 않으면:

```text
external_id = None
link_status = review
```

로 처리한다.

---

## 6-3. 저장용 구조

```python
demo_link = {
    "standard_id":
        local_entity["standard_id"],

    "name":
        local_entity["canonical_name"],

    "entity_type":
        local_entity["entity_type"],

    "external_id":
        selected_qid,

    "source_kb":
        "wikidata"
        if selected_qid
        else None,

    "link_status":
        "linked"
        if selected_qid
        else "review",

    "link_reason":
        reason
        if selected_qid
        else None,

    "review_reason":
        review_reason,
}
```

핵심:

```text

review → external_id 없이 review_reason 저장
```

# 7. Neo4j에 연결 결과 저장

## 7-1. Neo4j 연결

```python
from neo4j import GraphDatabase

driver = GraphDatabase.driver(
    neo4j_uri,
    auth=(
        NEO4J_USER,
        NEO4J_PASSWORD,
    ),
)

driver.verify_connectivity()
```

공통 Cypher 함수:

```python
def run_cypher(query, **params):
    with driver.session() as session:
        return [
            record.data()
            for record in session.run(
                query,
                **params,
            )
        ]
```

---

## 7-2. `MERGE` + `SET`

```python
def save_link(row):
    return run_cypher(
        """
        MERGE (
            n:$($entity_type)
            {standard_id: $row.standard_id}
        )

        SET
            n.name = $row.name,
            n.entity_type = $entity_type,
            n.external_id = $row.external_id,
            n.source_kb = $row.source_kb,
            n.link_status = $row.link_status,
            n.link_reason = $row.link_reason,
            n.review_reason = $row.review_reason

        RETURN
            n.standard_id AS standard_id,
            n.external_id AS external_id,
            n.source_kb AS source_kb,
            n.link_status AS link_status,
            n.link_reason AS link_reason,
            n.review_reason AS review_reason
        """,
        entity_type=row["entity_type"],
        row=row,
    )
```

핵심 문법:

```text
MERGE = 같은 Label + standard_id 노드를 찾고, 없으면 생성
SET   = 외부 ID와 판정 정보를 속성으로 저장
$row  = Python에서 전달한 dict
$($entity_type) = 전달한 값을 Label로 사용
```

Python의 `None`은 Cypher에서 `null`로 전달된다.

`SET n.property = null`이 되면 해당 속성은 제거된다.

### 중요한 역할 구분

```text
LLM / 검증 코드 = 어떤 후보를 연결할지 판단
save_link()      = 이미 결정된 결과를 저장
```

`save_link()` 자체는 후보를 선택하지 않는다.

# 8. 연결한 Q-ID로 외부 정보 가져오기

외부 ID를 연결한 뒤에는 **이름 검색을 다시 하지 않고 Q-ID로 직접 조회**할 수 있다.

## 8-1. 연결 완료 노드 조회

```cypher
MATCH (
    n:SoftwareFramework
    {standard_id: $standard_id}
)

WHERE
    n.source_kb = 'wikidata'
    AND n.link_status = 'linked'
    AND n.external_id IS NOT NULL

RETURN
    n.standard_id AS standard_id,
    n.name AS name,
    n.external_id AS qid
```

보류된 노드는 제외한다.

# 9. 외부 정보로 내부 노드 보완

기존 속성을 덮어쓰기보다 외부 정보에는 `kb_` 접두어를 사용한다.

예:

```text
name            = 내 그래프의 원래 이름
kb_description  = Wikidata 설명
kb_websites     = Wikidata 공식 사이트
kb_url          = Wikidata 항목 URL
kb_checked_at   = 마지막 조회 시각
```

---

## 9-1. `UNWIND`로 여러 상세 정보 저장

```cypher
UNWIND $details AS detail

MATCH (
    n:SoftwareFramework
    {standard_id: $standard_id}
)

WHERE
    n.source_kb = 'wikidata'
    AND n.link_status = 'linked'
    AND n.external_id = detail.qid

SET
    n.kb_description = detail.description,
    n.kb_websites = detail.websites,
    n.kb_url = detail.kb_url,
    n.kb_checked_at = datetime()
```

`UNWIND`:

```text
Python list
→ 각 원소를 Cypher의 한 행씩 처리
```

`datetime()`:

```text
외부 정보를 확인한 시각 기록
```

# 10. SPARQL로 Wikidata 관계 탐색

## 10-1. 역할

Q-ID를 확보하면 내 Neo4j에 저장되지 않은 관계도 Wikidata에서 직접 조회할 수 있다.

교안 예시:

```text
LangChain이 의존하는 라이브러리 찾기
→ 같은 라이브러리에 의존하는 다른 소프트웨어 찾기
```

---

## 10-2. RDF · SPARQL · Cypher 구분

| 용어 | 역할 |
|---|---|
| RDF | 주어-관계-목적어 트리플로 지식 표현 |
| SPARQL | RDF 관계 패턴 조회 |
| Cypher | Neo4j 그래프 조회 |

즉:

```text
내 Neo4j 조회 → Cypher
Wikidata 조회 → SPARQL
```

# 11. SPARQL 핵심 문법

공통 의존성을 찾는 핵심 패턴:

```sparql
?target wdt:P1547 ?dependency .
?other  wdt:P1547 ?dependency .
```

두 패턴에서 같은 `?dependency` 변수를 사용하므로:

```text
target과 other가
같은 dependency를 공유하는 경우
```

를 찾는다.

---

## 11-1. 주요 표기

| 문법 | 의미 |
|---|---|
| `wd:Q...` | Wikidata 특정 항목 |
| `wdt:P1547` | 속성의 직접 값 |
| `?target` | 조회 중 값이 들어갈 변수 |
| `SELECT` | 반환할 변수 |
| `WHERE` | 찾을 관계 패턴 |
| `VALUES` | 출발 항목 지정 |
| `FILTER` | 조건에 맞지 않는 행 제외 |
| `SERVICE wikibase:label` | 사람이 읽을 이름 조회 |
| `LIMIT 5` | 최대 5행 반환 |

---

## 11-2. 저장한 Q-ID를 SPARQL에 넣기

```python
wd_ids = " ".join(
    "wd:" + qid
    for qid in linked_qids
)
```

예:

```text
Q117340550
→ wd:Q117340550
```

SPARQL:

```sparql
PREFIX wd:
    <http://www.wikidata.org/entity/>

PREFIX wdt:
    <http://www.wikidata.org/prop/direct/>

PREFIX wikibase:
    <http://wikiba.se/ontology#>

PREFIX bd:
    <http://www.bigdata.com/rdf#>

SELECT DISTINCT
    ?target
    ?targetLabel
    ?dependencyLabel
    ?other
    ?otherLabel

WHERE {
    VALUES ?target {
        __QIDS__
    }

    ?target wdt:P1547 ?dependency .
    ?other  wdt:P1547 ?dependency .

    FILTER(
        ?other != ?target
    )

    SERVICE wikibase:label {
        bd:serviceParam
            wikibase:language
            "ko,en".
    }
}

LIMIT 5
```

`PREFIX`는 긴 URI를 `wd:`, `wdt:`처럼 짧게 쓰기 위한 선언이다.

# 12. Wikidata Query Service 호출

SPARQL 쿼리는 Neo4j가 아니라 **Wikidata Query Service**에 전달한다.

```python
sparql_response = requests.get(
    "https://query.wikidata.org/sparql",
    params={
        "query": sparql_query,
        "format": "json",
    },
    headers={
        "User-Agent":
            "EntityLinkingLesson/1.0 "
            "(educational Wikidata lookup)",

        "Accept":
            "application/sparql-results+json",
    },
    timeout=60,
)
```

응답 행:

```python
sparql_bindings = (
    sparql_response
    .json()["results"]["bindings"]
)
```

각 변수의 실제 값:

```python
binding["targetLabel"]["value"]
binding["dependencyLabel"]["value"]
binding["otherLabel"]["value"]
binding["other"]["value"]
```

### 해석 주의

공통 의존성을 공유한다고 해서:

```text
두 소프트웨어가 같은 개체
두 소프트웨어가 서로 대체 가능
```

이라는 뜻은 아니다.

단지 **Wikidata에 등록된 같은 dependency 관계를 공유**한다는 의미다.

또한 현재 설치 환경의 실제 의존성 전체를 검사하는 작업도 아니다.

# 13. `linked`와 `review` 흐름

```text
Wikidata 후보 검색
        ↓
LLM 후보 비교
        ↓
┌─────────────────────────────┐
│ 같은 대상이라는 근거 충분? │
└──────────────┬──────────────┘
               │
       ┌───────┴───────┐
      Yes              No
       │                │
    linked           review
       │                │
후보 Q-ID 검사       external_id=None
이유 존재 검사       review_reason 저장
       │
       ↓
external_id 저장
source_kb="wikidata"
link_reason 저장
```

`review`를 실패로 버리지 않고 **추가 검토가 필요한 상태로 저장**하는 것이 핵심이다.

# 15. 최종 구조 암기

```text
[1] 내부 개체 준비
standard_id + 이름 + 별칭 + 문맥
        ↓
[2] 후보 검색
이름·별칭으로 Wikidata Q-ID 후보 수집
        ↓
[3] 후보 상세 비교
이름 + 종류 + 설명 + 공식 사이트
        ↓
[4] LLM 판정
linked / review + qid + reason
        ↓
[5] 후보 ID 검증
전달한 후보 안의 Q-ID인지 확인
        ↓
[6] Neo4j 저장
standard_id는 유지
external_id + source_kb + 상태·이유 추가
        ↓
[7] 외부 정보 보완
저장한 Q-ID로 description / website 조회
        ↓
[8] SPARQL 확장
Q-ID를 출발점으로 Wikidata의 다른 관계 탐색
```

### 가장 중요한 구분

```text
standard_id
= 내 프로젝트에서 사용하는 내부 식별자

external_id
= Wikidata에서 사용하는 외부 Q-ID

Entity Linking
= 내부 개체와 외부 KB의 같은 대상을 연결

Candidate Search
= 가능한 Q-ID 후보를 모으는 단계

LLM Decision
= 후보 중 같은 대상을 고르는 단계

Candidate Validation
= LLM이 후보 밖 ID를 만들지 않았는지 검사

linked
= 연결 근거가 충분한 상태

review
= 하나로 확정하기 어려워 보류한 상태

Enrichment
= 연결한 Q-ID로 외부 정보를 추가

SPARQL
= Wikidata의 RDF 관계를 조회하는 언어
```
