# Neo4j 그래프 모델 설계 핵심 정리

## 1. 그래프 모델 설계 기준

그래프 모델은 **자주 조회할 질문에서 필요한 연결 경로가 만들어지는지**를 기준으로 설계한다.

온라인 서점에서 필요한 주요 개체와 관계는 다음과 같다.

| 구분 | 설계 | 핵심 의미 |
|---|---|---|
| 노드 | `Reader`, `Book`, `Author`, `Publisher`, `Category` | 독립적으로 구분·연결할 대상 |
| 관계 | `PURCHASED`, `REVIEWED`, `WROTE`, `PUBLISHED`, `IN_CATEGORY` | 개체 사이의 행동·연결 |
| 노드 속성 | `Reader.name`, `Book.title`, `Book.isbn` | 해당 개체 자체에 속하는 값 |
| 관계 속성 | `REVIEWED.rating`, `REVIEWED.summary`, `PURCHASED.purchased_at`, `PURCHASED.amount` | 특정 관계·행동마다 달라지는 값 |

특히 **별점은 책 자체의 값이 아니라 `Reader`가 `Book`을 평가한 행위마다 달라지는 값**이므로 `REVIEWED` 관계의 속성으로 둔다.

### 모델 코드

```python
book_model = {
    'nodes': {'Reader', 'Book', 'Author', 'Publisher', 'Category'},

    # 관계이름: (시작노드, 끝노드)
    'relationships': {
        'PURCHASED': ('Reader', 'Book'),
        'WROTE': ('Author', 'Book'),
        'REVIEWED': ('Reader', 'Book'),
        'PUBLISHED': ('Publisher', 'Book'),
        'IN_CATEGORY': ('Book', 'Category'),
    },

    'node_properties': {
        'Reader': {'name'},
        'Book': {'title', 'isbn'},
    },

    # 관계에 붙는 속성
    'rel_properties': {
        'REVIEWED': {'rating', 'summary'},
        'PURCHASED': {'purchased_at', 'amount'},
    }
}

assert validate_model(book_model) is True
print('✅ 형식 검사 통과! 이 설계로 실제 질문에 답할 수 있는지는 2번에서 확인합니다.')
```

**결과**

```text
✅ 형식 검사 통과! 이 설계로 실제 질문에 답할 수 있는지는 2번에서 확인합니다.
```

`validate_model()`의 핵심 점검 내용은 다음과 같다.

- 필요한 노드·관계가 충분히 존재하는가
- 관계의 시작·끝 노드가 실제 `nodes`에 존재하는가
- 어떤 관계에도 연결되지 않은 노드가 있는가
- `rating`이 노드가 아닌 **관계 속성**에 있는가

## 2. 설계한 모델이 실제 질문에 답할 수 있는지 확인

그래프 설계는 단순히 노드와 관계가 존재하는 것보다 **원하는 질문까지 실제 경로를 따라갈 수 있는지**가 중요하다.

| 질문 | 이동 경로 | 의미 |
|---|---|---|
| 같은 카테고리의 책 | `Book → Category → Book` | 같은 카테고리를 공유하는 다른 책 탐색 |
| 이 저자의 다른 책 | `Book ← Author → Book` | 같은 저자가 쓴 다른 책 탐색 |
| 이 독자가 산 책 | `Reader → Book` | 구매 관계를 바로 조회 |
| 이 책 평균 별점 | `Reader → Book`의 `REVIEWED.rating` | 리뷰 관계의 별점을 집계 |

### 관계 경로 정의

```python
answers = {
    '같은 카테고리 책': ['IN_CATEGORY', 'IN_CATEGORY'],
    '이 저자의 다른 책': ['WROTE', 'WROTE'],
    '이 독자가 산 책': ['PURCHASED'],
    '이 책 평균 별점': ['REVIEWED'],
}
```

### 실제 경로 예시

```cypher
// 같은 카테고리 책
// (Book)-[:IN_CATEGORY]->(Category)<-[:IN_CATEGORY]-(Book)
MATCH (b:Book {title: '데미안'})-[:IN_CATEGORY]->(c:Category)<-[:IN_CATEGORY]-(other:Book)
WHERE b <> other
RETURN other.title

// 이 저자의 다른 책
// (Book)<-[:WROTE]-(Author)-[:WROTE]->(Book)

// 이 독자가 산 책
// (Reader)-[:PURCHASED]->(Book)

// 이 책 평균 별점
// (Reader)-[r:REVIEWED]->(Book)
// RETURN avg(r.rating)
```

### 도달성 검사

```python
assert check_reachable(book_model, answers) is True
print('✅ 통과!')
```

**결과**

```text
✅ 통과!
```

### 핵심

`Category`와 `Author`를 별도 노드로 두는 이유는 단순 정보 저장뿐 아니라, **공통 값을 거쳐 다른 `Book`으로 이동하는 경로를 만들기 위해서**다.

```text
Book → Category → Book
Book ← Author → Book
```

즉, 그래프 모델에서는 **어떤 질문에 답해야 하는지가 노드와 관계를 정하는 기준**이 된다.

## 3. 후보 모델 점검

후보 모델에서는 형식뿐 아니라 다음 세 가지를 확인한다.

1. 값이 올바른 위치에 있는가
2. 모든 노드가 관계로 연결되어 있는가
3. 관계 방향이 실제 의미와 맞는가

### 점검 코드

```python
for key, model in candidates.items():
    result = model_error(model)
    if result:
        print(f"{key}", result)
```

**결과**

```text
B 별점(rating)은 '누가 무엇을 평가했나'마다 달라지는 값입니다 - 관계 속성으로 두세요 (별점 자체를 기준으로 다른 개체와 연결할 일이 없다면 노드로 올리지 않습니다)
D 어떤 관계에도 연결되지 않은 레이블이 있습니다: ['Publisher']
```

### 후보별 핵심 판단

| 후보 | 판단 | 이유 |
|---|---|---|
| A | 정상 | 별점이 `REVIEWED` 관계 속성에 있고 전체 구조가 연결됨 |
| B | 오류 | `rating`을 `Book`의 노드 속성으로 둠 |
| C | 의미상 오류 | `WROTE: ('Book', 'Author')`로 방향이 반대임 |
| D | 오류 | `Publisher` 노드는 있지만 연결 관계가 없음 |
| E | 정상 | 이름은 다르지만 구조와 속성 위치가 설계 원칙에 맞음 |

후보 C는 검증기를 통과할 수 있지만 관계를 읽으면 다음과 같은 의미가 된다.

```text
Book -[:WROTE]-> Author
책이 저자를 집필했다
```

실제 의미는 다음 방향이어야 한다.

```text
Author -[:WROTE]-> Book
저자가 책을 집필했다
```

즉, **자동 검증기는 자료형·연결 여부·속성 위치 같은 구조적 규칙은 검사할 수 있지만, 관계 이름의 의미까지 해석해 방향이 자연스러운지는 판단하지 못할 수 있다.**

## 4. 그래프 모델 설계 핵심 원칙

```text
개체 자체로 구분·연결할 대상      → Node
개체 사이의 행동·연결            → Relationship
개체 자체에 고정적으로 붙는 값   → Node Property
특정 행동·관계마다 달라지는 값   → Relationship Property
```

예를 들어 별점은 다음처럼 생각한다.

```text
철수 -[:REVIEWED {rating: 5}]-> 데미안
영희 -[:REVIEWED {rating: 3}]-> 데미안
```

같은 책이라도 사람마다 별점이 다르므로 `Book.rating`이 아니라 **`REVIEWED.rating`**이 적절하다.

그래프 설계에서 가장 중요한 판단은 결국 다음 두 가지다.

> **이 값은 무엇마다 달라지는가?**  
> **내가 자주 묻는 질문에 필요한 이동 경로가 만들어지는가?**
