# 표준 ID 연결과 새 관계 증분 적재

## 핵심 개념

교안 01에서 새 관계를 **추출·검사해 JSON으로 저장**했다면, 교안 02에서는 이를 실제 Neo4j 그래프에 연결한다.

```text
교안 01
기존 그래프 준비
→ 새 관계 추출
→ 스키마·근거 검사
→ JSON 저장

교안 02
JSON 불러오기
→ 표준 ID 연결
→ 문서·청크 재사용
→ 새 개체·관계 증분 적재
→ 출처 연결
→ 재실행 검사
→ 계층 연결
→ 처리 이력·롤백
```

핵심은 **기존 노드와 관계를 유지하면서 새 관계만 중복 없이 추가하는 것**이다.

---

## 1. 새 관계에 표준 ID 연결

빌더의 임시 `id`와 DB의 `standard_id`는 역할이 다르다.

| ID | 역할 |
|---|---|
| 빌더 `id` | 한 번의 추출 결과 내부에서 노드 연결 |
| `standard_id` | DB에서 같은 실제 개체를 식별 |

처리는 다음 기준으로 나눈다.

```text
validated
│  교안 01 검사 통과
│
├─ 양 끝 ID 확정 → ready
└─ ID 미확정    → pending

rejected
└─ 교안 01 검사 실패 결과 그대로 유지
```

### ID 조회용 딕셔너리

타입과 별칭을 함께 키로 사용한다.

```python
ids_by_name = {}

for entity in expanded_catalog:
    for alias in entity["aliases"]:
        key = (entity["entity_type"], alias)
        ids_by_name.setdefault(key, set()).add(
            entity["standard_id"]
        )
```

예:

```text
('Compound', 'gabapentin')
→ {'Compound::DB00996'}
```

같은 이름이라도 타입이 다르면 다른 개체로 처리한다.

### 관계 양 끝에 ID 붙이기

```python
ready, pending = [], []

for original in validated:
    row = dict(original)
    unresolved = []

    for role in ("subject", "object"):
        key = (
            row[role + "_type"],
            row[role],
        )
        candidates = ids_by_name.get(key, set())

        if len(candidates) == 1:
            row[role + "_id"] = next(iter(candidates))
        else:
            unresolved.append(row[role])

    if unresolved:
        pending.append(
            dict(row, unresolved_names=unresolved)
        )
    else:
        ready.append(row)
```

후보가 **정확히 하나일 때만** ID를 확정한다.  
후보가 없거나 여러 개면 자동 결정하지 않고 `pending`으로 보낸다.

### 의료 결과

```text
적재 가능: 6
ID 보류: 0
검사 기각: 0
```

예:

```text
Compound::DB00996
→ PALLIATES_CS
→ local:symptom:perioperative-pain
```

## 2. 문서와 청크를 재사용

증분 적재에서는 개체와 관계뿐 아니라 **Document와 Chunk도 다시 만들지 않아야 한다.**

### 주요 식별자

| 식별자 | 구분 대상 |
|---|---|
| `standard_id` | 개체 |
| `doc_id` | 출처 문서 |
| `chunk_id` | 특정 문서의 특정 청크 |
| `claim_id` | 특정 문서에서 추출한 특정 관계 |
| `batch_id` | 한 번의 증분 적재 묶음 |

---

## 3. 고정 `chunk_id` 만들기

SimpleKGPipeline의 임시 청크 ID 대신 재실행해도 같은 ID를 만들어 사용한다.

기준:

```text
문서 ID
+ 청크 순번
+ 청크 원문 해시
```

```python
text_hash = hashlib.sha256(
    chunk["text"].encode("utf-8")
).hexdigest()

chunk_id = (
    f"{doc_id}:chunk:"
    f"{chunk['index']}:{text_hash}"
)
```

따라서

```text
같은 문서
+ 같은 순번
+ 같은 원문
→ 같은 chunk_id
```

원문이 바뀌면 해시도 달라져 다른 청크로 처리된다.

## 4. Document · Chunk 중복 없이 저장

### Document

`doc_id`를 고유 키로 사용한다.

```cypher
CREATE CONSTRAINT IF NOT EXISTS
FOR (d:Document)
REQUIRE d.doc_id IS UNIQUE
```

```cypher
UNWIND $rows AS item

MERGE (d:Document {doc_id: item.doc_id})
ON CREATE SET
    d.title = item.title,
    d.url = item.url
```

제목이 비슷한지가 아니라 **`doc_id`가 같은지**로 판단한다.

### Chunk

```cypher
CREATE CONSTRAINT IF NOT EXISTS
FOR (c:Chunk)
REQUIRE c.chunk_id IS UNIQUE
```

```cypher
UNWIND $rows AS item

MATCH (d:Document {doc_id: item.doc_id})

MERGE (c:Chunk {chunk_id: item.chunk_id})

ON CREATE SET
    c.text = item.text,
    c.index = item.index,
    c.embedding = item.embedding,
    c.embedding_model = item.embedding_model

MERGE (c)-[:FROM_DOCUMENT]->(d)
```

교안 01에서 만든 **기존 임베딩을 그대로 재사용**한다.

### 의료 결과

```text
Document: 1개
Chunk: 1개
Embedding: 768차원
```

재실행 후에도:

```text
Document: 1
Chunk: 1
```

즉 같은 입력으로 노드가 증가하지 않는다.

## 5. 표준 개체 노드 준비

새로 승인한 개체는 `entity_type`과 `standard_id`로 저장한다.

```python
def put_nodes(catalog):
    rows = run_cypher(
        """
        UNWIND $catalog AS item

        MERGE (
            n:$(item.entity_type)
            {standard_id: item.standard_id}
        )

        ON CREATE SET
            n.name = item.name,
            n.aliases = item.aliases

        RETURN count(n) AS processed
        """,
        catalog=catalog,
    )

    return rows[0]["processed"]
```

핵심:

```text
같은 standard_id 존재
→ 기존 노드 사용

없음
→ 새 노드 생성
```

## 6. 관계의 고정 키 `claim_id`

같은 관계를 다시 실행해도 중복 생성되지 않도록 관계에도 고정 ID를 만든다.

구성 요소:

```text
source_doc_id
+ subject_id
+ relation
+ object_id
```

```python
def claim_key(row):
    values = [
        row["source_doc_id"],
        row["subject_id"],
        row["relation"],
        row["object_id"],
    ]

    text = json.dumps(
        values,
        ensure_ascii=False,
    )

    return (
        "claim:"
        + hashlib.sha256(
            text.encode("utf-8")
        ).hexdigest()
    )
```

### 의미

```text
같은 문서 + 같은 관계
→ 같은 claim_id

다른 문서 + 같은 관계
→ 다른 claim_id
```

즉 같은 사실이라도 **출처 문서가 다르면 별도의 추출 기록**으로 남긴다.

## 7. 새 관계 증분 적재

`ready`만 Neo4j에 저장한다.

```python
def put_claims(rows, batch_id, schema_version):
    records = [
        dict(row, claim_id=claim_key(row))
        for row in rows
    ]

    result = run_cypher(
        """
        UNWIND $rows AS item

        MATCH (
            s:$(item.subject_type)
            {standard_id: item.subject_id}
        )

        MATCH (
            o:$(item.object_type)
            {standard_id: item.object_id}
        )

        MERGE (
            s
        )-[r:$(item.relation)
            {claim_id: item.claim_id}
        ]->(
            o
        )

        ON CREATE SET
            r.source_doc_id = item.source_doc_id,
            r.evidence = item.evidence,
            r.batch_id = $batch_id,
            r.schema_version = $schema_version

        RETURN count(r) AS processed
        """,
        rows=records,
        batch_id=batch_id,
        schema_version=schema_version,
    )

    return result[0]["processed"]
```

### `MERGE` + `ON CREATE SET`

```text
기존 claim_id 있음
→ 기존 관계 재사용

없음
→ 새 관계 생성
  + evidence
  + source_doc_id
  + batch_id
  + schema_version 저장
```

기존 관계의 근거와 속성은 덮어쓰지 않는다.

## 8. `batch_id`와 멱등성

새 적재를 시작할 때 별도의 ID를 만든다.

```python
batch_id = "paper:delta:" + str(uuid4())
```

### ID 역할 차이

```text
claim_id
→ 어떤 문서의 어떤 관계인가?

batch_id
→ 어느 적재 작업에서 처음 생성됐는가?
```

같은 데이터를 다시 실행해도 `claim_id`가 같기 때문에 관계가 늘어나지 않는다.

이를 **멱등성(idempotency)** 이라고 한다.

### 영화 예시

```text
적재 전 관계: 8
새 관계 처리: 1
적재 후 관계: 9
```

같은 관계 재실행:

```text
재실행 전: 9
재실행 후: 9
ID와 근거까지 동일: True
```

### 의료 예시

```text
기존 관계: 4
새 증상 관계: 6

4 → 10
```

기존 관계는 그대로 유지된다.

## 9. 개체에서 원문으로 출처 연결

관계뿐 아니라 개체가 어느 청크에서 나온 것인지도 연결한다.

```text
Entity
  │
  └─ FROM_CHUNK
       ↓
     Chunk
       │
       └─ FROM_DOCUMENT
            ↓
          Document
```

빌더의 임시 ID를 저장용 ID로 변환한다.

```text
Entity 임시 ID
→ standard_id

Chunk 임시 ID
→ 고정 chunk_id
```

저장은 다음처럼 한다.

```cypher
UNWIND $rows AS item

MATCH (
    e:$(item.entity_type)
    {standard_id: item.standard_id}
)

MATCH (
    c:Chunk
    {chunk_id: item.chunk_id}
)

MERGE (e)-[:FROM_CHUNK]->(c)
```

> 원본 답안의 `->(C)`는 앞에서 조회한 `c`와 다른 변수이므로 `->(c)`로 교정.

이 연결을 통해:

```text
개체
→ 출처 청크
→ 원문
→ 출처 문서
```

순서로 다시 추적할 수 있다.

## 10. 서로 다른 개념은 합치지 않고 계층 연결

좁은 개념과 넓은 개념을 같은 노드로 합치지 않는다.

예:

```text
supernatural horror
→ BROADER
→ horror
```

또는:

```text
plaque psoriasis
→ BROADER
→ psoriasis
```

### 계층 구조

```text
하위 개념
   │
   └─ BROADER
        ↓
     상위 개념
```

조회에서는 가변 길이 경로를 사용한다.

```cypher
MATCH
    (d:Disease)
    -[:BROADER*0..]->
    (:Disease {standard_id: $top_id})
```

`*0..`는

```text
현재 개념 자체
또는
BROADER를 따라 올라간 상위 개념
```

을 모두 포함한다.

따라서 세부 개념을 없애지 않고도 상위 개념으로 검색할 수 있다.

### 의료 결과

`plaque psoriasis`를 그대로 유지하면서:

```text
psoriasis
→ 검색
→ Tapinarof / plaque psoriasis 조회 가능
```

## 11. 처리 상태 기록

`ProcessingState`는 원문 저장 노드가 아니라 **최근 적재 처리 상태**를 기록한다.

주요 속성:

| 속성 | 의미 |
|---|---|
| `doc_id` | 처리한 문서 |
| `schema_version` | 사용한 검사 규칙 |
| `accepted` | ID 연결까지 완료한 행 |
| `pending` | ID 미확정 행 |
| `rejected` | 검사 기각 행 |
| `batch_id` | 이번 적재 묶음 |
| `status` | `stored` / `reverted` |

의료 결과:

```text
accepted: 6
pending: 0
rejected: 0
schema_version: 2
status: stored
```

`accepted`는 **새로 생성된 관계 수**가 아니라 적재 가능한 입력 행 수다.

## 12. 이번 증분 적재만 롤백

`batch_id`를 이용해 이번 작업에서 생성한 관계만 제거한다.

```cypher
MATCH ()-[r]->()
WHERE r.batch_id = $batch_id

DELETE r

RETURN count(*) AS removed
```

이때 유지되는 것:

```text
기존 관계
Document
Chunk
Entity
FROM_CHUNK
FROM_DOCUMENT
BROADER
```

삭제되는 것:

```text
이번 batch_id로 생성된 새 추출 관계
```

처리 상태는:

```cypher
MATCH (
    d:ProcessingState
    {batch_id: $batch_id}
)

SET d.status = 'reverted'
```

로 변경한다.

### 의료 결과

```text
새 관계 제거: 6
남은 기존 관계: 4
기존 관계와 근거 유지: True
출처 연결 유지: True
```

# 전체 흐름

```text
1. 교안 01의 validated 관계 읽기
   ↓
2. 기존 catalog + 검토한 새 개체 목록 결합
   ↓
3. 타입 + 별칭으로 standard_id 조회
   ↓
4. ready / pending 분리
   ↓
5. doc_id로 Document 재사용
   ↓
6. doc_id + index + text hash로 Chunk 재사용
   ↓
7. 새 표준 개체 MERGE
   ↓
8. source_doc_id + subject_id
   + relation + object_id
   → claim_id 생성
   ↓
9. ready 관계만 MERGE
   ↓
10. Entity → Chunk → Document 출처 연결
   ↓
11. 같은 입력 재실행
   → 노드·관계가 늘지 않는지 확인
   ↓
12. 필요하면 BROADER 계층 연결
   ↓
13. ProcessingState 기록
   ↓
14. batch_id로 이번 추가 관계만 롤백
```

---

## 기억할 핵심

- 빌더 임시 ID와 DB의 `standard_id`를 구분
- 검증 통과 관계라도 ID가 확정되지 않으면 `pending`
- `doc_id`로 문서를 재사용
- `chunk_id`는 **문서 + 순번 + 원문 해시**로 고정
- `claim_id`는 **문서 + 주어 ID + 관계 + 목적어 ID**로 고정
- `MERGE`로 재실행 중복 방지
- `batch_id`는 증분 적재 묶음과 롤백 범위를 구분
- 다른 문서에서 나온 같은 관계는 별도 `claim_id`로 출처 보존
- 세부 개념과 상위 개념은 합치지 않고 `BROADER`로 연결
- 롤백은 전체 그래프가 아니라 **이번 batch에서 생성한 관계만 삭제**
