# 기초 코드 정리 — 트리플 검증과 그래프 적재 준비

## 전체 흐름

```text
LLM/API로 트리플 추출
→ 온톨로지 규칙으로 진단·필터링
→ 중복 제거
→ 개체 이름을 ID로 정규화
→ Cypher로 변환해 그래프 적재 준비
```

> 이 문서에서는 `RELATION_SIGNATURES`, `NODE_TYPES`, `lookup_id()`가 앞 단계에서 이미 준비되어 있다고 가정함.

### 1-2. 트리플에서 세 칸 꺼내기

트리플의 기본 구조는 `(주어, 관계, 목적어)`임. 튜플 인덱스로 각 값을 꺼낼 수 있음.

```python
# 기본 트리플
fact = ("AML", "BINDS", "CACNA1C")

# 튜플에서 값 꺼내기
subj = fact[0]  # 주어
rel = fact[1]   # 관계
obj = fact[2]   # 목적어

print("주어 :", subj)
print("관계 :", rel)
print("목적어 :", obj)
```

**결과**

```text
주어 : AML
관계 : BINDS
목적어 : CACNA1C
```

### 1-3. 트리플 문자열 파싱하기

정해진 문자열 형식 `(주어, 관계, 목적어)`를 받아 튜플로 변환함.

```python
def parse_triple(text):
    # 바깥 괄호 제거
    text = text.strip("()")

    # 쉼표를 기준으로 세 부분으로 나누기
    parts = text.split(",")

    # 주어, 관계, 목적어 배정
    subj = parts[0].strip()
    rel = parts[1].strip()
    obj = parts[2].strip()

    return (subj, rel, obj)


result = parse_triple("(ADHD, ASSOCIATES, CACNA1D)")
print(result)
```

**결과**

```text
('ADHD', 'ASSOCIATES', 'CACNA1D')
```

> 이 방식은 **쉼표가 필드 내부에 들어오지 않는 단순한 연습용 형식**을 전제로 함. 실제 구조화 데이터라면 JSON처럼 필드 구조가 명확한 형식을 사용하는 편이 안전함.

### 1-4. JSONL 전체를 트리플 목록으로 읽기

각 줄의 JSON 문자열을 `dict`로 변환해 `triples` 리스트에 저장함.

```python
# 추출된 트리플 데이터 경로
path = "data/pgx_lv1_triples.jsonl"

# JSONL 파일을 줄 단위로 읽기
lines = Path(path).read_text(encoding="utf-8").splitlines()

# 각 줄을 dict로 변환
triples = []

for line in lines:
    triple = json.loads(line)
    triples.append(triple)

# 전체 트리플 개수
n_total = len(triples)

print(n_total)
display(triples)
```

**결과**

```text
12
```

```text
[{'subject': 'AML',
  'subject_type': 'Compound',
  'relation': 'BINDS',
  'object': 'CACNA1C',
  'object_type': 'Gene',
  'evidence': 'Interestingly, CACNA1C, CACNA1D, CACNB1, and CACNA2D3 are direct targets of AML.'},
 ...]
```

> 원본 노트북에서는 전체 출력이 길어 중간 부분이 생략되어 표시됨.

## 2. 트리플 진단과 필터링

```python
# BINDS 트리플을 담을 리스트
binds = []

for t in triples:
    if t["relation"] == "BINDS":
        binds.append(t)

n_binds = len(binds)

print(n_binds)
display(binds)
```

 {'subject': 'AML', 'relation': 'BINDS', 'object': 'CACNA1D', ...},
 {'subject': 'AML', 'relation': 'BINDS', 'object': 'CACNB1', ...},
 {'subject': 'AML', 'relation': 'BINDS', 'object': 'CACNA2D3', ...},

### 2-2. 관계별 개수 집계하기

관계 이름을 딕셔너리의 키로 사용해 출현 횟수를 누적함.

```python
# 관계별 개수를 담을 사전
by_rel = {}

for t in triples:
    # 현재 트리플의 관계 이름
    rel = t["relation"]

    # 이미 등장한 관계라면 1 증가
    if rel in by_rel:
        by_rel[rel] = by_rel[rel] + 1

    # 처음 등장한 관계라면 1로 시작
    else:
        by_rel[rel] = 1

# 확인
display(by_rel)
```

**결과**

```python
{
    'BINDS': 5,
    'ASSOCIATES': 4,
    'TREATS': 1,
    'MODULATES': 1,
    'CAUSES': 1
}
```

### 2-3. 근거가 부족한 트리플 골라내기

간단한 규칙으로 `subject`와 `object` 문자열이 모두 `evidence` 안에 직접 등장하는지 확인함.

```python
def is_grounded(t):
    # 주어와 목적어가 모두 evidence 안에 직접 등장하는지 확인
    if t["subject"] in t["evidence"] and t["object"] in t["evidence"]:
        return True

    return False


# 근거가 부족한 트리플
ungrounded = []

for t in triples:
    if is_grounded(t) == False:
        ungrounded.append(t)

print(len(ungrounded))
display(ungrounded)
```

**결과**

```text
1
```

```python
[{
    'subject': 'AML',
    'subject_type': 'Compound',
    'relation': 'MODULATES',
    'object': 'LTCC',
    'object_type': 'Gene',
    'evidence': 'the broader implications for LTCC modulation in neuropsychiatric therapeutics'
}]
```

> **주의:** 이 코드는 실제 의미적 근거성을 판정하는 것이 아니라 **문자열 존재 여부만 검사하는 단순 휴리스틱**임. 주어·목적어가 문장에 모두 있어도 그 관계 자체가 근거로 뒷받침된다고 단정할 수는 없음.

### 2-4. 온톨로지에 허용된 관계만 남기기

현재 코드는 `RELATION_SIGNATURES`에 **관계 이름이 등록되어 있는지**만 확인함.

```python

allowed = []

for t in triples:
    # relation이 온톨로지의 허용 관계 이름에 있으면 추가
    if t["relation"] in RELATION_SIGNATURES:
        allowed.append(t)

n_allowed = len(allowed)

print(n_allowed)
display(allowed)
```

**결과**

```text

```

```text

### 2-5. 중복 트리플 제거하기

`(주어, 관계, 목적어)`를 튜플로 만들고 `set`에 넣으면 같은 사실은 하나만 남음.

unique = set()

for t in triples:

```

## 3. 그래프로 옮길 준비

### 3-1. 개체 이름을 ID로 바꾸기

그래프에 문자열 이름만 적재하기보다, 표준 ID 사전에서 개체를 찾아 고유 ID로 정규화함.

```python
# 서로 다른 (이름, 타입) 쌍을 담을 집합
entities = set()

# allowed의 주어와 목적어 수집
for t in allowed:
    entities.add(
        (t["subject"], t["subject_type"])
    )

    entities.add(
        (t["object"], t["object_type"])
    )


# ID를 찾은 개체
resolved = {}

# ID를 못 찾은 개체 이름
unresolved = []

for name, entity_type in entities:
    # lookup_id()는 (id, 사유)를 반환한다고 가정
    entity_id, reason = lookup_id(name, entity_type)

    if entity_id is not None:
        resolved[name] = entity_id
    else:
        unresolved.append(name)

# 못 찾은 이름 정렬
candidates = sorted(unresolved)

print(resolved)
print(candidates)
```

**결과**

```python
{
    'CACNA1D': 'Gene::776',
    'CACNA2D3': 'Gene::55799',
    'CACNB1': 'Gene::782',
    'CACNA1C': 'Gene::775'
}

['ADHD', 'AML']
```

> `entities`는 `(이름, 타입)`으로 구분하지만 `resolved`의 키는 현재 **이름만 사용**함. 동일한 이름이 여러 노드 타입에 걸쳐 등장할 수 있는 데이터라면 `(name, entity_type)`을 키로 쓰는 편이 안전함.

### 3-2. 트리플을 Cypher `MERGE`문으로 바꾸기

주어·목적어 노드를 `MERGE`하고 두 노드 사이의 관계도 `MERGE`하는 문자열을 생성함.

```python
def to_merge(subj_id, subj_type, rel, obj_id, obj_type):
    """
    다음 형태의 Cypher를 생성함.

    MERGE (a:주어타입 {id: '주어id'})
    MERGE (b:목적어타입 {id: '목적어id'})
    MERGE (a)-[:관계]->(b)
    """

    query = (
        f"MERGE (a:{subj_type} {{id: '{subj_id}'}})\n"
        f"MERGE (b:{obj_type} {{id: '{obj_id}'}})\n"
        f"MERGE (a)-[:{rel}]->(b)"
    )

    return query


result = to_merge(
    "Compound::DB00381",
    "Compound",
    "BINDS",
    "Gene::775",
    "Gene"
)

print(result)
```

**결과**

```cypher
MERGE (a:Compound {id: 'Compound::DB00381'})
MERGE (b:Gene {id: 'Gene::775'})
MERGE (a)-[:BINDS]->(b)
```

> f-string 안에서 Cypher의 `{}`를 그대로 출력하려면 `{{`와 `}}`처럼 중괄호를 두 번 작성해야 함.
>
> 이 예시는 구조 이해용 문자열 생성 방식임. 실제 실행 코드에서는 `id` 같은 값은 Cypher 파라미터로 넘기는 방식이 더 안전함. 레이블과 관계 타입은 파라미터화할 수 없으므로 온톨로지에서 허용된 값만 사용하는 방식이 적절함.

## 4. 온톨로지와 구조화 출력 스키마

> **실행 순서:** 관계 시그니처를 먼저 확정한 뒤 Pydantic의 `Literal` 타입을 만드는 편이 안전함. `Literal`은 생성된 뒤 `RELATION_SIGNATURES`가 바뀌어도 자동으로 갱신되지 않음.

### 4-1. 관계 시그니처 확장하기

`RESEMBLES_DD`는 `Disease → Disease` 관계로 정의함.

```python
# Disease끼리의 유사 관계 추가
RELATION_SIGNATURES["RESEMBLES_DD"] = (
    "Disease",
    "Disease",
    "두 질병이 공통 증상이나 관련 유전자를 공유하는 경우"
)

# 확인
display(RELATION_SIGNATURES["RESEMBLES_DD"])
```

**결과**

```python
('Disease', 'Disease', '두 질병이 공통 증상이나 관련 유전자를 공유하는 경우')
```

### 4-2. 트리플 구조화 출력 스키마 만들기

Pydantic 모델을 사용해 LLM이 자유 텍스트가 아니라 **정해진 필드와 허용 값**으로 트리플을 반환하도록 제한함.

```python
from typing import Literal
from pydantic import BaseModel, Field


# 온톨로지에 정의된 관계 이름만 허용
RelationName = Literal[*tuple(RELATION_SIGNATURES.keys())]

# 온톨로지에 정의된 노드 타입만 허용
# 집합은 순서가 없으므로 정렬한 뒤 사용
NodeType = Literal[*tuple(sorted(NODE_TYPES))]


class Triple(BaseModel):
    subject: str = Field(
        description="트리플의 주어가 되는 개체 이름"
    )

    subject_type: NodeType = Field(
        description="주어 개체의 노드 타입"
    )

    relation: RelationName = Field(
        description="주어와 목적어 사이의 관계 이름"
    )

    object: str = Field(
        description="트리플의 목적어가 되는 개체 이름"
    )

    object_type: NodeType = Field(
        description="목적어 개체의 노드 타입"
    )

    evidence: str = Field(
        description="이 트리플을 뒷받침하는 원문 근거"
    )
```

#### 테스트

```python
triple = Triple(
    subject="AML",
    subject_type="Compound",
    relation="BINDS",
    object="CACNA1C",
    object_type="Gene",
    evidence="direct targets of AML"
)

print(triple)
print(triple.subject)
```

**결과**

```text
subject='AML' subject_type='Compound' relation='BINDS' object='CACNA1C' object_type='Gene' evidence='direct targets of AML'
AML
```

## 핵심 정리

| 단계 | 핵심 작업 |
|---|---|
| 트리플 읽기 | JSONL을 `dict` 목록으로 변환 |
| 관계 진단 | 특정 관계 개수, 관계별 통계 확인 |
| 근거 확인 | `evidence`와 트리플의 연결 여부 점검 |
| 온톨로지 필터 | 허용된 관계인지 확인 |
| 중복 제거 | `(주어, 관계, 목적어)` 기준으로 동일 사실 제거 |
| ID 정규화 | 개체 이름을 표준 ID로 변환 |
| 그래프 준비 | 트리플을 Cypher `MERGE` 구조로 변환 |
| 구조화 출력 | `Literal` + Pydantic으로 허용 타입과 관계 제한 |

### 기억할 점

- 트리플 기본 구조: `(주어, 관계, 목적어)`
- `set` 중복 제거는 간단하지만 부가 필드는 사라짐.
- 문자열 존재 여부만으로는 의미적 근거성을 완전히 판정할 수 없음.
- 관계 이름만 확인하는 것과 **관계 시그니처 전체를 검증하는 것**은 다름.
- 온톨로지 변경 후에는 이를 참조해 만든 `Literal`/Pydantic 스키마도 다시 생성해야 함.
