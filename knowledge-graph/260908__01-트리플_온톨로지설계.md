# 트리플과 온톨로지 설계 — 압축 정리

> 핵심 흐름  
> **문장 → 트리플 → 타입 부여 → ID 정규화 → 관계 시그니처 검증 → 그래프 적재**

---

# 1. 핵심 개념

## 1-1. 트리플: 사실을 그래프로 바꾸는 최소 단위

**트리플(Triple)** = `(주어, 관계, 목적어)`

```text
Tapinarof ──치료한다──> plaque psoriasis
```

논문 한 문장에는 사실이 여러 개 들어갈 수 있으므로 **한 문장 → 여러 트리플**이 될 수 있다.

```python
triples = [
    ("Tapinarof", "결합한다", "AHR"),
    ("Tapinarof", "치료한다", "plaque psoriasis"),
    ("Tapinarof", "치료한다", "atopic dermatitis"),
]
```

중요한 기준:

- 개체 사이의 **사실 하나당 트리플 하나**
- 숫자·통계값 자체를 무조건 노드로 만들지 않음
- 문단의 중심 개체를 주어로 통일하면 관련 사실이 한곳에 모임

### 그래프로 옮길 때는 타입 2칸이 추가됨

사실 자체는 3칸이지만, LPG에 적재하려면 노드 레이블을 알아야 한다.

```text
(주어, 주어 타입, 관계, 목적어, 목적어 타입)
```

예:

```text
(Tapinarof, Compound, TREATS, plaque psoriasis, Disease)
```

그래프에서는 다음 구조가 된다.

```text
(:Compound) ──[:TREATS]──> (:Disease)
```

즉 이미지의 핵심 구조를 텍스트로 바꾸면 다음과 같다.

```text
5칸 트리플
(subject, subject_type, relation, object, object_type)
                      │
                      ▼
LPG
(:subject_type {id}) -[:relation]-> (:object_type {id})
```

---

## 1-2. 온톨로지: 그래프에 허용할 의미를 미리 정하는 설계도

트리플이 **사실을 적는 형식**이라면, 온톨로지는 **어떤 종류의 사실을 허용할지 정하는 규칙**이다.

이 교안에서는 크게 두 가지를 정한다.

1. **노드를 무엇으로 식별할 것인가**
2. **어떤 관계를 어떤 타입 사이에 허용할 것인가**

```text
트리플 추출
    ↓
온톨로지 규칙 적용
    ├─ 노드 식별 규칙: name이 아니라 id
    └─ 관계 규칙: (주어 타입, 목적어 타입, 판정 기준)
    ↓
지식 그래프
```

핵심 원칙:

> **관계를 추출하기 전에 온톨로지를 먼저 정함**

모델이 관계를 자유롭게 만들게 두면 같은 의미가 여러 관계명으로 갈리고, 타입상 말이 안 되는 연결도 생길 수 있다.

---

## 1-3. 노드의 키는 이름이 아니라 ID

이름은 개체를 안정적으로 식별하지 못한다.

```cypher
MERGE (n:Disease {name: 'obesity'})
MERGE (n:Symptom {name: 'obesity'})
```

같은 문자열이라도 서로 다른 타입의 개체일 수 있다.

반대로 같은 개체가 문서마다 다른 표기로 등장할 수도 있다.

따라서 실제 키는 이름보다 **정규화된 고유 ID**를 사용한다.

```cypher
MERGE (n:Compound {id: 'Compound::DB00758'})
```

이름은 식별자가 아니라 뒤에서 붙이는 속성으로 취급한다.

### 이름 조회 결과는 3가지로 구분

`lookup_id(name, node_type)`은 `(id, 사유)`를 반환한다.

| 결과 | 의미 | 처리 |
|---|---|---|
| `("Compound::DB00758", "hit")` | ID 확정 | 해당 ID로 적재 |
| `(None, "miss")` | 사전에 없음 또는 타입 불일치 | `:Candidate` |
| `(None, "ambiguous")` | 후보가 여러 개 | `:Candidate` |

`miss`와 `ambiguous`는 둘 다 ID가 없지만 의미가 다르다.

```text
miss
└─ 사전이 이름을 모름

ambiguous
└─ 사전은 알고 있지만 후보가 여러 개라 이름만으로 결정 불가
```

---

## 1-4. Candidate: 모르는 개체를 버리지 않고 격리

사전에 없다는 이유만으로 잘못된 개체라고 볼 수 없다.

예:

- 사전보다 뒤에 등장한 신약
- 논문마다 다른 표기
- 문맥 없이는 결정할 수 없는 동명이 개체

따라서 바로 기존 노드에 섞지도 않고 버리지도 않는다.

```text
ID 확정 ───────────────> 정상 노드
사전에 없음 ─┐
후보 여러 개 ─┴────────> :Candidate
```

후속 엔티티 정규화 단계에서 문맥을 이용해 후보를 확정하고 승격할 수 있다.

---

## 1-5. 관계 시그니처: 관계가 허용되는 형태를 고정

**관계 시그니처(Relation Signature)**

```text
관계 = (주어 타입, 목적어 타입, 판정 기준)
```

타입만 적는 것이 아니라 **언제 그 관계로 판정할지**까지 함께 정한다.

### 이 교안의 노드 타입

```python
NODE_TYPES = {
    "Compound",
    "Disease",
    "Gene",
    "Symptom",
    "PharmacologicClass",
}
```

### 관계 시그니처

| 관계 | 주어 → 목적어 | 판정 기준 |
|---|---|---|
| `TREATS` | Compound → Disease | 질병의 원인·진행 자체에 작용해 치료 |
| `PALLIATES` | Compound → Disease | 질병 자체가 아니라 증상을 완화 |
| `BINDS` | Compound → Gene | 단백질 결합. 이 교안에서는 대사·수송 관계도 포함 |
| `UPREGULATES_CG` | Compound → Gene | 유전자 발현 증가 |
| `DOWNREGULATES_CG` | Compound → Gene | 유전자 발현 감소 |
| `ASSOCIATES` | Disease → Gene | 질병과 유전자 연관 |
| `PRESENTS` | Disease → Symptom | 질병이 해당 증상으로 나타남 |
| `INCLUDES` | PharmacologicClass → Compound | 약효 분류가 약물을 포함 |

이미지의 온톨로지 구조를 텍스트로 바꾸면 다음과 같다.

```text
(:PharmacologicClass)
        │
    [:INCLUDES]
        ▼
   (:Compound)
     ├─[:TREATS]───────────────> (:Disease)
     ├─[:PALLIATES]────────────> (:Disease)
     ├─[:BINDS]────────────────> (:Gene)
     ├─[:UPREGULATES_CG]───────> (:Gene)
     └─[:DOWNREGULATES_CG]─────> (:Gene)

(:Disease) ──[:ASSOCIATES]──> (:Gene)
(:Disease) ──[:PRESENTS]────> (:Symptom)
```

---

## 1-6. 타입만으로 관계를 결정할 수 없는 경우

### `TREATS` vs `PALLIATES`

둘 다 타입은 같다.

```text
Compound → Disease
```

따라서 타입이 아니라 **판정 기준**으로 구분한다.

```text
TREATS
└─ 질병 자체의 치료

PALLIATES
└─ 질병은 그대로 두고 증상을 완화
```

예:

| 문장 의미 | 판정 |
|---|---|
| 질병 치료제로 승인됨 | `TREATS` |
| 신경병증성 통증을 관리함 | `PALLIATES` |
| 치료제로 연구되고 있음 | 판단 보류 |

`investigated as a treatment`처럼 **연구되었다는 사실**과 **치료 효과가 확정된 사실**은 같지 않다.

---

## 1-7. 온톨로지가 합친 차이는 나중에 복구하기 어려움

이 교안의 `BINDS`는 다음을 하나로 묶는다.

```text
약물 표적
약물 대사 효소
약물 수송체
        ↓
      BINDS
```

예:

```text
Clopidogrel ──BINDS──> CYP2C19
Simvastatin  ──BINDS──> SLCO1B1
Warfarin     ──BINDS──> VKORC1
```

장점:

- 기존 그래프의 관계 체계와 맞출 수 있음
- 같은 사실이 `BINDS`, `METABOLIZES` 등으로 갈라지는 것을 피함

대가:

- 실제 약물 **표적**인지
- 약물을 분해하는 **효소**인지
- 약물을 운반하는 **수송체**인지

그래프만 보고는 다시 구분하기 어려워진다.

> **온톨로지가 구분하지 않기로 한 정보는 데이터에 남지 않는다.**

따라서 관계 설계 시 **무엇을 표현할지뿐 아니라 무엇을 포기할지도 기록**해야 한다.

## 2-2. 이름을 키로 쓰는 초기 형태

```python
def merge_by_name(triple):
    subj, subj_type, rel, obj, obj_type = triple

    return (
        f"MERGE (a:{subj_type} {{name: '{subj}'}})\n"
        f"MERGE (b:{obj_type} {{name: '{obj}'}})\n"
        f"MERGE (a)-[:{rel}]->(b)"
    )
```

생성되는 형태:

```cypher
MERGE (a:Compound {name: 'Tapinarof'})
MERGE (b:Disease {name: 'plaque psoriasis'})
MERGE (a)-[:TREATS]->(b)
```

`MERGE`를 쓰므로 동일 패턴을 반복 실행해도 같은 노드·관계가 계속 새로 늘어나는 것을 막는다.

단, **이름을 키로 쓰는 방식 자체는 실제 지식 그래프의 안정적인 식별 방식으로 부적합**하다.

## 2-3. 이름 정규화

유전자 이외의 이름은 표기 차이를 줄인 뒤 사전을 조회한다.

```python
def normalize_name(name):
    s = re.sub(r"\s+", " ", name).strip().lower()
    return re.sub(r"\s*\([^)]*\)$", "", s).strip()
```

처리:

```text
소문자화
→ 앞뒤 공백 제거
→ 연속 공백을 1칸으로
→ 끝의 괄호 주석 제거
```

### Gene은 별도 처리

유전자 기호는 대소문자가 의미에 영향을 줄 수 있으므로 원형을 유지한다.

```python
if node_type == "Gene":
    found = NAME2ID["genes"].get(name.strip())
```

## 2-4. 이름 → ID 조회

핵심 형태만 압축하면 다음과 같다.

```python
def lookup_id(name, node_type):
    if node_type == "Gene":
        found = NAME2ID["genes"].get(name.strip())
        return (found, "hit") if found else (None, "miss")

    key = normalize_name(name)

    if key in NAME2ID["ambiguous"]:
        return None, "ambiguous"

    entry = NAME2ID["entries"].get(key)

    if entry and entry["label"] == node_type:
        return entry["id"], "hit"

    return None, "miss"
```

사용:

```python
found, why = lookup_id("Clopidogrel", "Compound")
```

결과 해석:

```text
found != None
└─ hit

found == None
├─ miss
└─ ambiguous
```

## 2-5. ID를 키로 Cypher 생성

이름 해소가 끝난 뒤에는 ID를 노드 키로 사용한다.

```python
def triple_to_cypher(triple):
    subj_id, subj_type, rel, obj_id, obj_type = triple

    return (
        f"MERGE (a:{subj_type} {{id: '{subj_id}'}})\n"
        f"MERGE (b:{obj_type} {{id: '{obj_id}'}})\n"
        f"MERGE (a)-[:{rel}]->(b)"
    )
```

사용:

```python
triple_to_cypher(
    (
        "Compound::DB00758",
        "Compound",
        "BINDS",
        "Gene::1557",
        "Gene",
    )
)
```

생성 구조:

```cypher
MERGE (a:Compound {id: 'Compound::DB00758'})
MERGE (b:Gene {id: 'Gene::1557'})
MERGE (a)-[:BINDS]->(b)
```

## 2-6. 관계 시그니처를 dict로 관리

관계 규칙은 코드 여러 곳에 흩어 놓지 않고 한 곳에 모은다.

```python
RELATION_SIGNATURES = {
    "TREATS": (
        "Compound",
        "Disease",
        "약이 질병을 치료한다. 질병의 원인이나 진행 자체에 작용한다",
    ),

    "PALLIATES": (
        "Compound",
        "Disease",
        "약이 질병의 증상을 완화한다",
    ),

    "BINDS": (
        "Compound",
        "Gene",
        "단백질 결합. 이 교안에서는 대사·수송 진술도 포함한다",
    ),

    "UPREGULATES_CG": (
        "Compound",
        "Gene",
        "유전자 발현 증가",
    ),

    "DOWNREGULATES_CG": (
        "Compound",
        "Gene",
        "유전자 발현 감소",
    ),

    "ASSOCIATES": (
        "Disease",
        "Gene",
        "질병과 유전자의 연관",
    ),

    "PRESENTS": (
        "Disease",
        "Symptom",
        "질병이 증상으로 나타남",
    ),

    "INCLUDES": (
        "PharmacologicClass",
        "Compound",
        "약효 분류가 약물을 포함",
    ),
}
```

조회:

```python
subj_type, obj_type, criterion = RELATION_SIGNATURES["PALLIATES"]
```

핵심:

```text
relation
    ↓
(subject_type, object_type, criterion)
```

이 구조가 이후 추출 결과를 검사하는 **단일 관계 규격**이 된다.

## 2-7. 여러 트리플을 하나의 Cypher 스크립트로

교안 실습의 요구 구조를 압축하면 다음과 같다.

```python
def triples_to_script(triples):
    return "\n\n".join(
        triple_to_cypher(triple)
        for triple in triples
    )
```

```text
트리플 1 → MERGE 3줄
빈 줄
트리플 2 → MERGE 3줄
빈 줄
트리플 3 → MERGE 3줄
```

# 3. 도메인이 바뀌면 온톨로지도 바뀜

트리플의 **형태**는 유지되지만 노드 타입과 관계의 의미는 도메인마다 달라진다.

의학 그래프:

```text
Compound ──TREATS────> Disease
Compound ──BINDS─────> Gene
Disease  ──PRESENTS──> Symptom
```

파이썬 라이브러리 문서 그래프:

| 관계 | 주어 → 목적어 | 의미 |
|---|---|---|
| `DEMONSTRATES` | Document → ApiElement | 문서가 API를 예제로 보여 줌 |
| `RAISES` | ApiElement → ApiElement | API가 예외를 냄 |
| `INCLUDES` | Document → Change | 릴리스 문서가 변경을 포함 |
| `AFFECTS` | Change → ApiElement | 변경이 API에 영향을 줌 |
| `REFERENCES` | Change → Issue | 변경이 이슈를 참조 |

```text
도메인 변경
    ↓
노드 타입 변경
관계 목록 변경
판정 기준 변경

하지만

(subject, subject_type, relation, object, object_type)
형식은 유지
```

즉 **트리플 처리 코드의 틀은 재사용 가능하지만 온톨로지는 도메인별로 다시 설계**해야 한다.

# 4. 전체 처리 흐름

```text
[1] 문서 문장
        ↓
[2] 개체 추출
        ↓
[3] 사실 단위 트리플 생성
    (주어, 관계, 목적어)
        ↓
[4] 노드 타입 추가
    (주어, 주어타입, 관계, 목적어, 목적어타입)
        ↓
[5] 이름 → ID 조회
        ├─ hit ───────────────┐
        ├─ miss ─> Candidate  │
        └─ ambiguous -> Candidate
                              │
[6] 관계 시그니처 적용       │
    - 허용 관계인가           │
    - 주어 타입이 맞는가      │
    - 목적어 타입이 맞는가    │
    - 판정 기준에 맞는가      │
                              ↓
[7] Cypher 변환
    MERGE (:Type {id})
    MERGE (:Type {id})
    MERGE ()-[:REL]->()
        ↓
[8] 지식 그래프 적재
```

# 5. 최종 핵심 정리

| 핵심 | 기억할 내용 |
|---|---|
| 트리플 | 사실 하나 = `(주어, 관계, 목적어)` |
| 그래프 적재용 트리플 | 타입 2칸을 추가한 5칸 구조 사용 |
| 노드 식별 | **name이 아니라 id** |
| `lookup_id()` | `hit / miss / ambiguous`를 구분 |
| `:Candidate` | 못 붙인 개체를 버리지 않고 격리 |
| 관계 시그니처 | `(주어 타입, 목적어 타입, 판정 기준)` |
| `TREATS / PALLIATES` | 타입이 같으므로 판정 기준으로 구분 |
| `BINDS` | 표적·대사·수송을 하나로 묶는 대신 세부 구분을 잃음 |
| `MERGE` | 같은 패턴을 반복 적재할 때 중복 증가 방지 |
| 온톨로지 | **무엇을 허용할지 + 무엇을 구분하지 않을지 결정하는 설계** |

> **가장 중요한 흐름**  
> `문장에서 사실을 뽑는 것`보다 먼저  
> **어떤 개체와 관계를 어떤 기준으로 그래프에 넣을지 정해야 한다.**

## 다음 단계

이 교안의 다음 흐름은 다음과 연결된다.

```text
관계 시그니처
    ↓
구조화 출력으로 트리플 추출
    ↓
evidence 포함
    ↓
온톨로지 기준 검증
    ↓
ID 정규화
    ↓
Neo4j MERGE
    ↓
미해결 개체는 Candidate
```

`evidence_level`은 노트북 서두에서 언급되지만, 이 교안 본문에서는 실제 구현하지 않고 다음 차시의 **근거 등급** 내용으로 이어진다.
