# 온톨로지 기반 추출·적재 — 압축 정리

> 핵심 흐름  
> **온톨로지 규격 → 구조화 출력 → 문서 추출 → 근거/시그니처 검사 → ID 해소 → Neo4j 적재 → 근거 등급·타입 계층**

---

# 1. 전체 개념

앞 단계에서는 트리플과 관계 시그니처를 **설계**했다.  
이번 단계에서는 그 설계를 실제 추출·적재 파이프라인에 연결한다.

```text
[온톨로지]
노드 타입 + 관계 시그니처
        ↓
[구조화 출력]
트리플의 필드·허용값 고정
        ↓
[추출 프롬프트]
온톨로지 + 추출 규칙 주입
        ↓
[후처리]
근거 확인 + 중복 제거
        ↓
[시그니처 검사]
관계 방향과 타입 검증
        ↓
[이름 해소]
name → id
    ├─ 성공 → 정식 노드
    └─ 실패 → :Candidate
        ↓
[Neo4j 적재]
관계에 evidence / source_doc_id / evidence_level 저장
```

핵심 원칙:

> **모델이 추출한 값을 곧바로 그래프에 넣지 않는다.**  
> 규격 → 근거 → 타입 → ID 순으로 검증한 뒤 적재한다.

# 2. 온톨로지를 하나의 계약으로 관리

## 2-1. Single Source of Truth

추출·적재·평가·쿼리가 서로 다른 규칙을 쓰면 그래프가 어긋난다.

따라서 노드 타입과 관계 규칙을 **코드 한 곳**에 둔다.

```python
RELATION_SIGNATURES = {
    "TREATS": (
        "Compound",
        "Disease",
        "약이 질병을 치료한다"
    ),

    "PALLIATES": (
        "Compound",
        "Disease",
        "약이 질병의 증상을 완화한다"
    ),

    "BINDS": (
        "Compound",
        "Gene",
        "약이 단백질에 결합한다. "
        "이 교안에서는 대사·수송 진술도 포함한다"
    ),

    "UPREGULATES_CG": (
        "Compound",
        "Gene",
        "유전자 발현 증가"
    ),

    "DOWNREGULATES_CG": (
        "Compound",
        "Gene",
        "유전자 발현 감소"
    ),

    "ASSOCIATES": (
        "Disease",
        "Gene",
        "질병과 유전자의 연관"
    ),

    "PRESENTS": (
        "Disease",
        "Symptom",
        "질병이 증상으로 나타남"
    ),

    "INCLUDES": (
        "PharmacologicClass",
        "Compound",
        "약효 분류가 약물을 포함"
    ),
}

NODE_TYPES = {
    "Compound",
    "Disease",
    "Gene",
    "Symptom",
    "PharmacologicClass",
}
```

관계 하나는 다음 3칸으로 관리한다.

```text
RELATION
    ↓
(주어 타입, 목적어 타입, 판정 기준)
```

예:

```text
PALLIATES
└─ (Compound, Disease, "질병 자체가 아니라 증상을 완화")
```

### 온톨로지 구조

노트북의 `ontology_schema.png`가 나타내는 구조를 텍스트로 옮기면 다음과 같다.

```text
(:PharmacologicClass)
        │
    [:INCLUDES]
        ▼
   (:Compound)
     ├─[:TREATS]───────────────> (:Disease)
     ├─[:PALLIATES]────────────> (:Disease)
     ├─[:BINDS]────────────────> (:Gene)
     ├─[:UPREGULATES_CG]───────> (:Gene)
     └─[:DOWNREGULATES_CG]─────> (:Gene)

(:Disease) ──[:ASSOCIATES]──> (:Gene)
(:Disease) ──[:PRESENTS]────> (:Symptom)
```

## 2-2. 온톨로지를 프롬프트 블록으로 변환

관계 규칙을 프롬프트에 손으로 다시 쓰지 않고 `dict`에서 만든다.

```python
def build_ontology_block(sigs):
    lines = ["[허용 관계]"]

    for rel, (subj, obj, crit) in sigs.items():
        lines.append(
            f"- {rel}: ({subj}) -> ({obj})  # {crit}"
        )

    return "\n".join(lines)
```

결과 형태:

```text
[허용 관계]
- TREATS: (Compound) -> (Disease)  # ...
- PALLIATES: (Compound) -> (Disease)  # ...
- BINDS: (Compound) -> (Gene)  # ...
...
```

장점:

```text
RELATION_SIGNATURES 수정
        ↓
온톨로지 블록 자동 변경
        ↓
추출 프롬프트도 자동 변경
```

즉 **온톨로지 규격을 여러 곳에서 따로 관리하지 않는다.**

# 3. 구조화 출력으로 트리플 형식 고정

## 3-1. 느슨한 서식의 문제

다음처럼 타입만 `str`로 두면 모델은 관계 이름을 자유롭게 만든다.

```python
class LooseTriple(BaseModel):
    subject: str
    subject_type: str
    relation: str
    object: str
    object_type: str
    evidence: str
```

`relation: str`의 의미는 단순하다.

```text
"문자열이면 된다"
```

따라서 온톨로지에 없는 `associated_with` 같은 관계가 나올 수 있다.

---

## 3-2. Literal로 허용값 제한

이미 온톨로지에 값 목록이 있으므로 그대로 가져온다.

```python
from typing import Literal

RelationName = Literal[tuple(RELATION_SIGNATURES)]
NodeType = Literal[tuple(sorted(NODE_TYPES))]
```

트리플 서식:

```python
class Triple(BaseModel):
    subject: str = Field(
        description="주어. 논문에 적힌 표기 그대로"
    )

    subject_type: NodeType = Field(
        description="주어 타입"
    )

    relation: RelationName = Field(
        description="관계. 온톨로지의 허용 관계 중 하나"
    )

    object: str = Field(
        description="목적어. 논문에 적힌 표기 그대로"
    )

    object_type: NodeType = Field(
        description="목적어 타입"
    )

    evidence: str = Field(
        description="근거가 된 원문 문장 하나를 그대로"
    )


class Extraction(BaseModel):
    triples: list[Triple]
```

모델에는 이 파이썬 클래스가 그대로 넘어가는 것이 아니라 **JSON Schema**가 전달된다.

```python
Triple.model_json_schema()
```

`Literal`은 JSON Schema에서 `enum`으로 변환된다.

```text
relation
└─ enum:
   TREATS
   PALLIATES
   BINDS
   ...
```

따라서 목록 밖 관계명은 출력할 수 없게 된다.

### 중요한 한계

구조화 출력은 **필드 하나의 값**은 제한할 수 있지만  
**필드끼리의 조합**까지 완전히 검사하지는 못한다.

예:

```text
relation = PALLIATES
object_type = Symptom
```

둘 다 개별적으로 허용된 값이지만,

```text
PALLIATES = Compound → Disease
```

이므로 조합은 잘못되었다.

따라서 뒤에서 **시그니처 검사**가 따로 필요하다.

# 4. 추출 프롬프트 설계

## 4-1. 프롬프트의 4요소

구조화 출력은 **답의 모양**을 정하고,  
프롬프트는 **무엇을 어떻게 뽑을지** 정한다.

추출 프롬프트는 크게 네 부분으로 구성한다.

```text
1. 역할
2. 온톨로지
3. 추출 규칙
4. 실제 문서
```

핵심 구현:

```python
from langchain_core.prompts import ChatPromptTemplate


def build_extraction_prompt():
    ontology = build_ontology_block(
        RELATION_SIGNATURES
    )

    system = (
        "너는 의학 논문에서 트리플을 뽑는 도구야.\n\n"
        f"{ontology}\n\n"

        "[규칙]\n"
        "- 관계는 허용 관계 중 하나만 쓴다.\n"
        "- 주어 타입 -> 목적어 타입 방향을 지킨다.\n"
        "- 맞는 관계가 없으면 억지로 넣지 않는다.\n"
        "- 개체 이름만 넣는다.\n"
        "- evidence는 원문 문장 하나를 그대로 옮긴다."
    )

    return ChatPromptTemplate.from_messages([
        ("system", system),
        ("human", "[문서]\n{text}")
    ])
```

체인:

```python
extractor = make_model().with_structured_output(
    Extraction
)

extraction_chain = (
    build_extraction_prompt()
    | extractor
)

result = extraction_chain.invoke({
    "text": doc
})
```

---

## 4-2. 온톨로지 판정 기준의 역할

예를 들어 이 교안에는 별도의 `METABOLIZES`, `TRANSPORTS` 관계가 없다.

대신 `BINDS` 판정 기준에 다음을 넣었다.

```text
대사·수송 진술도 BINDS에 포함
```

그래서 모델은 다음을 모두 `BINDS`로 표현한다.

```text
CYP2C19 → 약물 대사 효소
SLCO1B1 → 약물 수송체
VKORC1  → 약물 표적
```

장점:

```text
관계 종류가 통제됨
```

대가:

```text
표적 / 대사 / 수송의 관계 차이를 잃음
```

즉 **판정 기준 한 줄이 실제 그래프 의미를 결정한다.**

# 5. evidence를 트리플에 포함

트리플은 5칸이 아니라 근거까지 포함한 **6칸**으로 받는다.

```text
subject
subject_type
relation
object
object_type
evidence
```

`evidence`의 역할:

```text
모델의 트리플
      ↓
"이 원문이 정말 이 트리플을 뒷받침하는가?"
      ↓
검증 가능
```

평가 기준은:

```text
세상에서 사실인가?       X
근거 문장이 이 사실을 말하는가? O
```

특히 모델은:

- 문서에 없는 개체를 만들 수 있음
- 문서에 없는 근거 문장을 만들 수 있음
- 실제 문장을 가져왔지만 엉뚱한 트리플의 근거로 붙일 수 있음

따라서 근거까지 함께 저장해야 한다.

# 6. CoT 형태의 단계적 추출

교안에서는 복잡한 문장에서 관계 방향을 덜 틀리게 하고,  
모델이 어디에서 잘못 판단했는지 보기 위해 `reasoning` 칸을 앞에 둔다.

```python
class CoTExtraction(BaseModel):
    reasoning: str = Field(
        description=(
            "1) 개체 나열 "
            "2) 관계 후보 "
            "3) 시그니처 대조"
        )
    )

    triples: list[Triple]
```

생각 순서:

```text
1. 개체 + 타입 나열
2. 개체 쌍 중 관계 후보 선택
3. 시그니처와 대조
4. 통과한 것만 최종 트리플
```

중요한 점:

- 모델 호출을 4번 하는 것이 아니라 **한 번의 구조화 출력 안에서 단계 필드를 추가한 것**
- 항상 성능이 좋아지는 것은 아님
- `reasoning`만큼 출력이 늘어 속도·비용이 증가
- 큰 모델에서는 차이가 작고, 작은 모델에서는 타입 방향 오류를 줄이는 데 도움이 될 수 있음
- 실제 효과는 **모델·문서·프롬프트별로 평가해야 함**

즉 이 교안에서 CoT의 핵심 목적은:

```text
"무조건 성능 향상"
        X

"어느 판단 단계에서 어긋났는지 확인"
        O
```

# 7. 적재 전 3단계 검사

노트북의 `three_filters.png`를 텍스트 구조로 옮기면 다음과 같다.

```text
모델 추출 트리플
        │
        ▼
① 후처리 / 근거 검사
   - 중복 제거
   - evidence가 원문에 있는가
   - subject/object가 evidence에 있는가
        │
        ▼
② 시그니처 검사
   - 허용 관계인가
   - 주어 타입이 맞는가
   - 목적어 타입이 맞는가
        │
        ▼
③ 이름 해소
   - name → id
   - 실패하면 :Candidate 격리
        │
        ▼
Neo4j 적재
```

세 단계는 각각 다른 오류를 잡는다.

| 단계 | 잡는 문제 |
|---|---|
| 근거 검사 | 환각·엉뚱한 근거 |
| 시그니처 검사 | 잘못된 관계 방향·타입 |
| 이름 해소 | 사전에 없는 이름·애매한 이름 |

# 8. 후처리: 근거 확인과 중복 제거

## 8-1. 근거 검사

```python
def ground_check(row, text):
    if row["evidence"] not in text:
        return "근거가 원문에 없다"

    for side in ("subject", "object"):
        if row[side] not in row["evidence"]:
            return f"근거에 {row[side]} 가 없다"

    return None
```

통과:

```python
None
```

실패:

```text
"근거가 원문에 없다"
"근거에 Tapinarof 가 없다"
```

### 한계

이 검사는 **정확한 문자열 일치**를 사용한다.

따라서 다음도 실패할 수 있다.

```text
원문: Tapinarof
모델: tapinarof
```

또는 모델이 긴 근거 문장을 `...`로 줄이면 원문에 그대로 존재하지 않으므로 실패한다.

그래서 프롬프트에서:

```text
근거 문장 하나를 원문 그대로 옮긴다
```

라고 강하게 지정한다.

> 검사는 잘못된 트리플을 잡는 것뿐 아니라  
> **맞는 트리플을 잘못 버리는 경우도 확인해야 한다.**

---

## 8-2. 중복 제거

```python
def drop_duplicates(rows):
    seen = set()
    kept = []

    for r in rows:
        key = (
            r["subject"],
            r["relation"],
            r["object"],
        )

        if key not in seen:
            seen.add(key)
            kept.append(r)

    return kept
```

중복 기준:

```text
(subject, relation, object)
```

# 9. 시그니처 검사

관계 이름만 맞는다고 정상 트리플은 아니다.

```python
def check_signature(row):
    if row["relation"] not in RELATION_SIGNATURES:
        return "허용 관계가 아님"

    subj_type, obj_type, _ = (
        RELATION_SIGNATURES[row["relation"]]
    )

    if row["subject_type"] != subj_type:
        return f"주어 타입이 {subj_type} 이어야 함"

    if row["object_type"] != obj_type:
        return f"목적어 타입이 {obj_type} 이어야 함"

    return None
```

예:

```text
gabapentin[Compound]
    ──PALLIATES──>
neuropathic symptoms[Symptom]
```

하지만 온톨로지는:

```text
PALLIATES
Compound → Disease
```

이므로 **관계 이름은 맞지만 목적어 타입이 틀려 기각**한다.

# 10. 이름 해소와 Candidate 격리

## 10-1. 정식 노드는 ID로 MERGE

모델은 이름을 출력하지만 그래프의 식별 키는 `id`다.

```text
"clopidogrel"
      ↓ lookup_id()
Compound::DB00758
```

ID를 찾으면:

```cypher
MERGE (a:Compound {id: $s_id})
```

---

## 10-2. 못 붙는 이름은 Candidate

사전에 없거나 이름만으로 결정할 수 없으면 버리지 않는다.

```cypher
MERGE (
    a:Candidate {
        name: $s_name,
        type: $s_type
    }
)
```

`Candidate`의 키를 이름 하나만 쓰지 않는 이유:

```text
obesity
├─ Disease
└─ Symptom
```

따라서:

```text
(name, type)
```

두 값을 함께 사용한다.

핵심 함수:

```python
def node_pattern(
    alias,
    name,
    node_type,
    prefix
):
    found = lookup_id(
        name,
        node_type
    )[0]

    if found:
        return (
            f"({alias}:{node_type} "
            f"{{id: ${prefix}_id}})",
            {f"{prefix}_id": found},
            False,
        )

    return (
        f"({alias}:Candidate "
        f"{{name: ${prefix}_name, "
        f"type: ${prefix}_type}})",
        {
            f"{prefix}_name": name,
            f"{prefix}_type": node_type,
        },
        True,
    )
```

# 11. 값은 Cypher 파라미터로 전달

잘못된 예:

```python
f"MATCH (n {{name: '{name}'}})"
```

문자열에 다음이 들어가면 문제가 생긴다.

```text
Parkinson's disease
```

따라서 값은 `$파라미터`로 둔다.

```cypher
MATCH (n {name: $name})
```

```python
run_cypher(
    query,
    name=value
)
```

구분:

```text
레이블·관계 타입
:Compound
:BINDS
→ Cypher 문장의 구조

실제 값
id
name
evidence
→ 파라미터로 전달
```

# 12. 트리플 적재

## 12-1. 모델이 만든 값 + 파이프라인이 붙이는 값

모델이 만든 6칸:

```text
subject
subject_type
relation
object
object_type
evidence
```

파이프라인이 추가하는 2칸:

```text
source_doc_id
evidence_level
```

```python
rows = [
    tp.model_dump()
    | {
        "source_doc_id": demo["doc_id"],
        "evidence_level": "reported",
    }
    for tp in doc_result.triples
]
```

이 두 값은 모델에게 물어보는 값이 아니다.

```text
source_doc_id
└─ 어느 파일을 처리 중인지 파이프라인만 앎

evidence_level
└─ 현재 적재 출처가 논문인지 큐레이션 자료인지 파이프라인이 결정
```

## 12-2. Neo4j MERGE

핵심 구조:

```python
def load_triple(row):
    s_pat, s_params, s_new = node_pattern(
        "a",
        row["subject"],
        row["subject_type"],
        "s",
    )

    o_pat, o_params, o_new = node_pattern(
        "b",
        row["object"],
        row["object_type"],
        "o",
    )

    cy = (
        f"MERGE {s_pat}\n"
        f"MERGE {o_pat}\n"
        f"MERGE (a)-[r:{row['relation']}]->(b)\n"

        "SET "
        "a.name = coalesce(a.name, $sname), "
        "b.name = coalesce(b.name, $oname),\n"

        "r.evidence = "
        "coalesce(r.evidence, $ev),\n"

        "r.source_doc_id = "
        "coalesce(r.source_doc_id, $doc),\n"

        "r.evidence_level = "
        "coalesce(r.evidence_level, $level)"
    )

    run_cypher(
        cy,
        sname=row["subject"],
        oname=row["object"],
        ev=row["evidence"],
        doc=row["source_doc_id"],
        level=row["evidence_level"],
        **s_params,
        **o_params,
    )

    return s_new or o_new
```

`MERGE`를 사용하므로 동일한 노드·관계를 반복 적재해도 같은 패턴이 계속 늘어나는 것을 막는다.

# 13. 적재 루프의 핵심 순서

```python
for row in drop_duplicates(rows):

    if ground_check(row, text) is not None:
        continue

    if check_signature(row) is not None:
        continue

    load_triple(row)
```

실제 처리 상태는 네 갈래로 센다.

```text
적재
근거 미달
기각
격리
```

관계:

```text
적재
├─ 정상 ID 노드
└─ Candidate 포함
      ↑
     격리
```

따라서 `격리`는 **적재된 것 중 일부를 다시 센 값**이다.

# 14. 여러 문서는 batch로 추출

문서를 하나씩 `invoke()`하지 않고 묶어서 처리할 수 있다.

```python
results = extraction_chain.batch(
    [
        {"text": doc1},
        {"text": doc2},
        {"text": doc3},
    ],
    config={
        "max_concurrency": 2
    }
)
```

핵심:

```text
batch()
└─ 여러 입력을 묶어 처리

max_concurrency
└─ 동시에 내보낼 요청 수 제한
```

결과는 **입력 순서대로 반환**되므로 다음처럼 짝지을 수 있다.

```python
for doc_id, result in zip(
    doc_ids,
    results
):
    ...
```

`max_concurrency`를 두는 이유:

```text
문서 수만큼 API 요청 동시 발생
        ↓
분당 요청 제한 가능
        ↓
동시 요청 수 제한
```

# 15. Candidate가 생기는 이유

이름 해소 실패는 전부 같은 문제가 아니다.

| 경우 | 예 | 해결 방향 |
|---|---|---|
| 사전에 없음 | Tapinarof | 사전 확장 |
| 표기 차이 | Parkinson disease / Parkinson's disease | 표기 정규화 |
| 타입 불일치 | 같은 이름이 다른 타입에 존재 | 타입까지 검사 |
| 일반명 ↔ 공식 기호 | H1 receptor ↔ HRH1 | 별칭·매핑 규칙 |
| 분류명 표현 차이 | antiplatelet agent | 분류명 정규화 |

따라서:

```text
lookup 실패
    ≠
잘못된 개체
```

못 붙인 사실도 버리지 않고 `:Candidate`로 남긴 뒤 후속 정규화 단계에서 처리한다.

# 16. 근거 등급 evidence_level

## 16-1. 관계가 어디서 왔는지 기록

같은 `TREATS` 관계라도 출처의 성격이 다를 수 있다.

```text
논문 한 편에서 보고됨
큐레이션 DB에도 존재
```

이를 관계 속성으로 남긴다.

| 값 | 의미 |
|---|---|
| `reported` | 논문 한 편이 그렇게 보고함 |
| `curated` | 사람이 여러 근거를 모아 정리한 DB에도 있음 |

논문 적재:

```cypher
SET r.evidence_level =
    coalesce(
        r.evidence_level,
        'reported'
    )
```

큐레이션 자료 적재:

```cypher
SET r.evidence_level = 'curated'
```

핵심 규칙:

```text
curated가 이미 있음
        +
reported 추가
        ↓
curated 유지
```

즉 논문 적재가 기존 `curated`를 `reported`로 낮추지 않는다.

---

## 16-2. coalesce

```cypher
coalesce(a, b)
```

의미:

```text
a가 있으면 a
없으면 b
```

사용:

```cypher
SET r.evidence_level =
    coalesce(
        r.evidence_level,
        $level
    )
```

같은 방식으로 처음 저장한:

```text
evidence
source_doc_id
```

도 함부로 덮어쓰지 않는다.

---

## 16-3. evidence_level이 의미하지 않는 것

중요:

```text
curated / reported
```

는 **효능의 확실성이나 승인 여부를 직접 나타내는 등급이 아니다.**

예:

```text
Tapinarof
└─ 승인된 치료

Laquinimod
└─ 치료제로 연구됨
```

둘 다 큐레이션 DB에 없으면:

```text
reported
```

일 수 있다.

즉 `evidence_level`이 답하는 질문은:

```text
"이 사실은 어디서 왔는가?"
```

이지,

```text
"이 치료가 얼마나 확실한가?"
```

가 아니다.

# 17. 타입 계층

관계 설계에서 `BINDS` 하나로 합쳐 잃은 구분 일부를 노드 타입으로 보완한다.

노트북의 `type_hierarchy.png` 구조:

```text
             Gene
            /    \
           /      \
      Enzyme    Transporter
```

Neo4j에서는 하위 타입을 별도 노드로 만들지 않고 **레이블을 겹쳐 붙인다.**

```text
:Gene:Enzyme
:Gene:Transporter
```

구현:

```python
TYPE_HIERARCHY = {
    "Enzyme": "Gene",
    "Transporter": "Gene",
}
```

```python
def labels_for(node_type):
    parent = TYPE_HIERARCHY.get(
        node_type
    )

    return (
        [parent, node_type]
        if parent
        else [node_type]
    )
```

```python
def set_labels(
    node_id,
    node_type
):
    labels = ":".join(
        labels_for(node_type)
    )

    run_cypher(
        f"MATCH (n {{id: $id}}) "
        f"SET n:{labels}",
        id=node_id
    )
```

결과:

```text
CYP2C19
:Gene:Enzyme

SLCO1B1
:Gene:Transporter
```

---

## 17-1. 장점

상위 타입 쿼리:

```cypher
MATCH (g:Gene)
```

로 물어도:

```text
:Gene
:Gene:Enzyme
:Gene:Transporter
```

가 모두 잡힌다.

하위 타입으로 좁힐 수도 있다.

```cypher
MATCH (c:Compound)-[:BINDS]->(g:Enzyme)
RETURN c, g
```

시그니처:

```text
BINDS = Compound → Gene
```

는 수정하지 않아도 된다.

---

## 17-2. 타입 계층의 한계

타입 계층으로 되찾을 수 있는 것:

```text
이 Gene가 Enzyme인가?
이 Gene가 Transporter인가?
```

되찾을 수 없는 것:

```text
이 Compound-Gene 관계가
표적 결합인가?
대사 관계인가?
수송 관계인가?
```

이 정보는 관계 `BINDS`에 저장하지 않았기 때문이다.

> **온톨로지에서 처음 구분하지 않은 정보는 나중에 완전히 복구하기 어렵다.**

따라서 계층은 깊게 시작하지 않고 **필요한 한 단계부터** 추가한다.

# 19. 종합 코드 구조

실전에서는 기존 조각을 한 함수에서 순서대로 호출한다.

```python
def extract_and_load_batch(rows):

    results = extraction_chain.batch(
        [
            {"text": row["text"]}
            for row in rows
        ],
        config={
            "max_concurrency": 2
        }
    )

    report = []

    for row, result in zip(
        rows,
        results
    ):
        triples = [
            tp.model_dump()
            | {
                "source_doc_id": row["doc_id"],
                "evidence_level": "reported",
            }
            for tp in result.triples
        ]

        loaded = 0
        grounded_bad = 0
        rejected = 0
        isolated = 0

        for triple in drop_duplicates(
            triples
        ):
            if ground_check(
                triple,
                row["text"]
            ) is not None:
                grounded_bad += 1
                continue

            if check_signature(
                triple
            ) is not None:
                rejected += 1
                continue

            if load_triple(triple):
                isolated += 1

            loaded += 1

        report.append(
            (
                row["doc_id"],
                loaded,
                grounded_bad,
                rejected,
                isolated,
            )
        )

    return report
```

처리 순서만 기억하면 된다.

```text
batch 추출
→ 메타데이터 추가
→ 중복 제거
→ 근거 검사
→ 시그니처 검사
→ ID 해소
→ 적재
```

# 20. 핵심 문법 정리

| 목적 | 핵심 문법 |
|---|---|
| 온톨로지 단일 관리 | `RELATION_SIGNATURES = {...}` |
| 허용값 제한 | `Literal[...]` |
| 구조화 출력 | `.with_structured_output(Extraction)` |
| Pydantic → 실제 모델 규격 확인 | `.model_json_schema()` |
| 프롬프트 구성 | `ChatPromptTemplate.from_messages()` |
| 프롬프트 + 모델 연결 | `prompt \| extractor` |
| 객체 → dict | `.model_dump()` |
| dict에 메타데이터 추가 | `a \| {"key": value}` |
| 여러 문서 추출 | `chain.batch([...])` |
| 동시 요청 제한 | `config={"max_concurrency": 2}` |
| ID 기반 노드 생성 | `MERGE (:Type {id: $id})` |
| 값 전달 | `$param` + `run_cypher(..., param=value)` |
| 기존 값 유지 | `coalesce(existing, new)` |
| 복수 레이블 | `SET n:Gene:Enzyme` |
| 관계 종류 조회 | `type(r)` |
| 관계 속성 저장 | `r.evidence`, `r.source_doc_id`, `r.evidence_level` |

# 21. 최종 핵심 정리

| 개념 | 기억할 내용 |
|---|---|
| 온톨로지 | 추출·적재·평가·쿼리가 공유하는 **단일 계약** |
| `Literal` | 허용 관계·타입을 JSON Schema의 `enum`으로 제한 |
| 구조화 출력 | 답의 **필드와 값 범위**를 강제 |
| 시그니처 검사 | 필드 사이의 **관계 방향·타입 조합** 검사 |
| evidence | 트리플을 뒷받침하는 원문 |
| `ground_check` | 근거가 실제 원문에 있고 양 끝 개체를 포함하는지 검사 |
| ID 해소 | `name → id` |
| `:Candidate` | ID를 못 찾은 개체를 버리지 않고 격리 |
| `source_doc_id` | 관계가 어느 문서에서 왔는지 기록 |
| `evidence_level` | 사실의 **출처 성격**을 `reported / curated`로 구분 |
| `coalesce` | 기존의 더 중요한 값을 함부로 덮어쓰지 않음 |
| `batch` | 여러 문서를 묶어 추출 |
| `max_concurrency` | 동시에 보내는 API 요청 수 제한 |
| 타입 계층 | `:Gene:Enzyme`처럼 레이블을 겹쳐 상·하위 타입 표현 |

> **가장 중요한 흐름**
>
> `LLM이 뽑았다 → 적재`가 아니라
>
> **LLM 추출 → 근거 검사 → 시그니처 검사 → ID 정규화 → 적재**
>
> 순으로 처리한다.
