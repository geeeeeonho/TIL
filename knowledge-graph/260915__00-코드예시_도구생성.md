# GraphDB 조회 도구 생성 및 근거 검증 코드 예시

> `drugs` 데이터셋을 기준으로 그래프 스키마 확인 → Cypher 조회 검증 → Text2Cypher Agent → Vector Search Agent → 인용 근거 확인까지 이어지는 흐름.
>
> 전제: `read_schema`, `run_cypher`, `read_query`, `create_agent`, `select_names`, `search_graph`, `search_documents`, `ask`, `show_response`, `show_citations` 등의 함수와 `llm`, 프롬프트 템플릿은 이전 단계에서 정의되어 있다고 가정.

## 1. 저장된 그래프 구조와 관계 확인

그래프를 LLM이나 검색 도구에 연결하기 전에 **어떤 노드·관계가 저장되어 있는지**, 그리고 **실제 조회 결과가 의도한 의미와 일치하는지** 먼저 확인한다.

### 1-1. 노드·관계 스키마 확인

`drugs` 데이터셋의 JSON 스키마를 읽어 노드 타입, 관계 타입, 허용 관계 패턴을 확인한다.

```python
# 1. drugs 데이터셋의 JSON 스키마를 읽어옵니다.
drugs_schema = read_schema("drugs")

# 2. 노드 타입의 label과 description을 출력합니다.
print("[노드 타입]")
for node_type in drugs_schema["node_types"]:
    print(node_type["label"], ":", node_type["description"])

# 3. 관계 타입의 label과 description을 출력합니다.
print("\n[관계 타입]")
for relationship_type in drugs_schema["relationship_types"]:
    print(relationship_type["label"], ":", relationship_type["description"])

# 4. 허용 관계 패턴을 출력합니다.
print("\n[관계 패턴]")
for pattern in drugs_schema["patterns"]:
    print(pattern[0], "->", pattern[1], "->", pattern[2])
```

**결과**

```text
[노드 타입]
Drug : 의약품 제품. name은 원문에 저장된 등록 제품명이고 aliases는 축약명 등이다.
Symptom : 효능 또는 이상반응으로 언급된 증상. 둘은 관계 타입으로 구분한다.
RiskGroup : 복용 시 주의가 필요한 대상 집단. 범위가 넓은 표기를 좁은 표기와 임의로 합치지 않는다.
Ingredient : 제품 성분 또는 상호작용 대상 성분.
Manufacturer : 의약품 제조사.

[관계 타입]
TREATS : 제품 효능·효과에 포함된 증상. evidence에 한정 조건이 있으면 함께 읽는다.
HAS_SIDE_EFFECT : 제품 복용 후 나타날 수 있는 이상반응. 치료 효능과 구분한다.
CAUTION_FOR : 제품 복용 시 주의 대상 집단. 원문의 주의 내용과 대상 범위를 확인한다.
INTERACTS_WITH : 함께 복용 시 주의할 제품 또는 성분. 목적어 타입은 Drug 또는 Ingredient이다.
CONTAINS : 제품에 포함된 성분.
MADE_BY : 제품을 제조한 회사.

[관계 패턴]
Drug -> TREATS -> Symptom
Drug -> HAS_SIDE_EFFECT -> Symptom
Drug -> CAUTION_FOR -> RiskGroup
Drug -> INTERACTS_WITH -> Drug
Drug -> INTERACTS_WITH -> Ingredient
Drug -> CONTAINS -> Ingredient
Drug -> MADE_BY -> Manufacturer
```

**핵심**

- 같은 `Symptom`이라도 `TREATS`와 `HAS_SIDE_EFFECT`는 의미가 다름.
- 스키마의 `patterns`는 **어떤 타입의 노드끼리 어떤 관계로 연결될 수 있는지** 정의한 허용 구조.
- LLM이 Cypher를 만들 때도 이 스키마를 기준으로 관계 방향과 타입을 제한해야 함.

### 1-2. 등록 이름과 별칭 조회 확인

제품의 정식 이름뿐 아니라 `aliases`에 저장된 별칭으로도 같은 `Drug` 노드를 찾을 수 있는지 확인한다.

```python
alias_query = """
// Drug 노드 중에서 검색
MATCH (d:Drug)

// 같은 데이터셋에서 정식 이름 또는 별칭이 일치하는 노드 선택
WHERE d.dataset = $dataset
  AND (d.name = $name OR $name IN d.aliases)

RETURN
    d.standard_id AS standard_id,
    d.name AS name,
    d.aliases AS aliases
"""

# 별칭으로 조회
short_matches = run_cypher(
    alias_query,
    dataset="drugs",
    name="게보린정"
)

# 등록 이름으로 조회
product_matches = run_cypher(
    alias_query,
    dataset="drugs",
    name="메카인정"
)

print("게보린정으로 조회:", short_matches)
print("메카인정으로 조회:", product_matches)
```

**결과**

```text
게보린정으로 조회: [{'standard_id': 'rag:drugs:drug:drug_197900277',
                    'name': '게보린정(수출명:돌로린정)',
                    'aliases': ['게보린정']}]

메카인정으로 조회: [{'standard_id': 'rag:drugs:drug:drug_199100996',
                    'name': '메카인정',
                    'aliases': []}]
```

**해석**

- `게보린정`은 `aliases`를 통해 등록 제품명 `게보린정(수출명:돌로린정)`으로 연결됨.
- `메카인정`은 `name` 자체가 일치하므로 별칭 없이 조회됨.
- 사용자 입력을 그래프 조회에 바로 넣기 전에 **정식 이름/별칭을 표준 노드에 연결하는 단계**가 필요한 이유를 보여주는 예시.

### 1-3. 2-hop 관계 조회

`두통을 치료하면서 임부가 주의해야 하는 약`처럼 **두 관계를 동시에 만족하는 약**을 찾는다.

관계 구조:

```text
(Symptom) <-[:TREATS]- (Drug) -[:CAUTION_FOR]-> (RiskGroup)
```

```python
two_hop_query = """
// 하나의 Drug에서 증상과 위험군으로 이어지는 두 관계를 함께 검색
MATCH (s)<-[t:TREATS]-(d:Drug)-[c:CAUTION_FOR]->(r)

// 증상과 위험군 이름을 정확히 비교하고,
// 두 관계가 같은 데이터셋의 관계인지 확인
WHERE s.name = $symptom
  AND r.name = $risk_group
  AND t.dataset = $dataset
  AND c.dataset = $dataset

// 약 이름과 각 관계의 근거 정보를 함께 반환
RETURN
    d.name AS answer_value,
    [t.claim_id, c.claim_id] AS evidence_ids,
    [t.evidence, c.evidence] AS evidence_texts,
    [t.source_doc_id, c.source_doc_id] AS source_doc_ids,
    [t.source_kind, c.source_kind] AS source_kinds,
    [type(t), type(c)] AS relation_types

ORDER BY answer_value ASC, evidence_ids ASC
"""

# 첫 번째 조회: 위험군 이름이 "임부"
headache_pregnant_rows = run_cypher(
    two_hop_query,
    symptom="두통",
    risk_group="임부",
    dataset="drugs"
)

print("임부")
for row in headache_pregnant_rows:
    print(row["answer_value"], row["evidence_ids"])

# 두 번째 조회: 더 긴 위험군 표현
variant_rows = run_cypher(
    two_hop_query,
    symptom="두통",
    risk_group="임부 또는 임신하고 있을 가능성이 있는 여성",
    dataset="drugs"
)

print("\n임부 또는 임신하고 있을 가능성이 있는 여성")
for row in variant_rows:
    print(row["answer_value"])
```

**결과**

```text
임부
게보린정(수출명:돌로린정) ['TR001', 'CA006']
뇌선 ['TR042', 'CA028']
메카인정 ['TR072', 'CA039']
부루펜정400밀리그램(이부프로펜) ['TR024', 'CA010']
세토펜정(아세트아미노펜) ['TR034', 'CA023']
판토-에이내복액 ['TR067', 'CA031']

임부 또는 임신하고 있을 가능성이 있는 여성
이지롱내복액
```

**해석**

- 하나의 약이 `TREATS`와 `CAUTION_FOR` 두 관계를 모두 만족해야 결과에 포함됨.
- `r.name = $risk_group`는 **정확 일치**이므로 `임부`와 `임부 또는 임신하고 있을 가능성이 있는 여성`은 별개의 표현으로 조회됨.
- 넓은 표현과 좁은 표현을 임의로 같은 엔티티로 합치지 않는 현재 스키마 정책과도 연결됨.

> 주의: 현재 수동 쿼리는 관계의 `dataset`을 기준으로 제한함. 여러 데이터셋의 노드가 같은 그래프에 섞이는 구조라면 `d.dataset`, `s.dataset`, `r.dataset`까지 함께 제한하는 편이 더 엄격함.

### 1-4. 효능과 이상반응을 구분하고, "관계 없음"의 의미 확인

같은 증상이라도 `TREATS`와 `HAS_SIDE_EFFECT`는 완전히 다른 의미다. 또한 **그래프에서 관계가 조회되지 않았다고 해서 원문에도 정보가 없다고 단정할 수는 없음**.

```python
# 1. TREATS 관계로 두통을 가리키는 약
treats_query = """
MATCH (d:Drug)-[r:TREATS]->(s:Symptom)
WHERE s.name = $symptom
  AND r.dataset = $dataset
RETURN d.name AS drug
ORDER BY drug ASC
"""

headache_treats = run_cypher(
    treats_query,
    symptom="두통",
    dataset="drugs"
)
print("1. 두통 치료:", headache_treats)


# 2. HAS_SIDE_EFFECT 관계로 두통을 가리키는 약
side_effects_query = """
MATCH (d:Drug)-[r:HAS_SIDE_EFFECT]->(s:Symptom)
WHERE s.name = $symptom
  AND r.dataset = $dataset
RETURN d.name AS drug
ORDER BY drug ASC
"""

headache_side_effects = run_cypher(
    side_effects_query,
    symptom="두통",
    dataset="drugs"
)
print("2. 두통 이상반응:", headache_side_effects)


# 3. 특정 약에 변비 이상반응 관계가 저장되어 있는지 검색
side_effect_query = """
MATCH (d:Drug)-[r:HAS_SIDE_EFFECT]->(s:Symptom)
WHERE d.name = $drug
  AND s.name = $symptom
  AND r.dataset = $dataset
RETURN r.claim_id AS claim_id
"""

side_effect_rows = run_cypher(
    side_effect_query,
    drug="부루펜정400밀리그램(이부프로펜)",
    symptom="변비",
    dataset="drugs"
)
print("3. 변비 이상반응:", side_effect_rows)


# 4. 해당 제품의 원문에 "변비"가 실제로 존재하는지 직접 확인
constipation_in_text = (
    "변비" in drugs["documents"]["drug_198300343"]["text"]
)

print("4-1. 그래프 조회:", side_effect_rows)
print("4-2. 원문에 변비 포함:", constipation_in_text)
```

**결과**

```text
1. 두통 치료: [{'drug': '게보린정(수출명:돌로린정)'},
               {'drug': '뇌선'},
               {'drug': '메카인정'},
               {'drug': '부루펜정400밀리그램(이부프로펜)'},
               {'drug': '세토펜정(아세트아미노펜)'},
               {'drug': '이지롱내복액'},
               {'drug': '판토-에이내복액'}]

2. 두통 이상반응: [{'drug': '메카인정'},
                  {'drug': '부루펜정400밀리그램(이부프로펜)'},
                  {'drug': '신일비사코딜정'}]

3. 변비 이상반응: []
4-1. 그래프 조회: []
4-2. 원문에 변비 포함: True
```

**핵심 해석**

- `두통`은 어떤 약에서는 효능(`TREATS`), 다른 약에서는 이상반응(`HAS_SIDE_EFFECT`)으로 저장될 수 있음.
- `side_effect_rows == []`는 **해당 관계가 현재 그래프에 저장되어 있지 않음**을 의미할 뿐임.
- 원문에는 `변비`가 존재하므로, 그래프의 빈 결과만 보고 `원문에도 변비가 없다`고 판단하면 안 됨.
- 즉, 그래프 조회는 **구조화되어 적재된 정보의 범위**를 반영하며, 누락 가능성이 있는 경우 원문 검색으로 보완해야 함.

## 2. LLM으로 Cypher 조회와 근거 기반 답변 생성

그래프 스키마를 확인한 뒤 LLM이 사용자 질문을 Cypher 조회로 변환하도록 한다. 이때 임의의 쓰기 쿼리를 실행하지 못하도록 **조회 전용 실행 경계**를 먼저 확인한다.

### 2-1. 조회 전용 함수가 쓰기 Cypher를 차단하는지 확인

```python
# 1. 정상적인 읽기 쿼리
risk_count_rows = read_query(
    """
    MATCH (r:RiskGroup)
    WHERE r.dataset = $dataset
    RETURN count(r) AS count
    """,
    {"dataset": "drugs"}
)

# 2. 쓰기 쿼리가 차단되는지 확인
blocked_message = ""

try:
    read_query(
        """
        CREATE (:Day42AssignmentProbe {dataset: "drugs"})
        RETURN 1 AS created
        """
    )
except ValueError as e:
    blocked_message = str(e)

# 3. 결과 출력
print("RiskGroup 개수:", risk_count_rows)
print("차단 메시지:", blocked_message)
```

**결과**

```text
RiskGroup 개수: [{'count': 67}]
차단 메시지: 조회 전용 Cypher만 실행합니다.
```

**해석**

- `MATCH ... RETURN`은 정상 실행됨.
- `CREATE`가 포함된 쓰기 쿼리는 `ValueError`로 차단됨.
- 이 테스트는 **현재 `read_query()` 구현에서 CREATE가 차단되는지 확인한 것**. 전체 보안을 보장하는 테스트는 아니므로 실제 운영에서는 `DELETE`, `SET`, `MERGE`, `DROP` 등 다른 쓰기 구문도 함께 제한해야 함.

### 2-2. Text2Cypher Agent 생성 및 실행

사용자 질문에서 엔티티를 먼저 확인하고, 그래프 스키마에 맞는 Cypher를 생성해 조회한 뒤, 조회 결과의 근거만 사용해 답변하도록 구성한다.

```python
# 사용자 질문
constipation_question = "변비를 이상반응으로 안내하는 약은 무엇인가요?"

# drugs 그래프용 시스템 프롬프트 조립
drugs_graph_system = graph_template.format(
    domain="drugs",
    schema=drugs_schema,
    cypher_rules=cypher_rules,
    answer_rules=answer_rules,
)

# Text2Cypher Agent 생성
drugs_graph_agent = create_agent(
    model=llm,
    tools=[select_names, search_graph],
    system_prompt=drugs_graph_system,
    response_format=ProviderStrategy(
        GroundedAnswer,
        strict=True
    ),
)

# 질문 실행
constipation_response = ask(
    drugs_graph_agent,
    constipation_question
)

# 전체 응답 출력
show_response(constipation_response)

# search_graph가 실제로 반환한 rows
constipation_rows = constipation_response["rows"]
print(constipation_rows)
```

### 2-3. 최종 답변과 인용 근거 대조

LLM의 최종 문장이 그래프 관계의 의미를 바꾸지 않았는지 확인한다. 특히 `HAS_SIDE_EFFECT`를 `TREATS`처럼 설명하지 않는지, 각 답변이 실제 evidence와 연결되는지 확인하는 단계.

```python

# 2. 최종 답변에 사용된 근거 ID
constipation_evidence_ids = constipation_response["evidence_ids"]

# 3. 확인용 출력
print("최종 답변:")
print(constipation_answer)

print("\n근거 ID:")
print(constipation_evidence_ids)

print("\n답변과 인용 근거:")
show_citations(constipation_response)
```

## 3. Vector Search로 원문 검색 및 청크 인용 확인

그래프에 구조화되지 않았거나 누락될 수 있는 정보는 원문 청크 검색으로 보완한다. Vector Search는 **질문과 의미적으로 가까운 청크를 후보로 찾는 단계**이며, 검색 점수 자체가 정답 여부를 의미하지는 않는다.

### 3-1. Vector Search Agent로 원문 검색

```python
milk_question = "우유를 마신 뒤 바로 먹으면 안 되는 약은 무엇인가요?"

# 벡터 검색 전용 시스템 프롬프트
drugs_vector_system = vector_template.format(
    domain="drugs",
    answer_rules=answer_rules,
)

# Vector Search Agent 생성
drugs_vector_agent = create_agent(
    model=llm,
    tools=[search_documents],
    system_prompt=drugs_vector_system,
    response_format=ProviderStrategy(
        GroundedAnswer,
        strict=True
    ),
)

# 질문 실행
milk_response = ask(
    drugs_vector_agent,
    milk_question
)

show_response(milk_response)

# 실제 벡터 검색으로 찾은 chunk 후보
milk_hits = milk_response["chunks"]
```

## 전체 흐름 정리

```text
[그래프 구조 확인]
스키마 → 노드/관계 타입 → 관계 패턴
        ↓
[그래프 조회 검증]
별칭 조회 → 2-hop 조회 → 관계 의미 구분 → 그래프 누락 확인
        ↓
[Text2Cypher]
사용자 질문 → 이름 정규화 → Cypher 생성/조회 → 관계 근거 기반 답변
        ↓
[Vector Search]
원문 검색 → 관련 청크 후보 → 답변 생성 → 실제 사용 청크만 인용
        ↓
[최종 검증]
답변 내용 ↔ evidence/claim_id 또는 chunk_id ↔ 원문 대조
```

### 핵심 포인트

- **그래프 조회 결과와 원문 존재 여부는 같지 않음.** 관계가 없다고 원문 정보까지 없다고 단정하면 안 됨.
- **관계 타입의 의미를 유지해야 함.** `TREATS`와 `HAS_SIDE_EFFECT`처럼 같은 엔티티 조합이라도 관계가 다르면 의미도 달라짐.
- **LLM이 만든 Cypher는 조회 전용 경계를 통과시켜야 함.** 쓰기 쿼리를 차단하는 실행 계층이 필요함.
- **Vector Search의 검색 후보와 최종 근거를 구분해야 함.** 유사도가 높은 청크가 자동으로 정답 근거가 되는 것은 아님.
- **최종 답변은 근거 ID로 되짚을 수 있어야 함.** Graph에서는 `claim_id`, Vector Search에서는 `chunk_id`가 추적 기준이 됨.
