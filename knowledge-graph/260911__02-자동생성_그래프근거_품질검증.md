> 목적: 반복 실습은 줄이고, **평가 개념 · 핵심 문법 · 해석 방법** 중심으로 정리

## 0. 전체 평가 흐름

교안 01에서 생성한 그래프를 그대로 정답으로 보지 않고, 저장된 관계의 품질을 단계별로 확인한다.

```text
자동 생성 그래프
    ↓
[1] GraphPruning 결과 확인
    ↓
[2] 저장 관계의 Schema 준수 검사
    ↓
[3] evidence 원문 일치 검사
    ↓
[4] Gold와 TP / FP / FN 비교
    ↓
[5] Precision / Recall / F1 계산
    ↓
[6] Chunk 설정 변경 후 재실행
    ↓
[7] 같은 Gold로 전후 결과 비교
```

핵심 구분:

```text
Schema 준수      = 허용한 그래프 구조인가?
Evidence 일치    = 인용한 문구가 실제 원문에 있는가?
Gold 비교        = 추출한 관계 자체가 정답인가?
```

세 검사는 서로 다른 품질을 본다.

# 1. 평가 대상과 GraphPruning

## 1-1. 무엇을 평가하는가

교안 01의 저장본은 다음 단계를 거친 결과다.

```text
LLM 관계 추출
→ GraphPruning
→ Neo4j 저장
→ Snapshot 저장
→ 이후 Entity Resolution
```

교안 02의 기본 평가 대상은 **GraphPruning을 통과해 DB에 저장된 관계**다.

예:

```text
LLM 추출 10건
→ Pruning에서 2건 제거
→ DB 저장 8건
→ 평가 대상 8건
```

즉 저장 후 스키마 준수율은 **가지치기 이후 결과를 확인하는 지표**다.  
LLM이 처음부터 스키마를 얼마나 잘 지켰는지를 직접 나타내지는 않는다.

---

## 1-2. GraphPruning

**Pruning**은 스키마가 허용하지 않은 노드, 관계, 속성, 연결 패턴을 제거하는 작업이다.

핵심 객체:

```python
Neo4jGraph
Neo4jNode
Neo4jRelationship
GraphSchema
GraphPruning
```

기본 사용:

```python
from copy import deepcopy

pruned = await GraphPruning().run(
    graph=pruning_input,
    schema=GraphSchema.model_validate(
        deepcopy(schema)
    ),
)
```

- `Neo4jGraph`: DB에 저장하기 전 Python 그래프 객체
- `GraphSchema.model_validate(...)`: Schema 사전을 검사 가능한 객체로 변환
- `GraphPruning.run(...)`: Schema에 맞지 않는 요소 제거
- `pruned.graph`: 가지치기 후 그래프
- `pruned.pruning_stats`: 제거된 요소와 사유

예시 결과:

```text
가지치기 전 관계: 2
가지치기 후 관계: 1
제거 사유: INVALID_PATTERN
```

### 중요한 점

```text
Schema에 맞음 ≠ 관계가 사실임
```

예를 들어 관계 방향을 허용 패턴에 맞게 고쳤더라도,  
**원문이 실제로 그 관계를 뒷받침하는지는 별도 검사**가 필요하다.

# 2. 저장 관계의 Schema와 Evidence 검사

## 2-1. 저장 관계 한 행

교안의 `rows`에서 한 행은 **DB에 저장된 관계 한 건**이다.

대표 구조:

```python
{
    "relationship_id": "...",
    "subject": "2.0.3",
    "subject_type": "Release",
    "relation": "FIXES_API",
    "object": "read_csv",
    "object_type": "ApiElement",
    "evidence": "...",
    "source_doc_id": "...",
    "chunk_texts": [...]
}
```

같은 `(subject, relation, object)`라도 DB 관계 ID가 다르면  
Schema/Evidence 검사에서는 각각 별도 행으로 본다.

---

## 2-2. Schema 준수 검사

질문:

```text
이 관계가 허용한
(주어 타입, 관계 타입, 목적어 타입)
조합인가?
```

핵심 함수:

```python
def schema_ok(row, patterns):
    return (
        row["subject_type"],
        row["relation"],
        row["object_type"],
    ) in [tuple(pattern) for pattern in patterns]
```

예:

```text
허용:
("Release", "FIXES_API", "ApiElement")

통과:
Release -> FIXES_API -> ApiElement

실패:
ApiElement -> FIXES_API -> ApiElement
```

준수율:

```python
schema_count = sum(
    schema_ok(row, snapshot["schema"]["patterns"])
    for row in rows
)

schema_rate = schema_count / len(rows)
```

```text
Schema 준수율
= Schema를 통과한 저장 행 수
  ÷ 저장 관계 전체 행 수
```

---

## 2-3. Evidence 원문 일치 검사

질문:

```text
관계에 저장된 evidence가
해당 출처 원문에 실제로 그대로 있는가?
```

핵심 함수:

```python
def evidence_ok(row, document):
    # 다른 문서의 관계면 실패
    if row["source_doc_id"] != document["doc_id"]:
        return False

    evidence = row["evidence"]

    # 빈 문자열이나 잘못된 자료형이면 실패
    if not isinstance(evidence, str) or not evidence.strip():
        return False

    # 전체 원문에 그대로 존재하는지 검사
    return evidence in document["text"]
```

일치율:

```python
evidence_count = sum(
    evidence_ok(row, document)
    for row in rows
)

evidence_rate = evidence_count / len(rows)
```

```text
Evidence 원문 일치율
= 비어 있지 않은 evidence가
  해당 문서 원문에 그대로 있는 행 수
  ÷ 저장 관계 전체 행 수
```

---

## 2-4. `document["text"]`와 `chunk_texts`

교안의 기본 `evidence_ok()`는 **전체 문서 원문**과 비교한다.

```python
evidence in document["text"]
```

`chunk_texts`는 관계와 연결된 청크 원문을 확인하기 위한 정보다.

```text
document["text"] : 인용 문자열의 실제 존재 여부 검사
row["chunk_texts"] : 관계 주변 문맥 검토
```

현재 함수는 evidence가 **정확히 어느 청크에서 나왔는지**까지 판정하지 않는다.

# 3. 인용 일치와 의미 정확성은 다름

Evidence가 원문에 있다고 해서 관계가 맞는 것은 아니다.

| 상황 | Evidence 원문 일치 | 관계 의미 |
|---|---:|---:|
| 부정 문장을 그대로 인용하고 사실 관계로 추출 | 통과 | 틀림 |
| 관계는 맞지만 근거를 요약해서 저장 | 실패 | 맞을 수 있음 |
| 원문과 관계가 모두 정확 | 통과 | 맞음 |

따라서 평가를 다음처럼 분리한다.

```text
Evidence 검사
= 인용 문자열 검사

Gold 비교
= 관계 의미 검사
```

### 오류별 교정 방향

| 문제 | 교정 방향 |
|---|---|
| evidence가 비었거나 원문과 다름 | 원문 구절을 그대로 인용 |
| 주어·목적어 연결 오류 | 주변 문맥에서 개체가 가리키는 대상 확인 |
| 예정·부정 표현을 사실로 추출 | Prompt에 포함·제외 기준 명시 |

# 4. Gold와 관계 비교

## 4-1. Gold

**Gold**는 원문과 포함 기준을 사람이 확인해 작성한 정답 트리플 목록이다.

```text
Prediction과 Gold는 반드시 같은 원문 범위를 사용
```

예:

```python
{
    "subject": "2.0.3",
    "relation": "FIXES_API",
    "object": "read_csv",
    "paragraph_id": "p03"
}
```

`paragraph_id`는 정답을 만든 원문 위치를 다시 확인할 때 사용한다.

---

## 4-2. Triple Key

평가에서는 관계를 다음 세 값으로 비교한다.

```python
def triple_key(row):
    return (
        row["subject"],
        row["relation"],
        row["object"],
    )
```

즉:

```text
(subject, relation, object)
```

예:

```python
("2.0.3", "FIXES_API", "read_csv")
```

---

## 4-3. 완전일치 평가

교안에서는 세 문자열이 모두 같은 **Exact Match**를 사용한다.

```text
"read_csv" ≠ "Read_Csv"
"2.0.3" ≠ "2.0.3 (June 28, 2023)"
```

따라서 FP와 FN이 발생했을 때는 다음을 구분해야 한다.

```text
실제 의미 오류인가?
표기만 다른가?
```

# 5. TP / FP / FN과 Precision · Recall · F1

## 5-1. 관계 집합 만들기

Gold 비교에서는 같은 트리플이 여러 행에 있어도 한 번만 센다.

```python
predicted = {
    triple_key(row)
    for row in rows
}

expected = {
    triple_key(row)
    for row in gold
}
```

즉:

```text
Schema / Evidence 검사
→ DB 관계 행 단위

Gold 비교
→ 고유 Triple 단위
```

---

## 5-2. TP / FP / FN

```python
tp = predicted & expected
fp = predicted - expected
fn = expected - predicted
```

| 구분 | 의미 |
|---|---|
| `TP` | Prediction과 Gold 모두 존재 |
| `FP` | Prediction에만 존재 |
| `FN` | Gold에만 존재 |

집합 연산으로 보면:

```text
TP = Prediction ∩ Gold
FP = Prediction - Gold
FN = Gold - Prediction
```

---

## 5-3. Precision

```text
추출한 관계 중 실제 정답의 비율
```

```python
precision = TP / (TP + FP)
```

코드:

```python
precision = (
    len(tp) / len(predicted)
    if predicted else None
)
```

Precision이 낮으면:

```text
잘못 뽑은 관계(FP)가 많음
```

---

## 5-4. Recall

```text
찾아야 할 정답 중 실제로 찾은 비율
```

```python
recall = TP / (TP + FN)
```

코드:

```python
recall = (
    len(tp) / len(expected)
    if expected else None
)
```

Recall이 낮으면:

```text
놓친 관계(FN)가 많음
```

---

## 5-5. F1

Precision과 Recall을 함께 보는 조화평균이다.

```python
F1 = 2 × Precision × Recall
     ─────────────────────
      Precision + Recall
```

TP/FP/FN으로 직접 계산하면:

```python
F1 = 2 × TP
     ───────────────
     2×TP + FP + FN
```

코드:

```python
denominator = (
    2 * len(tp)
    + len(fp)
    + len(fn)
)

f1 = (
    2 * len(tp) / denominator
    if denominator else None
)
```

---

# 6. 평가 함수 통합

```python
def score_relations(rows, gold):
    # 고유 Triple 집합
    predicted = {
        triple_key(row)
        for row in rows
    }
    expected = {
        triple_key(row)
        for row in gold
    }

    # 집합 비교
    tp = predicted & expected
    fp = predicted - expected
    fn = expected - predicted

    # 지표
    precision = (
        len(tp) / len(predicted)
        if predicted else None
    )

    recall = (
        len(tp) / len(expected)
        if expected else None
    )

    denominator = (
        2 * len(tp)
        + len(fp)
        + len(fn)
    )

    f1 = (
        2 * len(tp) / denominator
        if denominator else None
    )

    return {
        "tp": tp,
        "fp": fp,
        "fn": fn,
        "precision": precision,
        "recall": recall,
        "f1": f1,
    }
```

### 중요한 평가 원칙

Schema나 Evidence 검사에서 실패했다고 그 행을 먼저 삭제하지 않는다.

```text
저장 관계 전체
→ Schema 검사

같은 저장 관계 전체
→ Evidence 검사

같은 저장 관계 전체의 고유 Triple
→ 고정된 Gold와 비교
```

검사 결과에 따라 Prediction이나 Gold를 줄이면 서로 다른 평가가 된다.

# 7. Chunk 설정 변경 실험

## 7-1. 비교 목적

청크가 너무 작으면 관련 문장이 서로 떨어져 LLM이 관계를 놓칠 수 있다.

교안에서는:

| 설정 | 기준 | 변경 |
|---|---:|---:|
| `chunk_size` | 500 | 2000 |
| `chunk_overlap` | 100 | 400 |
| 겹침 비율 | 20% | 20% |

```text
chunk_overlap / chunk_size = 0.2
```

두 설정 모두 20%로 맞춘다.

단, `RecursiveCharacterTextSplitter`는 문단·구분자 경계를 고려하므로  
**실제 겹치는 문자 수가 항상 정확히 설정값과 같지는 않다.**

---

## 7-2. 비교 실험의 핵심 원칙

청크 설정만 바꾸고 나머지는 유지한다.

```text
유지:
원문
Schema
Prompt
LLM
Embedding 모델
Gold

변경:
chunk_size
chunk_overlap
```

그래야 점수 변화가 청크 설정 변화와 관련 있는지 비교할 수 있다.

---

## 7-3. Chunk 변경 문법

```python

    RecursiveCharacterTextSplitter
)

    chunk_size=2000,

```

청크 확인:

```python
chunks = await splitter.run(
    text=document["text"]

for chunk in chunks.chunks:

        chunk.index,
        len(chunk.text),
        chunk.text,
    )
```

# 9. 실행 결과 다시 읽기

## 9-1. 관계 조회 핵심 구조

```cypher
MATCH
  (d:Document {execution_id: $execution_id})
  <-[:FROM_DOCUMENT]-(c:Chunk)
  <-[:FROM_CHUNK]-(s:__Entity__)

MATCH
  (s)-[r]->(o:__Entity__)
  -[:FROM_CHUNK]->(c)

RETURN
  elementId(r) AS relationship_id,
  s.name AS subject,
  head([
    x IN labels(s)
    WHERE NOT x STARTS WITH '__'
  ]) AS subject_type,
  type(r) AS relation,
  o.name AS object,
  head([
    x IN labels(o)
    WHERE NOT x STARTS WITH '__'
  ]) AS object_type,
  coalesce(r.evidence, '') AS evidence,
  d.source_doc_id AS source_doc_id,
  collect(DISTINCT c.text) AS chunk_texts
```

평가에 필요한 값을 한 번에 가져온다.

---

## 9-2. Chunk 조회

```cypher
MATCH
  (c:Chunk)-[:FROM_DOCUMENT]->
  (d:Document {execution_id: $execution_id})

RETURN
  c.index AS index,
  c.text AS text,
  size(c.embedding) AS dimensions

ORDER BY index
```

확인 항목:

```text
청크 수
청크 순서
청크 원문
Embedding 차원
```

# 12. 교안의 실제 비교 결과

## 12-1. pandas 2.0.3

| 설정 | 저장 관계 | 청크 | Schema | Evidence | P | R | F1 |

| 2000 / 400 | 5 | 1 | 100% | 100% | 1.0 | 1.0 | 1.0 |

기준 설정의 FN:

```text
Series.str.split
Series.str.rsplit
```

2000자 청크에서는 두 관계도 추출되어 FN이 0이 됐다.

단, 이 원문은 전체가 약 514자라 변경 후 청크가 하나가 됐다.  
따라서 **400자 overlap 자체의 효과를 분리해서 본 실험은 아니다.**

---

## 12-2. 의료 논문

| 설정 | 저장 관계 | 청크 | Schema | Evidence | P | R | F1 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 500 / 100 | 3 | 2 | 100% | 100% | 1.0 | 1.0 | 1.0 |
| 2000 / 400 | 3 | 1 | 100% | 66.67% | 1.0 | 1.0 | 1.0 |

여기서는 관계 자체는 모두 Gold와 일치했지만  
한 evidence 문자열이 전체 원문과 정확하게 일치하지 않아 Evidence 비율만 내려갔다.

즉:

```text
관계 평가 100%
Evidence 평가 66.67%
```

가 동시에 가능하다.

이 결과가 **관계 정확성과 인용 정확성을 따로 평가해야 하는 이유**다.

---

# 13. 결과 해석 기준

## Recall이 올라간 경우

```text
전에 놓친 FN을 새로 찾았는가?
```

실제 FN 목록을 확인한다.

---

## Precision이 내려간 경우

```text
새로운 FP가 생겼는가?
```

FP의 원문을 확인해:

```text
실제 의미 오류
vs
표기 불일치
```

를 구분한다.

---

## Evidence만 좋아진 경우

```text
인용 정확도는 개선됨
```

하지만 관계 정확도까지 좋아졌다는 뜻은 아니다.  
Gold의 Precision/Recall/F1을 별도로 본다.

---

## 한 문서에서 좋아진 경우

그 설정을 바로 최적값으로 확정하지 않는다.

교안의 원칙:

```text
설정 조정에 사용하지 않은
다른 문서 + 다른 Gold
로 다시 평가
```

즉 한 샘플의 개선이 일반적인 성능 향상을 의미하지는 않는다.

---

# 14. `SimpleKGPipeline`과 `LLMGraphTransformer`

교안 부록에서는 두 방식의 역할을 비교한다.

## SimpleKGPipeline

```text
Document
→ Chunk
→ Embedding
→ LLM 추출
→ GraphPruning
→ Neo4j 저장
```

Pipeline 자체가 여러 단계를 묶는다.

---

## LLMGraphTransformer

```text
LangChain Document
→ LLM 추출
→ GraphDocument 반환
```

`GraphDocument`는 DB가 아니라 **Python의 추출 결과 객체**다.

```text
.nodes          : 노드
.relationships  : 관계
.source         : 입력 문서
```

청크 분할, 임베딩, Neo4j 저장, Entity Resolution이 필요하면 별도로 연결한다.

---

## 핵심 문법

```python
transformer = LLMGraphTransformer(
    llm=ChatOpenAI(
        model="gpt-5.6-luna"
    ),

    allowed_nodes=[
        "Release",
        "ApiElement",
    ],

    allowed_relationships=[
        (
            "Release",
            "FIXES_API",
            "ApiElement",
        )
    ],

    node_properties=["name"],
    relationship_properties=["evidence"],

    strict_mode=True,

    additional_instructions="...",
)
```

입력:

```python
Document(
    page_content=document["text"],
    metadata={
        "source_doc_id":
            document["doc_id"]
    },
)
```

비동기 실행:

```python
graph_documents = await transformer.aconvert_to_graph_documents(
    [document]
)
```

관계 읽기:

```python
for relation in graph_documents[0].relationships:
    print(
        relation.source.id,
        relation.type,
        relation.target.id,
    )

    print(
        relation.properties.get(
            "evidence",
            "",
        )
    )
```

---

## `strict_mode=True`

허용 목록 밖 노드와 관계를 반환 전에 제외한다.

```text
허용:
Release -> FIXES_API -> ApiElement

제외:
MENTIONS
허용하지 않은 Node Type
허용하지 않은 관계 조합
```

하지만 여기서도:

```text
허용 구조를 통과함
≠
관계 의미가 정답임
```

원문 또는 Gold와 별도 검증이 필요하다.

# 15. 핵심 문법 빠른 참조

| 문법 | 역할 |
|---|---|
| `GraphSchema.model_validate(schema)` | Schema 사전 검증·변환 |
| `GraphPruning().run(...)` | Schema 밖 그래프 요소 제거 |
| `pruned.pruning_stats` | 제거 항목과 사유 확인 |
| `schema_ok()` | `(주어 타입, 관계, 목적어 타입)` 검사 |
| `evidence_ok()` | evidence가 같은 문서 원문에 있는지 검사 |
| `triple_key()` | `(subject, relation, object)` 추출 |
| `{triple_key(row) for row in rows}` | 중복 관계 제거 |
| `predicted & expected` | TP |
| `predicted - expected` | FP |
| `expected - predicted` | FN |
| `score_relations()` | P/R/F1 및 오류 목록 계산 |
| `RecursiveCharacterTextSplitter(...)` | Chunk 설정 변경 |
| `SimpleKGPipeline(...)` | 동일 조건으로 그래프 재생성 |
| `execution_id` | 실행별 결과 구분 |
| `LLMGraphTransformer(...)` | DB 저장 전 GraphDocument 추출 |
| `strict_mode=True` | 허용 타입·관계 밖 결과 제거 |

# 16. 최종 구조 암기

```text
[1] Schema 검사
허용한 구조인지 확인
        ↓
[2] Evidence 검사
인용문이 원문에 그대로 있는지 확인
        ↓
[3] Gold 비교
관계 자체가 정답인지 확인
        ↓
[4] TP / FP / FN
맞힘 · 잘못 추출 · 누락 구분
        ↓
[5] Precision / Recall / F1
관계 품질 정량화
        ↓
[6] 오류 관계 직접 확인
FP / FN / Evidence 문제 해석
        ↓
[7] 한 설정만 변경해 재실행
예: Chunk 500/100 → 2000/400
        ↓
[8] 같은 Gold로 전후 비교
설정 변화가 실제 품질에 미친 영향 확인
        ↓
[9] 다른 문서로 재검증
한 문서의 개선을 일반화하지 않음
```

### 가장 중요한 구분

```text
Pruning
= 허용하지 않은 구조 제거

Schema 준수율
= 저장된 관계가 허용 구조를 지키는지

Evidence 원문 일치율
= 인용 문자열이 원문에 존재하는지

Precision
= 추출한 것 중 정답 비율

Recall
= 전체 정답 중 찾아낸 비율

F1
= Precision과 Recall의 균형

Gold
= 원문과 포함 기준을 보고 만든 고정 정답

Exact Match
= 주어 · 관계 · 목적어 문자열이 모두 같아야 일치
```
