# 문서 → 지식 그래프 자동 생성 핵심 정리

> 기준: `교안_01_문서에서_지식그래프_자동으로_만들기.ipynb`  
> 목적: 실습 반복은 줄이고, **개념 · 핵심 문법 · 전체 처리 흐름** 중심으로 정리

---

## 0. 전체 흐름

`SimpleKGPipeline`은 문서를 입력받아 지식 그래프를 만드는 여러 작업을 연결한 파이프라인이다.

```text
원문
→ Chunk 분할
→ Embedding 생성
→ LLM 개체·관계 추출
→ Schema 기반 GraphPruning
→ Neo4j 저장
→ 관계·근거 조회 및 Snapshot 저장
→ Entity Resolution(중복 노드 통합)
```

핵심 구분:

- **Schema**: 허용할 노드 타입, 관계 타입, 속성, 연결 패턴 정의
- **Chunk**: LLM이 한 번에 읽을 원문 단위
- **Embedding**: 청크를 검색 가능한 벡터로 변환
- **LLM 추출**: 원문에서 실제 개체와 관계 추출
- **GraphPruning**: 스키마에 맞지 않는 타입·관계·패턴 제거
- **Writer**: 정제된 그래프를 Neo4j에 저장
- **ER(Entity Resolution)**: 같은 개체로 판단되는 중복 노드 통합

> 임베딩이 관계를 만드는 것이 아님.  
> `원문 + Schema → LLM 추출`이 관계를 만들고, 임베딩은 주로 이후 검색에 사용됨.

# 1. 입력 문서와 Schema

## 1-1. Schema의 역할

Schema는 **그래프에 허용할 구조를 미리 정하는 규칙**이다.

```text
Node Type      : 노드 종류
Relationship   : 관계 종류
Property       : 노드·관계에 저장할 값
Pattern        : 허용할 주어 타입 → 관계 → 목적어 타입
Constraint     : 목록 밖 타입·관계·패턴 허용 여부
```

예:

```text
Release -[:FIXES_API]-> ApiElement
Compound -[:TREATS]-> Disease
```

Schema는 크게 다음 방식으로 사용할 수 있다.

- **직접 지정**: 사람이 타입·관계·패턴을 명확하게 정의
- **FREE**: 타입·관계 이름을 미리 제한하지 않고 추출
- **자동 Schema**: LLM이 먼저 구조를 만들고 그 구조로 추출

목적이 명확한 지식 그래프라면 직접 지정 방식이 결과를 통제하기 쉽다.

---

## 1-2. Schema 기본 문법

```python
node_types = [
    {
        "label": "Release",
        "description": "Release version in the text.",
        "properties": [
            {"name": "name", "type": "STRING"}
        ],
        "additional_properties": False,
    },
    {
        "label": "ApiElement",
        "description": "API whose bug was fixed.",
        "properties": [
            {"name": "name", "type": "STRING"}
        ],
        "additional_properties": False,
    },
]

relationship_types = [
    {
        "label": "FIXES_API",
        "description": "This release fixes a bug in this API.",
        "properties": [
            {"name": "evidence", "type": "STRING"}
        ],
        "additional_properties": False,
    }
]

schema = {
    "node_types": node_types,
    "relationship_types": relationship_types,
    "patterns": [
        ("Release", "FIXES_API", "ApiElement")
    ],
    "additional_node_types": False,
    "additional_relationship_types": False,
    "additional_patterns": False,
}
```

### 주요 키

| 키 | 의미 |
|---|---|
| `label` | 노드 또는 관계 타입 이름 |
| `description` | LLM에 전달할 타입·관계의 의미와 추출 기준 |
| `properties` | 저장할 속성 |
| `patterns` | 허용할 `(주어 타입, 관계, 목적어 타입)` |
| `additional_properties=False` | 정의하지 않은 속성 차단 |
| `additional_node_types=False` | 정의하지 않은 노드 타입 차단 |
| `additional_relationship_types=False` | 정의하지 않은 관계 차단 |
| `additional_patterns=False` | 정의하지 않은 연결 조합 차단 |

`evidence`를 속성으로 허용해도 근거가 반드시 정확하게 채워지는 것은 아니다.  
실제 원문과 일치하는지는 별도 평가가 필요하다.

## 1-3. Prompt로 추출 기준 보강

Schema가 **출력 구조**를 제한한다면 Prompt는 **어떤 경우를 추출할지** 더 구체적으로 지시한다.

```python
from neo4j_graphrag.generation.prompts import ERExtractionTemplate

prompt_template = (
    ERExtractionTemplate.DEFAULT_TEMPLATE
    + """
원문이 직접 뒷받침하는 관계만 추출하세요.
이름은 원문 표기를 유지하세요.
evidence에는 관계를 뒷받침하는 연속된 원문 구절을 복사하세요.
근거를 요약하거나 외부 지식을 추가하지 마세요.
"""
)
```

`DEFAULT_TEMPLATE`에는 빌더가 사용할 기본 출력 형식과 `{text}`, `{schema}`, `{examples}` 자리가 포함된다.

# 2. Chunk 분할과 Embedding

## 2-1. Chunk

Chunk는 긴 문서를 LLM이 처리할 수 있도록 나눈 원문 조각이다.

`RecursiveCharacterTextSplitter`는 가능한 큰 문맥을 유지하면서 대략 다음 순서로 분할한다.

```text
문단 → 줄바꿈 → 공백 → 문자
```

주요 설정:

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=100,
)
```

- `chunk_size=500`: 청크 최대 문자 수
- `chunk_overlap=100`: 경계 부분의 겹침 목표
- 문자 수와 모델의 **토큰 수는 다름**
- 겹침이 커지면 문맥 연결은 좋아질 수 있지만 반복 전송량도 증가

Neo4j GraphRAG 빌더에서 사용하려면 Adapter로 감싼다.

```python
from neo4j_graphrag.experimental.components.text_splitters.langchain import (
    LangChainTextSplitterAdapter,
)

splitter = LangChainTextSplitterAdapter(text_splitter)
chunks = await splitter.run(text=document["text"])

for chunk in chunks.chunks:
    print(chunk.index, chunk.text)
```

---

## 2-2. Embedding

Embedding은 문자열을 숫자 벡터로 바꾸는 작업이다.

```python
from functools import partial
from neo4j_graphrag.embeddings import OpenAIEmbeddings

embedder = OpenAIEmbeddings(
    model="text-embedding-3-large"
)

embedder.embed_query = partial(
    embedder.embed_query,
    dimensions=768,
)

vector = embedder.embed_query(chunks.chunks[0].text)
print(len(vector))
```

여기서는 청크 하나를 **768개의 숫자**로 표현한다.

### Chunk Embedding과 LLM 추출 차이

| 작업 | 입력 → 출력 | 목적 |
|---|---|---|
| Embedding | 원문 → 숫자 벡터 | 관련 원문 검색 |
| LLM 추출 | 원문 + Schema → 노드·관계 | 지식 그래프 생성 |

# 3. `SimpleKGPipeline` 구성과 실행

## 3-1. 모델 준비

```python
from neo4j_graphrag.llm import OpenAILLM

llm = OpenAILLM(
    model_name="gpt-5.6-luna"
)
```

LLM은 개체·관계를 추출하고, Embedder는 청크 벡터를 만든다.

---

## 3-2. Pipeline 구성

```python
from copy import deepcopy
from neo4j_graphrag.experimental.pipeline.kg_builder import SimpleKGPipeline

builder = SimpleKGPipeline(
    llm=llm,
    driver=driver,
    embedder=embedder,
    schema=deepcopy(schema),
    prompt_template=prompt_template,
    text_splitter=splitter,
    from_file=False,
    on_error="RAISE",
    perform_entity_resolution=False,
)
```

### 핵심 인수

| 인수 | 역할 |
|---|---|
| `llm` | 원문에서 개체·관계 추출 |
| `driver` | Neo4j 연결 |
| `embedder` | 청크 벡터 생성 |
| `schema` | 허용할 그래프 구조 |
| `prompt_template` | 세부 추출 기준 |
| `text_splitter` | 원문 분할 방식 |
| `from_file=False` | 파일 대신 `text=`로 원문 전달 |
| `on_error="RAISE"` | 처리 실패를 오류로 드러냄 |
| `perform_entity_resolution=False` | 저장 시 자동 중복 통합을 끔 |

`deepcopy(schema)`를 사용하면 파이프라인 내부 처리 때문에 원본 Schema 객체가 변하는 것을 막을 수 있다.

### 정상 0건과 오류 구분

- **정상 0건**: 원문에 조건을 만족하는 관계 자체가 없음
- **처리 실패**: LLM 응답 처리·검증 등에 실패
- 실습에서는 `on_error="RAISE"`로 실패를 숨기지 않음

---

## 3-3. Pipeline 실행

```python
from uuid import uuid4

execution_id = str(uuid4())

result = await builder.run_async(
    text=document["text"],
    file_path=document["url"],
    document_metadata={
        "source_doc_id": document["doc_id"],
        "execution_id": execution_id,
    },
)
```

### 추적용 ID 구분

```text
source_doc_id : 어떤 원문인지 구분
execution_id  : 같은 원문을 몇 번째 실행한 결과인지 구분
```

같은 원문을 다시 처리해도 `source_doc_id`는 유지할 수 있지만 `execution_id`는 새로 만든다.  
`execution_id`는 개체의 표준 ID가 아니다.

저장 성공 여부는 Writer 상태로 확인한다.

```python
writer_status = result.result["writer"]["status"]

if writer_status != "SUCCESS":
    raise RuntimeError(result.result["writer"])
```

# 4. Schema 적용과 GraphPruning

Schema는 LLM에게 원하는 구조를 알려 주지만, **LLM 출력이 항상 Schema를 완벽하게 지킨다고 가정하지 않는다.**

파이프라인 내부에서는 저장 전에 `GraphPruning`으로 허용하지 않은 내용을 제거한다.

```text
LLM 추출 결과
    ↓
GraphPruning
    ├─ 목록 밖 Node Type 제거
    ├─ 목록 밖 Relationship 제거
    └─ 잘못된 Pattern 제거
    ↓
Neo4j 저장
```

예:

```text
허용:
Release -[:FIXES_API]-> ApiElement

제외 가능:
Release -[:MENTIONS]-> ApiElement
ApiElement -[:FIXES_API]-> Release
```

단, **Schema를 통과했다 = 의미적으로 정답**은 아니다.  
허용된 구조라도 실제 관계가 원문에서 성립하는지는 evidence와 정답 데이터로 평가해야 한다.

# 5. Neo4j에 저장되는 구조와 출처 연결

빌더는 크게 **어휘 그래프(Lexical Graph)**와 **개체 그래프(Entity Graph)**를 함께 저장한다.

| 구조 | 저장 내용 |
|---|---|
| Lexical Graph | `Document`, `Chunk`, 청크 원문·순서·Embedding |
| Entity Graph | LLM이 추출한 개체 노드와 관계 |

## 5-1. 주요 Label

```text
Document    : 원본 문서
Chunk       : 분할된 원문
__Entity__  : 추출된 모든 개체에 공통으로 붙는 관리 Label
Release     : 실제 개체 타입
ApiElement  : 실제 개체 타입
```

한 노드에는 여러 Label이 붙을 수 있다.

```text
(:Release:__Entity__)
(:ApiElement:__Entity__)
```

`__Entity__`는 별도 노드나 개체 ID가 아니라 **추출 개체를 공통으로 찾기 위한 Label**이다.

---

## 5-2. 출처 연결

```text
Entity -[:FROM_CHUNK]-> Chunk
Chunk  -[:FROM_DOCUMENT]-> Document
Chunk  -[:NEXT_CHUNK]-> 다음 Chunk
```

즉 그래프의 개체에서 원문까지 역으로 추적할 수 있다.

```text
개체
→ 추출된 Chunk
→ 원본 Document
```

기본 이름은 `LexicalGraphConfig()`로 확인할 수 있다.

```python
from neo4j_graphrag.experimental.components.types import LexicalGraphConfig

config = LexicalGraphConfig()

config.document_node_label
config.chunk_node_label
config.node_to_chunk_relationship_type
config.chunk_to_document_relationship_type
config.next_chunk_relationship_type
```

# 6. Cypher로 관계와 Chunk 조회

## 6-1. 공통 실행 함수

```python
def run_cypher(query, **params):
    with driver.session() as session:
        return [
            record.data()
            for record in session.run(query, **params)
        ]
```

`RETURN ... AS 이름`에서 지정한 별칭이 Python 딕셔너리의 Key가 된다.

---

## 6-2. 현재 실행의 관계 조회

핵심 패턴:

```cypher
MATCH
  (d:Document {execution_id: $execution_id})
  <-[:FROM_DOCUMENT]-(c:Chunk)
  <-[:FROM_CHUNK]-(s:__Entity__)

MATCH
  (s)-[r]->(o:__Entity__)-[:FROM_CHUNK]->(c)

RETURN
  s.name AS subject,
  type(r) AS relation,
  o.name AS object,
  coalesce(r.evidence, '') AS evidence,
  d.source_doc_id AS source_doc_id
```

주요 문법:

- `type(r)`: 관계 타입 반환
- `labels(n)`: 노드의 Label 목록 반환
- `elementId(r)`: DB 내부 관계 식별자
- `coalesce(a, b)`: `a`가 없으면 `b` 사용
- `collect(DISTINCT x)`: 중복 없이 여러 값을 목록으로 수집
- `$execution_id`: Python에서 전달하는 Cypher Parameter

실습에서는 관리용 Label인 `__Entity__`를 제외하고 실제 타입을 찾기 위해 다음 형태도 사용한다.

```cypher
head([
  x IN labels(s)
  WHERE NOT x STARTS WITH '__'
]) AS subject_type
```

---

## 6-3. Chunk 조회

```cypher
MATCH
  (c:Chunk)-[:FROM_DOCUMENT]->
  (d:Document {execution_id: $execution_id})

RETURN
  c.index AS index,
  c.text AS text,
  size(c.embedding) AS dimensions

ORDER BY index
```

이를 통해 저장된 청크의 순서, 원문, Embedding 차원을 확인한다.

# 7. Snapshot 저장

평가를 위해 **원문 + 설정 + 추출 결과 + 당시 Chunk**를 한 JSON에 저장한다.

```python
snapshot = {
    "stage": "중복 노드 통합 전",
    "execution_id": execution_id,
    "document": document,
    "chunk_size": 500,
    "chunk_overlap": 100,
    "text_splitter": "RecursiveCharacterTextSplitter",
    "model": "gpt-5.6-luna",
    "embedding_model": "text-embedding-3-large",
    "dimensions": 768,
    "schema": schema,
    "prompt_template": prompt_template,
    "perform_entity_resolution": False,
    "rows": relation_rows,
    "chunks": stored_chunks,
}
```

Snapshot을 남기는 이유:

```text
같은 원문이라도
모델 / Prompt / Schema / Chunk 설정 / 실행 시점
에 따라 결과가 달라질 수 있음
```

따라서 평가나 비교 실험을 하려면 **어떤 설정으로 나온 결과인지 함께 저장**해야 한다.

# 8. Entity Resolution: 중복 노드 통합

## 8-1. 개념

ER(Entity Resolution)은 같은 개체의 여러 기록을 하나로 통합하는 작업이다.

이 교안에서는:

```python
SinglePropertyExactMatchResolver
```

를 사용하며, **같은 Label + 같은 `name`**을 가진 노드를 통합한다.

```text
(:ApiElement {name: "read_csv"})
(:ApiElement {name: "read_csv"})
                ↓
대표 노드 하나
```

이는 의미 기반 동일 개체 판별이 아니라 **정확 일치 기반 통합**이다.

---

## 8-2. 현재 실행만 통합

다른 실행의 노드까지 합치지 않도록 `filter_query`로 범위를 제한한다.

```python
from uuid import UUID
from neo4j_graphrag.experimental.components.resolver import (
    SinglePropertyExactMatchResolver,
)

async def merge_this_execution(execution_id):
    checked_id = str(UUID(execution_id))

    filter_query = f"""
    WHERE EXISTS {{
        MATCH
          (entity)-[:FROM_CHUNK]->
          (:Chunk)-[:FROM_DOCUMENT]->
          (d:Document)

        WHERE d.execution_id = '{checked_id}'
    }}
    """

    resolver = SinglePropertyExactMatchResolver(
        driver=driver,
        filter_query=filter_query,
    )

    return await resolver.run()
```

실행:

```python
resolution = await merge_this_execution(execution_id)

print(resolution.number_of_nodes_to_resolve)
print(resolution.number_of_created_nodes or 0)
```

---

## 8-3. 정확 일치 ER의 한계

| 경우 | 결과 |
|---|---|
| 같은 Label + 같은 이름 | 통합 |
| `read_csv` / `pandas.read_csv` | 이름이 달라 통합하지 않음 |
| 같은 이름의 서로 다른 개체 | 잘못 통합할 가능성 있음 |

즉 별칭·동명이름 문제는 별도 동일 개체 판별 과정이 필요하다.

```text
후보 검색
→ 원문·속성 비교
→ 동일 개체 판정
→ 표준 ID 연결
→ 통합
```

---

## 8-4. ER 전에 평가 결과를 저장하는 이유

노드를 통합하면 관계도 대표 노드에 맞춰 합쳐질 수 있다.

특히:

```text
시작 노드 + 끝 노드 + 관계 타입
```

이 모두 같아진 관계는 하나로 통합될 수 있다.

이때 관계별 `evidence`가 서로 다르면 **모든 근거를 보존하지 않고 하나만 남을 수 있다.**

따라서 교안에서는:

```text
1. 추출·저장
2. 관계와 evidence 조회
3. Snapshot 저장
4. 이후 ER 수행
```

순서로 진행한다.

**품질 평가는 ER 이전 Snapshot을 사용한다.**

# 9. 공통 준비 문법

## JSON 읽기·저장

```python
import json
from pathlib import Path

def read_json(path):
    return json.loads(
        path.read_text(encoding="utf-8")
    )

def save_json(path, value):
    path.write_text(
        json.dumps(
            value,
            ensure_ascii=False,
            indent=2,
        ),
        encoding="utf-8",
    )
```

- `encoding="utf-8"`: 한글 포함 파일을 UTF-8로 처리
- `ensure_ascii=False`: 한글을 `\uXXXX` 형태가 아닌 문자 그대로 저장
- `indent=2`: JSON 들여쓰기

# 11. 최종 구조 암기

```text
[1] Schema
허용할 Node / Relationship / Property / Pattern 정의
        ↓
[2] Chunk
긴 원문을 LLM 처리 단위로 분할
        ↓
[3] Embedding
Chunk를 검색용 벡터로 저장
        ↓
[4] LLM Extraction
원문 + Schema + Prompt로 개체·관계 추출
        ↓
[5] GraphPruning
Schema 밖 타입·관계·패턴 제거
        ↓
[6] Neo4j Writer
Entity Graph + Lexical Graph 저장
        ↓
[7] Provenance / Snapshot
관계 → Chunk → Document 근거 추적 및 결과 보존
        ↓
[8] Entity Resolution
같은 Label + name의 중복 노드 통합
```

### 가장 중요한 구분

```text
Schema       = 무엇을 허용할지 정의
Prompt       = 어떻게 판단할지 지시
Chunk        = LLM이 읽는 원문 단위
Embedding    = 검색용 벡터
LLM          = 개체·관계 추출
Pruning      = Schema 위반 제거
Snapshot     = 평가용 실행 결과 보존
ER           = 중복 개체 통합
```
