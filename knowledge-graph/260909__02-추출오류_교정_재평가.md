# 추출 오류 교정과 재평가 — 압축 정리

## 1. 전체 교정 흐름

```text
품질 지표 확인
   ↓
기각 행 · FP · FN 조사
   ↓
원문 + 스키마 + 골드 기준 대조
   ↓
오류 원인 구분
   ↓
검토한 항목만 교정
   ↓
같은 문서 · 골드 · 평가 기준으로 전체 재평가
   ↓
점수 변화 + 새 오류 + 사라진 정답 확인
   ↓
채택 / 보류 결정
```

핵심은 **점수가 낮다는 사실보다 왜 낮아졌는지를 먼저 찾는 것**이다.

또한 최종 `FN`은 두 경우가 모두 포함된다.

```text
① 처음부터 올바른 관계를 추출하지 못함
② 올바르게 추출했지만 타입·evidence·후처리 검사에서 제거됨
```

---

## 2. 오류 원인 구분

| 구분 | 확인할 것 | 대표 교정 |
|---|---|---|
| **타입 오류** | 관계의 주어·목적어 타입이 스키마와 맞는가 | 잘못된 타입 필드 수정 |
| **인용 오류** | `evidence`가 원문과 문자열 그대로 일치하는가 | 원문 구절 그대로 인용 |
| **의미 오류(FP)** | 원문이 실제로 해당 관계를 말하는가 | 관계 판정 조건 보완 |
| **누락(FN)** | 처음부터 누락됐는가, 후처리에서 제거됐는가 | 추출 단계와 기각 기록 추적 |
| **표기 차이** | 의미는 같지만 이름 문자열이 다른가 | 평가 후 원인으로 따로 기록 |
| **후처리 손실** | 필터가 오답뿐 아니라 정답도 제거했는가 | 제거된 TP 확인 |

> `FP`, `FN`은 **골드와 비교한 결과**이지 오류 원인의 이름은 아니다.

---

## 3. 원문으로 오류를 확인하는 대표 사례

### 타입 오류

```text
추출:
diphenhydramine
    -[PALLIATES]->
transient insomnia

추출 object_type : Symptom
스키마 요구 타입 : Disease
```

원문과 현재 데이터 모델의 분류 규칙을 대조한 뒤 해당 행의 `object_type`만 `Disease`로 교정한다.

다른 기각 항목까지 일괄 변경하면 안 된다.

### evidence 오류

```text
추출 evidence 끝 : progression.
원문 실제 표기    : progression;
```

의미는 같아 보여도 현재 검사가 **문자열 완전일치**이므로 `False`가 된다.

따라서 이 경우는 관계 자체보다 `evidence` 필드를 교정한다.

### 의미 오류 — FP

```text
(Laquinimod, TREATS, multiple sclerosis)
```

원문의 표현은 Laquinimod가 치료한다고 확정한 것이 아니라 치료제로 **연구되었다(`investigated as`)**는 내용이다.

교안의 골드 기준에서는 가능성·연구 대상 표현만으로 관계를 정답으로 넣지 않으므로 FP가 된다.

즉:

```text
evidence 존재
+ 타입 정상
≠ 관계 의미까지 정답
```

---

## 4. FN이 생긴 단계를 추적하기

의약품 예시에서는 `현기`와 `발진`이 최종 골드에는 있지만 최종 추출에는 없다.

### 현기

```text
골드             : 존재
초기 추출 후보    : 존재
evidence 검사     : 실패
최종 결과         : 제거됨
```

주어·관계·목적어는 맞았지만 `evidence`의 공백이 원문과 달라 행 전체가 제거됐다.

→ **후처리로 생긴 FN**

### 발진

```text
골드             : 존재
최종 결과         : 없음
기각 기록         : 없음
```

제공된 저장 기록만 보면 초기 추출 단계에서 빠진 사례로 구분한다.

→ 서로 같은 FN이어도 원인은 다를 수 있다.

---

## 5. 논리적 모순은 바로 삭제하지 않기

같은 주어·목적어에 반대 관계가 있으면 **모순 후보**로 찾는다.

```text
약물A -[UPREGULATES_CG]→ 유전자X
약물A -[DOWNREGULATES_CG]→ 유전자X
```

하지만 다음 조건이 다르면 둘 다 맞을 수 있다.

```text
세포 종류
실험 조건
용량
시간
출처
```

따라서 처리 순서는 다음과 같다.

```text
반대 관계 발견
→ 출처·조건·시점 확인
→ 실제 모순 / 조건 차이 / 판단 보류
```

자동 검사는 **후보 탐색**까지만 담당한다.

---

## 6. 교정할 때 지켜야 할 원칙

수정 전후를 비교하려면 **같은 시험으로 다시 채점**해야 한다.

### 고정할 조건

```text
같은 문서
같은 골드
같은 허용 관계
같은 완전일치 기준
같은 검사 순서
```

### 한 번에 하나만 수정

교안에서는 같은 원본을 복사한 뒤 두 실험을 분리한다.

```text
실험 A : object_type 한 필드만 수정
실험 B : evidence 한 필드만 수정
```

그래야 어떤 변경이 지표를 바꿨는지 알 수 있다.

변경 기록도 남긴다.

```python
{
    "source_doc_id": "...",
    "triple": [...],
    "field": "object_type",
    "before": "Symptom",
    "after": "Disease",
    "method": "원문 대조 후 사람 교정"
}
```

> 저장된 한 행을 사람이 고친 결과는 **모델 성능 개선**이 아니다.

프롬프트 개선 효과를 말하려면 수정된 프롬프트로 **다시 추출 → 같은 기준으로 재평가**해야 한다.

---

## 7. 같은 평가 함수로 전체 재평가

평가 단위는 고유한 트리플 키다.

```python
(subject, relation, object)
```

```text
TP = 추출 ∩ 골드
FP = 추출 - 골드
FN = 골드 - 추출
```

교안의 평가 순서:

```text
원래 추출 행
   ↓
평가 범위 문서만 선택
   ↓
스키마 검사
   ↓
고유 트리플로 중복 제거
   ↓
골드와 완전일치 비교
   ↓
Precision / Recall / F1
```

`evidence` 검사까지 통과한 최종 후보는 별도로 다시 평가한다.

---

## 8. 실제 한 항목 교정 결과

| 지표 | 교정 전 | 타입 1건 교정 | evidence 1건 교정 |
|---|---:|---:|---:|
| 스키마 통과 | 65 / 80 | 66 / 80 | 65 / 80 |
| 근거 원문 일치 | 45 / 65 | 46 / 66 | 46 / 65 |
| TP | 58 | 59 | 58 |
| FP | 5 | 5 | 5 |
| FN | 10 | 9 | 10 |
| Precision | 0.9206 | 0.9219 | 0.9206 |
| Recall | 0.8529 | 0.8676 | 0.8529 |
| F1 | 0.8855 | 0.8939 | 0.8855 |

### 타입 교정

기각됐던 정답 관계가 스키마를 통과한다.

```text
TP +1
FN -1
F1 상승
```

### evidence 교정

주어·관계·목적어는 바뀌지 않으므로 **스키마 통과 추출 전체**의 TP·FP·FN은 그대로다.

하지만 evidence 검사까지 적용한 최종 사용 후보에서는:

```text
교정 전 : TP 41 / FN 27
교정 후 : TP 42 / FN 26
```

즉, 어느 **평가 단계의 결과를 보고 있는지** 구분해야 한다.

---

## 9. 기존 추출 버전 비교

예시를 추가하기 전과 후의 저장 결과를 같은 골드로 비교한 결과:

| 지표 | 기존 | 예시 추가 | 변화 |
|---|---:|---:|---:|
| 스키마 준수율 | 1.0000 | 0.8125 | -0.1875 |
| 근거 원문 일치율 | 0.4048 | 0.6923 | +0.2875 |
| TP | 31 | 58 | +27 |
| FP | 11 | 5 | -6 |
| FN | 37 | 10 | -27 |
| Precision | 0.7381 | 0.9206 | +0.1825 |
| Recall | 0.4559 | 0.8529 | +0.3971 |
| F1 | 0.5636 | 0.8855 | +0.3219 |

F1은 크게 올랐지만 스키마 준수율은 **100% → 81.25%, 18.75%p 하락**했다.

따라서:

> 한 지표가 좋아졌다고 모든 품질이 함께 좋아진 것은 아니다.

또한 이 비교의 Few-shot 예시는 평가 자료의 개체·관계와 겹친다.  
따라서 실제 일반화 성능은 **예시에 쓰지 않은 별도 문서**에서 확인해야 한다.

## 10. 후처리는 FP와 TP를 함께 제거할 수 있다

의약품 `HAS_SIDE_EFFECT` 비교:

```text
후처리 전 후보          : 48
evidence 검사 통과      : 47
근거·절 검사 최종 통과 : 42
골드                    : 44
```

평가 결과:

```text
검사 전 : TP 41 / FP 7 / FN 3
검사 후 : TP 40 / FP 2 / FN 4
```

후처리로 FP 5개를 없앴지만 **정답 1개도 함께 제거**했다.

```text
Precision ↑
F1 ↑
Recall ↓
```

따라서 필터의 성능은 F1만 보고 판단하지 않는다.

## 11. 총점 외에 관계 집합 변화 확인

전체 TP가 증가해도 기존 정답을 잃었을 수 있다.

반드시 네 종류를 따로 본다.

```text
새 정답       = 새 TP 중 기존에 없던 것
새 오답       = 새 FP 중 기존에 없던 것
사라진 정답   = 기존 TP 중 새 결과에서 없어진 것
없어진 오답   = 기존 FP 중 새 결과에서 없어진 것
```

예시 추가 버전에서는:

```text
새 정답       27건
새 오답        0건
사라진 정답    0건
없어진 오답    6건
```

즉, 점수뿐 아니라 **무엇을 새로 얻고 무엇을 잃었는지** 확인해야 한다.

## 12. 채택 판단

이번 교안의 개발 후보 결정 규칙:

```text
F1 상승
+ Recall 상승
+ 기존 정답 손실 0건
→ 다음 개발 실험 후보
```

실습에서는 예시 추가 버전을 다음 개발 후보로 선택한다.

하지만 이것은 곧바로 운영 적용한다는 뜻은 아니다.

남은 확인:

```text
타입 위반 개선
남은 FP / FN 원문 검토
평가 예시와 겹치지 않는 새 문서 평가
```

보고서에는 다음을 같이 남긴다.

```text
점수
평가 범위와 기준
오류의 원문 근거
변경 내용
사라진 정답
채택·보류 이유
다음 실험
```

## 13. 문맥 처리 확장

상호참조가 있는 문장은 입력 방법에 따라 비교할 수 있다.

예:

```text
앞 문장 : diphenhydramine, doxylamine, hydroxyzine ...
목표 문장 : These agents ...
```

세 조건을 같은 모델·골드·평가 함수로 비교한다.

```text
1. 목표 문장만 입력
2. 앞 문장을 문맥으로 추가
3. These agents를 실제 개체명으로 치환
```

중요한 점:

- 평가할 **목표 문장과 관계 범위**는 고정
- 문맥에만 있는 다른 관계는 범위 밖 출력으로 기록
- 한 번의 실행 결과로 특정 방식이 항상 더 좋다고 결론 내리지 않음

이 실험은 선택 실습이며 실제 실행하지 않았다면 점수도 **미실행**으로 기록한다.

## 14. AI 기반 검토는 최종 판정이 아님

모델에게 다음을 줄 수 있다.

```text
후보 트리플
원문
골드 판정 기준
```

모델은 다음과 같은 **검토 의견**을 낼 수 있다.

```text
지지됨
지지되지 않음
판단 보류
```

하지만 처리 흐름은:

```text
AI 의견
   ↓
사람이 원문 + 고정된 골드 기준 확인
   ↓
최종 판정
```

AI가 지지한다고 해도 골드에 자동 추가하지 않는다.

골드를 수정했다면:

```text
골드 버전 갱신
→ 이전 추출과 새 추출을 모두 새 골드로 재평가
```

## 15. 최종 정리

```text
지표가 낮다
   ↓
기각 행 · FP · FN으로 이동
   ↓
원문과 규칙으로 실제 원인 확인
   ↓
한 원인만 수정
   ↓
평가 조건을 고정해 전체 재평가
   ↓
Precision / Recall / F1 확인
   ↓
새 FP와 사라진 TP까지 확인
   ↓
채택 / 보류 + 다음 실험 기록
```

### 반드시 구분할 것

- **최종 FN ≠ 처음부터 추출 못한 관계**
- **FP / FN ≠ 오류 원인 이름**
- **반대 관계 ≠ 즉시 모순**
- **한 행 수동 교정 ≠ 모델 개선**
- **F1 상승 ≠ 기존 정답 손실 없음**
- **후처리 개선 ≠ 모든 지표 상승**
- **AI 검토 의견 ≠ 사람의 최종 판정**
- **미실행 프롬프트 제안 ≠ 검증된 개선**

결국 오류 교정은 **점수를 올리는 작업이 아니라, 원인을 추적하고 같은 조건에서 개선 효과와 손실을 함께 검증하는 과정**이다.
