# Neo4j GDS 커뮤니티 탐지 정리

> 기준: `교안_01_커뮤니티_탐지(1).ipynb`
>
> 핵심 데이터: 아시아 공항 노선망 `Airport -[:ROUTE]-> Airport`

---

## 0. 전체 흐름

커뮤니티 탐지는 **그래프에서 서로 촘촘하게 연결된 묶음**을 찾는 작업.

```text
원본 Neo4j 그래프
        ↓
GDS용 무방향 투영
        ↓
Leiden으로 커뮤니티 탐지
        ↓
묶음 수 · 묶음 크기 확인
        ↓
국가 정보와 비교
교차표 → 순도 → NMI
        ↓
Louvain · Label Propagation과 비교
        ↓
재현성 확인
randomSeed · concurrency
        ↓
gamma로 묶음 세분화
        ↓
막대그래프 · 위치 산점도 · 메타그래프
```

핵심은 **커뮤니티 번호 자체가 아니라 각 묶음의 구성과 크기**를 읽는 것.

# 1. 데이터와 무방향 투영

## 1-1. 데이터 규모 먼저 확인

분석 전 노드와 관계 규모를 먼저 확인.

```python
size_rows = run_cypher('''
    MATCH (a:Airport)
    RETURN count(a) AS airports,
           count(DISTINCT a.country) AS countries,
           COUNT { ()-[:ROUTE]->() } AS routes
''')

print(size_rows[0])
```

**결과**

```text
{'airports': 767, 'countries': 47, 'routes': 8045}
```

노선 8,045개는 **방향별 관계 수**.

```text
인천 → 도쿄
도쿄 → 인천
```

왕복 노선이면 관계가 2개 존재.

실제 공항 쌍으로 세면:

```text
전체 방향 관계      8,045
공항 쌍             4,070
왕복 쌍             3,975
한 방향만 있는 쌍      95
```

고립된 공항은 없음.

```text
노선이 하나도 없는 공항: 0곳
```

---

## 1-2. 왜 `UNDIRECTED`로 투영하는가

커뮤니티 탐지에서 보고 싶은 것은 보통:

```text
누가 누구에게 갔는가     X
누구와 누구가 연결됐는가 O
```

따라서 방향보다 **연결 자체**가 중요.

```text
원본
A → B
B → A

커뮤니티 분석
A ─ B
```

### 무방향 투영

```python
run_cypher("CALL gds.graph.drop('air', false) YIELD graphName")

stats = run_cypher('''
    CALL gds.graph.project(
        'air',
        'Airport',
        {
            ROUTE: {
                orientation: 'UNDIRECTED',
                properties: ['km', 'hours', 'airlines']
            }
        }
    )
    YIELD graphName, nodeCount, relationshipCount
    RETURN graphName, nodeCount, relationshipCount
''')

print(stats[0])
```

**결과**

```text
{'graphName': 'air', 'nodeCount': 767, 'relationshipCount': 16090}
```

`8,045 × 2 = 16,090`.

`UNDIRECTED` 투영에서는 관계를 양쪽 방향에서 사용할 수 있도록 저장하므로 관계 수가 늘어나는 것이 정상.

## 1-3. 차수와 상대 공항 수는 다름

같은 공항과 왕복 노선이 있으면 관계는 2개지만 상대 공항은 1곳.

```text
A → B
A ← B

관계 수     = 2
상대 공항 수 = 1
```

### 직접 비교

```python
spread = run_cypher('''
    MATCH (a:Airport)
    OPTIONAL MATCH (a)--(x:Airport)
    WITH a,
         COUNT { (a)--() } AS rels,
         count(DISTINCT x) AS partners
    RETURN percentileCont(rels, 0.5) AS median_rels,
           percentileCont(partners, 0.5) AS median_partners
''')

print(spread[0])
```

**결과**

```text
{'median_rels': 6, 'median_partners': 4}
```

허브 공항에서는 차이가 더 커짐.

| 공항 | 도시 | 관계 수 | 서로 다른 상대 공항 |
|---|---|---:|---:|
| PEK | Beijing | 313 | 157 |
| CAN | Guangzhou | 255 | 128 |
| PVG | Shanghai | 237 | 120 |
| CTU | Chengdu | 202 | 101 |
| SIN | Singapore | 196 | 98 |

> 원본 노트북의 `gds.graph.list()` 실행 출력에는 `degreeDistribution.p50 = 18`이 남아 있지만, 바로 뒤 설명에는 `p50 = 6`으로 적혀 있어 서로 불일치함. 이 정리에서는 해석이 명확한 직접 Cypher 비교값 `median_rels=6`, `median_partners=4`를 기준으로 사용.

# 2. Leiden으로 커뮤니티 탐지

## 2-1. `stream`: 결과만 받아 보기

기본 문법:

```cypher
CALL gds.leiden.stream('투영이름')
YIELD nodeId, communityId
```

- `nodeId`: GDS 내부 노드 번호
- `gds.util.asNode(nodeId)`: 실제 Neo4j 노드로 변환
- `communityId`: 같은 묶음에 같은 번호 부여
- 번호 자체에는 의미 없음

### 실행

```python
comm_rows = run_cypher('''
    CALL gds.leiden.stream('air')
    YIELD nodeId, communityId
    RETURN gds.util.asNode(nodeId).iata AS iata,
           gds.util.asNode(nodeId).city AS city,
           gds.util.asNode(nodeId).country AS country,
           gds.util.asNode(nodeId).lat AS lat,
           gds.util.asNode(nodeId).lon AS lon,
           communityId AS community
''')

community = pd.DataFrame(comm_rows)
print('찾은 묶음 수:', community['community'].nunique())
```

**실행 예시**

```text
찾은 묶음 수: 8
```

커뮤니티 알고리즘은 실행마다 결과가 조금 달라질 수 있음.
따라서 `8개` 자체를 정답처럼 외우지 않음.

---

## 2-2. 묶음 수보다 크기 분포 먼저 확인

```python
sizes = community['community'].value_counts()

print('묶음 수:', len(sizes))
print('크기(큰 순서):', sorted(sizes, reverse=True))
```

**실행 예시**

```text
묶음 수: 8
크기(큰 순서): [179, 137, 101, 94, 76, 75, 70, 35]
```

묶음 수만 보면 놓치는 것:

```text
7개가 균등하게 나뉨
vs
7개지만 하나가 전체의 90% 차지
```

둘은 전혀 다른 결과.

따라서 최소 확인값:

```text
묶음 수
가장 큰 묶음 크기
가장 작은 묶음 크기
전체 크기 분포
```

## 2-3. `write`: 결과를 Neo4j에 저장

`stream`은 결과를 반환만 함.
일반 Cypher에서 다시 조회하려면 `write` 사용.

```python
written = run_cypher('''
    CALL gds.leiden.write(
        'air',
        { writeProperty: 'community' }
    )
    YIELD communityCount, nodePropertiesWritten, modularity
    RETURN communityCount,
           nodePropertiesWritten,
           round(modularity, 4) AS modularity
''')

print(written[0])
```

**실행 예시**

```text
{
  'communityCount': 7,
  'nodePropertiesWritten': 767,
  'modularity': 0.5557
}
```

이후 일반 Cypher 사용 가능.

```python
saved = run_cypher('''
    MATCH (a:Airport)
    WHERE a.community IS NOT NULL
    RETURN a.community AS community,
           count(*) AS airports
    ORDER BY airports DESC
    LIMIT 5
''')
```

**결과 예시**

```text
[
 {'community': 7, 'airports': 207},
 {'community': 1, 'airports': 179},
 {'community': 6, 'airports': 101},
 {'community': 5, 'airports': 94},
 {'community': 0, 'airports': 77}
]
```

`stream`과 `write`는 **서로 다른 알고리즘 실행**.
따라서 같은 노트북 안에서도 묶음 수와 구성은 달라질 수 있음.

---

## 2-4. GDS 실행 모드 구분

| 모드 | 결과 저장 위치 | 사용 상황 |
|---|---|---|
| `stream` | 저장 안 함 | 결과 행을 바로 받아 분석 |
| `stats` | 저장 안 함 | 모듈러리티·묶음 수 같은 요약만 필요 |
| `mutate` | GDS 투영 내부 | 결과를 다음 GDS 알고리즘에 이어 사용 |
| `write` | Neo4j DB 노드 속성 | 이후 일반 Cypher로 조회 |

```text
결과를 보기만 함        → stream
숫자 요약만 필요        → stats
GDS 안에서 이어서 사용   → mutate
DB에 남겨 일반 조회      → write
```

# 3. 찾은 커뮤니티가 실제 의미가 있는지 검증

커뮤니티 탐지는 정답 없이도 항상 어떤 묶음을 만듦.
따라서 **결과가 의미 있는지는 별도 검증** 필요.

이 데이터는 공항마다 `country`가 있으므로:

```text
알고리즘이 찾은 커뮤니티
        vs
실제 국가·지역
```

비교 가능.

검증 순서:

```text
교차표
  ↓
순도
  ↓
NMI
```

---

## 3-1. 교차표

```python
cross = pd.crosstab(
    community['community'],
    community['country']
)
```

일부 실행 결과:

| 커뮤니티 | China | India | Japan | Indonesia | Russia | Iran | Philippines |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 166 | 0 | 0 | 0 | 0 | 0 | 0 |
| 14 | 1 | 0 | 0 | 0 | 46 | 0 | 0 |
| 2 | 0 | 59 | 0 | 0 | 0 | 0 | 0 |
| 3 | 0 | 7 | 0 | 0 | 1 | 38 | 0 |
| 4 | 0 | 1 | 0 | 57 | 0 | 0 | 0 |
| 29 | 0 | 0 | 61 | 0 | 1 | 0 | 0 |
| 16 | 0 | 0 | 0 | 0 | 0 | 0 | 35 |

읽는 법:

```text
한 행에 큰 값 하나만 존재
→ 한 국가 중심의 커뮤니티

한 행에 여러 국가가 크게 존재
→ 여러 국가가 같은 권역처럼 연결됨
```

---

## 3-2. 순도(Purity)

한 커뮤니티 안에서 **가장 많은 국가가 차지하는 비율**.

```text
순도 = 해당 묶음에서 가장 많은 국가의 공항 수 / 묶음 전체 공항 수
```

```python
profile = pd.DataFrame({
    'airports': cross.sum(axis=1),
    'top_country': cross.idxmax(axis=1),
    'from_top': cross.max(axis=1),
})

profile['purity'] = (
    profile['from_top'] / profile['airports']
).round(3)
```

**실행 예시**

| 커뮤니티 | 공항 수 | 대표 국가 | 대표 국가 공항 수 | 순도 |
|---:|---:|---|---:|---:|
| 16 | 35 | Philippines | 35 | 1.000 |
| 1 | 179 | China | 166 | 0.927 |
| 2 | 70 | India | 59 | 0.843 |
| 29 | 75 | Japan | 61 | 0.813 |
| 4 | 94 | Indonesia | 57 | 0.606 |
| 14 | 101 | Russia | 46 | 0.455 |
| 17 | 76 | Thailand | 31 | 0.408 |
| 3 | 137 | Iran | 38 | 0.277 |

순도가 낮다고 바로 실패는 아님.

예: 순도 0.277인 묶음은 여러 나라가 섞여 있음.

```text
Iran                 38
Saudi Arabia         24
Pakistan             19
Yemen                 9
United Arab Emirates  8
Bangladesh            8
```

이 경우 알고리즘이 국경 대신 **실제 항공 연결 권역**을 찾은 것으로 해석 가능.

---

## 3-3. NMI로 전체 분할을 한 숫자로 비교

```python
from sklearn.metrics import normalized_mutual_info_score

nmi = normalized_mutual_info_score(
    community['country'],
    community['community']
)

print(f'묶음 대 국가·지역 NMI: {nmi:.4f}')
```

**이 노트북 저장 실행 결과**

```text
묶음 대 국가·지역 NMI: 0.7693
```

원본 교안에서는 여러 실행을 종합해 약 `0.675 ~ 0.767`, 보통 `0.738 안팎`으로 설명.

NMI 해석:

| 값 | 의미 |
|---:|---|
| `1.0` | 두 분할이 사실상 동일 |
| `0.7 ~ 0.9` | 대체로 비슷하고 일부 차이 |
| `0.4 ~ 0.6` | 일부 구조만 겹침 |
| `0.0` | 거의 관계 없음 |

커뮤니티 번호가 달라도 상관없음.
NMI는 번호 자체가 아니라 **같은 노드들이 같이 묶였는지**를 비교.

### 핵심 해석

```text
국가·지역: 47개
Leiden 커뮤니티: 대체로 5~8개
```

즉 알고리즘이 찾은 것은 국가보다 큰 **항공 권역**에 가까움.

# 4. Leiden · Louvain · Label Propagation 비교

## 4-1. 같은 기준으로 비교

| 알고리즘 | 특징 |
|---|---|
| Leiden | Louvain 개선 계열. 내부 연결 품질을 보완. `gamma` 사용 가능 |
| Louvain | 오래 쓰인 모듈러리티 기반 방식 |
| Label Propagation | 이웃 라벨 다수결. 빠르지만 큰 묶음으로 쏠릴 수 있음 |

비교할 최소 지표:

```text
묶음 수
가장 큰 묶음 크기
모듈러리티
NMI
```

### 노트북 실행 예시

| 알고리즘 | 묶음 수 | 최대 묶음 | 모듈러리티 | NMI |
|---|---:|---:|---:|---:|
| Leiden | 6 | 207 | 0.554 | 0.6933 |
| Louvain | 9 | 179 | 0.556 | 0.7745 |
| Label Propagation | 7 | 420 | 0.402 | 0.4878 |

여기서 중요한 부분은 단순 순위가 아님.

```text
Label Propagation 최대 묶음 = 420 / 767
```

한 묶음에 지나치게 몰림.
묶음 수만 보면 이런 문제를 놓침.

---

## 4-2. 모듈러리티

모듈러리티는 대략:

```text
같은 묶음 안의 관계가
무작위 연결보다 얼마나 더 많은가
```

를 측정.

커뮤니티 정답 라벨이 없어도 사용 가능.

```text
NMI         → 외부 정답이 있을 때 비교
모듈러리티 → 그래프 구조 자체로 평가
```

---

## 4-3. Leiden을 기본 기준으로 두는 이유

원본 실습에서는 각 커뮤니티의 내부 부분 그래프가 끊겼는지 직접 검사.

**결과**

```text
community_leiden   속이 끊긴 묶음 0개
community_louvain  속이 끊긴 묶음 0개
```

이 데이터에서는 둘 다 0개였음.
다만 교안의 핵심은:

```text
이번 실행에서 문제가 없었음
≠
알고리즘 차이가 없음
```

Leiden은 Louvain의 커뮤니티 연결성 문제를 개선한 방식이고, `gamma`를 이용한 해상도 조절도 가능하므로 기본 알고리즘으로 사용.

# 5. 관계 가중치 반영

기본 Leiden은 관계가 있는지만 사용.

```text
A ─ B
```

하지만 관계 속성 `airlines`를 넣으면:

```text
항공사 1개 노선  <  항공사 10개 노선
```

처럼 더 강한 연결로 취급 가능.

```python
plain = run_cypher('''
    CALL gds.leiden.stats(
        'air',
        { randomSeed: 42, concurrency: 1 }
    )
    YIELD modularity, communityCount
    RETURN round(modularity, 4) AS modularity,
           communityCount
''')[0]

weighted = run_cypher('''
    CALL gds.leiden.stats(
        'air',
        {
            relationshipWeightProperty: 'airlines',
            randomSeed: 42,
            concurrency: 1
        }
    )
    YIELD modularity, communityCount
    RETURN round(modularity, 4) AS modularity,
           communityCount
''')[0]
```

**결과**

```text
가중치 없이  : {'modularity': 0.5556, 'communityCount': 7}
airlines 실어: {'modularity': 0.5276, 'communityCount': 6}
```

가중치를 넣었다고 점수가 반드시 오르는 것은 아님.
가중치를 넣으면 **무엇을 강한 연결로 볼지 정의 자체가 바뀜**.

### 매우 중요한 구분

`relationshipWeightProperty`라는 이름이 같아도 알고리즘마다 의미가 다름.

```text
커뮤니티 탐지
값이 클수록 강한 연결

최단 경로
값이 클수록 큰 비용·거리
```

따라서 `km` 같은 거리를 커뮤니티 가중치로 그대로 넣으면 의미가 뒤집힐 수 있음.

# 6. 실행마다 결과가 흔들리는 문제

## 6-1. 여러 번 실행해 폭 확인

```python
runs = []

for _ in range(5):
    rows = run_cypher('''
        CALL gds.leiden.stream('air')
        YIELD nodeId, communityId
        RETURN gds.util.asNode(nodeId).country AS country,
               communityId AS community
    ''')

    one = pd.DataFrame(rows)

    runs.append({
        'communities': one['community'].nunique(),
        'biggest': int(one['community'].value_counts().max()),
        'nmi': round(normalized_mutual_info_score(
            one['country'], one['community']
        ), 4)
    })
```

**실행 예시**

| 실행 | 묶음 수 | 최대 묶음 | NMI |
|---:|---:|---:|---:|
| 1 | 7 | 207 | 0.7324 |
| 2 | 7 | 207 | 0.7348 |
| 3 | 8 | 179 | 0.7623 |
| 4 | 7 | 178 | 0.7329 |
| 5 | 8 | 179 | 0.7674 |

핵심:

```text
묶음 수가 비슷하다
≠
같은 분할이다
```

실제로 흔들리는 것은 **어떤 공항이 어느 묶음에 들어가는가**.

---

## 6-2. `randomSeed`만으로는 부족할 수 있음

```cypher
CALL gds.leiden.stream(
    'air',
    { randomSeed: 42 }
)
```

노트북 실행에서는 일부 NMI가 달라짐.

```text
7 / 207 / 0.7348
7 / 207 / 0.7348
7 / 207 / 0.7396
```

병렬 처리 순서가 달라질 수 있기 때문.

### 재현이 필요할 때

```cypher
CALL gds.leiden.stream(
    'air',
    {
        randomSeed: 42,
        concurrency: 1
    }
)
```

**결과 예시**

```text
7 / 177 / 0.745
7 / 177 / 0.745
7 / 177 / 0.745
```

정리:

```text
randomSeed     → 무작위 시작 조건 고정
concurrency: 1 → 병렬 처리 순서 영향 최소화
```

단, 데이터를 다시 적재하거나 투영을 새로 만들면서 내부 노드 순서가 바뀌면 결과가 달라질 수 있음.

따라서 재현성은:

```text
같은 데이터
+ 같은 적재
+ 같은 투영
+ 같은 알고리즘 설정
```

까지 함께 봐야 함.

# 7. `gamma`: 커뮤니티를 더 잘게 또는 크게

Leiden의 해상도 설정.

```text
gamma ↑ → 더 잘게 분할
gamma ↓ → 더 크게 통합
```

기본값은 `1.0`.

### 여러 값을 한 번에 비교

```python
sweep = []

for gamma in [0.5, 1.0, 1.5, 2.0, 2.5, 3.0]:
    rows = run_cypher('''
        CALL gds.leiden.stream(
            'air',
            {
                gamma: $gamma,
                randomSeed: 42,
                concurrency: 1
            }
        )
        YIELD nodeId, communityId
        RETURN gds.util.asNode(nodeId).country AS country,
               communityId AS community
    ''', gamma=gamma)

    one = pd.DataFrame(rows)
    counts = one['community'].value_counts()

    sweep.append({
        'gamma': gamma,
        'communities': len(counts),
        'biggest': int(counts.max()),
        'nmi': round(normalized_mutual_info_score(
            one['country'], one['community']
        ), 4)
    })
```

**노트북 실행 결과**

| gamma | 묶음 수 | 최대 묶음 | NMI |
|---:|---:|---:|---:|
| 0.5 | 6 | 331 | 0.6145 |
| 1.0 | 7 | 177 | 0.7450 |
| 1.5 | 9 | 167 | 0.7451 |
| 2.0 | 15 | 98 | 0.7843 |
| 2.5 | 22 | 93 | 0.8082 |
| 3.0 | 30 | 86 | 0.7903 |

이 실행에서는 `gamma=2.5`의 NMI가 가장 높음.

하지만 가장 높은 NMI가 항상 가장 좋은 설정은 아님.

```text
권역을 찾고 싶음 → 너무 잘게 쪼개면 의미 감소
국가 단위에 가깝게 나누고 싶음 → 높은 gamma가 유리할 수 있음
```

즉 `gamma`는 정답 맞히기용 숫자가 아니라 **분석 해상도 조절값**.

# 9. 응용: 커뮤니티 한 줄 요약 함수

원본 마지막 과제를 실제 사용 형태로 완성한 예시.

```python
from collections import Counter


def describe_community(community_id):
    community_id = int(community_id)

    rows = run_cypher('''
        MATCH (a:Airport)
        WHERE a.community = $community_id
        RETURN a.iata AS iata,
               a.country AS country,
               COUNT { (a)--() } AS degree
        ORDER BY degree DESC, iata
    ''', community_id=community_id)

    if not rows:
        return None

    # 가장 많이 등장한 국가·지역
    top_country = Counter(
        row['country'] for row in rows
    ).most_common(1)[0][0]

    # ORDER BY degree DESC 이므로 첫 공항이 허브
    hub = rows[0]['iata']

    return {
        'community': community_id,
        'airports': len(rows),
        'top_country': top_country,
        'hub': hub,
    }
```

가장 큰 묶음과 작은 묶음에 적용:

```python
largest_id = sizes_now.idxmax()
smallest_id = sizes_now.idxmin()

print(describe_community(largest_id))
print(describe_community(smallest_id))
```

**결과 형태**

```text
{
  'community': <묶음번호>,
  'airports': <공항수>,
  'top_country': '<대표 국가>',
  'hub': '<차수가 가장 큰 공항 IATA>'
}
```

커뮤니티 ID와 구성은 실행마다 달라질 수 있으므로 정리본에서 임의의 실제 값을 만들지는 않음.

# 11. 최종 치트시트

| 하고 싶은 일 | 핵심 코드 |
|---|---|
| GDS 무방향 투영 | `orientation: 'UNDIRECTED'` |
| Leiden 결과 받기 | `gds.leiden.stream()` |
| 결과 DB 저장 | `gds.leiden.write()` |
| 요약값만 받기 | `gds.leiden.stats()` |
| 투영 안에 결과 저장 | `gds.leiden.mutate()` |
| 커뮤니티 번호 | `communityId` |
| 노드 변환 | `gds.util.asNode(nodeId)` |
| 묶음 크기 | `value_counts()` |
| 교차표 | `pd.crosstab()` |
| 한 묶음의 순도 | `최대 국가 수 / 묶음 전체 수` |
| 전체 정답 일치도 | `normalized_mutual_info_score()` |
| 구조 자체 평가 | `gds.modularity.stats()` |
| 관계 가중치 | `relationshipWeightProperty` |
| Leiden 재현 | `randomSeed` + `concurrency: 1` |
| 묶음 세분화 | `gamma ↑` |
| 묶음 통합 | `gamma ↓` |

## 핵심 판단 순서

```text
1. 그래프 규모 확인
2. 분석 목적에 맞게 방향성 결정
3. Leiden 실행
4. 묶음 수보다 크기 분포 확인
5. 정답 라벨이 있으면 교차표·순도·NMI 확인
6. 알고리즘 비교 시 모듈러리티와 최대 묶음도 함께 확인
7. 결과가 흔들리는지 반복 실행
8. 필요하면 randomSeed + concurrency로 고정
9. gamma를 바꾸며 목적에 맞는 해상도 탐색
10. 큰 그래프는 먼저 줄인 뒤 시각화
```
