# Cypher 인덱스 · 제약조건 · 추천 랭킹 핵심 정리

> 원본 노트북을 **문법과 실사용 패턴 중심으로 압축**한 정리.  
> 반복 실습·퀴즈는 줄이고, 이후 Neo4j 조회·적재·추천에 계속 쓰이는 문법과 주의점은 유지함.

이번 실습의 흐름:

```text
조회 성능
INDEX + PROFILE / EXPLAIN
        ↓
데이터 무결성
CONSTRAINT
        ↓
추천·랭킹
공유 노드 집계 + 정렬 + 비율
```

---

# 1. 인덱스: 조회와 적재를 빠르게 만들기

인덱스는 답을 바꾸는 기능이 아니라 **노드를 찾는 방법을 바꾸는 기능**.

```cypher
CREATE INDEX gene_name IF NOT EXISTS
FOR (g:Gene)
ON (g.name)
```

인덱스 생성이 끝날 때까지 기다리기:

```cypher
CALL db.awaitIndexes()
```

확인:

```cypher
SHOW INDEXES
YIELD name, type, labelsOrTypes, properties
WHERE name = 'gene_name'
RETURN name, type, labelsOrTypes, properties
```

삭제:

```cypher
DROP INDEX gene_name IF EXISTS
```

## 실행계획 확인: `EXPLAIN` · `PROFILE`

```cypher
EXPLAIN
MATCH (g:Gene {name: 'ALB'})
RETURN g.id
```

```cypher
PROFILE
MATCH (g:Gene {name: 'ALB'})
RETURN g.id
```

| 문법 | 의미 |
|---|---|
| `EXPLAIN` | 쿼리를 실행하지 않고 **실행계획만** 확인 |
| `PROFILE` | 실제 실행하면서 **실행계획 + 비용** 확인 |
| `dbHits` | 저장소를 조회한 횟수 |

대표 실행 연산자:

```text
NodeByLabelScan
→ 특정 레이블의 노드를 전부 훑음

AllNodesScan
→ 전체 그래프 노드를 훑음

NodeIndexSeek
→ 인덱스로 원하는 값을 바로 찾음
```

원본 실습에서는 같은 `Gene.name='ALB'` 조회가:

```text
인덱스 전 : NodeByLabelScan / dbHits 26,228
인덱스 후 : NodeIndexSeek  / dbHits 3
```

처럼 바뀜.

---

## 인덱스를 쓰려면 레이블이 중요

인덱스는 **레이블 + 속성**에 걸림.

```cypher
CREATE INDEX gene_name
FOR (g:Gene)
ON (g.name)
```

따라서:

```cypher
MATCH (g:Gene {name: 'ALB'})
RETURN g
```

는 `Gene.name` 인덱스를 사용할 수 있지만,

```cypher
MATCH (g {name: 'ALB'})
RETURN g
```

처럼 레이블을 빼면 해당 인덱스를 사용할 수 없음.

원본 실습:

```text
레이블 있음 → NodeIndexSeek / dbHits 3
레이블 없음 → AllNodesScan  / dbHits 31,082
```

핵심:

```text
레이블 = 단순한 설명이 아니라 검색 범위
```

---

## 적재에서도 레이블이 중요

대량 관계 적재 예:

```cypher
UNWIND $rows AS row

MATCH (a:Compound {id: row.s}),
      (b:Disease {id: row.t})

MERGE (a)-[:TREATS]->(b)
```

양 끝 노드의 레이블을 알고 있다면 반드시 적는 편이 중요.

```cypher
// 비효율적인 형태
MATCH (a {id: row.s}),
      (b {id: row.t})
```

레이블이 빠지면 `id` 인덱스를 활용하지 못하고 각 행마다 그래프를 훑게 됨.

원본의 200개 관계 실측에서는 레이블을 뺀 적재가 약 **3,034배 많은 dbHits**를 사용함.

```text
조회가 느리다
또는
적재가 느리다

→ 조건 속성에 인덱스가 있는가?
→ MATCH에 레이블을 적었는가?
```

---

## 속성을 함수로 감싸면 인덱스를 못 쓰는 경우

다음처럼 저장된 속성 자체를 비교하면 인덱스를 사용할 수 있음.

```cypher
MATCH (g:Gene)
WHERE g.name = 'ALB'
RETURN g.id
```

하지만:

```cypher
MATCH (g:Gene)
WHERE toLower(g.name) = 'alb'
RETURN g.id
```

처럼 비교 전에 속성을 함수로 변형하면 기존 `g.name` 인덱스를 사용하지 못함.

원본 실습에서는:

```text
g.name 직접 비교      → dbHits 3
toLower(g.name) 비교 → dbHits 26,228
```

대소문자를 무시한 검색이 자주 필요하다면 파생 속성을 따로 저장하고 인덱스를 거는 방식 사용.

```cypher
MATCH (g:Gene)
SET g.name_lower = toLower(g.name)
```

```cypher
CREATE INDEX gene_name_lower IF NOT EXISTS
FOR (g:Gene)
ON (g.name_lower)
```

핵심:

```text
인덱스는 저장된 속성값에 걸림
→ 조건의 속성을 함수로 감싸면 인덱스 사용이 어려워질 수 있음
```

---

## RANGE 인덱스와 TEXT 인덱스

기본 `CREATE INDEX`는 RANGE 인덱스.

```cypher
CREATE INDEX gene_name IF NOT EXISTS
FOR (g:Gene)
ON (g.name)
```

부분 문자열 검색용 TEXT 인덱스:

```cypher
CREATE TEXT INDEX gene_name_text IF NOT EXISTS
FOR (g:Gene)
ON (g.name)
```

원본 실습의 핵심 구분:

| 조건 | RANGE | TEXT 추가 시 |
|---|---|---|
| `=` | 인덱스로 바로 탐색 | 가능 |
| `STARTS WITH` | RANGE로 효율적 탐색 | 가능 |
| `ENDS WITH` | RANGE에서는 전체 인덱스 스캔 | TEXT 사용 가능 |
| `CONTAINS` | RANGE에서는 전체 인덱스 스캔 | TEXT 사용 가능 |

예:

```cypher
MATCH (c:Compound)
WHERE c.name CONTAINS 'statin'
RETURN c.name
```

부분일치가 중요한 검색이라면:

```cypher
CREATE TEXT INDEX compound_name_text IF NOT EXISTS
FOR (c:Compound)
ON (c.name)
```

---

## 관계 속성에도 인덱스 가능

노드가 아니라 관계의 속성을 조건으로 자주 조회하는 경우:

```cypher
CREATE INDEX ordered_price IF NOT EXISTS
FOR ()-[r:ORDERED]-()
ON (r.price)
```

기본 형태:

```cypher
CREATE INDEX 이름 IF NOT EXISTS
FOR ()-[r:관계타입]-()
ON (r.속성)
```

# 2. 제약조건: 중복을 막고 키를 보호하기

인덱스는 **빠르게 찾게 하는 기능**.  
제약조건은 **잘못된 데이터를 들어오지 못하게 하는 규칙**.

## UNIQUE 제약

```cypher
CREATE CONSTRAINT compound_id IF NOT EXISTS
FOR (c:Compound)
REQUIRE c.id IS UNIQUE
```

확인:

```cypher
SHOW CONSTRAINTS
YIELD name, type, labelsOrTypes, properties
RETURN name, type, labelsOrTypes, properties
ORDER BY name
```

삭제:

```cypher
DROP CONSTRAINT compound_id IF EXISTS
```

이미 같은 값이 존재하는 상태에서 UNIQUE 제약을 만들면 **제약 생성 자체가 실패**함.

---

## UNIQUE 제약은 인덱스를 함께 만듦

제약이 만든 인덱스 확인:

```cypher
SHOW INDEXES
YIELD name, type, owningConstraint
WHERE owningConstraint IS NOT NULL
RETURN name, type, owningConstraint
```

즉 유일해야 하는 키라면:

```text
인덱스만 생성
```

보다

```text
UNIQUE 제약 생성
→ 중복 방지
→ 인덱스도 함께 사용
```

이 구조가 적합.

---

## 키는 표시용 이름보다 고유 `id`

다음처럼 이름이 겹치는 데이터가 존재할 수 있음.

```text
Compound          {name:'Cholecalciferol'}
PharmacologicClass{name:'Cholecalciferol'}
```

이때:

```cypher
MERGE (n {name: row.name})
```

처럼 **레이블도 없고 이름만 키로 사용**하면 서로 다른 개체가 하나의 노드로 합쳐질 수 있음.

적재에서는 보통:

```cypher
MERGE (n:Compound {id: row.id})
SET n.name = row.name
```

처럼:

```text
레이블 + 유일한 id
```

를 식별 기준으로 사용.

핵심:

```text
name → 사람이 읽는 표시값
id   → 개체를 구분하는 키
```

---

## 제약 종류

원본 노트북에서 구분한 네 종류:

| 종류 | 의미 |
|---|---|
| 유일성 `UNIQUE` | 값이 중복되지 않아야 함 |
| 존재 `IS NOT NULL` | 속성이 반드시 있어야 함 |
| 키 `NODE KEY` | 존재 + 유일성 |
| 타입 | 지정한 자료형이어야 함 |

예:

```cypher
// 유일성
CREATE CONSTRAINT symptom_unique IF NOT EXISTS
FOR (s:Symptom)
REQUIRE s.name IS UNIQUE
```

```cypher
// 존재
CREATE CONSTRAINT symptom_exists IF NOT EXISTS
FOR (s:Symptom)
REQUIRE s.name IS NOT NULL
```

```cypher
// 키
CREATE CONSTRAINT symptom_key IF NOT EXISTS
FOR (s:Symptom)
REQUIRE (s.name) IS NODE KEY
```

```cypher
// 타입
CREATE CONSTRAINT symptom_type IF NOT EXISTS
FOR (s:Symptom)
REQUIRE s.name IS :: STRING
```

지원되는 제약 종류는 **Neo4j 판(edition)과 환경에 따라 다를 수 있으므로 실제 환경에서 확인**.

---

## 제약 위반은 필요한 예외만 잡기

Python에서 UNIQUE 제약 위반 확인:

```python
from neo4j.exceptions import ConstraintError

try:
    run_cypher("""
        CREATE (:Compound {
            id: 'Compound::DB00682',
            name: '중복 시도'
        })
    """)

except ConstraintError:
    print("제약이 중복 생성을 막음")
```

가능하면:

```python
except Exception:
```

처럼 모든 예외를 한꺼번에 잡지 않음.

오타·접속 오류까지 제약 성공으로 착각할 수 있음.

# 3. 추천 랭킹: 공유 노드를 점수로 만들기

그래프 추천의 기본 형태:

```text
기준
 ↓
가운데 노드
 ↑
후보

→ 기준과 후보가 공유하는 가운데 노드 수를 점수로 사용
```

기본 문법:

```cypher
MATCH (기준)-[:관계]->(가운데)<-[:관계]-(후보)

WHERE 후보 <> 기준

RETURN 후보.name AS 이름,
       count(DISTINCT 가운데) AS 점수

ORDER BY 점수 DESC, 이름
LIMIT 5
```

핵심 네 가지:

```text
1. 가운데 노드를 센다
2. 자기 자신을 제외한다
3. DISTINCT로 중복 경로를 제거한다
4. 동점용 보조 정렬키를 둔다
```

---

## 예: 같은 유전자를 공유하는 유사 약물

```cypher
MATCH
(c:Compound {name: $drug})
-[:BINDS]->
(g:Gene)
<-[:BINDS]-
(other:Compound)

WHERE other <> c

RETURN other.name AS 약물,
       count(DISTINCT g) AS 공유표적수

ORDER BY 공유표적수 DESC, 약물
LIMIT 5
```

여기서:

```text
가운데 = Gene
점수   = 공유 Gene 수
```

`WHERE other <> c`가 없으면 자기 자신이 가장 높은 점수를 받기 쉬움.

`count(g)` 대신 `count(DISTINCT g)`를 쓰는 이유:

```text
같은 노드로 가는 경로가 여러 개 존재할 수 있음
→ 같은 Gene을 여러 번 세는 것 방지
```

---

## 가운데 노드가 추천의 의미를 결정

유전자 공유:

```text
Drug → Gene ← Drug
→ 표적이 비슷한 약
```

증상 공유:

```text
Disease → Symptom ← Disease
→ 증상이 비슷한 질병
```

즉:

```text
무엇을 가운데에 두는가
=
무엇을 비슷하다고 정의하는가
```

추천 점수는 숫자만 만드는 것이 아니라 **그 숫자가 무엇을 세는지 설명할 수 있어야 함**.

---

## 바뀌는 값은 파라미터로

문자열 조립:

```python
"... {name: '" + disease_name + "'} ..."
```

보다 파라미터 사용.

```python
def rank_drugs(disease_name, top=3):
    return run_cypher(
        """
        MATCH
        (c:Compound)-[:TREATS]->
        (d:Disease {name: $disease})

        MATCH
        (c)-[:BINDS]->
        (g:Gene)
        <-[:ASSOCIATES]-
        (d)

        RETURN c.name AS 약물,
               count(DISTINCT g) AS 공유유전자수

        ORDER BY 공유유전자수 DESC, 약물
        LIMIT $top
        """,
        disease=disease_name,
        top=top,
    )
```

장점:

```text
쿼리 구조 재사용
값에 따옴표가 있어도 안전하게 전달
문자열 직접 연결 방지
실행계획 재사용에 유리
```

---

## 그룹마다 상위 N개

`LIMIT`은 **전체 결과**에서 자름.

```cypher
ORDER BY 점수 DESC
LIMIT 3
```

분류마다 3개씩 필요하면:

```cypher
MATCH
(p:PharmacologicClass)
-[:INCLUDES]->
(c:Compound)
-[:BINDS]->
(g:Gene)

WITH p,
     c,
     count(DISTINCT g) AS 표적수

// collect하기 전에 정렬
ORDER BY 표적수 DESC, c.name

WITH p,
     count(c) AS 약물수,
     collect(c.name)[0..3] AS 대표약물

RETURN p.name AS 약효분류,
       약물수,
       대표약물
```

차이:

```text
LIMIT 3
→ 전체 결과에서 3개

collect(...)[0..3]
→ 그룹별 리스트에서 3개
```

중요:

```text
ORDER BY
   ↓
collect()
```

순서로 작성.

`collect()`한 뒤 `ORDER BY`해도 이미 만들어진 **리스트 내부 순서**는 정렬되지 않음.

## 원점수와 비율 점수

공유 노드 개수만 사용:

```text
공유표적수
```

는 연결이 원래 많은 후보에게 유리할 수 있음.

비율:

```cypher
round(
    toFloat(공유표적수) / 전체표적수,
    3
) AS 겹침비율
```

기본 흐름:

```cypher
MATCH
(c:Compound {name: $drug})
-[:BINDS]->
(g:Gene)
<-[:BINDS]-
(other:Compound)

WHERE other <> c

WITH other,
     count(DISTINCT g) AS 공유표적수

MATCH (other)-[:BINDS]->(t:Gene)

WITH other,
     공유표적수,
     count(DISTINCT t) AS 전체표적수

RETURN other.name AS 약물,
       공유표적수,
       전체표적수,
       round(
           toFloat(공유표적수) / 전체표적수,
           3
       ) AS 겹침비율

ORDER BY 겹침비율 DESC,
         공유표적수 DESC,
         약물
```

원본 노트북의 구분:

| 점수 | 의미 | 치우침 |
|---|---|---|
| 공유 개수 | 얼마나 많이 겹치는가 | 연결이 많은 후보에게 유리 |
| 공유 / 전체 | 후보의 연결 중 얼마나 많이 겹치는가 | 연결이 적은 후보가 높은 비율을 받기 쉬움 |

따라서 비율만 사용하는 것도 항상 정답은 아님.

---

## 비율 점수 + 최소 크기 조건

표적이 몇 개 없는 후보는 우연히 전부 겹치면 비율이 쉽게 `1.0`이 될 수 있음.

집계 후 최소 크기 조건 추가:

```cypher
WITH other,
     공유표적수,
     count(DISTINCT t) AS 전체표적수

WHERE 전체표적수 >= $최소표적
```

전체:

```text
공유 개수 계산
   ↓
후보의 전체 크기 계산
   ↓
WITH
   ↓
최소 크기 조건
   ↓
비율 계산
   ↓
정렬
```

`전체표적수`는 집계 후 생기는 값이므로:

```cypher
WITH ...
WHERE 전체표적수 >= ...
```

위치에 둠.

# 종합 패턴: 추천 리포트

공유 유전자가 없는 치료약도 유지하려면 `OPTIONAL MATCH`.

```cypher
MATCH
(c:Compound)-[:TREATS]->
(d:Disease {name: $disease})

OPTIONAL MATCH
(c)-[:BINDS]->
(g:Gene)
<-[:ASSOCIATES]-
(d)

WITH c,
     count(DISTINCT g) AS 공유유전자수

OPTIONAL MATCH
(p:PharmacologicClass)
-[:INCLUDES]->
(c)

RETURN c.name AS 약물,
       공유유전자수,
       collect(p.name) AS 약효분류

ORDER BY 공유유전자수 DESC, 약물
LIMIT $top
```

구조:

```text
Disease
  ↑ TREATS
Compound
  │
  ├─ BINDS → Gene ← ASSOCIATES ─ Disease
  │             ↑
  │         공유 개수 = 점수
  │
  └─ INCLUDES ← PharmacologicClass
```

# 최종 문법 치트시트

| 하고 싶은 일 | 핵심 문법 |
|---|---|
| 노드 속성 인덱스 | `CREATE INDEX ... FOR (n:Label) ON (n.prop)` |
| TEXT 인덱스 | `CREATE TEXT INDEX ...` |
| 관계 속성 인덱스 | `FOR ()-[r:REL]-() ON (r.prop)` |
| 인덱스 생성 대기 | `CALL db.awaitIndexes()` |
| 인덱스 확인 | `SHOW INDEXES` |
| 계획만 보기 | `EXPLAIN 쿼리` |
| 실제 비용 측정 | `PROFILE 쿼리` |
| 중복 방지 | `CREATE CONSTRAINT ... IS UNIQUE` |
| 제약 확인 | `SHOW CONSTRAINTS` |
| 안전한 키 | `레이블 + id` |
| 공유 기반 추천 | `(a)-[:R]->(x)<-[:R]-(b)` |
| 자기 자신 제외 | `WHERE other <> 기준` |
| 공유 노드 점수 | `count(DISTINCT x)` |
| 바뀌는 값 전달 | `$파라미터` |
| 전체 상위 N | `ORDER BY ... LIMIT N` |
| 그룹별 상위 N | `ORDER BY ...` → `collect(...)[0..N]` |
| 비율 점수 | `toFloat(공유) / 전체` |
| 집계 결과 필터 | `WITH ... WHERE ...` |

## 핵심 판단 순서

```text
[성능]
조건 속성에 인덱스가 있는가?
→ MATCH에 레이블을 적었는가?
→ 속성을 함수로 감싸지 않았는가?
→ 검색 방식에 맞는 인덱스 종류인가?

[무결성]
이 값이 실제 고유 키인가?
→ 이름이 아니라 id인가?
→ 고유해야 한다면 UNIQUE 제약을 걸었는가?

[추천]
무엇을 공유하면 비슷하다고 볼 것인가?
→ 가운데 노드 선택
→ count(DISTINCT 가운데)
→ 자기 자신 제외
→ 보조 정렬키 추가
→ 필요하면 원점수를 비율로 변환
→ 비율이면 최소 크기 조건 검토
```
