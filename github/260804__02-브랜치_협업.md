# Git 브랜치와 GitHub 협업

## 1. 브랜치와 병합

### 브랜치란

브랜치(branch)는 기존 작업과 분리된 **평행 작업 공간**.

`main`을 그대로 유지하면서 새로운 기능, 버그 수정, 문서 작업 등을 독립적으로 진행할 수 있음.

```text
main ────────────────
       \
        feature 작업 ── 커밋 ── 커밋
```

브랜치에서 만든 커밋은 다른 브랜치에 바로 반영되지 않음.  
`git switch`로 브랜치를 이동하면 작업 폴더의 파일도 해당 브랜치 시점으로 바뀜.

### 브랜치 기본 명령어

```bash
# 브랜치 목록 확인
# * 표시가 현재 브랜치
git branch

# 새 브랜치를 만들면서 이동
git switch -c feature/greeting

# 기존 브랜치로 이동
git switch main
```

| 명령어 | 의미 |
|---|---|
| `git branch` | 브랜치 목록 확인 |
| `git switch -c 이름` | 새 브랜치를 만들면서 이동 |
| `git switch 이름` | 이미 존재하는 브랜치로 이동 |

### 브랜치 이름 규칙

브랜치 이름은 보통 `종류/작업-내용` 형태로 작성.

| 예시 | 의미 |
|---|---|
| `feature/login-form` | 로그인 화면 추가 |
| `fix/signup-error` | 회원가입 오류 수정 |
| `docs/readme` | README 문서 수정 |
| `feature/minsu-chart` | 담당자와 작업 내용을 함께 표시 |

이름만 봐도 어떤 작업인지 알 수 있도록 작성하는 것이 목적.

---

### 브랜치에서 작업하기

```bash
# 1. 작업 브랜치 생성
git switch -c feature/greeting

# 2. 파일 수정 후 변경 저장
git add app.py
git commit -m "feat: 인사말 함수 추가"

# 3. main으로 이동
git switch main
```

`feature/greeting`에서 만든 커밋은 아직 `main`에 없음.  
`main`에 반영하려면 병합이 필요.

### 브랜치 병합

병합할 때는 먼저 **변경을 받을 브랜치**로 이동.

```bash
# feature/greeting의 작업을 main에 합침
git switch main
git merge feature/greeting
```

```text
git merge 합칠-브랜치
```

현재 브랜치가 변경을 받는 쪽이고, 명령어 뒤의 브랜치가 들어오는 쪽.

#### 병합 방식

| 방식 | 발생 조건 | 결과 |
|---|---|---|
| Fast-forward | 브랜치가 갈라진 뒤 `main`에 새 커밋이 없음 | `main`의 위치만 작업 브랜치 끝으로 이동 |
| Merge commit | 양쪽 브랜치에 모두 새 커밋이 있음 | 두 작업을 합친 병합 커밋 생성 |

병합 흐름 확인:

```bash
git log --oneline --graph
```

### 병합한 브랜치 삭제

```bash
# 병합이 끝난 브랜치를 안전하게 삭제
git branch -d feature/greeting
```

- `-d`: 병합되지 않은 브랜치 삭제를 거부
- `-D`: 병합 여부와 상관없이 강제 삭제

```bash
git branch -D 브랜치이름
```

`-D`는 아직 합치지 않은 커밋도 잃을 수 있으므로 주의.

## 2. 병합 충돌 해결

### 충돌이란

두 브랜치가 같은 파일의 같은 부분을 서로 다르게 수정하면 Git이 자동으로 선택하지 못함.  
이 상태를 **병합 충돌(merge conflict)**이라고 함.

```bash
git status
```

`git status`로 충돌 중인 파일과 현재 상태 확인.

### VS Code의 충돌 선택지

| 선택지 | 의미 |
|---|---|
| 현재 변경 사항 수락 | 현재 체크아웃한 브랜치의 내용 유지 |
| 수신 변경 사항 수락 | 병합해 들어오는 브랜치의 내용 유지 |
| 두 변경 사항 모두 수락 | 양쪽 내용을 모두 남김 |
| 변경 사항 비교 | 두 내용을 비교한 뒤 직접 수정 |

`현재 변경`과 `수신 변경`은 항상 `main`과 작업 브랜치로 고정되는 것이 아님.

예를 들어 작업 브랜치에서 `git merge main`을 실행했다면:

```text
현재 변경 = 작업 브랜치
수신 변경 = main
```

### 충돌 해결 순서

```bash
# 1. 충돌 파일을 직접 수정

# 2. 해결한 파일을 스테이징
git add 충돌파일

# 3. 병합 완료 커밋
git commit

# 4. 상태 확인
git status
```

`git add`는 “이 파일의 충돌을 해결했다”는 표시.  
모든 충돌을 해결한 뒤 `git commit`하면 병합 완료.

### 병합 취소

충돌 해결이 꼬였거나 병합을 처음부터 다시 하고 싶을 때:

```bash
git merge --abort
```

병합 명령을 실행하기 전 상태로 되돌림.

## 3. GitHub 협업과 Pull Request

### Pull Request란

Pull Request(PR)는 작업 브랜치를 `main`에 바로 합치지 않고, 팀원에게 **검토와 병합을 요청하는 절차**.

```text
작업 브랜치
→ GitHub에 push
→ Pull Request 생성
→ 코드 리뷰
→ 승인
→ main에 merge
```

### 팀원 초대

GitHub 저장소에서 진행.

```text
Settings
→ Collaborators
→ Add people
→ GitHub 아이디 또는 이메일 검색
→ 권한 설정 후 초대
```

팀원이 메일이나 GitHub 알림에서 초대를 수락하면 협업 가능.

---

### 작업자가 PR 만드는 과정

먼저 최신 `main`에서 새 브랜치를 시작.

```bash
# 1. main 최신화
git switch main
git pull

# 2. 작업 브랜치 생성
git switch -c feature/dashboard

# 3. 파일 수정 후 커밋
git add .
git commit -m "feat: 대시보드 화면 추가"

# 4. 처음 한 번 원격 브랜치 생성
git push -u origin feature/dashboard
```

`-u`는 로컬 브랜치와 GitHub의 원격 브랜치를 연결하는 옵션.  
처음 연결한 뒤부터는 다음 명령만 사용 가능.

```bash
git push
```

GitHub에서:

```text
Compare & pull request
→ 제목과 설명 작성
→ Create pull request
```

### 리뷰와 병합

리뷰어는 PR의 `Files changed` 탭에서 변경 내용을 확인.

- 초록색 `+`: 추가된 줄
- 빨간색 `-`: 삭제된 줄
- `Submit review → Approve`: 변경 승인
- `No conflicts`: 자동 병합 가능
- `Merge pull request → Confirm merge`: `main`에 병합

병합 후 GitHub의 `Delete branch` 버튼으로 원격 작업 브랜치 삭제.

---

### PR에서 충돌이 발생한 경우

`main`을 직접 수정하지 않고, **내 작업 브랜치 안에서 최신 main을 병합하고 충돌을 해결**.

```bash
# 1. 최신 main 받기
git switch main
git pull

# 2. 작업 브랜치로 이동
git switch feature/dashboard

# 3. 작업 브랜치에 main 병합
git merge main

# 4. VS Code에서 충돌 해결 후
git add .
git commit

# 5. 수정된 작업 브랜치 push
git push
```

같은 브랜치에 다시 push하면 기존 PR이 자동으로 갱신됨.

---

### PR 병합 후 로컬 정리

GitHub에서 병합해도 내 컴퓨터의 `main`은 자동으로 바뀌지 않음.

```bash
# 1. main으로 이동
git switch main

# 2. GitHub에서 병합된 최신 main 받기
git pull

# 3. 로컬 작업 브랜치 삭제
git branch -d feature/dashboard
```

정리 대상:

| 위치 | 삭제 방법 |
|---|---|
| GitHub 원격 브랜치 | PR 병합 후 `Delete branch` |
| 내 컴퓨터의 로컬 브랜치 | `git branch -d 브랜치이름` |

## 4. GitHub Flow

GitHub Flow는 `main`을 안정적으로 유지하면서 브랜치와 PR로 작업하는 협업 방식.

```text
main 최신화
→ 작업 브랜치 생성
→ 수정·커밋
→ GitHub에 push
→ Pull Request
→ 리뷰·승인
→ merge
→ 브랜치 정리
```

### 핵심 원칙

- `main`은 항상 실행 가능한 상태로 유지
- `main`에 직접 커밋하지 않음
- 모든 변경은 작업 브랜치에서 진행
- 작업 브랜치는 PR과 리뷰를 거쳐 병합
- 병합이 끝난 브랜치는 로컬과 원격에서 삭제

### 하루 작업 흐름

```bash
# 시작: main 최신화
git switch main
git pull

# 작업: 새 브랜치에서 수정
git switch -c feature/작업명
git add .
git commit -m "feat: 작업 내용"

# 공유: GitHub에 push 후 PR 생성
git push -u origin feature/작업명

# 마무리: GitHub에서 merge 후 로컬 정리
git switch main
git pull
git branch -d feature/작업명
```

## 5. 팀 작업 규칙

| 구분 | 권장 규칙 | 이유 |
|---|---|---|
| `main` | 직접 커밋 금지 | 항상 정상 작동하는 상태 유지 |
| 브랜치 | `feature/기능`, `fix/오류` 형식 | 작업 내용을 쉽게 구분 |
| 커밋 | 무엇을 바꿨는지 한 줄로 작성 | 변경 이력을 빠르게 파악 |
| 커밋 종류 | `feat:`, `fix:`, `docs:` 등 사용 | 변경 성격 구분 |
| 커밋 길이 | 50자 이내, 끝에 마침표 생략 | GitHub 목록에서 읽기 쉬움 |
| PR 크기 | 한 기능 단위로 작게 작성 | 리뷰와 오류 확인이 쉬움 |
| 리뷰 | 1명 이상 승인 후 병합 | 다른 사람의 검토로 실수 감소 |
| 정리 | 병합 후 브랜치 삭제 | 사용하지 않는 브랜치 누적 방지 |

### 커밋 메시지 예시

```text
feat: 로그인 폼 추가
fix: 회원가입 오류 수정
docs: README 실행 방법 추가
```

피해야 할 메시지:

```text
수정함
업데이트
작업 완료
```

무엇을 바꿨는지 알 수 없기 때문.

## 협업 명령어 치트시트

| 명령어 | 하는 일 | 사용 시점 |
|---|---|---|
| `git branch` | 브랜치 목록 확인 | 현재 위치가 헷갈릴 때 |
| `git switch 이름` | 기존 브랜치 이동 | 브랜치 전환 |
| `git switch -c 이름` | 새 브랜치 생성 후 이동 | 작업 시작 |
| `git merge 브랜치` | 현재 브랜치에 다른 브랜치 병합 | 작업 완료 또는 충돌 해결 |
| `git merge --abort` | 진행 중인 병합 취소 | 충돌 해결이 꼬였을 때 |
| `git branch -d 이름` | 병합된 로컬 브랜치 삭제 | 병합 후 정리 |
| `git branch -D 이름` | 로컬 브랜치 강제 삭제 | 미병합 작업 삭제가 확실할 때 |
| `git push -u origin 브랜치` | 원격 브랜치 생성 및 연결 | 첫 push |
| `git push` | 현재 브랜치 변경 업로드 | 추가 커밋 공유 |
| `git pull` | 원격 변경 내려받고 반영 | 작업 시작·병합 후 |
| `git log --oneline --graph` | 브랜치와 병합 이력 확인 | 작업 흐름 확인 |

## 핵심 정리

```text
GitHub Flow =
main 최신화
→ 작업 브랜치 생성
→ 수정·커밋
→ push
→ Pull Request
→ 리뷰·승인
→ merge
→ 원격·로컬 브랜치 정리
```

```text
병합 기본 원칙 =
변경을 받을 브랜치로 이동
→ git merge 가져올-브랜치
```

```text
PR 충돌 해결 =
작업 브랜치에 최신 main 병합
→ 충돌 해결
→ add·commit
→ push
→ 기존 PR 자동 갱신
```
