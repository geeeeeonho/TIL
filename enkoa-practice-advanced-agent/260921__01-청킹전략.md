# 청킹 전략과 검색 문맥

> 핵심 주제: **어떻게 나눠서 검색할 것인가**와 **검색 뒤 얼마만큼의 문맥을 반환할 것인가**를 분리해서 설계한다.

---

## 1. 전체 흐름

기본 RAG는 보통 아래처럼 동작한다.

```text
원문 Document
    ↓
청킹
    ↓
Embedding
    ↓
Vector DB(Chroma)
    ↓
질문과 가까운 Chunk 검색
    ↓
검색된 Chunk 그대로 LLM에 전달
```

문제는 두 가지다.

- 근거가 청크 경계에서 잘릴 수 있음.
- 질문에 필요한 문맥 크기와 검색하기 좋은 청크 크기가 다를 수 있음.

그래서 Advanced RAG에서는 **검색 단위와 반환 단위를 다르게 설계**한다.

```text
                 ┌─ Fixed
원문 ── 청킹 ────┼─ Recursive
                 └─ Semantic
                      ↓
                 검색용 Index
                      ↓
질문 ─────────────→ 검색
                      ↓
              ┌─ 검색 결과 그대로 반환
              ├─ Parent-Child : 부모로 확장
              ├─ Sentence Window : 앞뒤 문장 확장
              └─ Auto-merging : 필요할 때 부모로 병합
```

### 전략 분류

| 전략 | 핵심 역할 | 검색 단위 | 반환 단위 |
|---|---|---|---|
| Fixed | 일정 길이로 분할 | 고정 길이 청크 | 같은 청크 |
| Semantic | 의미 변화 지점에서 분할 | 의미 청크 | 같은 청크 |
| Parent-Child | 작은 조각으로 검색 | 자식 청크 | 부모 청크 |
| Sentence Window | 문장 단위 검색 | 한 문장 | 앞뒤 문장 포함 |
| Auto-merging | 계층형 검색·동적 병합 | 가장 작은 자식 | 자식 또는 부모 |

> **Fixed·Semantic**은 주로 `저장할 청크 경계`를 정하는 전략.  
> **Parent-Child·Sentence Window·Auto-merging**은 `검색 단위`와 `반환 문맥`을 분리하는 전략.

---

## 2. 공통 준비

### Document 구조

원문은 먼저 자르지 않고 `Document`로 만든다.

```python
from langchain_core.documents import Document


def make_documents(records):
    return [
        Document(
            page_content=record["text"],
            metadata={
                "source_id": record["doc_id"],
                "title": record["title"],
                "url": record["url"],
                "start_index": 0,
                "end_index": len(record["text"]),
            },
        )
        for record in records
    ]
```

구조는 다음과 같다.

```text
Document
├─ page_content : 실제 본문
└─ metadata
   ├─ source_id
   ├─ title
   ├─ url
   ├─ start_index
   └─ end_index
```

### 임베딩 설정

문서와 질문은 같은 임베딩 설정을 사용해야 한다.

```python
from langchain_openai import OpenAIEmbeddings

embedding_model = OpenAIEmbeddings(
    model="text-embedding-3-large",
    dimensions=768,
    check_embedding_ctx_length=False,
)
```

### PDF 출처 정보

긴 PDF 여러 페이지를 하나의 본문으로 연결했다면 청크 위치와 PDF 페이지를 따로 연결해야 한다.

```text
PDF 여러 페이지
    ↓ 추출
긴 text 하나
    ↓ 청킹
[start_index : end_index]
    ↓ page_spans와 대조
pdf_start_page ~ pdf_end_page
```

즉, **청크 경계와 PDF 페이지 경계는 같은 개념이 아님**.

# 3. Fixed Chunking

## 개념

Fixed는 **정해진 길이에 도달하면 그대로 자르는 방식**이다.

```text
원문
0                                              127
|-----------------------------------------------|

chunk_size = 80, overlap = 0
[-------------------- 0:80 --------------------]
                                        [80:127]

chunk_size = 80, overlap = 20
[-------------------- 0:80 --------------------]
                              [------ 60:127 ------]
                              ↑ 20자 중복
```

### 핵심 파라미터

- `chunk_size`: 청크 최대 길이.
- `chunk_overlap`: 앞 청크 끝부분을 다음 청크에 다시 포함하는 길이.
- `length_function=len`: 글자 수 기준.
- `separators=[""]`: 문단·공백 등을 고려하지 않고 문자 단위로 자름.

## 코드

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=80,
    chunk_overlap=20,
    separators=[""],
    length_function=len,
    strip_whitespace=False,
)

chunks = splitter.split_documents(documents)
```

### Fixed와 기본 Recursive 차이

`RecursiveCharacterTextSplitter`라도 `separators` 설정에 따라 동작이 달라진다.

```text
Fixed
문자 수 기준으로 강제 분할
─────────────────────────────X────────────────────

Recursive 기본값
문단 → 줄바꿈 → 공백 → 문자 순으로 가능한 경계를 찾음
──────── 문단 ────────|───── 문단 ───────────────
```

기본 Recursive 예시:

```python
recursive_splitter = RecursiveCharacterTextSplitter(
    chunk_size=80,
    chunk_overlap=20,
    strip_whitespace=False,
)
```

### 주의점

- overlap은 문장을 이해해서 붙이는 기능이 아님.
- 문장 중간이 잘릴 수 있음.
- overlap을 늘리면 문맥 보존 가능성은 높아지지만 저장량과 임베딩 비용도 증가.
- Recursive의 overlap은 경계 조건 때문에 정확히 지정한 글자 수가 겹치지 않을 수도 있음.

### 핵심 계산

`chunk_size=600`, `chunk_overlap=100`이면 다음 청크 시작 위치는 다음과 같다.

```text
step = 600 - 100 = 500

1번 청크 : 0 ~ 599
2번 청크 : 500 ~ 1099
3번 청크 : 1000 ~ 1599
```

# 4. Semantic Chunking

## 개념

Semantic 청킹은 길이가 아니라 **이웃 문장의 의미가 크게 달라지는 지점**에서 자른다.

```text
문장1 ─ 문장2 ─ 문장3 ─ 문장4
   0.20     0.70     0.25
     유지      ↑       유지
             의미 차이 큼
             → 경계 후보
```

`SemanticSplitterNodeParser`는 문장 주변 문맥을 임베딩하고 코사인 거리를 계산한다.

```text
코사인 거리 = 1 - 코사인 유사도

거리 작음 → 의미 비슷함
거리 큼   → 의미 차이 큼
```

## buffer_size

`buffer_size=1`이면 경계를 판단할 때 문장 하나만 비교하지 않고 주변 문장까지 함께 본다.

```text
문장 2와 3 사이 경계를 판단

왼쪽 문맥 : [문장1 + 문장2 + 문장3]
오른쪽 문맥: [문장2 + 문장3 + 문장4]
```

이 buffer는 **최종 청크 overlap이 아니라 경계 판단용 문맥**이다.

## 거리 백분위

`breakpoint_percentile_threshold=80`은 **유사도 80%**라는 뜻이 아니다.

원문에서 나온 거리값들을 정렬한 뒤 80백분위에 해당하는 거리값을 기준으로 사용한다.

예시:

```text
거리값: 0.20, 0.70, 0.25
정렬  : 0.20, 0.25, 0.70
위치  :   0%    50%   100%
```

80백분위는 50%와 100% 사이의 60% 지점이다.

```text
0.25 + 0.6 × (0.70 - 0.25)
= 0.52
```

따라서 다음처럼 분할한다.

```text
0.20 < 0.52  → 유지
0.70 > 0.52  → 분할
0.25 < 0.52  → 유지

결과
[문장1 + 문장2] | [문장3 + 문장4]
```

## 백분위를 높이면

```text
50 percentile ───── 기준 낮음 ───── 경계 많아질 가능성
80 percentile ──────────────── 중간
90 percentile ───────── 기준 높음 ─ 경계 적어질 가능성
```

- 백분위 ↑ → 더 큰 의미 차이가 있어야 분할.
- 청크가 더 크게 묶이는 방향.
- 단, 거리값이 적거나 반복되면 50과 90의 실제 분할 결과가 같을 수도 있음.

## 코드

LangChain 임베딩을 LlamaIndex에서 재사용한다.

```python
from llama_index.core import Document as IndexDocument
from llama_index.core.node_parser import SemanticSplitterNodeParser
from llama_index.embeddings.langchain import LangchainEmbedding

index_embedding = LangchainEmbedding(embedding_model)


def to_index_documents(documents):
    result = [IndexDocument.from_langchain_format(doc) for doc in documents]

    for doc in result:
        doc.id_ = doc.metadata["source_id"]
        doc.excluded_embed_metadata_keys = list(doc.metadata)
        doc.excluded_llm_metadata_keys = list(doc.metadata)

    return result
```

분할:

```python
semantic_parser = SemanticSplitterNodeParser(
    buffer_size=1,
    breakpoint_percentile_threshold=80,
    embed_model=index_embedding,
)

nodes = semantic_parser.get_nodes_from_documents(
    to_index_documents(documents)
)
```

### 핵심

```text
Fixed
길이 → 경계 결정

Semantic
문장 → 임베딩 → 의미 거리 → 경계 결정
```

Semantic은 GPT가 내용을 요약해서 나누는 방식이 아니다. **임베딩 기반 경계 선택**이다.

# 5. Parent-Child Retrieval

## 개념

Parent-Child는 **작은 자식 청크로 검색하고 더 큰 부모 청크를 반환**한다.

```text
                     검색
질문 ─────────→ [Child A-2] ─────┐
                [Child A-3] ─────┼─ parent_id = A
                [Child B-1] ──┐  │
                              │  │
                              ↓  ↓
                           DocStore
                         ┌──────────┐
                         │ Parent A │
                         │ Parent B │
                         └──────────┘
                              ↓
                      LLM에는 부모 반환
```

### 저장 구조

```text
Chroma
└─ Child Chunk
   ├─ text
   ├─ embedding
   └─ parent_id

InMemoryStore
└─ parent_id → Parent Document
```

`k=3`으로 자식 3개를 검색했어도 부모가 중복되면 반환 부모 수는 더 적을 수 있다.

```text
검색 자식 parent_id
A, A, B

최종 부모
A, B
```

## 기본 코드

```python
from langchain_chroma import Chroma
from langchain_core.stores import InMemoryStore
from langchain_classic.retrievers import ParentDocumentRetriever
from langchain_text_splitters import RecursiveCharacterTextSplitter

vectorstore = Chroma(
    collection_name="parent_child",
    embedding_function=embedding_model,
)

docstore = InMemoryStore()

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=docstore,
    child_splitter=RecursiveCharacterTextSplitter(
        chunk_size=300,
        chunk_overlap=50,
        add_start_index=True,
    ),
    id_key="parent_id",
    search_kwargs={"k": 3},
)

retriever.add_documents(parent_documents, ids=parent_ids)
```

검색:

```python
parents = retriever.invoke(question)
```

내부 흐름:

```text
질문
 ↓
Chroma에서 Child 검색
 ↓
Child.metadata["parent_id"] 수집
 ↓
중복 parent_id 제거
 ↓
DocStore에서 Parent 조회
 ↓
Parent 반환
```

## 긴 PDF에서 권장 구조

원문 전체를 부모로 두면 너무 큰 문맥이 반환될 수 있다.

교안에서는 다음처럼 2단계로 자른다.

```text
긴 PDF 본문
   ↓
Parent 1,500자 / overlap 200
   ↓
각 Parent 안에서
Child 300자 / overlap 50
```

부모 ID 예시:

```python
parent_ids = [
    f"{doc.metadata['source_id']}:parent:{doc.metadata['start_index']}"
    for doc in parent_documents
]
```

부모 메타데이터에는 실제 원문 위치와 PDF 페이지 범위를 보관한다.

```text
Parent metadata
├─ source_id
├─ start_index
├─ end_index
├─ pdf_start_page
└─ pdf_end_page
```

### 핵심

> Parent-Child에서 **부모를 임베딩해서 검색하는 것이 아님**.  
> 작은 자식이 검색 순위를 결정하고, 부모는 ID로 조회해 반환한다.

# 6. Sentence Window

## 개념

Sentence Window는 **한 문장으로 검색하고 검색된 문장의 앞뒤 문장을 반환**한다.

```text
원문
문장1 | 문장2 | 문장3 | 문장4 | 문장5

검색 Index
        [문장3]
           ↑
          질문

window_size = 1
           ↓
반환 문맥
[문장2 | 문장3 | 문장4]
```

`window_size=1`은 검색 문장의 앞뒤 문장을 최대 1개씩 포함한다.

### Fixed overlap과 차이

```text
chunk_overlap
저장 전부터 일부 본문을 중복 저장

Sentence Window
검색은 한 문장으로 수행
→ 검색 순위 결정 후 주변 문맥을 확장
```

즉, window 전체를 임베딩하면 Sentence Window의 목적이 달라진다.

## 코드

```python
from llama_index.core.node_parser import SentenceWindowNodeParser

window_parser = SentenceWindowNodeParser.from_defaults(
    window_size=1
)

window_nodes = window_parser.get_nodes_from_documents(
    to_index_documents(documents)
)
```

파서 결과는 다음 구조를 가진다.

```text
Node
├─ text                 → 검색할 한 문장
└─ metadata["window"]  → 앞뒤 문장을 포함한 문맥
```

검색용 문장만 Chroma에 저장한다.

```python
sentence_store = Chroma(
    collection_name="sentences",
    embedding_function=embedding_model,
)

sentence_store.add_documents(sentence_documents)
```

검색:

```python
hits = sentence_store.similarity_search(question, k=2)
```

검색 뒤 반환 문맥으로 교체한다.

```python
contexts = [
    Document(
        page_content=hit.metadata["window"],
        metadata=dict(hit.metadata),
    )
    for hit in hits
]
```

### 핵심

```text
검색 전
문장 하나만 임베딩

검색 후
metadata["window"]로 교체
```

페이지가 달라져도 하나의 긴 본문으로 연결돼 있다면 같은 입력 문서 내부에서는 window가 페이지 경계를 넘을 수 있다.

# 7. Auto-merging Retrieval

## 개념

Auto-merging은 문서를 **계층 구조로 미리 나눈 뒤**, 작은 자식으로 검색하고 같은 부모의 자식이 많이 검색되면 부모로 합친다.

```text
원문
│
├─ Parent A
│  ├─ Child A1
│  ├─ Child A2
│  ├─ Child A3
│  └─ Child A4
│
└─ Parent B
   ├─ Child B1
   ├─ Child B2
   └─ Child B3
```

검색 결과가 다음과 같다고 가정한다.

```text
검색된 Child
A1, A2, A3
```

Parent A의 전체 자식이 4개라면:

```text
검색 비율 = 3 / 4 = 0.75
```

기준 `simple_ratio_thresh=0.5`이면:

```text
0.75 > 0.5
→ A1, A2, A3 대신 Parent A 반환
```

반면 2개만 검색됐다면:

```text
2 / 4 = 0.5
0.5 > 0.5 는 False
→ 부모로 병합하지 않음
```

> 조건은 `>=`가 아니라 **`>`**.

## Parent-Child와 차이

```text
Parent-Child
Child 검색 → 항상 Parent 반환

Auto-merging
Child 검색 → 검색 비율 계산
             ├─ 기준 초과 → Parent 반환
             └─ 기준 이하 → Child 유지
```

## 계층 생성

```python
from llama_index.core.node_parser import (
    HierarchicalNodeParser,
    get_leaf_nodes,
)

parser = HierarchicalNodeParser.from_defaults(
    chunk_sizes=[128, 32],
    chunk_overlap=0,
    include_prev_next_rel=False,
)

nodes = parser.get_nodes_from_documents(
    to_index_documents(documents)
)
```

크기 단위는 **글자가 아니라 토큰**이다.

```text
128 token Parent
    ↓
32 token Child
```

## 저장 구조

```text
StorageContext.docstore
└─ Parent + Child 전체 노드 저장

VectorStoreIndex + Chroma
└─ Leaf Child만 임베딩하여 검색
```

## 코드

```python
from llama_index.core import StorageContext, VectorStoreIndex
from llama_index.core.retrievers import AutoMergingRetriever
from llama_index.vector_stores.chroma import ChromaVectorStore

vector_store = ChromaVectorStore(chroma_collection=collection)
storage = StorageContext.from_defaults(vector_store=vector_store)

storage.docstore.add_documents(nodes)

index = VectorStoreIndex(
    get_leaf_nodes(nodes),
    storage_context=storage,
    embed_model=index_embedding,
)

retriever = AutoMergingRetriever(
    index.as_retriever(similarity_top_k=3),
    storage,
    simple_ratio_thresh=0.5,
)
```

검색:

```python
results = retriever.retrieve(question)
```

### 시각화

```text
질문
 ↓
Leaf Child Vector Search
 ↓
┌─────────────────────────────┐
│ A1 검색                     │
│ A2 검색                     │
│ A3 검색                     │
└─────────────────────────────┘
 ↓
같은 Parent의 검색 비율 계산
 ↓
3 / 4 = 0.75 > 0.5
 ↓
A1 + A2 + A3 제거
 ↓
저장된 Parent A로 교체
 ↓
최종 Context 반환
```

# 8. 전략 비교

| 전략 | 경계 기준 | 검색 단위 | 반환 단위 | 장점 | 주의점 |
|---|---|---|---|---|---|
| Fixed | 글자/토큰 길이 | 청크 | 청크 | 단순, 예측 가능 | 의미 중간에서 잘릴 수 있음 |
| Recursive | 문단·줄바꿈·공백 우선 | 청크 | 청크 | 자연스러운 경계 활용 | 의미 자체를 이해하지는 않음 |
| Semantic | 임베딩 거리 | 의미 청크 | 의미 청크 | 주제 변화 반영 | 임베딩 비용 증가, 결과 크기 가변 |
| Parent-Child | 자식/부모 2단계 | 작은 자식 | 큰 부모 | 검색 정확도와 문맥 확보를 분리 | 부모가 너무 크면 불필요 문맥 증가 |
| Sentence Window | 문장 | 한 문장 | 앞뒤 문장 | 정밀 검색 + 주변 문맥 확보 | 문장 분리 품질에 영향 받음 |
| Auto-merging | 계층 + 검색 비율 | Leaf | Leaf 또는 Parent | 필요한 경우에만 큰 문맥 반환 | 계층 구조와 임계값 설계 필요 |

---

# 9. 선택 기준

```text
문서 구조가 단순하고 빠르게 시작
→ Fixed / Recursive

주제 전환이 분명하고 의미 단위 분할이 중요
→ Semantic

정확한 검색은 작은 청크가 좋지만 답변에는 넓은 문맥 필요
→ Parent-Child

한 문장을 정확히 찾고 주변 설명만 조금 추가
→ Sentence Window

문서에 계층성이 있고 검색 결과에 따라 반환 범위를 유동적으로 변경
→ Auto-merging
```

# 10. 가장 중요한 구분

## ① 청킹과 검색 문맥 확장은 다름

```text
청킹
원문을 어떻게 나눠 저장할 것인가?

문맥 확장
검색된 결과를 답변에 넘길 때 어디까지 보여줄 것인가?
```

## ② 검색 단위와 반환 단위는 같을 필요 없음

```text
작은 단위 검색
      ↓
높은 검색 정밀도
      ↓
큰 문맥 반환
      ↓
답변에 필요한 조건·예외 보존
```

## ③ 출처 위치는 청킹 뒤에도 유지

```text
source_id
 + start_index / end_index
 + pdf_start_page / pdf_end_page
```

이 정보가 있어야 검색 결과를 원문과 PDF 페이지까지 역추적 가능하다.

# 11. 핵심 체크

- `chunk_overlap=100`, `chunk_size=600` → 다음 청크 시작 간격은 **500**.
- Semantic의 `80 percentile` → 유사도 80%가 아니라 **거리 분포의 80백분위 기준값**.
- Parent-Child의 부모는 검색 순위를 정하지 않음. **Child가 검색하고 Parent가 반환됨**.
- Sentence Window는 **한 문장 검색 후 window로 교체**.
- Auto-merging은 `검색된 자식 수 / 부모 전체 자식 수 > threshold`일 때 부모로 병합.
- Parent-Child는 부모를 항상 반환하지만 Auto-merging은 조건부 반환.
- Fixed/Recursive의 크기 예시는 글자 수, Auto-merging의 `chunk_sizes`는 토큰 수.

# 12. 한 줄 정리

```text
Fixed / Semantic
= 어떻게 나눌까?

Parent-Child / Sentence Window / Auto-merging
= 작게 찾고, 필요한 만큼 어떻게 넓혀서 돌려줄까?
```
