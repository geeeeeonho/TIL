# 컨텍스트 압축(Contextual Compression) 압축 정리

> 질문에 필요한 근거만 남겨 LLM에 전달하는 흐름 정리  
> 핵심 구조: **검색 → 리랭킹 → 관련 구간 추출 → 답변**

---

## 1. 컨텍스트 압축이란?

**컨텍스트(Context)**는 LLM이 답변을 만들 때 읽는 근거 자료다.

**컨텍스트 압축(Contextual Compression)**은 검색된 문서 전체를 그대로 전달하지 않고,  
**현재 질문에 필요한 구간만 남겨 LLM에 전달하는 방식**이다.

```text
검색된 원문
   ↓
질문과 관련된 부분만 추출
   ↓
짧아진 근거(Context)
   ↓
LLM 답변
```

단, 압축이 항상 이득인 것은 아니다.

- 압축용 LLM도 원문을 읽고 결과를 생성하므로 **추가 토큰 비용**이 발생함
- 원문이 짧거나 문서 수가 적으면 오히려 압축 비용이 더 클 수 있음
- 중요한 **조건·예외·부정 표현**이 빠지면 답변 품질이 낮아질 수 있음
- 따라서 단순히 토큰 수만 줄었는지가 아니라 **필요한 근거가 보존됐는지** 확인해야 함

---

## 2. 전체 비교 구조

교안에서는 같은 질문과 같은 리랭킹 결과를 사용한 뒤,  
**원문 그대로 답변하는 A 경로**와 **관련 구간을 추출한 B 경로**를 비교한다.

```text
                  같은 질문
                     │
                     ▼
              같은 reranked 문서
                ┌────┴────┐
                │         │
             [A 경로]   [B 경로]
                │         │
            원문 그대로   LLMChainExtractor
                │         │
                │      관련 구간 추출
                │         │
                ▼         ▼
              answer_chain
                │         │
                ▼         ▼
              답변 A     답변 B
```

### 비교 원칙

| 항목 | A: 리랭킹만 | B: 리랭킹 + 추출 |
|---|---|---|
| 질문 | 동일 | 동일 |
| 선택 문서 | 동일한 `reranked` | 동일한 `reranked` |
| 답변 체인 | 동일 | 동일 |
| 전달 문맥 | 원문 전체 | 추출된 관련 구간 |
| 추가 LLM 호출 | 답변 | 문서별 추출 + 답변 |

**압축 효과만 비교하려면 검색을 다시 하지 않는다.**

검색 결과까지 달라지면 답변 차이가  
`검색 차이` 때문인지 `압축 차이` 때문인지 구분하기 어렵다.

---

## 3. 이미지 내용 텍스트 도식화

### 3.1 필요한 근거 보존

질문과 직접 관련된 문장만 남기더라도  
**부정 표현이나 예외 조건까지 함께 유지해야 한다.**

```text
[원문]

기능 A를 지원한다.
실행 기록을 조회할 수 있다.
하지만 실행 기록을 이용한 오류 추적 방법은 다루지 않는다.
다른 기능 B도 설명한다.

                ↓ 질문 기준 추출

[추출문]

실행 기록을 조회할 수 있다.
하지만 실행 기록을 이용한 오류 추적 방법은 다루지 않는다.
```

단순히 긍정 키워드만 남기면 안 된다.

```text
"지원한다"          → 유지 대상일 수 있음
"지원하지 않는다"   → 역시 중요한 근거
"특정 조건에서만"   → 조건까지 함께 유지
"예외적으로"        → 예외까지 함께 유지
```

---

### 3.2 원문 답변과 토큰 기록

```text
reranked 원문
     │
     ▼
answer_chain ─────────→ 답변 A
     │
     └───────────────→ UsageMetadataCallbackHandler
                        ├─ input_tokens
                        ├─ output_tokens
                        └─ total_tokens
```

---

### 3.3 추출 후 답변과 누적 토큰

```text
reranked 원문
     │
     ▼
LLMChainExtractor
     │
     ├───────────────→ usage_b에 추출 토큰 기록
     │
     ▼
compressed 문서
     │
     ▼
answer_chain
     │
     ├───────────────→ 같은 usage_b에 답변 토큰 추가
     ▼
   답변 B

usage_b
= 추출 토큰 + 답변 토큰
```

---

### 3.4 실제 검색 파이프라인

```text
사용자 질문
    │
    ▼
Hybrid Retriever
(BM25 + Dense)
    │
    ▼
후보 문서
    │
    ▼
CrossEncoderReranker
(top_n=3)
    │
    ▼
상위 문서
    │
    ▼
LLMChainExtractor
    │
    ▼
질문 관련 구간만 남은 문서
    │
    ▼
Answer Chain
    │
    ▼
최종 답변
```

파이프라인 순서는 다음처럼 유지한다.

```text
reranker → extractor
```

추출기를 먼저 실행하면 더 많은 후보 문서를 LLM이 읽어야 하고,  
리랭커도 원문이 아니라 추출된 문장을 평가하게 된다.

## 4. 검색 → 리랭킹으로 비교 원문 준비

교안에서는 하이브리드 검색 결과를 Cross-Encoder로 다시 평가해 상위 3개를 사용한다.

```python
question = (
    "에이전트가 도구를 잘못 고르거나 호출에 실패할 때 "
    "실행 기록을 추적해 원인을 찾는 방법을 배울 책을 찾아 주세요."
)

# 1. 후보 검색
candidates = hybrid.invoke(question)

# 2. 상위 3개 문서 선택
reranker = CrossEncoderReranker(
    model=cross_encoder,
    top_n=3,
)

reranked = list(
    reranker.compress_documents(candidates, question)
)

show_results(reranked)
```

### 결과

```text
결과 문서 수: 3

[1] book34
에이전트 도구 호출 실패 사례집
- 도구 호출 실패·반복 사례
- 단계별 실행 기록을 다시 읽어 최초 오류 지점 탐색

[2] book33
도구 선택 실수를 줄이는 에이전트 설계
- 잘못된 도구 선택 원인 분석
- 도구 설명 수정 전후의 호출 로그 비교

[3] book31
에이전트 실행 기록으로 찾는 오류
- 모델이 선택한 도구와 전달 인자 확인
- 잘못된 도구 선택과 인자 형식 오류를 구분
```

이 `reranked`를 A/B 경로에서 **그대로 재사용**한다.

## 5. 답변용 컨텍스트 만들기

원문 ID·제목·출처와 본문을 함께 전달하면  
답변을 다시 실제 근거와 연결하기 쉽다.

```python
def format_context(documents):
    context_parts = []

    for doc in documents:
        context = (
            f"[{doc.metadata['source_id']}] "
            f"{doc.metadata['title']}\n"
            f"출처: {doc.metadata['url']}\n"
            f"{doc.page_content}"
        )
        context_parts.append(context)

    return "\n\n".join(context_parts)
```

답변 체인은 **제공된 근거만 사용**하도록 제한한다.

```python
answer_prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        "제공된 원문 근거로만 답하세요. "
        "주장마다 [원문 ID]를 인용하세요. "
        "근거에 답이 없으면 확인할 수 없다고 말하세요. "
        "자료의 빈 부분을 추측하지 마세요."
    ),
    (
        "human",
        "질문: {question}\n\n원문 근거:\n{context}"
    ),
])

answer_chain = (
    answer_prompt
    | llm
    | StrOutputParser()
)
```

## 6. A 경로: 압축하지 않고 답변

`UsageMetadataCallbackHandler`는 LLM 응답에 포함된  
**실제 토큰 사용량 정보를 누적해서 기록**한다.

```python
from langchain_core.callbacks import UsageMetadataCallbackHandler

usage_a = UsageMetadataCallbackHandler()

baseline_answer = answer_chain.invoke(
    {
        "question": question,
        "context": format_context(reranked),
    },
    config={"callbacks": [usage_a]},
)

print(baseline_answer)
print("A 토큰 사용량:", usage_a.usage_metadata)
```

### 출력 형태

```text
<원문을 사용한 답변>

A 토큰 사용량:
{
    "<model>": {
        "input_tokens": ...,
        "output_tokens": ...,
        "total_tokens": ...
    }
}
```

### 콜백 사용 흐름

```text
UsageMetadataCallbackHandler()
          ↓
config={"callbacks": [usage_a]}
          ↓
LLM 실행
          ↓
usage_a.usage_metadata
```

주의:

- 같은 콜백을 재사용하면 사용량이 계속 누적됨
- 모델이 사용량 정보를 반환하지 않으면 값이 비어 있을 수 있음
- 빈 값은 곧바로 `0 token`이라는 뜻이 아님

## 7. B 경로: `LLMChainExtractor`로 관련 구간 추출

### 7.1 Extractor 생성

```python
from langchain_classic.retrievers.document_compressors import (
    LLMChainExtractor,
)

extractor = LLMChainExtractor.from_llm(llm)
```

이 단계는 **객체 생성만 수행**하며 LLM 요청은 발생하지 않는다.

`LLMChainExtractor`는 기본적으로 다음 역할을 한다.

```text
문서 + 질문
    │
    ▼
질문과 관련된 원문 구간 추출
    │
    ├─ 관련 내용 있음 → 추출문 반환
    │
    └─ 관련 내용 없음 → NO_OUTPUT
```

---

### 7.2 문서 압축

```python
usage_b = UsageMetadataCallbackHandler()

compressed = list(
    extractor.compress_documents(
        reranked,
        question,
        callbacks=[usage_b],
    )
)

show_results(compressed)
print("B 추출까지의 토큰:", usage_b.usage_metadata)
```

`compressed`도 `Document` 목록이다.

```text
Document
├─ page_content → 추출된 관련 구간
└─ metadata
   ├─ source_id
   ├─ title
   └─ url
```

즉, 본문은 줄어들지만 출처 메타데이터는 유지된다.

---

### 7.3 추출문으로 답변

같은 `answer_chain`을 사용하고 **문맥만 변경**한다.

```python
if compressed:
    compressed_answer = answer_chain.invoke(
        {
            "question": question,
            "context": format_context(compressed),
        },
        config={"callbacks": [usage_b]},
    )
else:
    compressed_answer = (
        "전달할 근거가 없어 답변을 생성하지 않았습니다."
    )

print(compressed_answer)
print(
    "B 추출+답변 토큰:",
    usage_b.usage_metadata,
)
```

### 토큰 기록

```text
usage_b

추출 실행 후
└─ 추출에 사용한 토큰

답변 실행 후
└─ 추출 토큰 + 답변 토큰
```

`compressed`가 비어 답변을 생성하지 않아도  
**앞에서 수행한 추출 호출의 토큰은 이미 사용된 상태**다.

## 8. A/B 비교 시 확인할 것

압축 결과는 원문과 직접 비교한다.

```text
[원문]
   │
   ├─ 핵심 조건
   ├─ 제한 사항
   ├─ 예외
   └─ 부정 표현
        │
        ▼
[추출문]
   └─ 위 근거가 그대로 남아 있는가?
```

좋은 압축은 단순히 짧은 문장이 아니다.

```text
좋은 압축
= 불필요한 문맥 감소
+ 질문에 필요한 근거 유지
```

## 9. 리랭킹 + 추출 파이프라인 만들기

`DocumentCompressorPipeline`에 리랭커와 추출기를 **순서대로** 넣는다.

```python
from langchain_classic.retrievers.document_compressors import (
    DocumentCompressorPipeline,
)
from langchain_classic.retrievers import (
    ContextualCompressionRetriever,
)

compressor = DocumentCompressorPipeline(
    transformers=[
        reranker,
        extractor,
    ]
)

compression_retriever = ContextualCompressionRetriever(
    base_retriever=hybrid,
    base_compressor=compressor,
)
```

### 내부 실행 흐름

```text
compression_retriever.invoke(question)

          │
          ▼
    base_retriever
       hybrid
          │
          ▼
      후보 검색
          │
          ▼
      reranker
          │
          ▼
     상위 문서 선택
          │
          ▼
      extractor
          │
          ▼
    관련 구간 추출
          │
          ▼
 compressed Documents
```

객체를 만드는 것만으로는 검색이나 LLM 요청이 발생하지 않는다.

실제 실행은 `invoke()`에서 시작한다.

```python
next_usage = UsageMetadataCallbackHandler()

next_compressed = compression_retriever.invoke(
    next_question,
    config={"callbacks": [next_usage]},
)

show_results(next_compressed)

print(
    "새 질문의 추출 토큰:",
    next_usage.usage_metadata,
)
```

## 10. 전체 핵심 코드

### 10.1 Retriever 준비

```python
# BM25
bm25 = BM25Retriever.from_documents(
    practice_documents,
    preprocess_func=kiwi_tokenize,
    k=5,
)

# Dense
dense = vec_store.as_retriever(
    search_kwargs={"k": 5}
)

# Hybrid
hybrid = EnsembleRetriever(
    retrievers=[bm25, dense],
    weights=[0.5, 0.5],
    c=60,
    id_key="source_id",
)
```

> 원본 교안의 이어서 보기 코드에서는 `vec_store`를 만든 뒤  
> Dense 검색기에서 `vector_store`를 참조한다. 아래 정리본은 변수명을 `vec_store`로 통일함.

## 11. Retriever와 답변 체인까지 하나로 연결

`RunnablePassthrough`를 이용하면 질문 하나만 넣어  
검색부터 답변까지 연결할 수 있다.

```python
from langchain_core.runnables import (
    RunnablePassthrough,
)

final_chain = (
    {
        "question": RunnablePassthrough(),
        "context": (
            compression_retriever
            | format_context
        ),
    }
    | answer_chain
)

answer = final_chain.invoke(
    practice_question
)

print(answer)
```

## 12. 비교 실험과 실제 사용의 차이

### 압축 효과 비교

검색 결과를 고정한다.

```text
검색 1회
  ↓
reranked 고정
  ├─ A: 원문 → 답변
  └─ B: 추출 → 답변
```

### 실제 서비스/새 질문

검색부터 다시 수행한다.

```text
새 질문
  ↓
ContextualCompressionRetriever.invoke()
  ↓
검색 → 리랭킹 → 추출
```

두 상황을 구분해야 한다.

## 13. 핵심 정리

```text
Contextual Compression
= 관련 문서를 고르는 것에서 끝나지 않고
  문서 내부에서 질문에 필요한 근거까지 줄이는 과정
```

- **리랭킹**: 어떤 문서를 사용할지 선택
- **컨텍스트 압축**: 선택한 문서에서 어떤 구간을 사용할지 선택
- `LLMChainExtractor`: 질문 관련 구간을 LLM으로 추출
- `UsageMetadataCallbackHandler`: LLM이 보고한 토큰 사용량 누적
- `DocumentCompressorPipeline`: `reranker → extractor` 순서로 연결
- `ContextualCompressionRetriever`: 검색기와 압축 파이프라인 통합
- A/B 비교에서는 **같은 질문·같은 선택 문서·같은 답변 체인** 유지
- 압축 결과는 토큰 절감뿐 아니라 **조건·예외·부정 표현 보존 여부** 확인
- 압축에도 LLM 호출이 필요하므로 **항상 비용이 줄어드는 것은 아님**

### 한 줄 흐름

```text
질문
→ Hybrid Search
→ Reranking
→ LLMChainExtractor
→ 압축된 근거
→ Answer Chain
→ 근거 기반 답변
```
